## 対象範囲

本文書は、create と update の run の中の流れを定める。本文書は `####` 見出し 1 つを 1 仕様項目とする。扱うのは次のとおり。

- create の対象スキルの置き場と、create・update の run が状態に残す入力
- 目標の固定（create は依頼文から、update は対象スキルの全体と修正の根拠から）
- 書く・検証する・書き直す反復と、その中での形の判定の当て方
- 検証の観点、担当の作り方、合否の判定、反復の上限の当て方
- Claude Code での役ごとの制限の確かめ方
- 合否が合格になった後の形式検証の段
- update の既存の振る舞い（契約）の判定
- create・update に固有の異常系
- 完了時の出力と、完了の前に止まったときの報告

次の事柄は他の文書が定め、本文書は参照だけにする。

| 事柄 | 正本 |
|---|---|
| 依頼の振り分け、機能の連鎖、callsite の入力の項目と綴り、update の対象スキルのパスの一覧 | `docs/specifications/bp-entry.md` |
| run の境界、状態とその更新、停止の種類、next_args と再開、起動数の上限、役ごとのモデル・effort・権限、共通の異常系、どの停止でも返す項目 | `docs/specifications/bp-run.md` |
| 台帳、資産 ID・指摘 ID、反証、指摘の状態と見直し、カバレッジと skip 一覧、指摘の形、修正の根拠の形 | `docs/specifications/bp-findings.md` |
| 対象スキルの判定基準（配置の原則・形の判定・設計の説明・部品・資産台帳・形に関わる原則・配布先での確認・起動数の上限）と確定値 | `docs/specifications/bp-conformance.md` |

## 用語定義

要求文書の用語（`docs/requirements/bp-operations.md`「用語」）、`docs/specifications/bp-run.md` の用語定義（状態・作業場所・前提・修正の根拠の記録 ID・起動数・未着手の項目・破棄した未着手の項目・停止の記録・書いたファイルの一覧・判定基準の写しなど）、`docs/specifications/bp-findings.md` の用語定義（台帳・資産・担当・判定・指摘の候補・観点・指摘の種類・指摘の鍵・見直し）、`docs/specifications/bp-conformance.md` の用語定義（判定の単位・判定の結果）はそのまま使う。本表は本文書で足す語だけを持つ。

| 用語 | 意味 |
|---|---|
| 依頼文 | create では、callsite が渡す依頼の文言（SP-BPENTRY-013）。update では、PR-BPOPERATIONS-003 の読み替えにより「対象スキルの全体から読み取った目的と修正の根拠」を指す |
| 作り直す前の写し | update の最初の run が対象スキルに書く前の、対象スキルの各ファイルの内容の写し（SP-BPAUTHORING-004） |
| 目標の要素 | 固定した目標を構成する欄。成果物・範囲・禁止事項・数値条件・指示語の置き換えの 5 種（SP-BPAUTHORING-006） |
| 出所 | 目標の要素ごとに付ける根拠。依頼文・利用者の回答・作り直す前の写しのどれかからの逐語の引用か、修正の根拠の記録 ID |
| 反復 | 書く段から合否の段までの段の並び 1 回（SP-BPAUTHORING-005） |
| 反復の番号 | 状態の中で反復を区別する番号。反復を始めるたびに 1 増える。反復の上限に当てる反復の回数（SP-BPAUTHORING-024）とは別に数える |
| 契約 | update の対象スキルの、外から見える振る舞い。description が定める発火する条件と発火しない条件、入力、出力、停止の種類の 5 つの要素からなる（依頼者の裁定） |
| 強いられた未検査 | `docs/specifications/bp-conformance.md` が判定する者に「未検査」を付けさせる判定の単位。無視される設定の一覧を読めないとき（SP-BPCONFORMANCE-019）の、Claude Code の PR-BPDESIGNEDSKILL-014 の判定の単位と、PR-BPDESIGNEDSKILL-010 の設計方針文書「権限」の表の最後の行だけを指す |
| 合否 | 1 回の反復の終わりに、script が運搬役を通じて CLI に決めさせる、合格・不合格・検証が成り立たないの 3 値（SP-BPAUTHORING-023） |
| 残る危険 | 対象スキルの役ごとの制限のうち、配布先で効くかを確かめられなかったもの（SP-BPCONFORMANCE-019・020）と、判断点の列挙の網羅を確かめていないこと（SP-BPCONFORMANCE-041）。best-practices 自身の役の制限（SP-BPRUN-025）とは別に数える |

## 機能仕様

### 対象スキルと run の入力

#### SP-BPAUTHORING-001 create の対象スキルのパス
create の対象スキルのパスの一覧は、`.agents/skills/<name>/` のディレクトリ 1 つでなければならない（未公開のスキルの実体の置き場：[repository-operations の現行案内]、設計時点の出典：[設計時点の出典／旧規約 @ c7759f1]）。`<name>` は、依頼文がスキル名として名指しする文字列とする。callsite は、この一覧を run の起動前に作り、入力に渡さなければならない（SP-BPENTRY-013）。依頼文がスキル名を名指ししないとき、callsite は create の run を起動してはならず、スキル名を利用者に尋ねなければならない（名前を推測で決めると、依頼文に無い制約を足すことになる：PR-BPOPERATIONS-003）。

`<name>` は、空でなく、`/` を含まず、`.` でも `..` でもない 1 つのパスの要素でなければならない。callsite は、名指しされた文字列が次のどれかに当たるとき、名指ししないときと同じく create の run を起動してはならず、スキル名を利用者に尋ねなければならない（`/` や `..` を含む文字列は `.agents/skills/` の外を指す：PR-BPOPERATIONS-037）。

- 名指しされた文字列が `<name>` の条件に当たらない。callsite は文字列を書き換えて名前を作ってはならない。
- 依頼文がスキル名として 2 つ以上の文字列を名指しする。callsite は、1 つ目を取ることを含め、推測で 1 つを選んではならない。

create が作る Workflow script は、このディレクトリの中に置かなければならない。`plugins/` の下へ置いてはならない（`plugins/` への移動は marketplace への登録の仕事であり、create の範囲の外にある：[repository-operations の現行案内]、設計時点の出典：[設計時点の出典／旧規約 @ c7759f1]）。

#### SP-BPAUTHORING-002 書き換えてよい範囲
create・update の書き手は、対象スキルのパスの一覧の中（「一覧の中」の意味は `docs/specifications/bp-run.md` の用語定義）のファイルだけを作り・書き換え・消してよい。一覧の外にある既存のファイルを書き換えてはならず、一覧の外に新しいファイルを作ってはならない（PR-BPOPERATIONS-037）。run の作業記録・証拠・記録台帳はこの制限の外とし、作業ファイルの置き場は SP-BPRUN-007・008 に従う。

- update の書き手は、スキルのディレクトリの中に新しいファイルを足してよく、一覧の中のファイルを消してもよい（全体の作り直しの許容：PR-BPOPERATIONS-018）。
- update で新しく Workflow script が要るとき、書き手はそれをスキルのディレクトリの中に置かなければならない（SP-BPAUTHORING-001 と同じ理由）。

#### SP-BPAUTHORING-003 依頼と根拠の保持
create の依頼文と update の修正の根拠は、原文を変えずに保存し、再開しても目標を固定する出発点として参照できなければならない。状態の新規作成だけが成功し入力が失われた状態を、再開可能として扱ってはならない。

#### SP-BPAUTHORING-004 作り直す前の写し
update は、最初に変更する前の対象全体を比較基準として保存し、元の目的と契約の確認に使わなければならない。再開時の対象は既に変更済みの場合があるため、比較基準を現在の対象で作り直してはならない。保存した基準の版を照合できなければ使用せず BLOCKED とし、食い違った範囲を報告しなければならない。

### 段の並び

#### SP-BPAUTHORING-005 作成と検証の依存順
create・update は、入力の確認、目標の固定、作成、独立検証、合否、必要な形式検証の依存順を守らなければならない。update は変更前の比較基準を先に保たなければならない。書き直しは不合格の検証結果を根拠にし、同じ run で形式検証の失敗から書き直しへ戻ってはならない。

書くから合否までを 1 回の反復とし、目標固定と形式検証は反復に数えない。検証役・反証役が結果を返せないことによる BLOCKED からは、書き直す根拠が無いため、書き手を起動せず検証から始める（依頼者の裁定）。その他の停止・再開は SP-BPAUTHORING-035 に従わなければならない。

上位の設計方針が課す生成・検証・反証・状態更新の分離は守らなければならない。内部の段数、役の起動の束ね方と運搬手順は実装の設計で決める。

### 目標の固定

#### SP-BPAUTHORING-006 目標の固定の段
目標は次の入力から固定しなければならない。

| 機能 | 渡すもの |
|---|---|
| create | 状態にある依頼文、前提にある利用者の回答の全て |
| update | 作り直す前の写しのパス、前提にある修正の根拠のうち SP-BPFINDINGS-031 が修正の根拠として扱うとしたもの、前提にある利用者の回答の全て |

目標を固定できたか、足りない入力があるかを区別しなければならない。

- 固定した目標: 下の表の欄を全て持つ。値が無い欄は「なし」と書く。
- 足りない入力: 利用者への問いの一覧 `missing`（`{question, reason}` の 1 つ以上の並び。どちらも空でない文字列：SP-BPAUTHORING-008）。書き手は、任意の欄 `impact` に、問いの答えで変わる目標の要素の種類（下の表の 5 種の欄の名前 `deliverables`・`scope`・`prohibitions`・`numeric`・`deixis` の重複の無い並び）を添えてもよい。影響を推測で補ってはならない。

| 目標の要素 | 中身 | 対応する設計方針文書「目標の固定」の行 |
|---|---|---|
| 成果物 | 最終的に検証できる成果物。調査・手段・検証の手順を入れない。成果物が互いに独立なときだけ複数に分ける | 「目標は「最終的に検証できる成果物」とし」の行 |
| 範囲 | 依頼文から抜き出した、作るスキルが扱う範囲 | 「依頼文から範囲と禁止事項を先に抜き出し」の行 |
| 禁止事項 | 依頼文から抜き出した、作るスキルがしてはならないこと | 同上 |
| 数値条件 | 依頼文にある、数値で判定できる条件 | 「目標に数値で判定できる条件」の行 |
| 指示語の置き換え | 依頼文の指示語と、それを置き換えた固有名の組 | 「依頼文から範囲と禁止事項を先に抜き出し」の行 |

目標の要素ごとに、書き手は 1 つ以上の出所を付けなければならない。ただし、値が「なし」の欄の要素には出所を付けない（成果物の欄は「なし」にできない：SP-BPAUTHORING-008）。出所は次のどれかとする。

| 機能 | 出所に使えるもの |
|---|---|
| create | 依頼文か利用者の回答からの逐語の引用 |
| update | 作り直す前の写しのパスとそのファイルからの逐語の引用、修正の根拠の記録 ID、利用者の回答からの逐語の引用 |

update では、SP-BPFINDINGS-031 が修正の根拠として扱うとした根拠の全てを、成果物か範囲の要素の出所として 1 回以上指さなければならない（修正の根拠を目標の固定の出発点にするため：PR-BPOPERATIONS-003）。

#### SP-BPAUTHORING-007 出所の照合
固定した目標の各要素には、実際の依頼文・回答・比較基準中に存在する逐語の引用、または受け取った修正の根拠への参照が必要であり、決定的に照合しなければならない。「なし」の欄には出所を要求しないが、成果物を「なし」としてはならない。update の扱う全ての根拠は、成果物か範囲の出所として少なくとも 1 回は対応していなければならない。

照合できない場合は要素の種類・値・理由を保存し、同じ run で SP-BPCONFORMANCE-028 の上限まで目標を固定し直してよい。上限でも照合できない場合は needs_input とし、その全ての要素と理由を、改変せず判断材料に含めなければならない。固定済みの目標を引用が実在することだけで意味まで正しいと扱ってはならない。

#### SP-BPAUTHORING-008 待たれる入力の不足
書き手は、次のどれかに当たるとき、固定した目標の代わりに足りない入力を返さなければならない。

- 依頼文と回答から、最終的に検証できる成果物を 1 つも特定できない。
- 指示語が指すものを、依頼文と回答の中の固有名に置き換えられない。
- 依頼文と回答に、成果物か範囲が違ってくる複数の読みがあり、どれかに決める記述が無い。
- 依頼文の中の 2 つ以上の記述が、同時には満たせない。

足りない入力は問いと理由を保存し、分かる場合だけ SP-BPAUTHORING-006 の影響の種類を添えなければならない。run は needs_input として止まり、問い・理由と SP-BPAUTHORING-034 の判断材料を返さなければならない。入力不足自体を目標の照合失敗の繰り返しとして数えてはならない。回答を足した再開では回答を保存し、目標の固定から始めなければならない。

#### SP-BPAUTHORING-009 固定した目標を前提に書く
出所を照合した目標を以後の作業の入力として保存し、その同じ目標を作成と独立検証に使わなければならない。入力の固定に検証役の受理を条件としてはならない。目標自体に混入した依頼外の制約は、SP-BPAUTHORING-037 に従って原文から別に検証しなければならない。

#### SP-BPAUTHORING-010 再開した run の目標の固定
再開した run は、前提に固定した目標があるとき、目標の固定の段を飛ばさなければならない。前提に固定した目標が無いとき、目標の固定の段から始めなければならない（SP-BPRUN-015）。

### 書く

#### SP-BPAUTHORING-011 書く段の書き手
作成は、固定した目標、対象の全体、判定基準、update の変更前の比較基準と修正の根拠、書き直す場合は直前に確定した修正根拠に基づいて行わなければならない。対象へ書く流れは 1 本に保ち、並行する書き手による競合を作ってはならない（上位の設計制約）。

作成後は、作成・変更・削除したパスと、設計の説明の位置を返さなければならない。設計の説明の公開された位置の形は `designNote: {path, startLine, endLine}` とする。path は対象スキルの根からの相対パス、行は 1 始まりの閉区間とする。update は根拠が触れない部分も含む全体を作り直してよい。

#### SP-BPAUTHORING-012 形の判定の当て方
書く段の書き手は、対象スキルの形を SP-BPCONFORMANCE-004 の順で問いに答えて決め、Q3 では SP-BPCONFORMANCE-005 に従わなければならない（1 体の agent の 1 回の実行で解ける課題は探索グラフ型にしない：PR-BPOPERATIONS-008）。そのうえで、資産台帳の要否を SP-BPCONFORMANCE-009 で決め、部品を SP-BPCONFORMANCE-008 で選んで組まなければならない。書き手は、答えた問いと答え、重い形を強いた事実（SP-BPCONFORMANCE-006）、段ごとの部品の名前（SP-BPCONFORMANCE-008）、判断点の表（SP-BPCONFORMANCE-041）を、対象スキルの設計の説明に書かなければならない。2 回目以降の反復で形が変わらないときも、設計の説明を今の対象スキルと食い違わないように保たなければならない。

#### SP-BPAUTHORING-013 書き手が対象スキルに入れてはならないもの
固定した目標に無い目標・制約と、対象外のファイルへの書き込みを対象スキルに入れてはならない。判定基準が求める制約の扱いは SP-BPAUTHORING-038 に従う。

設計の説明は対象スキル内の 1 ファイルに置き、SP-BPAUTHORING-011 の位置が既存ファイルの実際の行範囲を指すことを確かめなければならない。範囲外・不存在・不正な区間であれば BLOCKED とし、対象を再び書き直して説明の拒否だけを試し直してはならない。拒否した場合も確認できる変更パスを未検証として残さなければならない。

#### SP-BPAUTHORING-014 書き直しの入力
書き直しに使ってよいのは、直前の合否で不合格とした指摘、判定の単位と理由、および別 run での形式検証で成り立たなかった性質と理由だけとする。指摘は SP-BPFINDINGS-029 のまま使わなければならない。

同じ書き直しを上限停止や中断後に再開する場合も、合否時点で確定した同じ根拠を使い、後の台帳の変化で入力を書き換えてはならない。生成者の未検証の説明や反証で却下した候補を修正の根拠として足してはならない。

#### SP-BPAUTHORING-015 書いたパスの照合
書いた/消したパスを SP-BPAUTHORING-002 の対象範囲と決定的に照合し、範囲内の変更は範囲外の変更の有無によらず記録しなければならない。範囲外は SP-BPAUTHORING-031 に従わなければならない。

変更後は、追加・削除と自分の plugin の Workflow 呼び出しの変化を対象の一覧と資産へ反映しなければならない。解決できない呼び出しは黙って除外せず、パス・SKILL.md の行番号・文言を返さなければならない。

書き手が結果を返さない場合も、最後に保存した版と今の対象を照合して把握できる変更を未検証として残さなければならない。対象外をこの照合で確認していないことを報告し、検証済みとしてはならない。

### 検証

#### SP-BPAUTHORING-016 観点と担当
検証は次の観点を含めなければならない。

> 条件の値: 機能 = create / update
> 条件の値: 観点 = 適合 / 目標 / 契約

| 条件: 機能 | 条件: 観点 | 結果 |
|---|---|---|
| create | 適合 | 適用する（SP-BPAUTHORING-017） |
| create | 目標 | 適用する（SP-BPAUTHORING-018） |
| create | 契約 | 適用しない（create には作り直す前の振る舞いが無い） |
| update | 適合 | 適用する（SP-BPAUTHORING-017） |
| update | 目標 | 適用する（SP-BPAUTHORING-018） |
| update | 契約 | 適用する（SP-BPAUTHORING-019） |

観点の担当範囲は、一緒に読まなければ判断できない資産間の依存を含め、決定的な規則または閉集合からの選択で確定しなければならない（設計方針文書「資産台帳」）。

各観点の指摘の種類の閉集合は次のとおりとする。

| 観点 | 指摘の種類の閉集合 |
|---|---|
| 適合 | SP-BPFINDINGS-010 の適合の観点の行 |
| 目標 | 成果物の未達、範囲の逸脱、禁止事項の違反、数値条件の未達、修正の根拠の未反映（update だけ）、依頼に無い目標・制約 |
| 契約 | 発火する条件の変化、発火しない条件の変化、入力の変化、出力の変化、停止の種類の変化 |

検証役が返す形は SP-BPFINDINGS-007 に従う。script は、検証役と反証役に、書き手の返り値のうちパス以外を渡してはならない（生成した本人の説明を検証の材料にすると、生成と別の context で検証する意味が無くなる：PR-BPOPERATIONS-009）。検証役と反証役は書き手と別の agent の起動とする（SP-BPRUN-024）。

#### SP-BPAUTHORING-017 適合の観点
適合の観点は SP-BPCONFORMANCE-003・SP-BPINSPECTION-006 で適用範囲を確定し、適用される全ての判定の単位に、適合・不適合・対象外・未検査と理由を付けなければならない。形と適用行は答えから決定的に導き、担当ごとに変えてはならない。SP-BPCONFORMANCE-041 は機械照合で判定し、LLM に判定させてはならない。

不適合の単位は同じ結果の実在する指摘候補と結び付け、未検査は理由と、強いられた未検査か判定できない未検査かを区別しなければならない。単位の不足・重複・対象外の値・存在しない候補や資産への参照・根拠の無い強いられた未検査を受理してはならない。結果を拒否した場合は SP-BPFINDINGS-034 に従う。

結果には適用の判定、単位ごとの結果、残る危険、照らした制限を含めなければならない。役ごとの制限を確認できなかった残る危険は、役・制限・host・未確認理由の 4 項目としなければならない。SP-BPCONFORMANCE-041 の判断点列挙の網羅に関する残る危険はこの 4 項目の対象外とし、同項の仕様項目 ID と網羅を確認していない理由の 2 項目で返さなければならない。照らした制限は SP-BPAUTHORING-046 に従う。効かない制限があれば PR-BPDESIGNEDSKILL-046 の不適合に対応しなければならない。判断点列挙の網羅を機械では確認していないことは SP-BPCONFORMANCE-041 のとおり毎回 1 件返し、検証役の任意の省略に任せてはならない。

複数 run の適用判定に関する未裁定の入力については、SP-BPINSPECTION-006 の保持規則をそのまま適用し、受理・拒否をここで決めてはならない。

#### SP-BPAUTHORING-046 Claude Code での役ごとの制限の照らし方
各反復の検証で、Claude Code での役ごとの制限の確かめ（PR-BPDESIGNEDSKILL-014）を SP-BPCONFORMANCE-019 の Claude Code の行と判定表のとおりに行わなければならない。この確かめは形式検証の段に置かない。検証役は、照らした結果を `checkedRoleLimits` に、照らした制限ごとに役の名前・制限の中身・配布先（Claude Code）・結果（効く・効かない）の 4 項目で返し、確認結果として保存する。

> 条件の値: 一覧 = 読めた / 読めない

| 条件: 一覧 | 結果 |
|---|---|
| 読めた | `checkedRoleLimits` に照らした全ての制限を載せる。効かない制限は PR-BPDESIGNEDSKILL-046 の不適合として指摘の候補にし（合否が不合格になり、書き直しで効く形に直す：PR-BPOPERATIONS-011）、一覧に照らした制限を Claude Code の残る危険 `residualRisks` に載せない |
| 読めない | `checkedRoleLimits` を空の並びにし、対象スキルの全ての役ごとの制限を、配布先を Claude Code、理由を無視される設定の一覧を読めないこととして、SP-BPCONFORMANCE-020 の 4 項目で `residualRisks` に載せる |

Codex runner で確かめられなかった制限は、一覧を読めたかによらず、SP-BPCONFORMANCE-019 の Codex runner の行のとおり `residualRisks` に載せる。

#### SP-BPAUTHORING-018 目標の観点
目標の観点の検証役には、今の対象スキルのパスと、状態にある固定した目標と出所を渡さなければならない。create では状態にある依頼文と回答を、update では作り直す前の写しのパスと、SP-BPFINDINGS-031 が修正の根拠として扱うとした根拠と、回答を合わせて渡さなければならない。検証役は、次を指摘の候補にしなければならない。

| 指摘の種類 | 候補にするとき |
|---|---|
| 成果物の未達 | 固定した目標の成果物を、対象スキルが作らない |
| 範囲の逸脱 | 対象スキルが固定した目標の範囲の外を扱う |
| 禁止事項の違反 | 対象スキルが固定した目標の禁止事項に反する |
| 数値条件の未達 | 対象スキルが固定した目標の数値条件を満たさない |
| 修正の根拠の未反映 | update で、修正の根拠として扱うとした根拠が、対象スキルに反映されていない |
| 依頼に無い目標・制約 | 対象スキルが持つ目標・制約に、create では依頼文と回答の中に、update では作り直す前の写し・修正の根拠・回答の中に根拠が無い（PR-BPOPERATIONS-003、update では PR-BPOPERATIONS-003 の読み替え） |

「依頼に無い目標・制約」の照らし方は SP-BPAUTHORING-037 に、判定基準が求める制約の扱いは SP-BPAUTHORING-038 に従う。

#### SP-BPAUTHORING-037 依頼に無い目標・制約の照らし方
目標の観点の検証役は、「依頼に無い目標・制約」を、固定した目標ではなく、依頼文・写し・修正の根拠・回答の原文に照らさなければならない（固定した目標は検証役の受理を通さずに書かれるので、目標の固定で紛れ込んだ目標を、固定した目標に照らすと見逃す）。

#### SP-BPAUTHORING-038 判定基準が求めた制約
SP-BPCONFORMANCE-003 の判定表で対象スキルに当たる仕様項目（その項目が参照する設計方針文書の原則の表の行を含む）が求める制約（同時実行の上限、`model` と `effort` の明示、停止の種類、資産台帳など）を、目標の観点の検証役は根拠のある制約として扱い、「依頼に無い目標・制約」の候補にしてはならない（候補にすると、適合の観点が求める制約を目標の観点が消させ、反復が上限まで往復する。PR-BPOPERATIONS-008 と PR-BPOPERATIONS-003 を両立させるため）。検証役は、そう扱った制約ごとに、資産 ID と、その制約を求める仕様項目 ID を「基準が求めた制約」として返さなければならない。CLI は、「基準が求めた制約」の欄 `basisConstraints` が無い結果と、担当に無い資産 ID か `docs/specifications/bp-conformance.md` の写しに無い仕様項目 ID を持つ結果を拒否しなければならない（拒否された結果の扱いは SP-BPFINDINGS-034）。

#### SP-BPAUTHORING-019 契約の観点
契約の観点の検証役には、作り直す前の写しのパスと、今の対象スキルのパスと、SP-BPFINDINGS-031 が修正の根拠として扱うとした根拠とその根拠の記録 ID の一覧と、判定基準の写し（SP-BPRUN-036）の場所を渡さなければならない。検証役は、契約の 5 つの要素ごとに、写しと今の対象スキルを照らし、変わったところを全て挙げなければならない。変わったところごとに、検証役は、その変化を求めたものとして次のどれか 1 つを選ばなければならない。

- 渡された一覧の修正の根拠の記録 ID
- 判定基準の仕様項目 ID: SP-BPAUTHORING-038 が根拠のある制約を求めるとした仕様項目のうち、その変化を求めたもの
- 「該当なし」

選んだものに従った返し方は SP-BPAUTHORING-039 に、既存の振る舞いが保たれたかの判定は SP-BPAUTHORING-040 に従う。

#### SP-BPAUTHORING-039 契約の変化の返し方
契約の観点の検証役は、SP-BPAUTHORING-019 で選んだものに従って、次のとおり返さなければならない。

- 「該当なし」を選んだ変化は、その要素の指摘の種類の指摘の候補にしなければならない。資産は、変化が現れる今の資産とする。要素が消えたときは、写しでその要素があったのと同じパスの今の資産とし、そのパスが今の対象スキルに無ければ今の SKILL.md の frontmatter の資産とする。
- 修正の根拠の記録 ID か判定基準の仕様項目 ID を選んだ変化は、指摘の候補にせず、変化と選んだ ID を「契約の判定の結果」として返さなければならない。CLI は、選ばれた記録 ID が渡した一覧にあることと、選ばれた仕様項目 ID が `docs/specifications/bp-conformance.md` の写し（SP-BPRUN-036）の仕様項目 ID であることを決定的に確かめ、当たらなければその結果の記録を拒否しなければならない（拒否された結果の扱いは SP-BPFINDINGS-034 と同じ）。CLI は、契約の変化の欄 `contractChanges` が無い結果と、契約の 5 つの要素の外の要素を持つ結果も拒否しなければならない。

#### SP-BPAUTHORING-040 既存の振る舞いの判定
既存の振る舞いが保たれたかは、契約の観点の結果と、SP-BPAUTHORING-022 の合否だけで判定しなければならない。書き手の申告や、写しとの差分の大きさで判定してはならない（PR-BPOPERATIONS-019）。修正の根拠も判定基準も求めないのに契約が変わったときは不合格とし、判定基準が求めた契約の変化は許す（依頼者の裁定）。判定基準が求めた変化は、変わった契約と、それを強いた仕様項目 ID を返り値に載せなければならない（SP-BPAUTHORING-032）。

#### SP-BPAUTHORING-020 合否に必要な検証の順
変更後の資産と版を確定して検証し、未確認の資産は SP-BPFINDINGS-025 に従って追加確認しなければならない。重複でない候補は反証し、消えた資産の照合と同じ指摘の見直しを反映してから合否を決めなければならない。この依存関係を満たす内部の段の分割・並列化・運搬の手順は実装の設計で決める。

#### SP-BPAUTHORING-041 fan-out の項目の順位
create・update の fan-out の項目の順位（SP-BPRUN-038 の列挙の順。起動数の上限で止まるときの未着手の項目の順位にも使う：SP-BPRUN-020）は、次の表のとおりとしなければならない。

| 段 | 順位 |
|---|---|
| 検証 | SP-BPAUTHORING-016 の判定表で起動するとした観点の、表の行の順（適合・目標・契約） |
| 追加の検証 | 検証の段と同じ観点の順 |
| 反証 | `docs/specifications/bp-inspection.md` の SP-BPINSPECTION-018 の反証役の項目の順位の規則を、検証の段と追加の検証の段の項目の順位（検証の段の項目が先）に当てる |
| 消えた資産の照合 | `docs/specifications/bp-findings.md` の SP-BPFINDINGS-020 |

### 合否

#### SP-BPAUTHORING-021 判定の単位の結果
合否では、保存した根拠から次の判定表で単位ごとの結果を決定的に求めなければならない。合否の決定は CLI の 1 箇所に置き、script が別に計算してはならない（依頼者の裁定）。

> 条件の値: 検証役が返した結果 = 適合 / 不適合 / 対象外 / 未検査
> 条件の値: 添えた鍵の指摘 = 不合格とした指摘が 1 つ以上ある / 全て合格を妨げない / 上記以外

| 条件: 検証役が返した結果 | 条件: 添えた鍵の指摘 | 結果 |
|---|---|---|
| 適合 | * | 適合 |
| 対象外 | * | 対象外 |
| 未検査 | * | 未検査（検証役が添えた区分のまま） |
| 不適合 | 不合格とした指摘が 1 つ以上ある | 不適合 |
| 不適合 | 全て合格を妨げない | 適合（反証で退けられたか直った単位として、理由に指摘 ID を添える） |
| 不適合 | 上記以外 | 未検査（強いられていない未検査） |

SP-BPCONFORMANCE-041 の単位には表を当てず、同じ対象版についての機械照合の結果と理由を使わなければならない。照合記録が無いまま合否を決めてはならない。未検査は強いられていない未検査とする。

「添えた鍵の指摘」は、添えた鍵が指す台帳の指摘に SP-BPAUTHORING-022 を当てた結果で数える（前の run が状態を記録した指摘も、同項のとおり、この run の見直しの判定で数える）。「上記以外」は、不合格とした指摘が無く、かつ「検証が成り立たない」とした指摘か、台帳に指摘の無い鍵（未反証の候補：SP-BPFINDINGS-015）が 1 つ以上あることを指す。適合の観点の検証役の項目が打ち切りになったときは、適用の判定表の行が決まらないので、判定の単位ごとの結果を（判断点の機械照合 の記録があっても SP-BPCONFORMANCE-041 の単位を含めて）空にし、打ち切った項目 ID を合否の理由と検証の結果に載せる（SP-BPAUTHORING-023 の 1 で「検証が成り立たない」になる）。

#### SP-BPAUTHORING-022 指摘による合否
合否では、指摘ごとに次の判定表を適用しなければならない。「記録した run」は、指摘の最後の状態の記録を記録した run である（SP-BPFINDINGS-019）。「この run の見直しの判定」は、記録した run が前の run の指摘にだけ CLI が記録する（SP-BPFINDINGS-019）。「記録なし」は、この run にその記録が無いこと（SP-BPFINDINGS-018 の「判定しない」を含む）を指す。「今の内容で判定したか」は SP-BPFINDINGS-021 の値で、記録した run が前の run の指摘では、この run の見直しの判定が記録された時点の値とする。

> 条件の値: 記録した run = 今の run / 前の run
> 条件の値: 状態 = open / dismissed / resolved / regressed
> 条件の値: この run の見直しの判定 = 存在する / 存在しない / 判定できない / 記録なし
> 条件の値: 今の内容で判定したか = はい / いいえ

| 条件: 記録した run | 条件: 状態 | 条件: この run の見直しの判定 | 条件: 今の内容で判定したか | 結果 |
|---|---|---|---|---|
| 今の run | open | * | * | 不合格（書き直しの入力にする） |
| 今の run | regressed | * | * | 不合格（書き直しの入力にする） |
| 今の run | dismissed | * | はい | 合格を妨げない |
| 今の run | dismissed | * | いいえ | 検証が成り立たない |
| 今の run | resolved | * | はい | 合格を妨げない |
| 今の run | resolved | * | いいえ | 検証が成り立たない |
| 前の run | * | 存在する | * | 不合格（書き直しの入力にする） |
| 前の run | * | 存在しない | はい | 合格を妨げない |
| 前の run | * | 存在しない | いいえ | 検証が成り立たない |
| 前の run | * | 判定できない | * | 検証が成り立たない |
| 前の run | open | 記録なし | はい | 不合格（書き直しの入力にする） |
| 前の run | regressed | 記録なし | はい | 不合格（書き直しの入力にする） |
| 前の run | dismissed | 記録なし | はい | 合格を妨げない |
| 前の run | resolved | 記録なし | はい | 合格を妨げない |
| 前の run | * | 記録なし | いいえ | 検証が成り立たない |

今の run が記録した指摘は、この run の見直しの判定を持たないので、その列を問わない。前の run が記録した指摘を、この run で resolved / regressed として報告してはならない（PR-BPOPERATIONS-022）。報告の形は SP-BPFINDINGS-028 に従う。

#### SP-BPAUTHORING-023 反復の合否
合否は次の順に条件を当て、最初に当たった値としなければならない。

1. 次のどれかに当たれば「検証が成り立たない」。
   - SP-BPAUTHORING-022 で「検証が成り立たない」とした指摘がある。
   - 未反証の候補（SP-BPFINDINGS-015）がある。
   - 追加の検証の段の後に、どれかの観点の skip 一覧が空でない。
   - その反復の検証の段に、結果を持つ適合の観点の検証役の項目が無い（項目が打ち切りになったか、項目そのものが無い）。理由には打ち切った項目、または適合の観点そのものが無いことを載せる。このとき判定の単位ごとの結果は空なので（SP-BPAUTHORING-021）、この条件は判定の単位の結果からではなく項目から決める。
2. 次のどれかに当たれば「不合格」。
   - SP-BPAUTHORING-022 で「不合格」とした指摘がある。
   - SP-BPAUTHORING-021 で「不適合」か、強いられた未検査でない「未検査」とした単位がある。
3. 上記以外は「合格」。

強いられた未検査の単位と、残る危険は、合否を妨げない。これらは完了時の出力で宣言する（SP-BPAUTHORING-033）。

合否とその根拠を保存し、書き直しに使う指摘・単位と理由は合否時点のまま保持しなければならない。合格または検証が成り立たない場合は、同じ run の書き直しの根拠を作ってはならない。

#### SP-BPAUTHORING-024 反復の数え方
合否を確定した反復を 1 回と数え、検証が成り立たない場合も 1 回に数えなければならない。目標の固定と形式検証は反復に含めてはならない。記録の中断・再送で数えが抜けたり二重になったりしてはならない。累計と run ごとの増分を残し、上限は SP-BPRUN-013 に従って増分に当てなければならない。

#### SP-BPAUTHORING-025 合否の後の進み方
合否を状態に書いた後、script は、CLI が次の判定表で決めて返した進み方に従わなければならない（script は同じ判定を計算し直さない）。「増分」は SP-BPRUN-013 の、現在の run の開始時からの反復の回数の増分である。

> 条件の値: 合否 = 合格 / 不合格 / 検証が成り立たない
> 条件の値: 増分 = 反復の上限より小さい / 反復の上限に達した

| 条件: 合否 | 条件: 増分 | 結果 |
|---|---|---|
| 合格 | * | 形式検証の段へ進む（SP-BPAUTHORING-042） |
| 不合格 | 反復の上限より小さい | 次の反復の書く段へ戻る（書き直しの許容：PR-BPOPERATIONS-011） |
| 不合格 | 反復の上限に達した | 反復の上限で止まる（SP-BPRUN-010・013）。理由に、不合格とした指摘 ID と判定の単位を書く（PR-BPOPERATIONS-010） |
| 検証が成り立たない | * | SP-BPAUTHORING-030 に従い BLOCKED で止まる |

#### SP-BPAUTHORING-026 完了の条件
直前の反復の合否が合格で、その後の対象版に対する形式検証が SP-BPAUTHORING-044 を満たした場合だけ、完了としてよい。それまでは完了と報告してはならない。完了の判定と変更ファイルの検証済みの記録は矛盾せず、同じ対象版を指さなければならない。その他の停止で未検証のファイルを検証済みにしてはならない。

### 形式検証

#### SP-BPAUTHORING-042 形式検証の段
独立検証の合格後、生成と別の context で、要求・状態・遷移・入出力・制約から検証すべき性質を洗い出し、適用できる形式検証を行わなければならない。形式化できない性質には理由を付け、別の方法の結果または未確認の理由を残さなければならない。結果と範囲は SP-BPAUTHORING-043 に従って保存し、保存した性質ごとの結果から SP-BPAUTHORING-044 の完了条件を決定的に求めなければならない。

再開後に検証し直す場合、前の対象版や未完了の検証結果を、今の回の合格として使ってはならない。内部の worker 件数と結果の受け渡し形式は実装の設計に委ねる。

#### SP-BPAUTHORING-043 形式検証の記録
形式検証の段の検証役は、結果を自分の作業記録（`docs/specifications/bp-run.md` の作業記録）に書き、記録台帳がその作業記録を指さなければならない。作業記録は、洗い出した性質ごとに 1 行を持ち、行ごとに形式化できたかを示す。行の欄は次の表とする。洗い出した性質が 0 件のときは、0 件であることを書く。作業記録は、洗い出した性質が検証すべき性質の全てであることを検証役の判断が保証しないこと（洗い出しの網羅の限界）の宣言を持たなければならない。網羅の限界の宣言を、網羅の証明としてはならない。

| 性質の区分 | 行が持つ欄 |
|---|---|
| 形式化できた | 対象・手法・道具（名前と版）・前提・検証した範囲・結果・未検証の範囲（PR-BPDESIGNEDSKILL-026） |
| 形式化できない | 形式化できない理由（PR-BPDESIGNEDSKILL-024）と、別の確認の方法と結果、又は未確認であることと理由（PR-BPDESIGNEDSKILL-024） |

create・update の返り値の検証の結果（SP-BPAUTHORING-032・034）は、この作業記録のパスを指す。

#### SP-BPAUTHORING-044 形式検証の段を通ったとするとき
保存した形式検証の結果から次の表で判定しなければならない。複数の失敗がある場合は性質が成り立たないことを優先して停止原因とし、実行できなかった性質も報告から落としてはならない。

| 対象を読み性質を洗い出せたか | 成り立たない性質 | 実行できない性質 | 結果 |
|---|---|---|---|
| いいえ | * | * | 通らない。formalUnrunnable |
| はい | 無 | 無 | 通る |
| はい | 無 | 有 | 通らない。formalUnrunnable |
| はい | 有 | 無 | 通らない。formalFailed |
| はい | 有 | 有 | 通らない。formalFailed |

洗い出しができて 0 件の場合と、形式化できない性質の未確認が残る場合は、表の「通る」に含め、その 0 件または未確認と理由を記録に示さなければならない。0 件を洗い出し不能と混同してはならず、未確認を確認済みとしてはならない。

#### SP-BPAUTHORING-045 形式検証の失敗
SP-BPAUTHORING-044 を通らなければその run は BLOCKED で止まり、対象・失敗理由・実行不能か性質が成り立たないかを報告しなければならない。同じ run の書き直しへ戻ってはならない。

原因は同表の `formalUnrunnable`・`formalFailed` とし、検証役が結果を返さない場合は `verifiers` としなければならない。結果の保存拒否や運搬失敗の場合はこの原因の値を付けず、その失敗を報告しなければならない。再開は SP-BPAUTHORING-035 に従う。

### 停止

#### SP-BPAUTHORING-027 needs_input で止まるところ
create・update の run が needs_input で止まってよいのは、目標の固定の段（SP-BPAUTHORING-007・008）と、状態を作る前の入力の確かめ（SP-BPAUTHORING-029）だけとする。書く段から合否の段までの間は、人間の入力を求めて止まってはならない（反復の中で人間の入力を待つ手順を持たない：PR-BPOPERATIONS-005）。

#### SP-BPAUTHORING-028 止まったときに書いたファイルと報告
完了の前に止まったとき、run は書いたファイルを残さなければならない（SP-BPRUN-012）。返り値は SP-BPRUN-032 の項目に加えて、SP-BPAUTHORING-034 の項目を持たなければならない。

#### SP-BPAUTHORING-035 再開した run が始めるところ
create・update の再開した run は、SP-BPRUN-015 の 1・2 を行った後、同じ反復の続きとして始めるときは、終えていない段の未着手の項目から続け、終えた段の結果を処理し直してはならない。止まった段の項目が 0 件なら、その段を最初から行う。ただし、再開した run の開始で機能によらず行う台帳の取り直し（SP-BPFINDINGS-005）と、その取り直しで消えた資産が新しく記録されたときの消えた資産の照合の段は、それぞれの段を終えていても行い、本項の例外とする。停止の種類（反復の上限は、停止の記録が残す当たった上限で分ける：SP-BPRUN-011）と止まった段ごとの始め方は、次の表とする（保存された停止と進みから決める）。

| 前の run の停止 | 止まった段 | 始め方 | 前の回の未着手の項目 |
|---|---|---|---|
| needs_input | 目標の固定 | 回答を前提に書き、前回と別の目標固定として始め直し、新しい反復の書く段へ進む | 破棄する |
| 反復の上限（反復の回数） | 合否 | 新しい反復の書く段から。書き直しの入力は最後の合否の書き直しの入力（SP-BPAUTHORING-014） | 破棄する |
| 反復の上限（起動数の上限） | 全て | 同じ反復・同じ回の続き（形式検証の段も同じ回：SP-BPRUN-038）。止まった段を同じ項目として確認し、結果の無い項目だけを処理する。止まった段が書く段より前（開始・作り直す前の写し・目標の固定）なら、目標の固定は同じ回の続き（前提に目標が無いとき）から、最初の反復の書く段へ進む。追加の検証の段は、未着手の項目を破棄して、再開の時点の skip 一覧から次の部分を作り直す | 処理する（追加の検証の段は破棄する） |
| BLOCKED | 開始・作り直す前の写し | 写しの段から（記録があれば照らすだけ：SP-BPAUTHORING-004）。前提に目標が無ければ前回と別の目標固定として始め直し、新しい反復の書く段へ進む | 破棄する |
| BLOCKED | 目標の固定 | 前提に目標があれば飛ばし（SP-BPAUTHORING-010）、無ければ前回と別の目標固定として始め直す。繰り返しの回数は引き継ぐ。新しい反復の書く段へ進む | 破棄する |
| BLOCKED | 書く | 新しい反復の書く段から。書き直しの入力は、前の反復の合否があればその書き直しの入力（最後に確定した根拠。その合否が「検証が成り立たない」なら空：SP-BPAUTHORING-023）、無ければ無し | 破棄する |
| BLOCKED（検証役・反証役が結果を返せないことによる：`verifiers`） | 台帳・検証・追加の検証・反証・消えた資産の照合・見直し・合否 | 書き手を起動せず、新しい反復の台帳の段から検証し直す（SP-BPAUTHORING-005 のただし書き） | 破棄する |
| BLOCKED（それ以外：CLI の拒否・運搬役の失敗） | 台帳・検証・追加の検証・反証・消えた資産の照合・見直し・合否 | 新しい反復の書く段から。書き直しの入力は、前の反復の合否があればその書き直しの入力（最後に確定した根拠。その合否が「検証が成り立たない」なら空：SP-BPAUTHORING-023）、無ければ無し | 破棄する |
| BLOCKED（形式検証を実行できない：`formalUnrunnable`） | 形式検証 | 書き手を起動せず、前回と別の検証として形式検証の段から始める | 破棄する |
| BLOCKED（性質が成り立たない：`formalFailed`） | 形式検証 | 新しい反復の書く段から。書き直しの入力は、成り立たなかった性質と理由（SP-BPAUTHORING-014） | 破棄する |
| BLOCKED（検証役が結果を返さない：`verifiers`） | 形式検証 | 書き手を起動せず、書き直しの入力なしで、前回と別の検証として形式検証の段から始める | 破棄する |
| BLOCKED（`cause` なし：形式検証の段の結果の書き込みでの CLI の拒否・運搬役の失敗） | 形式検証 | 書き手を起動せず、書き直しの入力なしで、前回と別の検証として形式検証の段から始める | 破棄する |
| 停止の記録が無い | SP-BPRUN-018 で決めた段 | 反復の上限（起動数の上限）の行と同じ | 処理する |
| 完了 | — | 再開を拒否する | — |

新しい反復や始め直した目標の固定に移るとき、前の回の未着手の項目を処理してはならない（前の回の項目は、利用者が直す前の条件で出したものである）。それらは SP-BPRUN-015 の 5 のとおり破棄した未着手の項目として状態に書かせる。

## エラー処理と異常系

本章は create・update に固有の異常系だけを置く。agent の失敗・工程の欠け・CLI の拒否・途中終了・不正か最小に満たない起動数の上限は `docs/specifications/bp-run.md` の SP-BPRUN-027〜030・SP-BPRUN-018・SP-BPRUN-037 に、台帳の資産が 0 件のときと台帳に無い値を含む結果は `docs/specifications/bp-findings.md` の SP-BPFINDINGS-033〜035 に従う。停止の種類は SP-BPRUN-010 の表で create・update が使うとしたものから選ぶ。起動数の上限で止まるときの停止の種類と理由は SP-BPRUN-035 に従う。

#### SP-BPAUTHORING-029 状態を作る前の入力の確かめ
create・update の run は、状態を作る前に、入力を次の判定表で確かめなければならない。「確かめる時点」が「agent の起動の前」の行は、script が入力の値だけから決定的に確かめ、agent を 1 体も起動せずに止まる。「開始の操作」の行は、最初の運搬役が呼ぶ CLI の開始の操作（SP-BPRUN-003）が確かめ、CLI は状態と作業場所を作らずに理由を返し、script は次の agent を起動せずに止まる（script はファイルに触れないので、ファイルの有無は CLI が確かめる）。

> 条件の値: 機能 = create / update
> 条件の値: 当たること = 依頼文が空 / 修正の根拠として扱う根拠が 0 件 / 対象スキルのディレクトリが既にある / 対象スキルのディレクトリが無い

| 条件: 機能 | 条件: 当たること | 結果 |
|---|---|---|
| create | 依頼文が空 | agent の起動の前に、needs_input と理由（依頼文が要ること）を返す |
| create | 修正の根拠として扱う根拠が 0 件 | 起こりえない（create は修正の根拠を受け取らない） |
| create | 対象スキルのディレクトリが既にある | 開始の操作で、BLOCKED と理由（既にあるパスと、既存のスキルを直すなら update を使うこと）を返す。既にあるものに書いてはならず、消してもならない（PR-BPOPERATIONS-037）。`.agents/skills/<name>` に何かが在るとき（ディレクトリ・symlink（公開済みのスキル：[repository-operations の現行案内]、設計時点の出典：[設計時点の出典／旧規約 @ c7759f1]）・通常のファイルを含め、種類を問わない）を既にあるとし、理由に在るものの種類も書く |
| create | 対象スキルのディレクトリが無い | 起こりえない（create はディレクトリを新しく作る。「無い」は `.agents/skills/<name>` に何も無いときを指す） |
| update | 依頼文が空 | 起こりえない（update は依頼文を受け取らない：SP-BPENTRY-013） |
| update | 修正の根拠として扱う根拠が 0 件 | agent の起動の前に、needs_input と理由（受け取った修正の根拠の件数と、SP-BPFINDINGS-031 で扱わなかった件数と、1 件以上の修正の根拠が要ること）を返す（PR-BPOPERATIONS-015） |
| update | 対象スキルのディレクトリが既にある | 起こりえない（update はディレクトリがあることを前提にする） |
| update | 対象スキルのディレクトリが無い | 開始の操作で、BLOCKED と理由（無いパス）を返す |

「修正の根拠として扱う根拠」は SP-BPFINDINGS-031 に従い、参照の形で渡した場合も元の結果へ展開して件数を確認しなければならない。扱う根拠が 0 件なら状態と作業場所を作らず needs_input とし、受け取った件数・扱わなかった件数・1 件以上が必要であることを返さなければならない。参照が完了した review・audit の結果を指さない、または対象スキルが違う場合は BLOCKED としなければならない。

この入力確認で止まる場合、状態 ID と next_args を返してはならず、利用者は入力を直して新しく起動する。

#### SP-BPAUTHORING-030 検証が成り立たない
反復の合否が「検証が成り立たない」のとき、run は BLOCKED で止まらなければならない。理由には、SP-BPAUTHORING-023 の 1 で当たった項目（指摘 ID、未反証の候補、skip 一覧に残った資産 ID、打ち切りになった項目）を全て書かなければならない（書き直しでは直らず、検証役か反証役が結果を返せない原因を利用者が直す必要がある）。この反復を反復の上限で止まった反復として扱ってはならない。

#### SP-BPAUTHORING-031 一覧の外へのパス
書く段の書き手が対象スキルのパスの一覧の外のパスを返したとき（SP-BPAUTHORING-015）、run は次の段へ進まず、BLOCKED で止まらなければならない。理由には一覧の外のパスを全て書く。返り値の SP-BPAUTHORING-034 の「検証を通っていないこと」には、一覧の外のパスも、書いたが検証を通っていないものとして載せる。script は、一覧の外のファイルを戻させてはならない（戻すかどうかは利用者が決める：PR-BPOPERATIONS-040）。

## 外部インタフェース

create・update の入力の項目と綴りは SP-BPENTRY-013 の表と綴りの表に従う。どの停止でも返す共通の項目は SP-BPRUN-032 に、指摘と台帳の項目は SP-BPFINDINGS-029・030・032 に従う。本章は、create・update に固有の返り値の項目だけを定める。項目の綴りは各表の「綴り」の列とする。状態を作った後の返り値は保存済みの根拠から決定的に作り、書いた run と完了した run が別でも同じ意味を保たなければならない。状態を作る前の入力の確かめ（SP-BPAUTHORING-029）で止まるときの返り値は、SP-BPAUTHORING-034 の判断材料の表のその行のとおり script が作る。

#### SP-BPAUTHORING-032 検証の結果
create・update の返り値の「検証の結果」は、最後に合否を書いた反復について、次の項目を持たなければならない。

検証の結果は、返り値の `verification` の中に次の綴りで置く。

| 項目 | 綴り | 中身（検証の結果） |
|---|---|---|
| 合否 | `decision` | SP-BPAUTHORING-023 の合格/不合格/検証が成り立たないに対応する pass・fail・unverifiable と、当たった指摘 ID と判定の単位 |
| 反復の回数 | `iterations` | 状態の累計と、この run での増分 |
| 判定の単位ごとの結果 | `units` | 適合の観点の判定の単位ごとに、SP-BPAUTHORING-021 の結果と理由。適合の観点の検証役の項目が打ち切りになった反復では空で、打ち切った項目 ID は合否の中に載る |
| 強いられた未検査 | `forcedUnchecked` | 強いられた未検査の判定の単位の一覧と、保留の根拠の仕様項目 ID |
| 基準が求めた制約 | `basisConstraints` | SP-BPAUTHORING-038 で目標の観点の検証役が返した、資産 ID と仕様項目 ID の組の一覧 |
| 契約の判定の結果 | `contract` | update だけ。変わったところごとに、契約の要素・変わった契約の中身・選んだもの（修正の根拠の記録 ID、強いた判定基準の仕様項目 ID、「該当なし」のどれか）・指摘 ID（「該当なし」のとき）。判定基準が強いた変化は 1 件も省かない（SP-BPAUTHORING-039・SP-BPAUTHORING-040） |
| 台帳 | `ledger` | SP-BPFINDINGS-030 の項目から指摘の一覧を除いた欄（カバレッジ・skip 一覧・資産の結末・未反証の候補・拒否された結果）。review・audit の `ledger` と同じ形とする。指摘の一覧は返り値の最上位の `findings`（SP-BPAUTHORING-033・034）だけに置く |
| 形式検証の記録 | `formalVerification` | 状態で最後の合否の段の項目の結果の記録より後に始めた形式検証の段の回のうち、最後の回の項目の結果（SP-BPAUTHORING-042 の結果）の 作業記録のパス（SP-BPAUTHORING-043）。その結果が無いとき（最後の合否が合格でないか、合格の後の形式検証の段に結果が無いとき）は `null`。記録の前後は保存した実行の順で決める |

#### SP-BPAUTHORING-033 完了時の出力
create・update が完了で止まったとき、返り値は SP-BPRUN-032 の項目に加えて、次の項目を持たなければならない。

> 条件の値: 機能 = create / update
> 条件の値: 項目 = スキル / 設計の説明 / 検証の結果 / 指摘の状態 / 残る危険 / 受け取った修正の根拠 / 対象スキルから外した callsite

| 条件: 機能 | 条件: 項目 | 綴り | 結果 |
|---|---|---|---|
| create | スキル | `skill` | 作ったスキルのディレクトリのパス（連鎖で次の機能の対象スキルにする：SP-BPENTRY-009）と、作ったスキルのパスの一覧と各ファイルの内容の指紋（PR-BPOPERATIONS-014） |
| update | スキル | `skill` | 直したスキルのパスの一覧と、各ファイルの内容の指紋。消したファイルのパスも載せる（PR-BPOPERATIONS-014） |

止まった理由は SP-BPRUN-032 の「理由」`reason` に書く。理由には、本文書の各項目が理由に書くとした内容を含めなければならない。

needs_input で止まった create・update の返り値は、理由 `reason` に加えて、判断材料の 4 つの欄（決めること `toDecide`・ここまでの検証結果 `verification`・影響の範囲 `impact`・残った作業 `remainingWork`）を常に持たなければならない（PR-BPOPERATIONS-052）。まだ無い材料の欄の値は `null` にする。判断材料の欄は SP-BPRUN-032 の共通の項目に足さない。`verification` の中身は SP-BPAUTHORING-032 とし、needs_input 以外の停止での `verification` の返し方は上の表のまま変えない。欄の値は、止まったところで次の表のとおりとする。状態を作った後の停止（表の目標の固定の 2 行）では、欄の値を停止の入力ではなく状態に保存した記録から作る（判断材料を未検証の停止入力から補わない）。状態を作る前の入力の確かめ（表の 1 行目）では、状態も停止の記録も作らず 返り値を作る処理 を呼べないので、script が SP-BPAUTHORING-029 の判定表の当たった行の理由（開始の操作の拒否の応答を含む）から欄の値を作る。

> 条件の値: 止まったところ = 状態を作る前の入力の確かめ / 目標の固定（書き手が足りない入力を返した） / 目標の固定（出所の照合が上限の回まで通らない）

| 条件: 止まったところ | 結果 |
|---|---|
| 状態を作る前の入力の確かめ | `toDecide` は SP-BPAUTHORING-029 の判定表がその行の理由に挙げる要る入力。`verification`・`impact`・`remainingWork` は `null` |
| 目標の固定（書き手が足りない入力を返した） | `toDecide` は状態の最後の目標の固定の段の項目の結果の `missing` の問いの一覧（SP-BPAUTHORING-008）。`impact` は同じ項目の結果の `impact`（SP-BPAUTHORING-006）とし、その欄が無いときは `null`。`remainingWork` は 保存済みの結果 が停止の記録の未着手の項目の一覧（SP-BPRUN-011）から作った残った作業。`verification` は合否を書いた反復があれば最後の反復の検証の結果、無ければ `null` |
| 目標の固定（出所の照合が上限の回まで通らない） | `toDecide` は、状態の最後の 目標の照合で通らなかった要素（SP-BPAUTHORING-007）の要素ごとに 1 つの要素を持つ並びとし、各要素は 通らなかった要素の `{要素の種類, 書き手の値, 理由}` を値を変えずに持つ。決めるのに要る回答を別の欄に持たない（SP-BPAUTHORING-007）。返り値を作る処理 は問いの文を作らず、理由を書き換えず、欄を省かない。`impact` は `null`。`remainingWork` と `verification` は上の行と同じ |

## 検証方法

入力と対象を制御した fixture で、目標と出所、変更範囲、独立検証、合否、形式検証の結果、停止と再開後の成果を観測する。入力不足、既存パス、根拠 0 件、検証の欠け、範囲外の変更、上限の直前/到達時、保存できない場合と再開を含める。合否・形式検証・再開の表の閉じた組合せを全件照合する。

生成・検証・反証の分離と権限は実行記録と権限設定に照合する。模擬の agent は制御と結果の対応だけを確かめ、判断の質の証拠にしてはならない。公開前には本物の agent で create・update・review・audit を各 1 回以上試走し、判断の当たり・偽陽性・偽陰性と、実際に確認できた範囲を記録しなければならない（依頼者の裁定）。内部運搬の不一致も測り、記録を正本とする。
