# 網羅の台帳で見落としを減らす仕組み

LLM の agent の作業（設計・レビュー・計画・実装）で、見落としを構造で減らす仕組みの方式設計。軸は「確率的な部品から、全体として信頼できる結果を出す」こと。1 体に任せる量を小さくし、どこを見たかを台帳に残して空きを見える形にし、独立に重ね、生成と検証を分け、測り、網羅で止める。

この文書は方式設計の層にある（要求の前段の調査と構成の設計）。決めるのは、目的に効く構成、置き場と境界、依存の向き、判断の理由と退けた案、規模の桁、未確認の前提とその確かめ方まで。op の入出力・エラーの扱い・状態機械の細部・定数・閾値は決めず、「下の層で決める」とする。

利用者が固定した決定（この文書では変えない。以下「決定 N」で引く）：
1. 特定のスキルに依存させない。repo-review・prd-spec・設計レビュー・計画などの複数のスキルから使える汎用の仕組みにする。
2. 考え方は、ブラックボード型の構成と、[skill-design-patterns](skill-design-patterns.md) の探索グラフ・資産台帳に近いものにする。
3. Codex では、既存の workflow runner（`plugins/workflow/skills/dynamic-workflow-runner`）で動かす。
4. 静的に決まるもの（範囲の列挙・枡の生成・照合・形式・上限・止める条件）は script とスキーマに持たせる。判断に任せるものは、目的と理由だけで書く。
5. 役ごとのモデルと effort を、性能と費用のよい組で設定できる設計にする。Haiku にも使い道がある。値は実測で見直す。
6. 局所最適にしない。欠陥は、原因のある層（方針・要求・方式設計・詳細設計・実装）へ戻す。
7. この文書は方式設計の層に置く。

## 背景

前の設計レビューと計画の作業では、次のことが起きた。
- 計画の段で、2 回目以降に出た指摘 27 件のうち 18 件は、前からあった見落としだった。9 件は、直しが持ち込んだ誤りだった。reviewer は前の回を知らず、毎回全体を初めて読み、どこを見たかの記録も無かった。
- 合否が「指摘 0 件」だけで決まっていた。網羅も、進み具合も見ていなかった。
- 改稿の依頼が「指摘の箇所だけ直す」になっていた。局所の修正が既定の経路として残り、改稿が発散した。
- 全体設計を経ずに計画へ入っていた。上の層の判断が欠けたまま、下の層で直し続けていた。
- 設計レビューと計画には、スキルの経路が無かった。即興のループで回したため、上限と設計へ戻る流れが当たらなかった。
- 状態を運ぶ役が、長い不透明な値（状態の sum）を写し間違えた。同じ失敗が 2 回再現した。

調査からは、次のことが分かっている。
- LLM のレビューの再現率は、1 回でおよそ 23% にとどまる。複数回の結果を統合すると上がる。同じモデルを 5 回走らせても、5 回とも出た正解の指摘は一部に限られる（SWR-Bench）。「新しい指摘が 0 件」では、見終えた証拠にならない。
- 同じモデルは盲点を共有する。別のモデルと組むほうが、同じモデル 2 回より多く見つかる（Song、抄録）。
- 観点は確認項目の列挙でなく、対象のモデルを作って問いに答える手続き（scenario）にしたときに効く（PBR、Porter）。ただし効果の再現は割れている（Ciolkowski、Regnell）。
- 合議させるより、独立に読ませて機械的に合わせるほうがよい（名目チーム、Halling と Biffl）。予算は人数より条件の多様性に配る（Biffl）。
- 捕獲再捕獲による残りの推定は、少人数では過小になり、LLM は独立性の前提を破る（Briand）。
- 読了を記録すると再現率が上がるかを、直接測った研究は無い。

## 結論

| 決めること | 判断 |
|---|---|
| 欠陥の戻し方 | 欠陥を「どの層の判断が原因か」で分類し、原因の層を作り直す。指摘の箇所を局所で直す経路を、構造として持たない |
| 置き場 | 特定のスキルの外に、台帳の静的な部分を持つ共有の CLI を置く。workflow plugin のスキルとして置く。呼ぶ側から仕組みへの一方向の依存にする |
| 役 | skill-design-patterns の役（計画役・実行役・回収役・検証役・運搬役・CLI・script・人間）を、全ての作業に共通の形で使う。新しい役は足さない |
| 台帳 | 資産・観点・枡・担当・「見た」の記録・指摘・原因の層を持つ。書くのは CLI だけ。「見た」は、機械で確かめられる記録にする |
| 枡 | 資産の列挙と、資産と観点の直積を script が決定的に作る。一緒に読まないと判断できない範囲は、束の資産として足す |
| 観点 | 確認項目でなく、モデルを作って問いに答える手続きとして定義する。形は仕組みが持ち、中身は呼ぶ側が持つ |
| 重ね | 重要な枡だけを、条件（観点・モデル・新しい文脈）を変えて独立に見直す。合議させない。指摘は決定的な規則で統合し、反証は統合の後に置く |
| 完了 | 「全ての枡を見たか、見られなかったと開示したか」で判定する。指摘の増分は、追加の周を打ち切る判断にだけ使う |
| モデル | 値の正本を 1 か所に置き、役の性質で初期値を決め、実測で見直す。費用は起動の前に静的に見積もる |
| 測り方 | 毎回の run の指標、正解つきの較正、前の作業との比較の 3 つに分ける。測定の結果は変更の提案として出し、自動では切り替えない |
| 組み込み | 経路の無い設計レビューと計画から始め、repo-review、repo-implement、prd-spec の順に組み込む |

## 層と差し戻し

**層と成果物。** 扱う層は、方針・要求・方式設計・詳細設計・実装の 5 つで、閉集合にする。層の一覧はデータとして、汎用の部品（script とスキーマ）に 1 つだけ置く。各行は次を持つ。
- 層の順序（どちらが上流か）。
- その層が決めること。
- その層が決めてはいけないこと。
- 成果物の種類。
- 判定の問い。

成果物は層ごとにおおむね 1 つにする。

| 層 | 成果物 |
|---|---|
| 方針 | 目的・固定した決定・やらないこと |
| 要求 | 結果としての要求（仕組みを書かない） |
| 方式設計 | 構成・置き場・境界・依存の向き・退けた案 |
| 詳細設計 | op の入出力・エラー・状態・定数・契約 |
| 実装 | コード・テスト・CLI |

各スキルが渡すのは、「自分の成果物がどの層か」の対応だけにする。層の定義を各スキルに写さない。

**分類。** 欠陥の原因の層は、自由記述で決めない。検証役が閉集合から選んだ判定をもとに、script が決定的に出す。
- 原因の層は「最も上流の、この欠陥を正しく決めていない層」とする。上流の判断が誤っていれば、下流は上流の写しなので、下流の直しは効かない。
- 「越境」（下の層で決めるべき細部や仕組みを、上の層に書いた）を、独立した原因の種別として持つ。越境の作り直しは、記述を足すことでなく、下の層へ移すか消すことになる。
- 分類は書き手と別の担当が行う（生成と検証の分離）。
- 分類の判定の形（層ごとに判定を返して script が導くか、検証役が 1 つの層を選ぶか）は、[未決](#未決)。

**戻し方。** 戻し方は「原因の層を作り直す」の 1 つだけにする。
- 指摘の箇所を直す操作は、script の遷移にも、書き手への入力のスキーマにも置かない。
- 欠陥は原因の層ごと、根本原因ごとにまとめ、最も上流の層から作り直す。書き手には、その層の目的・固定した決定・根本原因の記述を渡す。指摘の位置（行・節）は渡さない。
- 上流を作り直したら、下流の成果物を「古い」と台帳に印を付ける。下流で保留した指摘は、上流が安定してから分類し直す。上流の直しで消えるものがあるため。
- 作り直した層は、全体を新しい文脈で同じ検査にかける。下流は、上流の変更に触れる部分だけを導き直す。
- 方針が原因の欠陥と、要求が複数の解釈を許す欠陥は、価値判断なので利用者へ返して止める。
- 同じ層への戻しには上限を置く（値は下の層で決める）。戻した後に同じ根本原因が再発したら、原因の層の判定を見直す対象にする。
- 戻す遷移（作り直し・古い印・保留）を仕組みが実行するか、仕組みは戻す先を示すだけで呼ぶ側が実行するかは、[未決](#未決)。

**退けた案。**
- 規約の散文（必須欠陥は設計へ戻る）のまま、観点に層の分類を足す：「設計」が 1 つの塊で、どこへ戻すかの基準が無い。規約を読んでも自分のループに当てられなかった事例がある。決定 4 にも反する。
- 局所か設計かの 2 値の分類：要求の層・方針の層・越境を区別できない。「局所」の判定が局所修正の言い訳になる。
- 指摘の位置で戻し先を決める：位置は原因でない。同じ原因が毎回別の箇所に出る事例を拾えない。
- 書き手が原因の層を決める：生成と検証の分離に反する。書き手は自分の層の中で直そうとする。
- 層の定義を各スキルが持つ：決定 1 に反し、写しがスキルごとに食い違う。
- 「同じ箇所で 2 回出たら設計へ戻す」という発火の条件：事後の発火で、原因が同じで箇所が違うものを拾えない。既にある規則の再発明でもある。
- 戻した層より下流を全て作り直す：上流の変更に触れない下流にも費用を払う。

## 置き場と依存の向き

**置き場。** 汎用の仕組みは、規約と共有の CLI を持つ新しいスキル（仮称 coverage-board）として、workflow plugin（`plugins/workflow/skills/`）に置く。
- workflow plugin には、prd-spec と runner が既にある。prd-spec は同じ plugin の兄弟のスキルとして使え、新しい依存の宣言が要らない。
- 公開の前は `.agents/skills/` に実体を置き、公開の操作で `plugins/workflow/skills/` へ移す（[リポジトリの運用](../guidelines/repository-operations.md#配置と配布) のとおり）。

**CLI が持つもの。** 台帳の静的な部分を全て持つ。
- 資産の列挙と担当の割り当て。
- 本文の配達と、読んだことの照合（[台帳と見たの記録](#台帳と見たの記録)）。
- `stateDir` への状態の書き込みと照合。
- カバレッジと skip 一覧の計数。
- run の分割（残りの担当と次の引数）。
- 止める条件の判定（[完了と止める条件](#完了と止める条件)）。

CLI は、呼ぶ側のスキルの名前・観点の中身・重大度・指摘の中身を知らない。起動数・期限・同時実行の上限は、呼ぶ側が入力で渡す。呼ぶ側ごとに桁が違うため（差分のレビューと全体の監査では、起動数が 1 桁以上違う）。

**依存の向き。** 「呼ぶ側 → 仕組み」の一方向にする。
- 仕組みは呼ぶ側を参照しない。
- 呼び出しはスキルの呼び出しで行う。パスの直接参照は、同じ plugin の兄弟に限る。
- 別の plugin の呼ぶ側は、依存の宣言で workflow plugin を宣言する。
- 公開した plugin は未公開のスキルに依存できない。prd-spec が使えるのは、公開した後の仕組みだけになる。未公開の repo-review・repo-implement は、公開の前から使える。

**Workflow source の扱い。** 判定は全て CLI に置き、各呼ぶ側の source は、CLI を呼んで結果を運ぶ薄い段だけを持つ。この段の書き方は、規約の 1 か所にだけ置く。core を共有の Workflow source にする案との関係は、[未決](#未決)。
- runner は入れ子の workflow を持たない（[runtime の README](../../plugins/workflow/skills/dynamic-workflow-runner/scripts/runtime/README.md) の未実装の一覧）。
- native の Workflow でも、公開の操作が書き換えるのは callsite の 1 行だけで、source の置き場が変わる。共有の source を呼ぶ形は、両環境では成り立たない。

**既存の設計との関係。**
- skill-design-patterns の資産台帳と状態の書き込みの原則は、設計の正本のまま残す。この仕組みはその実装として位置づけ、原則を書き写さない。
- 探索グラフは取り込まない。探索グラフは、試すものが前の結果で変わる課題の形で、台帳とは層も適用の条件も違う。
- [review-mechanisms-import](review-mechanisms-import.md) の部品のうち、本文の配達・読んだことの照合・状態の照合・shard の割り当て・run の記録は、repo-review の CLI でなく、この仕組みの CLI に置く（広げる）。同文書はまだ実装されていないので、今なら正本が 2 つにならない。
- repo-review に残すのは、方針の束・pin・裏取り役の定義・観点の計画・指摘の合成と反証。これらは審査に固有。移した後の repo-review に、同じ照合の実装を残さない。

**Codex。** runner で動かす経路は repo-review と同じで、運搬役が CLI を呼び、`stateDir` へ書く。この仕組みに固有の runner の対応は設けない。上限の正本は呼ぶ側の `meta.limits` にし、仕組みはそれを入力で受ける。

**退けた案。**
- repo-review を汎用の基盤にする：repo-review は未公開で、公開した prd-spec が依存できない。審査に固有の語が基盤に混ざり、決定 1 に反する。
- 新しい plugin を作って置く：依存の宣言と、Codex での手動の依存の導入が増える。prd-spec と別の install の単位になる。
- 規約だけを置き、各スキルが CLI を自前で実装する：照合と計数が複製になり、食い違う。決定 4 と、二箇所へ書かない規則に反する。
- スキルごとに配布物へ CLI をコピーする：plugin 間の複製はリポジトリで禁じている。
- 探索グラフと台帳を 1 つの基盤にまとめる：層と適用の条件が違い、基盤が重くなる。

下の層で決めるもの：op の名前と入出力、CLI の core と cli の分け方、1 担当の行数や 1 run の担当数の定数。

## 役と制御の境界

役は [skill-design-patterns](skill-design-patterns.md#構成要素) の構成要素の役を、そのまま全ての作業（レビュー・設計・計画）の共通の形として使う。作業ごとに違うのは、枡の軸と、実行役が返す物の種類だけ。

**決定的な制御（script と CLI）に置くもの。** 結果が入力だけで決まるものを置く。
- 枡の生成（[枡の作り方](#枡の作り方)）。
- 担当の割り当てと起動。同時実行の上限の中で、未着手の枡を実行役へ渡す。役ごとのモデルと effort は、設定の正本を引いて決める。
- 受理の記録。状態を変えるのは、運搬役が呼ぶ CLI だけ。
- 機械的な統合。枡と指摘のキーでの和集合、重複の除去、件数と網羅の数え上げ、「見た」の形式の照合。
- 止める条件の判定。
- 差し戻しの検査。戻し先が層の列挙値であること、今の層より上であること。

**判断の役に置くもの。** 内容を読まないと決まらないものを置く。役の出力は列挙値や形式で受け、制御が形式を確かめる。
- 計画役：観点の追加の提案、次に試す意図、完了の主張、人間の入力が要るという判断。実行せず、状態も書かない。
- 実行役：1 つの枡を受け取り、成果物の候補（指摘・案・計画の項）と、見た範囲の記録を返す。受理を判定しない。他の枡を見ない。
- 回収役：工程が欠けた実行の記録から、確認済みの候補だけを拾う。
- 検証役：生成と別の新しい文脈で、候補の受理と却下、完了の主張の受理と却下を決める。実行役の「見た」を意味で確かめ、欠陥の原因の層を判定する。
- 運搬役：CLI を呼び、出力を逐語で写す。判断しない。
- 人間：目標・承認・価値判断が要るときだけ。

**生成と検証の境界。** 成果物（指摘・案・計画・修正の差分）を作る役と、受理を決める役の間に、1 本の境界を引く。
- 作る役は、自分の成果物に合否を出さない。
- 受理は、静的に決まる部分を CLI が、意味の部分を新しい文脈の検証役が決める。修正の差分も同じ境界を通す。
- 司令塔（main session）は、生成も受理もしない。script の起動、停止の種類の中継、承認の後の機械的な写しだけを行う。
- これを規約の文でなく構造で守る。受理の経路が script にしか無く、司令塔が本文を直して通す経路が無い形にする。司令塔が生成と検証の両方を担って、独立の検証を通らなかった事例がある。hook でも物理的に止めるかは、[利用者に聞くこと](#利用者に聞くこと)。

**作業ごとの当てはめ。**

| 作業 | 枡 | 実行役が返すもの | 書き手 |
|---|---|---|---|
| レビュー | 対象の単位 × 観点 | 指摘の候補 | 無い |
| 設計・要求・仕様 | 節 × 層の観点 | 論点ごとの案 | 1 体が統合する。検証は別の役が枡ごとに見る |
| 計画 | 計画の条件 × 観点 | ケース | 計画の形が文書に合わないときは、上の層へ戻す |

**退けた案。**
- 司令塔が枡の作成・割り当て・統合・止める判断まで行う：上限・再検証・網羅が判断に依存して落ちた。決定 4 に反する。
- 枡を全て静的に決め、計画役を置かない：観点の追加は対象を読まないと決まらない。
- 実行役が自分の「見た」と合否を判定する：生成者は自分の誤りが見えない。
- 書き手を新しい役として足す：書き手は「実行役が成果物を作る」の一例で、役を足すと共通の形が複雑になる。
- 作業ごとに専用の役の構成を持つ：決定 1 に反する。
- CLI に意味の重複の除去や原因の層の判定を任せる：意味の判定は CLI の持ち物でない。
- 担当どうしを合議させて統合する：盲点を共有しやすい。

下の層で決めるもの：状態の欄の名前と遷移、枡 ID の形式、抜き取りの率、上限の値。

## 台帳と見たの記録

**台帳の実体。** 台帳は `stateDir` の追記専用の記録にする。事実は足すだけで、状態は記録から導く。持つ実体は次の 7 つ。

| 実体 | 中身 | 書く経路 |
|---|---|---|
| 資産 | CLI が決定的に ID と内容の指紋を付ける単位。読む本文の写しを版つきで持つ | CLI |
| 観点 | 手続きとしての観点（[観点の定義と持ち主](#観点の定義と持ち主)） | 計画役が出し、CLI の形式の検査を通して取り込む |
| 枡 | 資産 × 観点。重要かどうかの印を持つ | CLI が展開する |
| 担当 | 枡に割り当てた 1 回の読み。ID は枡と何回目かと役から決定的に決まる | script が割り当て、CLI が発行する |
| 「見た」の記録 | 担当・本文の版・実行役の条件（モデル・effort など）・問いごとの答えと引用・該当なしの理由・指摘の候補 | 実行役の報告を CLI が検査して足す |
| 指摘 | 枡と位置を指すキー。状態は足す記録で遷移する | CLI。状態は検証役の判定から |
| 原因の層 | 指摘に結び付く記録 | 検証役の判定から |

CLI は記録から、カバレッジ、枡の状態の内訳、skip 一覧、「前の回に確かめた枡で出た指摘」の件数を導く。最後の値で、前からの見落としを機械で数えられる。

**誰が何を書けるか。**
- 実行役は台帳を書かない。割り当てられた置き場へ報告を 1 つ書き、その置き場だけを返す。
- 計画役と検証役の出力は、閉集合の選択として受け、CLI の検査を通して取り込む。
- 書き込みは全て CLI が行う。script は割り当て・受理・追加の起動・止める判定を持つ。

**「見た」を確かめられる記録にする。** 自己申告の「全部見た」は受け付けない。確かめ方を 3 段に分け、費用の出る確かめは重要な所へ寄せる。

| 段 | 確かめるもの | 費用 | 当てる範囲 |
|---|---|---|---|
| 1 | 配った本文に埋めた読取りの印を、返させて照合する。本文が届いたことの確認で、理解は示さない | ほぼ無い | 全ての枡 |
| 2 | 観点の問いごとの答え（閉集合）と、本文の位置と逐語の引用を返させる。位置が枡の範囲内か、引用が本文に一致するか、本文の版が今の資産と合うかを照らす。「該当なし」「問題なし」は、閉集合の理由と引用が無ければ却下する | ほぼ無い | 全ての枡 |
| 3 | 検証役が、「該当なし」「問題なし」の答えについて、引用がその理由を支えるかを閉じた問いで確かめる | モデルの費用 | 抜き取りと重要な枡 |

カバレッジは段ごとの内訳を付けて出す。「見た」は正しさを示さないので、指摘の正しさは検証役が別に持つ。

**写し間違いを構造で止める。** 状態を運ぶ役が長い不透明な値を写し間違えた事例から、次のようにする。
- 内容を運ばない。実行役が報告を置き場に書き、運搬役は担当の ID だけを渡す。CLI が置き場を読んで検査する。
- 運ぶ値を短い ID に限る。CLI は状態にある ID だけを受け付けるので、写し間違いは拒否に倒れる。書き込みは担当の ID を鍵にして冪等にし、再試行が費用だけで済むようにする。
- 運搬が続けて失敗したら、未完了として開示して止める。迂回して手で埋めない。
- 状態の全体と sum を運搬役に写させるかは、[未決](#未決)。

**台帳の寿命。** 同じ対象への review → 修正 → review の反復の間、台帳を続けるか、1 run で閉じて前の台帳を読み取り専用で渡すかは、[未決](#未決)。

**退けた案。**
- 自己申告の読了：検査が無く、前からの見落としの根になった形。
- 読取りの印だけで読了とする：配達の確認にとどまる。段 1 として残すが、単独では足りない。
- 全ての枡を別の検証役が読み直す：費用がおよそ 2 倍になる。機械の検査で落とせる分を先に落とす。
- 実行役が台帳の欄を直接書く：「欄だけを変えよ」を prompt に頼ると破られる。
- 今の運び方のまま再試行を増やす：長い値を写させる形そのものが原因で、再試行では直らない。
- 「該当なし」の理由を自由記述にする：言い換えで通り、検査できない。
- 既知の欠陥を常に本文に混ぜて「見た」の証拠にする：読む本文を変え、注入した欠陥は見つけやすい偏りがある。較正にだけ使う（[測り方](#測り方)）。
- harness の tool の呼び出しの記録で読了を証明する：runtime によって取れるかが違う。取れる環境では段 1 の補強として足せる。

下の層で決めるもの：報告と記録のスキーマ、読取りの印の形と置き方、引用の長さ、位置の ID の形式、指紋の方式、抜き取りの割合、再試行の回数。

## 枡の作り方

枡（資産 × 観点）は、「資産の列挙」「観点の供給」「枡の生成」の 3 つに分ける。目的は、誰にも割り当てられていない枡を無くし、網羅の分母を決定的に作ること。

**資産の列挙。** script が決定的に行う。対象の種類ごとに、列挙の規則を小さな差し替えの部品として持つ。汎用の層は、規則を呼んで資産 ID の一覧を受け取る形だけを決める。
- 文書は見出しの節、コードや設定は行範囲、要求・仕様は ID、設計の論点は節を単位にする。
- 資産は「1 体が全文を精読できる大きさ」を上限にする。1 体に任せる量を小さくする目的と、長い入力の中ほどを読み落とす問題（Lost in the Middle。レビューでの直接の測定ではない）による。
- 一緒に読まないと判断できない範囲は、単位の資産を置き換えず、束の資産として足す。束は、参照・import・ID の追跡のリンク・節の相互参照などの機械的な関係から作るか、抽出役が閉集合から選ぶ。LLM が自由に範囲を作らない。1 つの単位の資産が、単位の枡と束の枡の両方に入ってよい。
- 束を機械的に作れない対象では、跨ぐ検査を観点の手続き（参照を辿る）で持ち、束を作れなかったことを開示する。

**観点の供給。** 観点は、対象の種類と、リポジトリの正本（REVIEW.md など）から、計画役が run の最初に閉集合として固定する。観点と資産の種類の対応表は計画役が決めて記録し、script が静的な整合（全ての資産がどれかの観点に入る、対応表の観点が存在する）だけを照らす。run の途中で観点を足せるかは、[未決](#未決)。

**枡の生成。** 枡は、資産と、対応表で当たる観点の直積で、script が作る。
- 1 体の担当は、既定で 1 枡にする。同じ観点で小さい資産が続くときだけ、1 体の入力の上限まで同じ観点の枡を束ねて渡してよい。束ねても、記録は枡ごとに残す。
- 観点を資産ごとに選び直さない。選び直すと、挙げた観点の所だけ見つかる偏りが戻る。

**重要な枡。** 重要な枡だけが、条件を変えた 2 回目を受ける（[重ねと統合と反証](#重ねと統合と反証)）。候補の基準は次の 4 つ。
- 資産が変更中か、正本・契約を担うか。
- 他の資産から参照される数が多いか。
- その資産と観点の組で、過去に確定した指摘が出たか。
- 観点が高リスクと宣言されているか。

これらを script だけで算出するか、計画役の判断も入れるかは、[未決](#未決)。初めにどの基準を有効にするかは、[利用者に聞くこと](#利用者に聞くこと)。

**横展開。** 横展開を枡の作り方に含める。汎用の層が持つのは規則だけにする。
- 確定した指摘から型（観点と述語）を作り、同じ種類の全ての資産へ、その型を問い直す枡を足す。足した枡は、元の枡と区別して記録する。
- 分母は、初期の枡と、横展開で足した枡を別に数えて開示する。足した枡で分母が増えても、初期の枡の網羅の数字は崩さない。
- 1 回の run で足せる枡の数に上限を置き、届かない分は未読として開示する。
- 全行の走査と旗の判定・裏取りの機構は、review-mechanisms-import の横展開のモードを、この規則の実装の 1 つとして残す。repo-review がこの規則を使う側になり、汎用の層は repo-review に依存しない。
- 横展開を確定した指摘のたびに自動で足すか、依頼されたときだけにするかは、[利用者に聞くこと](#利用者に聞くこと)。

**退けた案。**
- 資産をファイルの単位だけで切る：ファイルを跨ぐ検査が誰の担当にも入らない。
- 束を LLM が自由に決める：範囲が run ごとに変わり、分母が安定しない。
- 束で単位の資産を置き換える：束に入らない資産が漏れる。
- 資産ごとに観点を選び直す：挙げた観点の所だけ見つかる偏りが戻る。
- 全ての観点を全ての資産に当てる：意味の無い枡に費用を払う。
- 全ての枡を 2 回見る：費用が倍になる。
- 横展開を repo-review のモードだけに置く：他のスキルから使えず、決定 1 に反する。
- 横展開の走査の機構も汎用の層に取り込む：走査の大きさと費用は実測で決まり、既に設計がある。二重に持たない。

下の層で決めるもの：行数の上限、1 体の入力の上限、束の関係の取り出し方、編集の前後で同じ資産と識別できる資産 ID の作り方、重要度の重みと閾値、横展開の上限の値。

## 観点の定義と持ち主

**定義の形。** 観点は確認項目の列挙でなく、次の欄を持つ小さな記録として書く。
- 目的：どの種類の欠陥を見つけるための観点か。理由もここに書く。
- 立場：誰の読み方か（作成者・テストの担当・利用者など）。
- 作るモデル：対象から取り出して作る中間の成果物の形。例は、状態と遷移の表、入力から出力への流れ、決定と前提の対応表、要求と検証方法の対応。各項目に対象の位置と短い引用を付ける。
- 答える問い：モデルを使わないと答えられない問いの列。答えは「指摘」か「該当なしと理由」のどちらか。
- 適用の条件：どの種類の対象・枡に当てるか。
- 成果物の形：モデル、問いごとの答え、範囲外の気づき。

**持ち主。** 3 者に分け、ある対象に当てる観点は 3 つの和集合にする。呼ぶ側の観点だけを使うことは許さない。呼ぶ側の観点だけでは、呼ぶ側の死角を共有するため。
- 汎用の仕組み：定義のスキーマと検査、対象の種類に依らない少数の標準の観点。標準の 1 つは、観点を絞らない通読にする。固定した観点の外の欠陥を落とす副作用を、構造でも和らげるため。
- 呼ぶ側のスキル：領域に固有の観点の中身。例は、repo-review の REVIEW.md の観点、prd-spec の要求と仕様の責務。仕組みはこれを写さない。
- 計画役：対象を読んで、足りない観点を理由つきで提案する。

**手続きに従ったかの確かめ。** 慣れると普段のやり方に戻るので、成果物で確かめる。
- CLI が決定的に確かめる：モデルの欄が埋まっているか、各項目の位置が枡の範囲内か、引用がその位置に実在するか、全ての問いに答えがあるか。欠けていれば枡を未完に戻す。
- 判断が要るもの（モデルが対象と合っているか、該当なしの理由が妥当か）は、新しい文脈の検証役が、CLI が決めた標本で確かめる。全ての枡にはかけない。

**範囲外の気づき。** 成果物の別の欄で受ける。この欄は、網羅にも指摘の件数にも数えない。CLI が集めて計画役へ渡し、計画役が、新しい枡や観点の候補にするか、理由つきで却下するかを決める。採った候補は、通常の枡と同じ検証を通る。

**改廃。** 観点ごとに安定した ID を付け、指摘への寄与と、注入した欠陥での再現率を観点ごとに測って見直す（[測り方](#測り方)）。改廃を自動で行うか、利用者の承認を挟むかは、[利用者に聞くこと](#利用者に聞くこと)。

**退けた案。**
- 確認項目の列挙として書く：通読と有意な差が無い（Hatton、Porter）。モデルを作らせないので、読んだかの検査もできない。
- 汎用の仕組みが全ての観点を持ち、呼ぶ側は選ぶだけにする：領域に固有の観点を写すと、写しが食い違う。決定 1 にも反する。
- 呼ぶ側だけが観点を持つ：呼ぶ側の死角を共有し、形の検査も呼ぶ側ごとに作り直しになる。
- 計画役が対象ごとに自由に作る：毎回の観点が変わり、観点ごとの再現率を測れない。提案の経路としてだけ残す。
- 全ての枡で検証役が推論の過程まで読む：費用が枡の数に比例する。
- 範囲外の気づきをそのまま指摘として受ける：検証を通っておらず、網羅の数え方を汚す。

下の層で決めるもの：欄の型、引用の一致の厳しさ（空白の扱いなど）、標本の割合。

## 重ねと統合と反証

見落としの原因のうち、検出が確率的であること、盲点が相関すること、誤検出の 3 つへの対策。

**重ねる枡。** 重要な枡と、script が機械的に足す枡（「見た」の記録が形式を満たさない枡、1 回目で指摘が出た枡）を重ねる。最初の発見で探索をやめる傾向があるため、指摘が出た枡も重ねる。重ねる回数は 2 回までにし、全ての枡を 2 回見ることはしない。予算は人数でなく条件の多様性に配る（Biffl）。

**変える条件。**
- 2 回目は、観点・モデル・新しい文脈のうち少なくとも 1 つの条件を変える。重要度の高い枡は、観点とモデルの 2 つを変える。
- 「別のモデル」に数えるのは、別の系統（Codex runner の経由など）か、同じ系統の上位のモデルまで。軽いモデルは同じモデルの繰り返しと変わらないという知見がある（Song、抄録）。
- 同じ設定の繰り返しは、重ねに数えない。

**独立の保ち方。**
- 実行役の入力は、自分の枡の資産と観点の手続きだけにする。他の実行役の結果、前の回の指摘、台帳の他の指摘は渡さない。
- 出力は実行役ごとの置き場に書き、実行役どうしの連絡と合議は置かない。
- 「既知の指摘を除いた残りを探す」役は、独立の重ねと別に扱う。最初の発見で止まる傾向の補強として使ってよいが、独立の票には数えない。
- 実行役ごとに出力を分けられない環境では、その枡の重ねを独立と数えない。

**統合。** 2 段にする。
- 1 段目は script が決定的に行う。実行役は生の情報（資産、位置、閉集合の種別、主張の文）だけを返し、同じ枡・同じ種別・位置の重なりで同じものとまとめる。agent に同一性を判定させない（資産台帳の原則）。
- 2 段目は、1 段目でまとまらなかった近い組だけを、統合の役が「同じか別か」の二択で判定する。まとめるだけで、指摘を足したり消したりしない。
- まとめた後も、元の全ての出どころ（どの実行役・どの条件か）を残す。重大度は最も重いものを採る。
- 票は、異なる条件の組の数で数え、優先度の参考にとどめる。1 票だけを理由に落とさない。少数の票にも当たりがある（SWR-Bench）。

**反証。** 統合の後、まとまりごとに 1 回置く。反証の役は生成と別の文脈にする。
- 結果は、確認・反証・検証不能の 3 つ。
- 反証にするには、対象の本文から反する箇所を引用させ、script が引用の実在を照らす。実在しない引用では反証にできず、検証不能に倒す。
- 落とす側だけを厳しくする。重大度の高いまとまりの反証は、別の反証の役がもう 1 回確かめる。
- 却下した指摘も、理由と引用つきで台帳に残す。反証の前と後の数を両方開示する。
- 検出の側は再現率寄り、反証の側は精度寄りに、設定を分けて組で運用する。検証役を強くすると正しい指摘も落とすため（CriticGPT）。

**規模の桁（暫定。実測で見直す）。** 枡が 30〜40 なら、重ねるのは 4 分の 1 から 3 分の 1 程度で、追加の実行役は 10 体前後。反証は、まとまりの数（数十）に 1 体ずつ。レビューの全体で数十体の規模になる。

**退けた案。**
- 同じ設定を n 回繰り返して和集合を取る：盲点を共有し、頭打ちが早い（Kim、Song）。条件を変えられない枡でだけ、最小の代替として許す。
- 実行役どうしに討論・合議させる：会議での損失と、更新の送りすぎで性能が下がる。
- 全ての枡を 2 回以上見る：費用が倍になり、効果は逓減する（Porter、Biffl）。
- 前の回の指摘を見せて残りを探させることを、重ねの本体にする：独立性を失う。
- 埋め込みの類似度や LLM だけで同一性を判定する：決定的でなく、検査できない。
- 多数決で採否を決める：盲点を共有した誤りを通し、少数の当たりを落とす。
- 反証で却下したものを根拠なしで捨てる：再現率を下げすぎ、検証役の誤りが記録に残らない。
- 反証を検出の役の中に置く：生成と検証の分離に反する。
- 捕獲再捕獲で残りを推定し、重ねる数や止める条件に使う：前提を破り、過小に推定する。

下の層で決めるもの：重ねる枡の割合、統合のキーと位置の粒度、種別の語彙、2 人目の反証を置く重大度の線。

## 再レビューと持ち越し

成果物を作り直した後の再レビューで、何を持ち越し、何を無効にするか。前の作業では、再レビューが「直した所だけ」と「全体」の間で回ごとにぶれ、前に何を見たかも引き継がれなかった。

**全体を覆う根拠を、毎回の作り直しに置く。** 再レビューのたびに、現在の成果物から枡を CLI が決定的に作り直す。全体を同じ検査で覆う根拠は、前の結果の持ち越しでなく、この作り直しに置く。これで「直した所だけ読む」を構造で不可能にする。持ち越しは、費用を減らすためだけに使う。

**持ち越せる条件。** 枡ごとに、次の 3 つが全て前と同じときだけ、CLI が持ち越す。
- 枡の対象の内容の指紋。
- 枡が依存する枡の指紋（ID の参照・リンクなど、CLI が取り出せる関係）。
- 観点と検査の手続きの版。

1 つでも違えば無効にして、新しく見る。全体の整合を見る枡は、成果物のどこかが変われば常に無効にする。依存の関係を取り出せない種類の成果物では、「全体に依存する」として扱い、常に無効にする。

**持ち越すものと持ち越さないもの。**
- 持ち越すもの：「見た」の結び付き、指摘の状態、独立に見た回数。
- 持ち越さないもの：前の reviewer の推論・文章・「問題なし」の理由。新しく見る reviewer には、前の中身を見せない。
- 持ち越した枡は「持ち越し」と印を付け、新しく見た枡と分けて数える。持ち越した「問題なし」は再現率の低い 1 回の読みに過ぎない。

**指摘の出どころの分類。** CLI が、指紋の照合だけで次の 3 つに分ける。
- 前からの見落とし：内容が変わっていない枡で、前は「見た・指摘なし」だったもの。
- 直しによる誤り：内容が変わった枡で出たもの。
- 依存を通じた波及：自分は変わらず、依存先が変わって無効になった枡で出たもの。

判断でなく照合で決まるので、収束の評価をこの 3 つの周ごとの推移で見られる。

**指摘の状態。** 前の指摘の ID と照らして決める。内容が変わった枡で、前の指摘が新しい独立の読みでも出なければ、検証役が確かめて解消とする。解消した指摘が同じ ID で再び出れば、再発とする。却下は、枡の指紋が変わらない間だけ有効にする。

**run の中の再レビュー。** run の中で書き換えて見直す構成でも、run をまたぐ場合と同じ判定（指紋・依存・手続きの版）を使う。

**壊れたときの扱い。** 前の記録が壊れている、成果物の基準の版と食い違う、手続きの版が違うときは、持ち越さずに全て無効にして最初から見る。損は費用だけで済む。持ち越した枡の数と理由は、結果に開示する。

**台帳の寿命との関係。** この持ち越しを、1 run で閉じた台帳を読み取り専用の入力として次の run に渡す形で行うか、台帳を反復の間続けて書き足す形で行うかは、[未決](#未決)。どちらでも、上の持ち越しの条件と分類は変わらない。

**退けた案。**
- 持ち越さず、毎回全体を最初から見る：網羅では最も安全だが、変わっていない枡に毎回費用を払う。直しによる誤りと前からの見落としの区別も出せない。
- 直した箇所とその直接の影響だけを読み直す：前の作業で実際に取ったやり方で、前からの見落としが見つからなかった。範囲を決める判断も LLM に残る。
- 同じ reviewer に再レビューを続けさせる：新しい文脈で検証する規約と逆で、前の盲点を引き継ぐ。
- 影響の範囲を LLM に判断させる：決定 4 に反し、影響の見落としがそのまま見ない枡になる。指紋の照合なら、見落としても無効にする側に倒れる。
- 持ち越した「問題なし」を新しい読みと同じ重みで数える：1 回の読みの再現率は低く、見落としが固定される。

下の層で決めるもの：指紋の方式、依存の関係の取り出し方、再読の割合が高すぎるときに持ち越しを打ち切る閾値、持ち越した読みの数え方。

## 完了と止める条件

どの停止も、台帳の状態だけから script が決定的に判定し、判定の結果と開示を必ず返す。

**完了を 2 つに分ける。**
- 網羅の完了：全ての枡が「見た記録あり」か「見られなかった理由つきで開示済み」のどちらかで、未処理の枡が 0。script が台帳から数える。
- 受理：呼ぶ側のスキルの合格基準。網羅の完了を前提に、範囲内の必須の欠陥が残っていないことなどを足す。仕組みが返すのは網羅の完了と開示までで、受理の中身は呼ぶ側が決める。受理が呼ぶ側ごとに違い、仕組みが握ると決定 1 に反するため。

網羅の完了に、各枡を独立に複数回見ることまで含めるかは、[未決](#未決)。

**飽和は完了の条件にしない。** 足した周の新しい発見の増分は、網羅の完了の後に重要な枡を重ねる追加の周を、続けるか打ち切るかの判断にだけ使う。
- 増分は、根本原因でまとめた新しい指摘の数と、新しく埋まった枡の数で数える。
- 増分が乾いた周が続いたら追加の周を打ち切り、停止の種類を「乾き」として、完了と別に返す。
- 乾きは、その観点とモデルの組では新しい発見が出ないという局所の事実で、残りが無い証拠ではない。

**安全網。** 周の上限と、予算の上限（起動数・token の量）の 2 系統を置く。
- 上限は網羅の完了より前に当たりうる。そのときは完了にせず、見ていない枡を全て開示して止める。上限で止まったことを、完了と取り違えない形にする。
- 上限で止まれた事例では、停止の理由と未達が開示されたので、止まった後に利用者が方針を決められた。

**人間への差し戻し。** script が判定できない価値判断が要る場合に限る。例は、範囲や基準を広げないと進めない場合、欠陥の原因が上の層にあり層を跨ぐ判断が要る場合。待たれる入力は、run の境界で止める既存の規則に従う。

**判定の優先順。** 続けられない失敗、人間への差し戻し、網羅の完了、上限、乾きの順にする。同時に成り立つときは先の種類で止める。網羅の完了と上限が同じ周で成り立ったら、網羅の完了として止め、上限に当たったことも開示する。

**止まったときに開示するもの。**
- 停止の種類と理由（どの上限か、どの条件が成り立ったか）。
- 枡ごとの状態の集計と、見られなかった枡の一覧。
- 1 回だけ見た枡と、条件を変えて 2 回以上見た枡の区別。
- 周ごとの増分の推移。
- 残った指摘を、根本原因と原因の層つきで。
- 再開の入口。

再現率や残りの欠陥の数の推定は、完了の根拠として返さない。

**既存の設計との関係。** [skill-design-patterns](skill-design-patterns.md#停止再開と人間の入力) の停止の種類（完了・乾き・needs_input・反復の上限・BLOCKED）と再開の規則は、そのまま使う。足すのは、完了を網羅の完了と受理に分けることと、乾きを完了の条件にしない位置づけだけ。

**退けた案。**
- 「新しい指摘が 0 件」（または K 周続けて 0 件）を完了にする：検出が確率的で、0 件は見落としが無い証拠にならない。計画の段が収束しなかった原因そのもの。
- 乾きを網羅と組み合わせて完了にする：同じモデルは盲点を共有し、乾きは残りが無い証拠でない。完了と呼ぶと、開示された残りが読まれなくなる。
- 網羅の完了だけで止め、追加の周を持たない：重要な枡を条件を変えて重ねる道が無くなる。
- 捕獲再捕獲の推定で止める：前提を破り、過小に推定する。参考値の表示にとどめる。
- 回数の上限だけで止める：何も保証せず、止まった理由も区別できない。
- 担当の LLM が「十分か」を判断する：決定 4 に反する。
- 仕組みが受理まで判定する：受理は呼ぶ側ごとに違う。

下の層で決めるもの：乾きの周の数、増分の閾値、上限の値、「新しい」の判定の細部、開示の形。

## モデルと費用

**値の正本。** 役ごとのモデルと effort の組の値は、1 か所にだけ置く。この文書は値の表を新しく書かない。役の性質と初期値の方針は、[best-practices §3](../../plugins/skill-creator/skills/skill-creator-best-practices/references/best-practices.md) と [skill-design-patterns](skill-design-patterns.md#モデルeffortprompt) の既存の表を参照する。この仕組みが足す役（枡を読む役、重要な枡を別の条件で読み直す役、統合を書く役、台帳の空きを見る役）は、既存の役の性質へ対応づけ、同じ対応の役は同じ組を共有する。表の形（役だけで引くか、役と重要度で引くか）と、正本を置く場所は、[未決](#未決)。

**初期値の決め方。** 判断の重さ、誤ったときの波及、1 回に読む量、独立性の要否の 4 点で決める。方向は次のとおり（値は実測で見直す）。
- 計画役・統合の書き手：最上位のモデル。
- 枡を読む実行役：中位のモデルと中程度の effort。
- 重要な枡の 2 回目：1 回目と別のモデルか別の系統で、同等以上の水準。
- 検証役（反証）：実行役と同等以上で、生成と別の文脈。
- 運搬役・回収役：小さいモデルと低い effort。

**Haiku の使い道。** 判断が薄く、結果を CLI や検証役が後で確かめられる役に使う。運搬、閉集合からの選択、形式の照合、重複の候補の提示が候補になる。小さいモデルで絞り込むときは、外した分から無作為に抜き取って上のモデルで精読し、偽陰性を測る。どの役に最初から置くか、測ってから置くかは、[未決](#未決)。

**見直し。**
- 起動した agent のモデルと token を、役ごとに run の結果へ記録する。
- 見直す契機は、モデルの世代が変わったとき、注入した欠陥での再現率が役・モデルごとに下限を割ったとき、確定した指摘 1 件あたりの費用が上のモデルに寄せたほうが低くなったとき。
- 上げ下げはこの指標で決める。最も高い effort は、質の向上を測れた役にだけ使う。
- Codex runner で起動したモデルが記録に残らない環境では、指定が効いたかを確かめられない。その場合は、指定が効いていない前提で、体数の側で費用を抑える。

**Codex。** 同じ論理名を、runner の `modelMap` で Codex 側のモデルと effort の組に解決する。両者の品質が同等かは推測せず、実測で確かめる。別の系統の 2 回目は、盲点の相関を減らす手段として使う。

**費用の見積もり。** script が起動の前に静的に見積もる。
- 起動数は、論点の数、書き手の数、枡の数と 2 回目が要る枡の割合、反証の段の数、空きを見る役の数から出す。枡の数は、資産の数と観点の数から静的に決まる。
- 規模の桁は、1 回の適用で担当 50〜70 体、500 万〜1,000 万 token を暫定の基準にする。実測の前の値で、確定ではない。
- 予算（最大の起動数と token の上限）は入力にし、見積もりが超えたら、run を始める前に止めて利用者に聞く。
- 最初の適用は、1 回のループで様子を見る。

**絞る順。** 網羅を保つ手段を先に、網羅を削る手段を後にする。
1. 網羅を保つ手段：2 回目を重要な枡と危険の旗が立った枡に絞る、共有の prompt を先頭にそろえてキャッシュを効かせる、本文の配達で冷読みの重複を減らす、同時実行を抑える。
2. 網羅を削る手段：枡の数や観点の数を削る。削った範囲は必ず開示し、「見ていない」を「問題なし」にしない。自動では削らず、利用者に聞く。

**退けた案。**
- この文書に値の表を書く：正本が 2 つになり、世代が変わるたびに食い違う。
- 全ての役を最上位のモデルにそろえる：機械的な照合まで最上位にする意味が無く、週の上限に当たる。
- 枡を読む実行役を Haiku にする：枡の読みは判断で、見落としが増える。
- 2 回目も同じモデルで観点だけを変える：盲点を共有しやすい。費用が低い枡に限って併用する。
- 走らせてから使用量を見て止める：前に週の上限に達した規模で、事後では遅い。
- 費用が超えたら枡や観点を自動で削る：「見ていない」が「問題なし」に見える。

下の層で決めるもの：具体のモデル名、effort の値、予算の上限の値、見直しの閾値。

## 測り方

測定は 3 つに分ける。どれも台帳の記録だけを読む。依存は測定から仕組みへの一方向にし、仕組みは測定を知らない。

| 測定 | 答える問い | 費用 | いつ |
|---|---|---|---|
| run の指標 | この run はどう進んだか | 追加なし | 毎回 |
| 較正 | 観点・モデル・effort の組は、どれだけ見つけ、どれだけ誤るか | 大きい（暫定で本番の 2 倍程度） | 観点・モデル・effort・prompt の指紋が変わったとき、利用者が求めたとき |
| 前の作業との比較 | 新しい方式は前より良いか | 小さい | 初回 |

1 つに寄せると、費用か妥当性のどちらかが崩れる。

**run の指標。** script とスキーマで決定的に集計し、LLM に集計させない。
- 周の数（reviewer を起動する 1 巡を 1 周とそろえる）。
- 指摘の内訳。前からの見落とし、直しによる誤り、新規に分ける（[再レビューと持ち越し](#再レビューと持ち越し)）。主な指標は、2 周目以降の前からの見落としと、直しによる誤りの数。網羅の仕組みが効けば前者が初回に出て周が減り、局所の直しをやめれば後者が減る、という仮説を直接確かめられる。
- 枡の網羅（見た枡、開示した残り、見ていない枡）。
- token と起動数（確定した指摘 1 件あたり、合格 1 件あたり）。
- 観点ごと・実行役の設定ごとの固有の寄与（他の全ての実行役の和集合に無かった確定の指摘の数）。
- 実行役を足したときの和集合の増分（止める条件と同じ値）。
- 同じ枡を複数の設定で見たときの発見の重なり（重ねが効いたかの確認）。
- 捕獲再捕獲の推定は、実行役が十分に多いときだけ参考値として載せ、完了の判定には使わない。

**較正。** 正解の付いた対象を、本番と同じ経路で走らせて採点する。本番と違うのは、入力に正解の集合を付けることと、採点の段があることだけ。
- 正解の集合は 2 種類持つ。主は自然の欠陥で、このリポジトリで後から見つかり反証を通った指摘を、その時点の版に戻した対象。補助は注入の欠陥で、注入する役を検出側と別の系統のモデルにし、複数の種類と箇所に散らす。注入の欠陥は本物と分布が違い、LLM が注入したものは LLM に見つけやすいため、主にしない。
- 観点の間とモデルの間の相対の比較にだけ使い、絶対値は上限寄りの目安と明記する。改廃を決める集合と、確かめる集合を分ける。
- 再現率と誤指摘の率を両方測り、欠陥の無い対照の枡も入れる。同じ組を複数回走らせ、ばらつきの区間が重なる差では改廃しない。
- 採点の照合は位置と種類で機械的に行い、曖昧なものだけ別のモデルの判定役に回す。判定役の誤りは採点の誤差として開示する。

**前の作業との比較。** relate の設計レビュー 4 回、取り込みの設計レビュー 2 回、計画の段の 6 回を、run の指標と同じ定義で事後に分類し直して比べる。
- 前の作業には台帳が無いので、周の数・指摘の内訳・token は比べられるが、枡の網羅は比べられない。比べられないことを開示する。
- 事例が少ないので、方向の目安にとどめ、合否の基準にしない。
- 同じ文書の前の版に新しい方式を走らせ直し、前の確定した指摘を正解にする比較は、条件がそろうので最も強い。行うかは、[利用者に聞くこと](#利用者に聞くこと)。

**結果の使い方。** 測定の結果は、観点の改廃・モデルと effort の割り当て・枡の切り方の変更の提案として台帳に出す。自動では切り替えず、人が承認する。少数の組と偏った正解で値を動かすと過適合するため。欠陥は原因の層へ戻す（観点が効かない → 観点の定義、モデルが落とす → 割り当て、枡の切り方 → 詳細設計）。測っていない初期値は「暫定・未測定」と開示する。

**初回の範囲。** 1 回のループで様子を見る方針に合わせ、run の指標と前の作業との比較から始める。較正を最小の規模で 1 回加えるかは、[利用者に聞くこと](#利用者に聞くこと)。

**退けた案。**
- 本番の run に常に既知の欠陥を混ぜる：利用者に出す指摘に混ざり、毎回費用が増える。
- 捕獲再捕獲を主な指標や完了の判定にする：前提を破り、過小に推定する。
- 注入の欠陥だけで測る：分布が違い、見つけやすい偏りがある。
- 測らずに初期値のまま固定する：観点の効果は割れており、決定 5 の見直しの根拠が得られない。
- 測定の結果で自動で切り替える：過適合する。
- 較正を毎回や定期の CI で回す：費用が大きい。
- 前の作業との比較だけで判断する：事例が少なく、網羅を比べられない。

下の層で決めるもの：指標の定義の細部、較正の規模と正解の集合の作り方、区間の計算、推定量の選び方。

## 既存のスキルへの組み込み

**渡すもの（宣言）。** 呼ぶ側は薄い宣言を渡す。静的に決まる部分は呼ぶ側の script とスキーマに、判断に属する部分は目的と理由で持つ。
- 資産の列挙の規則（差分の変更ファイル、監査の path、文書の節、計画のケースなど）。
- 観点の中身と、各観点が当たる資産の種類。
- 重大度の名前と定義、裁定済みの論点（再び起票しないもの）。
- 成果物の層の対応。
- 規則の束（repo-review なら方針の束と pin）と、役ごとのモデルと effort の上書き。
- 止める条件の上限（正本は呼ぶ側の `meta.limits`）。
- 検証役の定義を差し替えるときだけ、その定義。

**受け取るもの。**
- 台帳（枡ごとの状態と、見られなかった理由）。
- 根本原因でまとめた指摘の一覧。各指摘に、原因の層と、前からの見落としか直しによるかの印が付く。
- 周ごとの新しい指摘の数と、止まった理由。
- 費用の実測。

仕組みは修正をしない。

**経路の無い作業への経路。** 設計レビューと計画には今スキルの経路が無く、即興のループで回して上限と差し戻しが当たらなかった。経路を与えるのは、仕組みを直接呼ぶ入口にする。
- 入口は、設計文書用と計画用の宣言の雛形を持つ。設計レビューは「節 × 方式設計の観点」の枡、計画は「計画の条件 × 観点」の枡にする。
- [agent-work](../guidelines/agent-work.md) の既存の節（反復の収束と差し戻し）から、「スキルの経路が無い作業はこの入口を使う」と 1 行で指す。新しい司令塔の手順は増やさない。
- 入口の呼び出しそのものが上限・台帳・止める判定を持つので、規約を読んで自分のループに当てる必要が無くなる。
- 入口を仕組みのスキルと別のスキル（仮称 board-review）にするか、同じスキルの入口にするかは、[未決](#未決)。公開名と置き場は、[利用者に聞くこと](#利用者に聞くこと)。

**組み込みの順。**
1. 仕組みと、設計レビュー・計画の入口。経路が無くて発散した実例があり、既存の契約を壊さず、この方式設計自体の評価にも使えるため。
2. repo-review（差分・作業ツリー）。宣言を渡す形に変える。方針の束・pin・裏取り役は repo-review が持ち続ける。
3. repo-review の監査と横展開。review-mechanisms-import の「repo-review の中のモード」という置き場は変えない。モードが使う shard・本文の配達・読んだことの照合・run の状態は、この仕組みの契約に沿って作り、重複して持たない。
4. repo-implement の計画のレビューと実装のレビュー。計画のレビューは plan-reviewer の観点を宣言に写す。実装のレビューは既に repo-review を呼ぶので、2 の結果に乗る。
5. prd-spec。独自の run・保持規則・監査と改稿の輪を持ち、変える費用が最も大きいので最後にする。公開の後の仕組みだけを使える（[置き場と依存の向き](#置き場と依存の向き)）。

**退けた案。**
- 各スキルが自前で台帳・枡・止める判定を持つ：決定 1 に反し、正本が割れる。設計レビューと計画には経路が無いまま残る。
- 仕組みを repo-review の拡張にして、他のスキルが repo-review を呼ぶ：公開した prd-spec が依存できない。repo-review はリポジトリに固有で、汎用の核としては重い。
- 設計レビュー用と計画用に専用のスキルを個別に作る：規約を運ぶ経路がまた分かれる。入口 1 つで足りる。
- 規約の文だけで反復の収束を促す：規約を読んでも自分のループに当てなかった実例がある。
- prd-spec から先に組み込む：契約が実測で固まる前に着手すると、契約を prd-spec に合わせて歪める。

| 同じ plugin の兄弟のスキルの CLI を、公開の前後とも、install 先でも呼べる | workflow plugin を install した環境で、prd-spec から仕組みの CLI を呼ぶ最小の run を通す。Codex でも試す | 呼び出しをスキルの呼び出しだけに限る。それでも解決しなければ、配り方を利用者に諮る |
| Codex runner の運搬役が、`stateDir`（repo の外）へ書き、node の CLI を実行できる | runner の最小の source で、運搬役が CLI を呼び `stateDir` へ書く run を通す。runtime の拒否条件を読む | `stateDir` を runner が許す範囲へ移す。それでも書けなければ、Codex では単発の run に収まる範囲へ絞る |
| 実行役が CLI の割り当てた置き場に報告を書き、運搬役が ID だけを渡せる（native と Codex の両方） | 最小の run で試す | 報告を返り値で返させ、運搬役が逐語で写す形に落とす。写し間違いは引用の照合で拒否に倒れる |
| 問いごとの答えと引用を返させても、引用だけ正しく中身を読んでいない答えは多く出ない | 前からあった欠陥を含む枡に段 2 の形で実行役を当て、欠陥の行を引用して「問題なし」と答えた数を数える | 段 2 を所在の確認としてだけ扱い、検出は重ねと段 3 で担保する |
| 短い ID の写し間違いは稀で、拒否と冪等な再試行で回復できる | 運搬役に ID を故意に壊させるテストで、拒否と再試行での完了を確かめる | 運搬役を通さずに script が CLI を呼べる経路を探す。無ければ未完了として開示して止める |
| 跨ぐ検査の束を、機械的な関係から決定的に作れる | 過去の跨ぐ指摘を何件か選び、束の規則で同じ組が 1 つの束に入るかを試作で数える | 束の規則を種類ごとの部品にとどめ、作れない種類では観点の手続きで持ち、開示する |
| 小さい資産に分けると、中ほどの読み落としが減る | 同じ対象を大きい資産と小さい資産で見て、注入した欠陥での再現率を比べる | 資産の上限を大きい側へ緩める |
| 重要な枡の基準が、実際に見落としの多い枡を捉える（設計の判断で、出典は無い） | 前からあった見落とし 18 件を、基準で事後に採点する | 基準を変える。当たらなければ、2 回目をやめて全体に 1 回だけ別のモデルを当てる |
| 資産 ID を、内容が変わっても同じ資産と識別できる形で決められる | 編集の前後の台帳を照合する試作で確かめる | run をまたぐ識別を求めない |
| モデルを作らせる観点は、観点なしで読むより多く見つける | 注入した欠陥で、観点あり・なしの再現率と費用を比べる | モデルを必須の欄にするのをやめ、立場の多様性だけを与える軽い定義に縮める |
| 引用の実在を、CLI が安く決定的に確かめられる | 文書とコードで、改行や空白を崩した引用の偽陰性の率を数える | 正規化した一致に弱めるか、位置だけの検査にして標本の割合を増やす |
| 別の系統のモデルと観点の変更は、同じモデルの繰り返しより多く別の指摘を出す | 最初のループで、1 回目と 2 回目の指摘の重なりと、2 回目だけが出した確定の指摘の数を記録する | 重ねる条件を観点と文脈だけにし、浮いた費用を観点の追加に回す |
| 1 段目の決定的なキーで、同じ指摘の大半をまとめられる | 1 段目でまとまらず、後で同じと判定された組の割合を数える | 位置の粒度か種別の語彙を見直す |
| 反証の引用の照合と 2 人目で、再現率を下げすぎずに誤検出を減らせる | 反証の前後の再現率を比べ、反証で落としたもののうち後で正しかった割合を記録する | 2 人目を置く線を下げ、反証を既定で検証不能に倒す |
| 依存の関係を、主な成果物（Markdown）から CLI が決定的に取り出せる | 前の設計文書の複数の版に試作を当て、変わった枡・依存で無効になった枡と、実際の指摘との対応を数える | 取り出せない種類では「全体に依存」として常に無効にする |
| 変更があっても、波及が全体に及ぶ割合は低く、持ち越しで費用が減る | 前の版の列に試作を当て、毎回再読する枡の割合を測る | 再読の割合が閾値を超えたら持ち越しを使わない |
| 網羅の完了は、現実の予算の範囲で到達できる | 小さな実対象 1 つで、枡の規模と 1 周の token を測る | 上限で止まるのが常態になるなら、枡の粒度か優先の付け方を見直し、未見の枡の一覧を主な出力にする |
| 根本原因でまとめた新しい指摘の数を、安定して数えられる | 前の周ごとの指摘の記録で、まとめた数の推移が収まるかを後ろ向きに確かめる | 乾きの判定には新しく埋まった枡の数だけを使い、指摘の増分は開示にとどめる |
| 枡を読む実行役は、中位のモデルと中程度の effort で実用の再現率に届く | 最初の適用で、注入した欠陥での役・モデルごとの再現率と、確定の指摘 1 件あたりの token を測る | 上のモデルへ上げ、2 回目の対象を広げる |
| Codex runner で論理名を `modelMap` で解決でき、指定が効く | run の結果に起動したモデルが残るかを確かめる | 効いていない前提で、体数と段数で費用を抑える |
| 1 回の適用が、担当 50〜70 体・500 万〜1,000 万 token の桁に収まる | 最初の run で役ごとの token を記録し、見積もりと比べる | 網羅を保つ手段で絞り、それでも足りなければ範囲を絞って開示する |
| 前の作業の回ごとの指摘と確定の有無を、後から取り出せる | 該当の記録を開き、回ごとの指摘を列挙できるか確かめる | 取り出せない作業は比較から外し、その旨を開示する |
| token と起動数を、run ごと・役ごとに集計できる（native と Codex の両方） | 小さな run で、結果に使用量と agent の数が含まれるか確かめる | 起動数と入出力の文字数で代用し、概算と開示する |
| 前の作業の確定した指摘は、正解として使える程度に正確 | 標本を取り、利用者か別の検証役が実在を確かめる | 正解の集合を利用者が確かめたものだけに絞る |
| 薄い入口と agent-work の 1 行の参照で、経路の無い作業に実際に当たる | 入口の説明に、前の発散した事例の依頼文を当てて発火するかを確かめる | hook か AGENTS.md の必須項目で補う |
| review-mechanisms-import はまだ実装されておらず、置き場を変えても既存の実装を壊さない | repo-review の CLI に本文の配達・照合・shard の実装が無いことを確かめる | 実装済みの部分があれば、移す順序と互換の期間を、置き場の判断に戻して決める |

## 未決

論点どうしで食い違い、この文書では決めていないもの。決め方は、利用者の判断か、上の未確認の前提の実測による。

1. **台帳の寿命。** 案 A は、同じ対象への review → 修正 → review の反復の間、1 つの台帳を続け、指紋が変わった枡だけを開き直す。案 B は、台帳の寿命を 1 run のまま保ち、前の台帳を読み取り専用の入力として次の run に渡す。B は既存の skill-design-patterns と整合し、壊れたときに全てを捨ててやり直せる。A は前の「問題なし」が積み重なる危険がある一方、記録の連続性は高い。持ち越しの条件（[再レビューと持ち越し](#再レビューと持ち越し)）はどちらでも同じ。
2. **重要な枡を誰が決めるか。** 案 A は、script が静的な基準だけで算出する（run ごとに変わらず、費用を見積もれる）。案 B は、計画役が重要度と理由を付け、script が機械的な条件（形式を満たさない枡、指摘が出た枡）を足す。決め方は、基準が前からの見落としをどれだけ捉えるかの事後の採点による。
3. **状態と sum を運ぶ形。** 案 A は、review-mechanisms-import の形を受け継ぎ、運搬役が state と sum を写し、CLI が照合する。案 B は、sum を運搬役に通さず、CLI が自分で記録の先頭を持ち、運搬役は run の識別子と担当の ID だけを渡す。写し間違いが 2 回再現した事例は B を支える。B は CLI が自分の記録を信頼できる置き場（`stateDir` の扱い）に依存する。
4. **Workflow source を共有するか、入口を別のスキルにするか。** 案 A は、判定を全て CLI に置き、Workflow source は呼ぶ側ごとに薄い段を持つ。案 B は、仕組みの核を 1 本の Workflow source にし、runner がそのまま実行する。あわせて、設計レビューと計画の入口を、仕組みのスキル（仮称 coverage-board）と別のスキル（仮称 board-review）にするか、同じスキルにするかも決まっていない。A は、入れ子の workflow が無いことと公開の操作の制約に合わせた形。B を採るなら、両環境で同じ source を呼べる経路を示す必要がある。
5. **層の分類の形。** 案 A は、検証役が層ごとに閉集合の判定（正しく決めている・決めていない・誤り・越境・責務でない）を返し、独立に 2 回行い、script が最も上流を原因の層として導く。案 B は、検証役が層の閉集合（方針・要求・方式設計・詳細設計・実装・不明）から 1 つを選ぶ。A は判定を細かく検査でき、B は費用が小さい。分類の一致率の実測で決める。
6. **差し戻しを誰が実行するか。** 案 A は、汎用の部品が差し戻しの遷移（作り直し・下流の古い印・保留と分類し直し）を持つ。案 B は、仕組みは戻す先を示すだけで、作り直しは呼ぶ側が判断して行う。A は局所修正の経路を構造で塞ぐ範囲が広く、B は仕組みを小さく保つ。
7. **Haiku を置く役。** 案 A は、運搬役・回収役に加え、機械的な観点（リンク・用語・写しの検出）の実行役と、段 3 の抜き取りの確かめにも最初から置く。案 B は、閉集合の選択と逐語の写しだけに限り、枡の読み・判断・反証には使わない。案 C は、測定で上位のモデルと再現率が同等で誤指摘が多くないと出た役にだけ置く。初期値をどれにするかと、較正をいつ行うかが絡む。
8. **モデルの表の形と置き場。** 案 A は、役と重要度の 2 軸の表を 1 か所に置き、初期値の方向も示す。案 B は、役だけで引く `ROLE_MODELS` を Workflow source に置き、この文書には値を書かず、既存の表を参照する。さらに、Workflow source を呼ぶ側ごとに持つ形（未決 4 の案 A）では、`ROLE_MODELS` が呼ぶ側ごとに分かれ、「1 か所」と食い違う。正本を CLI 側か共有の設定に置くかを含めて決める。
9. **run の途中で観点を足すか。** 案 A は、観点を run の最初に固定し、途中で足すのは横展開の型だけにする（観点の偏りを防ぎ、分母を安定させる）。案 B は、計画役が途中でも観点や枡の追加を提案でき、範囲外の気づきからも昇格させ、CLI が形式を検査して足す。B を採るなら、足した枡を初期の分母と別に数える扱いを、横展開と同じにそろえる。
10. **網羅の完了に独立の回数を含めるか。** 案 A は、各枡が 1 回見られたか、見られなかったと開示されたかで網羅の完了とする。案 B は、各枡が k 回独立に見られたことを止める条件にし、持ち越した回数も累積で数える。A は費用が小さく、B は 1 回の再現率の低さを構造で補う。2 回目を重要な枡に絞る方針とも絡む。

## やらないこと

- 担当どうしの合議・討論を置かない。
- 「新しい指摘が 0 件」や乾きを、完了の条件にしない。
- 捕獲再捕獲などの残りの推定を、完了の判定に使わない。
- 指摘の箇所だけを直す経路を持たない。
- 探索グラフをこの仕組みに取り込まない。
- 測定の結果で、観点やモデルを自動で切り替えない。
- 費用が超えたときに、網羅を黙って削らない。
- この文書で、op の入出力・状態の欄・定数・閾値・モデルの値を決めない。
- この文書の確定の前に、既存の文書（skill-design-patterns・review-mechanisms-import・agent-work）を書き換えない。

## 利用者に聞くこと

各項の後ろの括弧は、答えを待っている節。

1. **層の順序と、利用者へ返す範囲。**（[層と差し戻し](#層と差し戻し)）
   - 依頼の並びは「方針・要求・方式設計・詳細設計・実装」だが、このリポジトリの design 文書は要求の前段で、方式設計が要求より前に来る使い方がある。層の順序をデータで持ち、既定は依頼の並びにして、方式設計 → 要求の順に並べ替えた一覧を渡せる形でよいか。実際にはどちらの順にしたいか。
   - 方針が原因の欠陥と、要求が複数の解釈を許す欠陥は、必ず利用者へ返して止める（自動で進めるのは方式設計より下だけ）という線引きでよいか。
   - 分類が食い違ったとき、上流の側を採る（費用より見落としの防止を優先する）既定でよいか。
   - agent-work の「必須欠陥は設計へ戻る」を、この設計の確定の後に層の一覧への参照へ置き換えてよいか。
2. **公開の時期と名前。**（[置き場と依存の向き](#置き場と依存の向き)、[既存のスキルへの組み込み](#既存のスキルへの組み込み)）
   - 仕組みを、develop の plugin ができる前に workflow plugin の一部として先に公開してよいか。公開しない場合、prd-spec への組み込みは公開の後になり、repo-review・repo-implement で先に実証する。
   - 仕組みのスキルと入口のスキルの公開名と置き場（workflow plugin の中か、新しい plugin か）。
3. **review-mechanisms-import との順序。**（[置き場と依存の向き](#置き場と依存の向き)、[既存のスキルへの組み込み](#既存のスキルへの組み込み)）
   - review-mechanisms-import の置き場の節（結論の表と共通する判断）を、実装の前に、この仕組みを使う形へ書き換えてよいか（取り込みの設計が 1 つ前に戻る）。
   - review-mechanisms-import の最初の単位（repo-review への横展開）を、この仕組みの契約が決まる前に進めてよいか。進めるなら重複を一時的に許して後で取り出し、止めるならこの設計の後にそろえる。
4. **司令塔の経路の塞ぎ方。**（[役と制御の境界](#役と制御の境界)）司令塔が成果物の本文を直す経路を、構造（受理の経路が script にしか無い）だけで塞ぐか、hook でも物理的に止めるか。後者は手間と確実さの価値判断がある。
5. **skill-design-patterns の更新。**（[台帳と見たの記録](#台帳と見たの記録)、[再レビューと持ち越し](#再レビューと持ち越し)）
   - 「資産台帳」の「『見た』は検証を通さずに入れる」を、機械の検査を常に、モデルの確かめを抜き取りと重要な枡に限る形へ改めてよいか。費用は主に段 3 で増え、1 回のループの様子見に収まる見込み。
   - 「資産台帳」の「台帳の寿命は 1 run」と、「水準と未決事項」の run をまたぐ追跡の行を、この設計の後で持ち越しの形に書き換えてよいか。
   - 持ち越しの信頼の方針。費用を抑えるなら、変更の無い枡の読みを次の run にも持ち越す。網羅を優先するなら、一定の run ごとか、モデルが変わったときに全ての枡を読み直す。初期値を「持ち越しを使い、モデルや手続きの版が変わったら全て無効」とする案でよいか。
6. **2 回目と重要な枡の既定。**（[枡の作り方](#枡の作り方)、[重ねと統合と反証](#重ねと統合と反証)、[完了と止める条件](#完了と止める条件)、[モデルと費用](#モデルと費用)）
   - 追加の周（重要な枡の 2 回目）を最初の既定で有効にするか、無効にして実測してから足すか。
   - 有効にするなら、重要な枡の基準をどこまで有効にするか。初回は「変更中」と「過去に確定した指摘」の 2 つだけで始めるか。
   - 2 回目の別の系統（Codex runner の経由）を、最初から使ってよいか。Codex 側の費用の扱いを判断してほしい。
7. **横展開の既定。**（[枡の作り方](#枡の作り方)）横展開を確定した指摘のたびに自動で足すか、依頼されたときと監査のときだけにするか。review-mechanisms-import の決定は後者で、それを既定として引き継ぐ案だが、費用の見え方が変わる。
8. **見られなかった枡を残した受理。**（[完了と止める条件](#完了と止める条件)）見られなかった枡が開示つきで残った状態を、呼ぶ側が受理として扱ってよいか。レビューなら指摘と未読の範囲を返して終わりでよいが、設計や計画の合格のように後の作業を許す場合に、未見の枡が残ったまま進めてよいか。既定を 1 つ決めるか、スキルごとに決めるか。
9. **観点の改廃の承認。**（[観点の定義と持ち主](#観点の定義と持ち主)）測定で寄与の無い観点をやめるとき、自動で行うか、利用者の承認を挟むか。標準の観点は仕組みの持ち物なので、呼ぶ側の観点と違い、利用者の判断が要る。
10. **却下の開示の粒度。**（[重ねと統合と反証](#重ねと統合と反証)）反証で落とした重大度の高い指摘を、結果で一覧として見たいか。見たいなら理由と引用を載せ、見なくてよいなら件数の開示にとどめる。
11. **予算。**（[モデルと費用](#モデルと費用)）最初の適用の予算の上限（体数と token）を、どの桁に置くか。暫定は 50〜70 体・500 万〜1,000 万 token。週の上限との兼ね合いを判断してほしい。
12. **測定の範囲。**（[測り方](#測り方)）
    - 初回の測定に、run の指標と前の作業との比較に加えて、最小の規模の較正を 1 回（概算で本番の 2 倍程度）加えるか。較正を省くと費用は増えないが、Haiku とモデルの割り当てを見直す根拠が得られない。
    - 同じ文書の前の版に新しい方式を走らせ直す比較を行うか。条件がそろい最も強いが、ループ 1 回分の費用が増える。
    - 較正の正解に使う前の確定した指摘を、利用者が標本で確かめるか、反証を通ったものをそのまま使うか。
