# 網羅の台帳で見落としを減らす仕組み

LLM の agent の作業（設計・レビュー・計画・実装）で、見落としを構造で減らす仕組みの方式設計。軸は「確率的な部品から、全体として信頼できる結果を出す」こと。1 体にはファイルを単位に、文脈に収まる分の全文を読ませ、全体の判断はその結果から次に調べることを決めて、意図ごとに台帳から必要な分だけを引く役に任せる。台帳をブラックボードにし、どの役も台帳を通してだけ読み書きする。どこを見たかを台帳に残して空きを見える形にし、生成と検証を分け、測り、網羅で止める。

この文書は方式設計の層にある（要求の前段の調査と構成の設計）。決めるのは、目的に効く構成、置き場と境界、依存の向き、判断の理由と退けた案、規模の桁、未確認の前提とその確かめ方まで。op の入出力・エラーの扱い・状態機械の細部・定数・閾値は決めず、「下の層で決める」とする。

利用者が固定した決定（この文書では変えない。以下「決定 N」で引く）：
1. 特定のスキルに依存させない。repo-review・prd-spec・設計レビュー・計画などの複数のスキルから使える汎用の仕組みにする。
2. 考え方は、ブラックボード型の構成と、[skill-design-patterns](skill-design-patterns.md) の探索グラフ・資産台帳に近いものにする。
3. Codex では、既存の workflow runner（`plugins/workflow/skills/dynamic-workflow-runner`）で動かす。
4. 静的に決まるもの（範囲の列挙・枡の生成・照合・形式・上限・止める条件）は script とスキーマに持たせる。判断に任せるものは、目的と理由だけで書く。
5. 役ごとのモデルと effort を、性能と費用のよい組で設定できる設計にする。Haiku にも使い道がある。値は実測で見直す。
6. 局所最適にしない。欠陥は、原因のある層（方針・要求・方式設計・詳細設計・実装）へ戻す。
7. この文書は方式設計の層に置く。
8. 資産 × 観点の枡をやめ、ファイルを単位にする。検査は、ファイルの段と全体の段の 2 段だけにする。主な用途は小さくない範囲（複数のファイル）。
9. 規模による分岐や数値の線引きを置かない。
10. 1 体で足りなくなる規模（境目）を測るための実験はしない。
11. 1 体の文脈に収まらない大きいファイルは、構造の境目（見出し・宣言）で分けて同格の単位にする。
12. 指摘は義務（目標・受け入れ基準）に結ぶ。結べないものは参考として別に開示する。確信度は並べ替えと開示に使う。
13. 主語の名寄せは、型の決まった判定（同じ・別・不明）で行う。担うのは全体の段の判定役で、別の小さいモデルの役を起動しない（理由は [モデルと費用](#モデルと費用) の起動の原則）。
14. 外部のスキルに依存しない。階層の合成・契約・glossary・z3 は入れない。
15. 台帳をブラックボードにする（[台帳と見たの記録](#台帳と見たの記録) の B1〜B6）。全体の段は探索グラフで進める（[全体の段と確認](#全体の段と確認)）。
16. 1 体の文脈に収まる範囲は 1 体に詰め、分けるのは独立と分離のためだけにする。1 体の中の受け渡しも、詰められる分をまとめる（[モデルと費用](#モデルと費用) の起動の原則）。
17. ファイルの段より先に、1 体の全文レビューで対象を読む。その指摘を台帳に足し、今の仕組み（ファイルの段・全体の段の判定・確認と束ね）に載せる。起動が 1 体増えることは受け入れる。1 体の文脈に収まらない対象では収まる分だけを読み、規模で段を分岐させない。全文レビューと重なっても、ファイルの段は省かない（[段の構成](#段の構成) の全文レビュー）。

決定 8 の後では、決定 4 の「枡の生成」を、ファイルの列挙と担当の生成と読む。決定 11 の後では、以下の「ファイル」「単位」は、分けたときは分けた 1 つを指す。決定 17 の後では、決定 8 の「検査は 2 段だけ」を、ファイルの段と全体の段の前に全文レビューを 1 つ足した構成と読む。

## 背景

前の設計レビューと計画の作業では、次のことが起きた。
- 計画の段で、2 回目以降に出た指摘 27 件のうち 18 件は、前からあった見落としだった。9 件は、直しが持ち込んだ誤りだった。reviewer は前の回を知らず、毎回全体を初めて読み、どこを見たかの記録も無かった。
- 合否が「指摘 0 件」だけで決まっていた。網羅も、進み具合も見ていなかった。
- 改稿の依頼が「指摘の箇所だけ直す」になっていた。局所の修正が既定の経路として残り、改稿が発散した。
- 全体設計を経ずに計画へ入っていた。上の層の判断が欠けたまま、下の層で直し続けていた。
- 設計レビューと計画には、スキルの経路が無かった。即興のループで回したため、上限と設計へ戻る流れが当たらなかった。
- 状態を運ぶ役が、長い不透明な値（状態の sum）を写し間違えた。同じ失敗が 2 回再現した。

その後、資産 × 観点の細かい枡に分けて読む実装（coverage-audit）を作って使うと、別の問題が出た。1 体に全体が見えないので無意味な指摘が増え、大きい単位でしか分からない判断（ファイルをまたぐ矛盾・境界・抜け）ができなかった。これを受けた試作の結果は、[試作の結果](#試作の結果) にまとめる。

調査からは、次のことが分かっている。
- LLM のレビューの再現率は、1 回でおよそ 23% にとどまる。複数回の結果を統合すると上がる。同じモデルを 5 回走らせても、5 回とも出た正解の指摘は一部に限られる（SWR-Bench）。「新しい指摘が 0 件」では、見終えた証拠にならない。
- 同じモデルは盲点を共有する。別のモデルと組むほうが、同じモデル 2 回より多く見つかる（Song、抄録）。
- 観点は確認項目の列挙でなく、対象のモデルを作って問いに答える手続き（scenario）にしたときに効く（PBR、Porter）。ただし効果の再現は割れている（Ciolkowski、Regnell）。
- 合議させるより、独立に読ませて機械的に合わせるほうがよい（名目チーム、Halling と Biffl）。予算は人数より条件の多様性に配る（Biffl）。
- 捕獲再捕獲による残りの推定は、少人数では過小になり、LLM は独立性の前提を破る（Briand）。
- 読了を記録すると再現率が上がるかを、直接測った研究は無い。

1 体に入りきらない範囲を LLM で扱う実践は、次の 3 つに集まる。この設計はこれに合わせる。
- 決まった形で map し、その出力を reduce する（LLM×MapReduce）。ファイルの段が map に当たる。
- 全てを比べず、索引やグラフで近いものだけを比べる（aider のリポジトリの地図、Greptile、知識グラフでの矛盾の検出）。全体の段は、主語と目標で引いた近傍だけを判定する。
- 文脈を分け、メモを外に置き、必要なときに引く（Anthropic の context engineering）。台帳を外のメモにし、役は `query` で要る分だけを引く。

## 結論

| 決めること | 判断 |
|---|---|
| 欠陥の戻し方 | 欠陥を「どの層の判断が原因か」で分類し、原因の層を作り直す。指摘の箇所を局所で直す経路を、構造として持たない |
| 置き場 | 特定のスキルの外に、台帳の静的な部分を持つ共有の CLI を置く。workflow plugin のスキルとして置く。呼ぶ側から仕組みへの一方向の依存にする |
| 役 | skill-design-patterns の役（計画役・実行役・回収役・検証役・CLI・script・人間）を、全ての作業に共通の形で使う。新しい役は足さない。運搬役は置かず、役が CLI を直接流し、CLI の照合で受理を決める |
| 段 | 目標の固定と観点の計画 → 観点の検証 → 静的な検査 → 全文レビュー（1 体が目標と対象だけを手に、観点に縛られずに読む）→ ファイルの段（文脈に収まる分の単位を 1 体に詰める）→ 全体の段（探索グラフ。名寄せ・主語の照合・指摘の判定・前提の消化・目標の判定・確認・束ねの意図を、開いた意図が 0 になるまで）の順にする。束ねは全体の段の最後の意図で、横展開と束ねの反証は持たない。規模で段を分岐させない |
| 起動 | 1 体の文脈に収まる範囲は 1 体に詰め、詰めきれない分だけ体数を増やす。分けるのは独立と分離のためだけにする。これと別に、拾える数を上げるために全文レビューの 1 体を足す。小さい対象の検査は 6 体で終わる（単独で呼ばれたときは振り返りの 1 体を足して 7 体。[モデルと費用](#モデルと費用) の起動の原則） |
| 単位 | 資産はファイルにする。1 体の文脈に収まらないファイルだけを構造の境目で分けて同格の単位にする。観点は一覧でファイルの段の全ての担当に渡し、資産 × 観点の枡を作らない |
| 台帳 | ブラックボードにする。資産（単位）・観点・担当・「見た」の記録・事実（保証と前提・指摘・判定）・意図・run の記録を持つ。どの役も入力を `claim` と `query` で台帳から引き、出力を `submit` で台帳に書く。書くのは CLI だけで、返り値と args で内容を運ばない。「見た」は、機械で確かめられる記録にする |
| 観点 | 確認項目でなく、モデルを作って問いに答える手続きとして定義する。形は仕組みが持ち、中身は呼ぶ側が持つ |
| 指摘 | 義務（目標・受け入れ基準）に結び、1 つ以上の path と原因の層を必ず持つ。確信度を持ち、並べ替えと開示に使う。義務に結べないものは参考として別に開示する |
| 全体の判断と確認 | CLI が受理した事実から、次に調べること（意図）を CLI が決定的に作る。全体の段の役は意図を取り、根拠と関係する事実だけを台帳から引いて、指摘を残すか落とすか、ファイルをまたぐ矛盾・境界、前提が満たされているか、目標の支えと抜けを判定する。別のモデルの確認が、足したものと落としたものを確かめ、落とす側を厳しくする。合議させず、同じ範囲を重ねて読まない |
| 完了 | 「全てのファイルを見たか見られなかったと開示し、開いた意図が 0 になり、完了の照合を通ったか」で判定する。指摘の増分は完了に使わない |
| モデル | 値の正本を 1 か所に置き、役の性質で初期値を決め、run の記録で見直す。費用は起動の前に静的に見積もる。判断を出す役と確かめる役は別のモデルにする |
| 測り方 | 毎回の run の指標、正解つきの較正、前の作業との比較の 3 つに分ける。run の指標に指摘の出どころの段を残し、境目を後から見られるようにする。測定の結果は変更の提案として出し、自動では切り替えない |
| 組み込み | 経路の無い設計レビューと計画から始め、repo-review、repo-implement、prd-spec の順に組み込む |

## 試作の結果

枡に分けて読む実装の問題（[背景](#背景)）を受けて、2026-11-20〜21 に、同じ対象で方式を比べた。
- 静的な解析だけでは、文書の 79% を意味の事実で覆えなかった。静的に確実に拾えたのは、参照と ID の欠陥だけだった。
- 見出しのセルから節・ファイル・根へ契約を積み上げる階層の合成は、段をまたぐ欠陥を拾えた。ただし無意味な指摘が残り、費用も大きかった（1 組 約 500 行で約 300 万 token）。
- 同じ組では、Opus medium 1 体が全文を読むレビューのほうが良かった。段をまたぐ欠陥の検出は 30/31（階層の合成は 23〜26/31）、誤検出は同等以下、token は約 1/33 だった。
- セルで切ると文脈が落ち、契約の受け渡しで情報が落ちる、と見ている。
- 1 体で足りなくなる規模（境目）は測っていない。

このため、1 体が読む単位をファイルの全文に広げ、全体を見る段を 1 つ足す（決定 8）。1 体の全文の読みが良かったのは約 500 行の 1 組の結果で、複数のファイルにまたがる大きい範囲で同じかは確かめていない。主な用途は小さくない範囲なので、全体の段は全文も全てのファイルの段の出力も受け取る前提にせず、意図ごとに台帳から要る事実だけを引き、原文は要る箇所だけ開く。

## 層と差し戻し

**層と成果物。** 扱う層は、方針・要求・方式設計・詳細設計・実装の 5 つで、閉集合にする。層の一覧はデータとして、汎用の部品（script とスキーマ）に 1 つだけ置く。各行は次を持つ。
- 層の順序（どちらが上流か）。
- その層が決めること。
- その層が決めてはいけないこと。
- 成果物の種類。
- 判定の問い。

成果物は層ごとにおおむね 1 つにする。

| 層 | 成果物 |
|---|---|
| 方針 | 目的・固定した決定・やらないこと |
| 要求 | 結果としての要求（仕組みを書かない） |
| 方式設計 | 構成・置き場・境界・依存の向き・退けた案 |
| 詳細設計 | op の入出力・エラー・状態・定数・契約 |
| 実装 | コード・テスト・CLI |

各スキルが渡すのは、「自分の成果物がどの層か」の対応だけにする。層の定義を各スキルに写さない。

**分類。** 欠陥の原因の層は、自由記述で決めない。検証役が閉集合から選んだ判定をもとに、script が決定的に出す。
- 原因の層は「最も上流の、この欠陥を正しく決めていない層」とする。上流の判断が誤っていれば、下流は上流の写しなので、下流の直しは効かない。
- 「越境」（下の層で決めるべき細部や仕組みを、上の層に書いた）を、独立した原因の種別として持つ。越境の作り直しは、記述を足すことでなく、下の層へ移すか消すことになる。
- 分類は書き手と別の担当が行う（生成と検証の分離）。
- 分類の判定の形（層ごとに判定を返して script が導くか、検証役が 1 つの層を選ぶか）は、[未決](#未決)。

**戻し方。** 戻し方は「原因の層を作り直す」の 1 つだけにする。
- 指摘の箇所を直す操作は、script の遷移にも、書き手への入力のスキーマにも置かない。
- 欠陥は原因の層ごと、根本原因ごとにまとめ、最も上流の層から作り直す。書き手には、その層の目的・固定した決定・根本原因の記述を渡す。指摘の位置（行・節）は渡さない。
- 上流を作り直したら、下流の成果物を「古い」と台帳に印を付ける。下流で保留した指摘は、上流が安定してから分類し直す。上流の直しで消えるものがあるため。
- 作り直した層は、全体を新しい文脈で同じ検査にかける。下流は、上流の変更に触れる部分だけを導き直す。
- 方針が原因の欠陥と、要求が複数の解釈を許す欠陥は、価値判断なので利用者へ返して止める。
- 同じ層への戻しには上限を置く（値は下の層で決める）。戻した後に同じ根本原因が再発したら、原因の層の判定を見直す対象にする。
- 戻す遷移（作り直し・古い印・保留）を仕組みが実行するか、仕組みは戻す先を示すだけで呼ぶ側が実行するかは、[未決](#未決)。

**退けた案。**
- 規約の散文（必須欠陥は設計へ戻る）のまま、観点に層の分類を足す：「設計」が 1 つの塊で、どこへ戻すかの基準が無い。規約を読んでも自分のループに当てられなかった事例がある。決定 4 にも反する。
- 局所か設計かの 2 値の分類：要求の層・方針の層・越境を区別できない。「局所」の判定が局所修正の言い訳になる。
- 指摘の位置で戻し先を決める：位置は原因でない。同じ原因が毎回別の箇所に出る事例を拾えない。
- 書き手が原因の層を決める：生成と検証の分離に反する。書き手は自分の層の中で直そうとする。
- 層の定義を各スキルが持つ：決定 1 に反し、写しがスキルごとに食い違う。
- 「同じ箇所で 2 回出たら設計へ戻す」という発火の条件：事後の発火で、原因が同じで箇所が違うものを拾えない。既にある規則の再発明でもある。
- 戻した層より下流を全て作り直す：上流の変更に触れない下流にも費用を払う。

## 置き場と依存の向き

**置き場。** 汎用の仕組みは、規約と共有の CLI を持つ新しいスキル（仮称 coverage-board）として、workflow plugin（`plugins/workflow/skills/`）に置く。
- workflow plugin には、prd-spec と runner が既にある。prd-spec は同じ plugin の兄弟のスキルとして使え、新しい依存の宣言が要らない。
- 公開の前は `.agents/skills/` に実体を置き、公開の操作で `plugins/workflow/skills/` へ移す（[リポジトリの運用](../guidelines/repository-operations.md#配置と配布) のとおり）。

**CLI が持つもの。** 台帳の静的な部分を全て持つ。
- 資産の列挙と担当の割り当て。
- 静的な検査（[段の構成](#段の構成)）。
- 本文の配達と、読んだことの照合（[台帳と見たの記録](#台帳と見たの記録)）。
- 役への仕事の受け渡し（`claim`）、読み出し（`query`）、書き込みの受理（`submit`）。
- 事実からの意図の生成（束ねの意図を含む）と、束ねた結果の照合（[全体の段と確認](#全体の段と確認)）。
- ファイルの段の担当（詰め合わせ）の決定的な生成（[段の構成](#段の構成)）。
- `stateDir` への状態の書き込みと照合。
- カバレッジと skip 一覧の計数。
- run の分割（残りの担当と次の引数）。
- 止める条件の判定（[完了と止める条件](#完了と止める条件)）。

CLI は、呼ぶ側のスキルの名前・観点の中身・重大度・指摘の中身を知らない。起動数・期限・同時実行の上限は、呼ぶ側が入力で渡す。呼ぶ側ごとに桁が違うため（差分のレビューと全体の監査では、起動数が 1 桁以上違う）。

**依存の向き。** 「呼ぶ側 → 仕組み」の一方向にする。
- 仕組みは呼ぶ側を参照しない。
- 呼び出しはスキルの呼び出しで行う。パスの直接参照は、同じ plugin の兄弟に限る。
- 別の plugin の呼ぶ側は、依存の宣言で workflow plugin を宣言する。
- 公開した plugin は未公開のスキルに依存できない。prd-spec が使えるのは、公開した後の仕組みだけになる。未公開の repo-review・repo-implement は、公開の前から使える。

**Workflow source の扱い。** 判定と集約は全て CLI に置き、各呼ぶ側の source は、役を起動するだけの薄い段を持つ（B3〜B5）。この段の書き方は、規約の 1 か所にだけ置く。core を共有の Workflow source にする案との関係は、[未決](#未決)。
- runner は入れ子の workflow を持たない（[runtime の README](../../plugins/workflow/skills/dynamic-workflow-runner/scripts/runtime/README.md) の未実装の一覧）。
- native の Workflow でも、公開の操作が書き換えるのは callsite の 1 行だけで、source の置き場が変わる。共有の source を呼ぶ形は、両環境では成り立たない。

**既存の設計との関係。**
- skill-design-patterns の資産台帳と状態の書き込みの原則は、設計の正本のまま残す。この仕組みはその実装として位置づけ、原則を書き写さない。
- 探索グラフは、全体の段の進め方として取り込む。全体の段で調べることは前の結果で変わり、パターンの適用条件がそろうため（理由と、前の版の「取り込まない」から変えた点は [段の構成](#段の構成) の表と [全体の段と確認](#全体の段と確認)）。グラフの事実と意図は台帳の記録として持ち、別の基盤を作らない。
- [review-mechanisms-import](review-mechanisms-import.md) の部品のうち、本文の配達・読んだことの照合・状態の照合・shard の割り当て・run の記録は、repo-review の CLI でなく、この仕組みの CLI に置く（広げる）。同文書はまだ実装されていないので、今なら正本が 2 つにならない。
- repo-review に残すのは、方針の束・pin・裏取り役の定義・観点の計画・指摘の合成と反証、横展開のモード（[既存のスキルへの組み込み](#既存のスキルへの組み込み) の組み込みの順 3）。これらは審査に固有で、repo-review の側の事柄として残る。この仕組みが束ねの反証と横展開を持たないこと（[全体の段と確認](#全体の段と確認) の束ね）とは別の判断。移した後の repo-review に、同じ照合の実装を残さない。

**Codex。** runner で動かす。役が CLI を直接流して `stateDir` へ書く（運搬役は置かない。B1・B2）。この仕組みに固有の runner の対応は設けない。runner の worker が CLI を流せるかは、[未確認の前提](#未確認の前提)。上限の正本は呼ぶ側の `meta.limits` にし、仕組みはそれを入力で受ける。

**退けた案。**
- repo-review を汎用の基盤にする：repo-review は未公開で、公開した prd-spec が依存できない。審査に固有の語が基盤に混ざり、決定 1 に反する。
- 新しい plugin を作って置く：依存の宣言と、Codex での手動の依存の導入が増える。prd-spec と別の install の単位になる。
- 規約だけを置き、各スキルが CLI を自前で実装する：照合と計数が複製になり、食い違う。決定 4 と、二箇所へ書かない規則に反する。
- スキルごとに配布物へ CLI をコピーする：plugin 間の複製はリポジトリで禁じている。
- 探索グラフの汎用の基盤を作り、台帳と 1 つにまとめる：この仕組みが使うのは全体の段の意図の 7 種類（束ねを含む）だけで、計画役が意図を出す形・ヒント・乾きの判定は要らない。汎用の基盤にすると重くなる。

下の層で決めるもの：op の名前と入出力、CLI の core と cli の分け方、1 run の担当数の定数。

## 役と制御の境界

役は [skill-design-patterns](skill-design-patterns.md#構成要素) の構成要素の役を、運搬役を除いて、全ての作業（レビュー・設計・計画）の共通の形として使う。作業ごとに違うのは、対象のファイルと観点と、実行役が台帳に書く物の種類だけ。

**決定的な制御（script と CLI）に置くもの。** 結果が入力だけで決まるものを置く。
- 対象のファイルの列挙と、静的な検査（[段の構成](#段の構成)）。
- 起動と仕事の受け渡し。script は同時実行の上限の中で役を起動し、役は CLI の `claim` で未着手の単位か意図の束を取る。役ごとのモデルと effort は、設定の正本を引いて決める。
- 意図の生成（束ねの意図を含む）と、ファイルの段の担当の詰め合わせ。CLI が台帳の事実と単位の一覧から決定的に行う。script は役の出力を加工しない。
- 受理の記録。状態を変えるのは、役が流す CLI の `submit` だけ。
- 機械的な照合。id の実在、引用と path の実在、件数と網羅の数え上げ、「見た」の形式、全体の段が落とした指摘に理由と引用があるか。
- 止める条件の判定。
- 差し戻しの検査。戻し先が層の列挙値であること、今の層より上であること。

**判断の役に置くもの。** 内容を読まないと決まらないものを置く。役の出力は列挙値や形式で受け、制御が形式を確かめる。
- 計画役：目標の照合と観点の計画を 1 体で行う。照合で目標の穴が見つかれば、人間の入力が要ると判断し、その回の計画は捨てる。全体の段の意図は出さない（意図は CLI が事実から作る）。
- 実行役：全文レビューは、読む範囲の全ての単位の全文を写しで読み、観点に縛られずに指摘と参考を台帳に書く（[段の構成](#段の構成) の全文レビュー）。ファイルの段は、担当に詰めた全ての単位の全文を写しで読み、単位ごとに指摘の候補・その単位が保証することと前提にしていること（主語・確信度・引用つき）・観点ごとの「見た」を台帳に書く。他の役の書き込みを読まず、受理を判定しない。全体の段の判定役は、名寄せの意図では主語の組ごとに同じ・別・不明を閉集合で選ぶ。全体の段は、自分が足す指摘（ファイルをまたぐ矛盾・境界、前提が満たされていないこと、目標の抜け）について実行役になる。
- 回収役：工程が欠けた実行の記録から、確認済みの候補だけを拾う。
- 検証役：生成と別の新しい文脈で、候補の受理と却下を決める。欠陥の原因の層を判定する。観点の検証役、確認の役、ファイルの段の指摘を判定するときの全体の段がこれに当たる。判断を出す役と確かめる役は別のモデルにする（観点の計画と観点の検証、全体の段の判定と確認）。
- 人間：目標・承認・価値判断が要るときだけ。

**運搬役を置かない。** どの役も、CLI を直接流して台帳から読み、台帳に書く（B1・B2）。受理は運搬役の写しでなく、CLI の照合（id の実在・逐語の引用・形）で決まる。運搬役が長い値を写し間違えた事例（[背景](#背景)）を、写す工程そのものを無くして構造で止めるため。skill-design-patterns の「状態の書き込み」の「書き込みの CLI を呼ぶのは運搬役」から外れる点は、[既存の文書との関係](#既存の文書との関係) に置く。

**生成と検証の境界。** 成果物（指摘・案・計画・修正の差分）を作る役と、受理を決める役の間に、1 本の境界を引く。
- 作る役は、自分の成果物に合否を出さない。
- 受理は、静的に決まる部分を CLI が、意味の部分を新しい文脈の検証役が決める。修正の差分も同じ境界を通す。
- 全体の段は、ファイルの段の指摘に対しては検証役、自分が足す指摘に対しては実行役になる。ファイルの段の指摘は自分の単位だけを引用する（またぐ関係は前提として書く。[段の構成](#段の構成)）。作った役と別の役（全体の段）が判定するので、残した指摘は確認に回さない。全文レビューの指摘は除き、全体の段が残したものも全件を確認に回す。全文レビューの指摘は複数の単位を引用でき、全体の段が足す指摘と同じくファイルをまたぐので、またぐ指摘は確認を通す規則に従う。全文レビューと全体の段は同じモデルなので、残す判定だけで確定させると、別のモデルの確認を通らずに確定する経路が増える。全体の段が足した指摘は作った役の判定だけで確定させず、落とした指摘は落とす判定の誤りを拾うため、両方を全体の段と別のモデルの確認が判定する。
- 司令塔（main session）は、生成も受理もしない。script の起動、停止の種類の中継だけを行い、役の出力を運ばない（B3）。
- これを規約の文でなく構造で守る。受理の経路が script にしか無く、司令塔が本文を直して通す経路が無い形にする。司令塔が生成と検証の両方を担って、独立の検証を通らなかった事例がある。hook でも物理的に止めるかは、[利用者に聞くこと](#利用者に聞くこと)。

**作業ごとの当てはめ。** どの作業でも、ファイルの段の単位はファイルにする。

| 作業 | 実行役が台帳に書くもの | 書き手 |
|---|---|---|
| レビュー | 指摘の候補、保証と前提 | 無い |
| 設計・要求・仕様 | 論点ごとの案 | 1 体が統合する。検証は別の役が見る |
| 計画 | ケース | 計画の形が文書に合わないときは、上の層へ戻す |

**全体の段と確認で、静的に決まるもの。** 入力だけで決まるのに役に書かせていたものを、CLI に移す。役の判断は、内容を読まないと決まらない所だけに残す。

| 何を | CLI が決めること | 役に残す判断 | 理由 |
|---|---|---|---|
| 全体の段と確認の担当に付ける観点の一覧 | 付けない | — | 全体の段と確認は意図と事実で判定し、観点の一覧を使わない。付けると、使われない入力が意図の数だけ積もる |
| 指摘の位置の単位（`locations[].unit`） | 引用が 1 つの単位にしか無ければ、CLI が引き当てる | 引用が複数の単位にあるときだけ、役が単位を書く | 引用の照合で、CLI は既に単位を順に照らしている |
| 目標の判定の意図が足す指摘の義務 | 意図の項目（目標・受け入れ基準の 1 つ）で決める | — | 意図が義務を 1 つに決めている |
| 同じ箇所の指摘の組（全文レビューとファイルの段の指摘で、同じ単位の引用が包含し合うもの） | 組を求め、判定・確認・束ねの担当に並べて渡す。まとめず、指摘ごとの出どころを残す | 同じ欠陥か、群の根本原因 | 包含は照合で決まるが、主張が違う組もあり、同じ欠陥かは読まないと決まらない。本物の run では 21 組あり、判定と確認を別々に流していた |

**退けた案。**
- 司令塔が担当の割り当て・統合・止める判断まで行う：上限・再検証・網羅が判断に依存して落ちた。決定 4 に反する。
- 観点を全て静的に決め、計画役を置かない：観点の追加は対象を読まないと決まらない。標準の観点は既に CLI が足しており、計画役に残るのは対象を読んで足す提案だけ。
- 計画役の目標の照合を CLI の引用の照合にする：依頼文の同じ行を複数の項目が引くことがあり、引用だけでは項目と結べない。
- 実行役が自分の「見た」と合否を判定する：生成者は自分の誤りが見えない。
- 書き手を新しい役として足す：書き手は「実行役が成果物を作る」の一例で、役を足すと共通の形が複雑になる。
- 作業ごとに専用の役の構成を持つ：決定 1 に反する。
- CLI に意味の重複の除去や原因の層の判定を任せる：意味の判定は CLI の持ち物でない。原因の層を指摘のあるファイルの種類から付けることもしない。求めるのは原因の層で、ファイルの種類と一致しない（本物の run では、仕様書の指摘で役ごとに層が割れた）。
- 担当どうしを合議させて統合する：盲点を共有しやすい。
- 全体の段の判定をそのまま確定にする：作る役と落とす役を兼ねたまま、独立の検証を通らない。
- 運搬役を置き、CLI の出力を逐語で写させる：写し違いが 2 回再現した（[背景](#背景)）。逐語の指示では止まらず、照合で拒否しても再試行の費用が残る。
- 計画役が全体の段の意図を出す：何を調べるかは事実の種類から決定的に決まり（[全体の段と確認](#全体の段と確認) の意図の表）、判断に任せると意図の漏れが run ごとに変わる。決定 4 にも反する。

下の層で決めるもの：状態の欄の名前と遷移、指摘 ID の形式、抜き取りの率、上限の値。

## 段の構成

| 段 | 担い手（小さい対象での体数） | 入力 | 出力 |
|---|---|---|---|
| 目標の固定と観点の計画 | init と計画役（1 体） | 依頼・決定、対象、呼ぶ側と仕組みの観点 | 目標・受け入れ基準・制約（逐語の引用つき）と、足す観点の提案。照合で目標の穴が見つかれば needs_input にし、その回の計画は捨てる |
| 観点の検証 | 観点の検証役（全ての観点で 1 体。計画役と別のモデル） | `claim` で取った計画の版 | 観点ごとの判定。欠陥があれば計画の段に戻し、次は変わった観点だけを確かめ直す |
| 静的な検査 | CLI | 対象の全ての単位 | 参照と ID の欠陥（範囲で書いた参照は展開する）。事実として台帳に足す |
| 全文レビュー | 全文レビューの役（いつも 1 体） | `claim` で取った読む範囲の単位の写しの全文と、目標。観点は渡さない | 指摘（義務と原因の層に結び、確信度と逐語の引用つき。複数の単位を引用してよい）と参考。読まなかった単位の一覧は CLI が開示する |
| ファイルの段 | 担当（詰め合わせ）ごとに 1 体（小さい対象なら 1 体） | `claim` で取った担当の全ての単位の写しの全文、目標、観点の一覧 | 単位ごとに、指摘（義務に結び、確信度と逐語の引用つき）、参考、その単位が保証すること・前提にしていること（主語・確信度・引用つき）、観点ごとの「見た」 |
| 意図の生成 | CLI | 台帳の事実 | 全体の段の意図（根拠の事実の id つき） |
| 全体の段 | 判定役（1 体） | `claim` で取った意図の束と、`query` で束ごとに 1 回で引いた根拠の事実と関係する事実、目標。原文は要る箇所だけ写しで開く | 意図ごとの事実（名寄せの判定、またぐ矛盾・境界、指摘の残す・落とす、前提の消化、目標の支えと抜け） |
| 確認と束ね | 確認役（1 体。判定役と別のモデル） | `claim` で取った確認の意図の束と、その根拠の事実。確認が全て閉じた後は、束ねの意図と確定した指摘 | 確定・棄却の判定（引用つき）。落としたものを誤りと判じたら復活させる。続けて、確定した指摘の根本原因の群と原因の層 |

表の体数は小さい対象での既定で、全文レビューはどの規模でも 1 体のまま読む範囲が変わるだけ、範囲が 1 体の文脈に収まらなければファイルの段の担当が増え、1 体の時間の上限に当たれば全体の段と確認の残りの意図を次の呼び出しが取る（[モデルと費用](#モデルと費用) の起動の原則）。段を分岐させず、変わるのは担当と呼び出しの数だけ。表は対象の検査の段で、単独で呼ばれたときの振り返り（1 体）は対象の指摘と分けて最後に走る（[全体の段と確認](#全体の段と確認) の完了と出来事）。

全体の段と確認の判定の規則は、[全体の段と確認](#全体の段と確認) に置く。どの段の役も、入力を返り値や args で受けず、出力を返り値で返さない（B1・B2）。

**段の流れ。**

```
目標の固定と観点の計画 → 観点の検証（欠陥があれば計画へ戻す） → 静的な検査
  → 全文レビュー（1 体。claim → submit）
  → ファイルの段（担当ごとに claim → submit） → 意図の生成（CLI）
  → 判定役：[ 名寄せ・主語の照合・指摘の判定・前提の消化・目標の判定 の意図を、束で claim → query → submit ]
  → 確認役：[ 確認の意図の束 → 確認が全て閉じたら CLI が作る束ねの意図 ]
     どちらも開いた意図が 0 になるまで（受理された事実から CLI が意図を足す）
  → 完了の照合 → 結果（status をファイルに書く）
```

**全文レビュー（ファイルの段より先に読む）。** ファイルの段の前に、1 体が対象の全文を観点に縛られずに読む段を置く（決定 17）。ファイルの段は観点ごとに答えと逐語の引用を全て書き、引用を自分の単位に限るので、自由に読む 1 体より拾いにくい、と見ている（[モデルと費用](#モデルと費用) の起動の原則の実測）。全文レビューの指摘を台帳に足し、後の段で同じ判定と確認にかける。
- 置き場：計画の段（と観点の検証）の後、ファイルの段の前にする。指摘を義務に結ぶには固定した目標が要り、目標は計画役が照合して固めるので、計画の段より前には置けない。観点は渡さないので、全文レビューが依るのは目標の版だけにし、観点の検証で計画が直っても、目標が変わらなければ読み直さない。ファイルの段は全文レビューの書き込みを読まないので、この順序はファイルの段の結果を変えない。
- 入力：目標と、読む範囲の単位の写しの全文だけ。観点の一覧・静的な検査の結果・他の役の書き込みは渡さない。
- 指摘：複数の単位を引用してよい。CLI は、引用が読む範囲の単位の本文に逐語であるかを照らす。指摘は義務（目標・受け入れ基準）と原因の層に結び、結べないものは参考として別に返す（ファイルの段と同じ扱い）。保証と前提は書かない。名寄せと意図の索引はファイルの段が作るため。
- 判定と確認：全文レビューの指摘は、ファイルの段の指摘と同じく指摘の判定の意図にかける。全体の段が残したものも落としたものも、重さによらず全件を確認にかける（[全体の段と確認](#全体の段と確認) の意図の表。残したものの理由は [役と制御の境界](#役と制御の境界) の生成と検証の境界）。落としたものも全件にするのは、全文レビューを足す価値が、ファイルの段の拾えなかった少数の指摘にあるため。重くない指摘を抜き取りに回すと、その指摘が確認を通らずに消えうる。数は全文レビュー 1 体の出力に限られ、全ての指摘の数には比例しないので、落とした指摘を全て確認にかける案を退けた理由（費用が指摘の数に比例する）とは両立する。他の指摘の「重い」の線は下の層で決める。
- 重なり：ファイルの段と同じ欠陥を挙げた指摘を、どちらの側も重複として落とさない。重複は欠陥の誤りでなく落とす理由にならず、ファイルの段の側を落とすと、重くないものは抜き取りでしか確かめないので、正しい指摘が落ちる経路になるため。重なりは束ねで同じ根本原因の群に入る。run の記録には指摘ごとの出どころ（全文レビューか、ファイルの段か）を残す。
- 読む範囲：1 体の文脈に収まる対象は全てを読む。収まらない対象は、単位の並び（列挙の順）で前から `UNIT_MAX_BYTES` に収まる所までを読む。ファイルの段の最初の詰め合わせと同じ規則で、新しい線も段の分岐も置かない（決定 9）。読まなかった単位は、全文レビューの読まなかった範囲として `status` に開示し、ファイルの段以降に任せる。
- 網羅に数えない：全文レビューは観点ごとの「見た」を書かないので、カバレッジにも網羅の完了にも数えない。網羅の証拠は、全てのファイルを全ての観点で読むファイルの段が持つ。このため、全文レビューと重なってもファイルの段を省かない。
- 失敗：全文レビューが返らない、または提出が試行の上限に達したときは、出来事として記録し、読まなかったとして開示して後の段へ進む。網羅はファイルの段が持つので、止める理由にならない。

**単位をファイルにする。**
- 資産は対象のファイルで、CLI が決定的に列挙し、path と内容の指紋を付ける。
- 1 体の文脈に収まらないファイルだけを、構造の境目（見出し・宣言）で分け、分けた 1 つずつを同格の単位にする（決定 11）。分けた単位どうしの関係は、他のファイルとの関係と同じく全体の段の意図が受け持つ。見出しや段落まで細かく切らないのは、細かい単位で起きた文脈の欠落を戻さないため。
- 分けても段の構成は分岐しない。変わるのは CLI が列挙する単位の一覧だけで、どの単位にも同じ段が当たる。分ける基準は「1 体の文脈に収まらない」で、調整した数値の線を置かない（決定 9）。収まるかの判じ方は、次の詰め合わせと同じ 1 つ（今の実装の定数 `UNIT_MAX_BYTES`）にし、値は下の層で決める。
- ファイルの段の担当は、文脈に収まる分の単位を詰めた組（詰め合わせ）にする（決定 16）。CLI が単位の並び（列挙の順）で前から、1 体の文脈に収まる上限まで決定的に詰める。上限は大きいファイルを分ける基準と同じで、新しい線でも段の分岐でもない（決定 9・11）。詰め合わせは起動の費用を減らすための並べ方で、関係の近い単位を集める束（退けた束の資産）ではない。単位どうしの関係は、同じ詰め合わせの中でも外でも全体の段の意図が受け持つ。
- 1 体は詰め合わせの全ての単位を全文、全ての観点で読み、「見た」と事実は単位ごとに書く。ファイルの段の指摘・保証・前提が引用してよいのは、その事実を書く単位だけにし、他の単位を引用した `submit` は CLI が拒む。詰め合わせの中で読み手が単位をまたぐ食い違いに気づいたら、気づいた側の単位の前提（相手の単位が満たすべきこと）として書く。前提は全体の段の前提の消化と主語の照合に渡り、またぐ指摘は詰め合わせの組み方によらず全体の段が足して確認を通る（[役と制御の境界](#役と制御の境界) の生成と検証の境界）。持ち越しも単位ごとに判定する。詰め合わせが変わっても（単位の増減や大きさの変化）、読み直すのは指紋の変わった単位だけで、読み直す単位を同じ規則で詰め直す（[再レビューと持ち越し](#再レビューと持ち越し)）。
- 観点は一覧でファイルの段の全ての担当に渡し、観点を当てる単位を選ばない。全文レビューには渡さず、全体の段と確認の担当にも付けない（[役と制御の境界](#役と制御の境界) の静的に決まるもの）。当たらない観点には、ファイルの段が「該当なし」と理由を書く。観点の一覧は、run の最初に [観点の定義と持ち主](#観点の定義と持ち主) の 3 者の和集合として固定する。run の途中で観点を足せるかは、[未決](#未決)。
- ファイルの段の 1 体は、他の役の書き込みを読まない。並列に走る段が書き込みの順序に依存すると、独立が崩れるため。守る独立は他の役の書き込みを読まないことで、複数のファイルを読まないことではない。これを prompt でなく構造で守る。`query` の規則は B1 に置き、ファイルの段の担当の id では `query` が拒否される。

**静的な検査。** CLI が全てのファイルから参照と ID の欠陥を拾う。範囲で書いた参照は展開して 1 件ずつ照らし、ID の形は呼ぶ側が渡す。試作で静的に確実に拾えたのはこの種類だけだった。結果は事実として台帳に足し、ファイルの段の指摘と同じく指摘の判定の意図にかけ、それだけで確定の指摘にはしない。意図した書き方が欠陥に見えることがあり、採るかは意味を読む役が決めるため。

**指摘は義務に結ぶ。** ファイルの段と全体の段の指摘は、どの目標・受け入れ基準に反するかを持つ。結べないものは参考として別の欄で返し、網羅にも指摘の件数にも数えない。義務に結べない指摘が、細かい単位の無意味な指摘の主な出どころだったため。

**保証と前提は、退けた契約の受け渡しと違う。** ファイルの段が書く保証と前提は、主語と引用を持ち、CLI が主語の名寄せと意図の生成に使う索引になる。試作の階層の合成では、下の段の契約だけが上の段に渡り、上の段は原文を見ずに積み上げたので情報が落ちた。ここでは段を 2 つに限って階層にせず、全体の段は保証と前提を、近傍を引く鍵として使い、判定に要る箇所は原文を開く。範囲が小さければ、結果として全てを開いてもよい。

|---|---|---|

| （前の版）探索グラフはこの仕組みに取り込まない | 全体の段を探索グラフで進める | 全体の段で何を調べるかが前の結果で変わり、パターンの適用条件がそろう（[全体の段と確認](#全体の段と確認) の探索グラフを使う理由） |

| （前の版）目標の照合役・計画役 2 体・統合役を別々に起動し、観点の計画は利用者が観点を渡さないときだけ行う | 目標の照合と観点の計画を 1 体の計画役が、いつも行う | 計画役を 2 体にする根拠が無く、照合と計画を別々に起動する理由も無い。呼ぶ側の観点だけを使うことは許さず（[観点の定義と持ち主](#観点の定義と持ち主) の 3 者の和集合）、計画はいつも要る |
| （前の版）観点の検証は観点 1 つに 1 体 | 全ての観点を 1 体が確かめる。担当は計画の版 | 観点ごとに起動する理由が無い。計画役と別のモデルにすることで独立は足りる |

| （前の版）束ねの群ごとに反証 2 体、確定した型ごとに横展開の読み | 束ねは確認役が取る全体の段の最後の意図にし、反証と横展開を持たない | 1 件ずつの指摘は確認で確かめてあり、反証が見るのは束ね方だけになる。同じ型が他にあるかは束ねの結果に既に出る（[全体の段と確認](#全体の段と確認) と [完了と止める条件](#完了と止める条件) の退けた案） |
| 「資産をファイルの単位だけで切る」を退けた（跨ぐ検査が誰の担当にも入らない） | ファイルを単位にし、跨ぐ検査は全体の段が持つ | 跨ぐ検査の受け皿を、束の資産から全体の段へ移した |
| 一緒に読む範囲を、束の資産（関係する資産）として足す | 束の資産を作らない。`--link` で渡す ID の形は、静的な検査に渡す | 束は細かい単位の文脈の欠落を補う仕掛けで、ファイルを単位にし全体の段を置けば要らない |
| 「全ての観点を全ての資産に当てる」を退けた（意味の無い枡に費用を払う） | 観点は一覧でファイルの段の全ての担当に渡す | 枡を作らないので、観点の数が起動数を増やさない。当てる資産を選ぶ判断（当てる資産の一覧と、その精査）も要らなくなる |
| （前の版）検査はファイルの段と全体の段の 2 段だけ（決定 8） | ファイルの段の前に 1 体の全文レビューを置き、指摘を台帳に足して同じ判定と確認にかける（決定 17） | 本物の run で、今の設計の拾えた数が 1 体の全文レビューより少なかった（[モデルと費用](#モデルと費用) の起動の原則の実測）。ファイルの段の窮屈な形が原因とみている |
| 重要な枡を、条件を変えて重ねて読む。統合は決定的なキーと二択の判定で行う | 同じ範囲を重ねて読まない。全体の段がファイルの段の指摘を判定し、別のモデルの確認が落とす側を厳しく確かめる | 重ねは枡の単位に結び付いた仕掛けで、単位と一緒にやめる。複数回の読みで再現率が上がる利点（SWR-Bench）は手放すので、段ごとにモデルを変えて補い、run の記録で見る |

長い入力の中ほどを読み落とす問題（Lost in the Middle。レビューでの直接の測定ではない）への備えは、ファイルを文脈に収まる限り分けないことで弱まるが、ファイルの段で単位を詰め、全体の段で 1 体が意図を順に処理する分だけ 1 体の入力は長くなる。1 体の全文の読みが良かったのは約 500 行の 1 組だけなので、全体の段と確認で補い、run の記録で見る（[未確認の前提](#未確認の前提)）。

| 全体の段の役が開く原文（今は対象の本体） | 写し（`snap/`）を開く。`query` が返す事実に、写しの file と範囲を載せる |
| `reframe` と `--phase` | 残す |
| 指摘の形と `status`、coverage-build の取り込み | 指摘に複数の path・確信度・原因の層（`layer`。必須）を持たせ、参考を別に出す。`status` をファイルで渡し、coverage-build の取り込みも合わせる（[既存のスキルへの組み込み](#既存のスキルへの組み込み)） |
| 目標の照合役と観点の計画（計画役 2 体・統合役・観点の検証 Q1〜Q3・目標と制約の受け皿の照合） | 目標の照合と観点の計画を 1 体の計画役にまとめ、いつも行う（観点は 3 者の和集合のため）。観点の検証 Q1〜Q3 は全ての観点を 1 体で行う。計画役 2 体と統合役はやめ、当てる資産に関わる部分も外す |
| 階層の合成・契約・glossary・z3 | 入れない |
| 全文レビュー（今は無い） | 足す。計画の段の後、ファイルの段の前の段にし、役を 1 体起動する。指摘は出どころを全文レビューとして指摘の判定と確認の意図にかける |

**退けた案。**
- セル（資産 × 観点の枡）を単位にする：無意味な指摘が増え、大きい単位の判断ができなかった（[背景](#背景)）。細かく切ると文脈が落ちる、と見ている。
- 階層の合成（見出しのセルから節・ファイル・根へ契約を積み上げる。契約・z3・glossary を含む）：段をまたぐ欠陥は拾えたが、無意味な指摘が残り、約 500 行で約 300 万 token と費用に見合わなかった。検出も 1 体の全文の読みより少なかった（23〜26/31 と 30/31）。契約の受け渡しで情報が落ちる。
- 静的な解析を主にする：文書の 79% を意味の事実で覆えず、確実に拾えたのは参照と ID の欠陥だけだった。静的な検査は全体の段の入力として残す。決定 4 は決定的な制御（列挙・照合・形式・上限・止める条件）を script に持たせる決定で、検出の主役を静的な解析にする決定ではないので、この案を退けても決定 4 に反しない。
- 規模で構成を分岐する（小さい範囲は 1 体の全文の読み、大きい範囲は 2 段など）：境目を測っておらず、線引きの根拠が無い（決定 9・10）。
- 大きいファイルを読めなかったと開示するだけにする（前の版）：大きいファイルが検査から丸ごと外れる。構造の境目で分けて同格の単位にする。
- 大きいファイルを見出しや段落まで細かく分けて読む：細かい単位で起きた文脈の欠落が戻る。
- 全体の段に全ての原文を読ませる：範囲が大きいと 1 体の文脈を超える。要る箇所だけ開く。
- 全体の段に全てのファイルの段の出力を渡す（前の版）：範囲が大きいと 1 体に入りきらない。意図ごとに要る事実だけを引く。
- ファイルの段だけにして全体の段を置かない：ファイルをまたぐ欠陥と、全体の文脈で落とせる無意味な指摘を扱えない。
- ファイルの段を 1 単位に 1 体にする（前の版）：起動 1 体ごとの前置きが体数分かかり、小さい対象でも単位の数だけ起動する（[モデルと費用](#モデルと費用) の起動の原則）。独立に要るのは他の役の書き込みを読まないことで、読むファイルの数を 1 つに限ることではない。
- 関係の近い単位を集めて詰める：何を近いとするかが判断になり、詰め方が run ごとに変わる（決定 4）。単位どうしの関係は全体の段の意図が受け持つので、詰め方は並びの順で足りる。
- 小さい対象では全文レビューだけで返す：1 体の文脈に収まるかで段を分岐させることになる（決定 9）。
- 全文レビューの指摘を確認にかけない：全文レビューと全体の段は同じモデルで、別のモデルの確認を通らずに確定する経路になる。
- 全文レビューと重なるファイルの段を省く：観点ごとの「見た」が無くなり、網羅の証拠が残らない。
- 全文レビューに観点の一覧を渡す、または計画役に兼ねさせる：観点に縛られた読みになり、ファイルの段と同じ窮屈さに戻る。計画役に兼ねさせると、観点の検証で計画が差し戻されるたびに読みもやり直しになる。
- 小さい対象で、ファイルの段の 1 体に全文レビューを兼ねさせる（同じ本文を読むので、決定 16 では詰められるように見える）：自由な読みの指摘を同じ体が先に持つと、観点ごとの「見た」がその読みに引きずられ、独立に残らない。分けるのは独立のためで、決定 16 の「分けるのは独立と分離のためだけ」の内側にある。
- 全文レビューを計画の段の前に置く：指摘を結ぶ固定した目標がまだ無い。
- 大きい対象で、全文レビューが読む範囲を役に選ばせる：何を読むかが run ごとに変わる（決定 4）。並びの順で前から詰める。

下の層で決めるもの：ファイルの段と全体の段の出力のスキーマ、保証と前提の形、範囲の参照の展開の規則、文脈に収まらないと判じる方法（`UNIT_MAX_BYTES` の値）と分ける境目の規則。

## 台帳と見たの記録

**台帳をブラックボードにする。** 台帳は、全ての役が読み書きする唯一の場所にする。役どうしは台帳の外で内容を受け渡さない。

| 規則 | 中身 |
|---|---|
| B1 読み | どの役も、入力を返り値や args で受けない。`claim` で担当を取り、担当の id を渡して `query` でその担当に関係する、今の根拠として有効な分だけを引く。ファイルの段の担当の id だけは `query` を拒否する（独立のため）。全文レビューの担当の id で引けるのは、目標と読む範囲の単位の一覧だけにする（他の役の書き込みと、前の run の指摘・判定を見せないため。[再レビューと持ち越し](#再レビューと持ち越し)）。原文は写し（`snap/`）を Read で開く。担当は、全文レビューでは読む範囲の単位の組、ファイルの段では単位の詰め合わせ、全体の段と確認では取った意図の束（束ねも意図の 1 つ）、計画の役（計画役・観点の検証役）では計画の版にする。これらの役も `claim` で担当を取り、前の役の出力は台帳から引く。全体の段と確認の `claim` は、その役の種類の開いた意図をまとめて返し、1 回で返す量は、その束で `query` が返す量（根拠の事実・関係する事実・索引の合計）で測り、`UNIT_MAX_BYTES` までにする。1 件だけで超える意図は、単独の束にする（ファイルの段の詰め合わせと同じ next-fit で、新しい線を置かない）。`query` は束の全ての意図を 1 回で引く。`claim` と `query` は分けたままにする。`query` が返す事実には、原文を開くための写しの file と範囲を載せる |
| B2 書き | どの役も、出力を返り値で返さない。CLI の `submit` で台帳に書く。CLI は lock で直列にし、id の実在・逐語の引用・形を照らして、通らなければ理由を返して拒む（今の review の worker と同じ形）。全体の段と確認では束の結果をまとめて受け、意図ごとに受理か拒否を返す。拒否された意図だけを、同じ役が直して出し直す |
| B3 返り値 | Workflow の返り値は、起動の記録（`agents`）と `tokens` だけにする（script の中でしか取れないため）。`ingest` は呼び出しを閉じるだけにする |
| B4 args | args は `{state, callId, stage, workers}` だけにする。台帳の写しを運ばないので、`argsSum` は要らない |
| B5 集約 | 観点の選び直し、束ねの意図の作成と束ねた結果の照合は CLI が台帳の上で行う。script では加工しない |
| B6 不変条件 | skill-design-patterns の「状態の書き込み」の規則に従う。書くのは CLI だけ、id は実在するものだけを受ける、冪等、足すだけで書き換えない、要約は CLI が作って上限と宣言を持つ |

役が CLI を直接流すので、運搬役は置かない（[役と制御の境界](#役と制御の境界)）。B4 で args に `callId` を残すのは、遅れて届いた書き込みと閉じた呼び出しを CLI が見分けるため。

**coverage-build の自分の Workflow にも当てる。** B1〜B6 は coverage-audit だけでなく、coverage-build が自分で起動する役（方式設計・詳細設計・テストを書く役・実装する役・振り返りの計画役・実行役・検証役）にも当てる。
- CLI に `claim`・`query`・`submit` を持たせ、args は `{state, callId, stage, workers}`、返り値は `agents` と `tokens` だけにする。`ingest` は呼び出しを閉じるだけにする。
- 前の役の出力（方式設計 → 詳細設計、振り返りの計画役 → 実行役 → 検証役）は、台帳から `query` で引く。script の中で出力を次の prompt に埋めない。
- 照合と、次に起動する役の判定は CLI が決め、script は判定しない。
- やり直しに新しい agent を起こさない。照合に落ちた提出は `submit` が理由を付けて拒み、同じ役が直して出し直す。試行の上限（今の実装の `MAX_ATTEMPTS`）に達したら、未完了として開示する。
- 起動の原則（[モデルと費用](#モデルと費用)）に従い、詳細設計の役・テストを書く役・実装する役は、それぞれ文脈に収まる分の単位を 1 体に詰める（テストを書く役は fixture を共有できる）。テストを書く役と実装する役は別の体のままにする。振り返りの実行役と検証役も、それぞれ 1 体にする。

**今の実装との差。** coverage-audit は B1〜B5 に沿っているが、全体の段の prompt が写しでなく対象の本体を開かせ、公開する事実に写しの path が無い。全体の段と確認の `claim` と `query` は意図を 1 件ずつ扱い、prompt も 1 件ごとに `submit` させる。coverage-build の自分の Workflow は、まだ内容を返り値と args で運んでいる。
- agent → agent：script の中で、方式設計の出力を詳細設計の prompt に、振り返りの計画役の出力を実行役・検証役の prompt に埋める。
- Workflow → 司令塔 → `ingest`：役の出力を返り値で返し、司令塔が `ingest --result` に運ぶ。
- args：束の参照・id の一覧・`argsSum` を載せる。
- 判定：照合・やり直し・検証役の起動を script が判定し、照合に落ちるたびに新しい agent を起こす。
- coverage-audit → coverage-build：coverage-audit の `status` の出力を司令塔が保存して `import-audit` に渡す（[既存のスキルへの組み込み](#既存のスキルへの組み込み)）。

**台帳の実体。** 台帳は `stateDir` の追記専用の記録にする。事実は足すだけで、状態は記録から導く。持つ実体は次の 8 つ。

| 実体 | 中身 | 書く経路 |
|---|---|---|
| 資産 | 対象の単位。CLI が決定的に path・範囲と内容の指紋を付け、読む本文の写しを版つきで持つ | CLI |
| 観点 | 手続きとしての観点（[観点の定義と持ち主](#観点の定義と持ち主)） | 計画役が `submit` し、CLI が形式を検査して取り込む |
| 担当 | 段ごとの 1 回の仕事（全文レビューの読む範囲、ファイルの段の単位の詰め合わせ、計画の版、または全体の段と確認の意図の束）。ID は対象と何回目かと役から決定的に決まる | CLI が `claim` で渡す |
| 「見た」の記録 | 単位と担当・単位の本文の版・実行役の条件（モデル・effort など）・観点ごとの答えと引用・該当なしの理由 | 実行役の `submit` を CLI が検査して足す |
| 事実 | 探索グラフの点。全文レビューの指摘、ファイルの段の指摘と保証・前提（主語・確信度・引用つき）、静的な検査の結果、名寄せの判定、全体の段の判定、確認の判定。指摘は 1 つ以上の path と位置、結ぶ義務、確信度、原因の層（必須）、出どころを持ち、状態は足す記録で遷移する。参考は別に持つ | 役の `submit` を CLI が検査して足す。静的な検査の結果は CLI |
| 意図 | 次に調べること。種類、根拠の事実の id、開いているか、閉じたか、判定できずに開示して閉じたか（理由つき） | CLI が事実から決定的に作る |
| 出来事 | 拒否、返らなかった役、確認での復活、不明のままの名寄せ | CLI |
| run の記録 | 指摘ごとの出どころ（全文レビューか、ファイルの段か、全体の段のどの種類の意図か）、全文レビューの読まなかった範囲、全体の段で落ちた数、確認で復活した数、名寄せの内訳（同じ・別・不明）、意図の数、範囲の大きさ（単位の数・行数）、段ごとの起動数と token | CLI |

CLI は記録から、カバレッジ、単位の状態の内訳、skip 一覧、開いた意図の一覧、「前の回に確かめた単位で出た指摘」の件数を導く。最後の値で、前からの見落としを機械で数えられる。

**誰が何を書けるか。**
- どの役も台帳を直接書かない。`submit` で出し、CLI が照合して足す（B2）。
- 計画役・観点の検証役・確認役の出力と、全体の段の名寄せの判定は、閉集合の選択として受ける。
- script は起動と、起動の記録・token の返り値だけを持つ。受理・意図の生成・集約・止める判定は CLI が持つ。

**「見た」を確かめられる記録にする。** 自己申告の「全部見た」は受け付けない。確かめ方を 3 段に分ける。

| 段 | 確かめるもの | 費用 | 当てる範囲 |
|---|---|---|---|
| 1 | 観点ごとの答え（閉集合）と逐語の引用を返させる。引用がそのファイルの本文にあるか、本文の版が今の資産と合うか、全ての観点に答えがあるかを照らす。「該当なし」「問題なし」は、閉集合の理由と引用が無ければ却下する | ほぼ無い | 全てのファイル |
| 2 | 全体の段が、ファイルの段の指摘と保証・前提を、意図ごとに要る箇所の原文で確かめる | 全体の段の費用に含む | 全ての指摘（指摘の判定）と、他の単位に関わる保証・前提（主語の照合・前提の消化） |
| 3 | 確認が、全体の段が足した指摘・全文レビューから残した指摘・落とした指摘を、引用で確かめる | モデルの費用 | 足した指摘と全文レビューの指摘（残したものも落としたものも）の全件と、他の落とした指摘（重いものは全件、他は抜き取り） |

機械の照合（段 1）が示すのは、観点ごとに本文のどこかを見たことまでで、ファイルの全体に読みが届いたことは示さない。全体に届くことは、1 体が単位を全文で受け取ることと、段 2・3 の判定で補う。カバレッジは段ごとの内訳を付けて出す。「見た」は正しさを示さないので、指摘の正しさは全体の段と確認が別に持つ。

**写し間違いを構造で止める。** 状態を運ぶ役が長い不透明な値を写し間違えた事例から、次のようにする。
- 内容も状態の写しも sum も運ばない（B1〜B4）。役は CLI から直接読み、CLI へ直接書く。
- 役が CLI に渡す値は、`claim` で受けた担当・意図の ID と、引く事実の ID のような短い ID に限る。CLI は状態にある ID だけを受け付けるので、取り違えは拒否に倒れる。書き込みは担当の ID を鍵にして冪等にし、再試行が費用だけで済むようにする。
- 提出が続けて失敗したら、未完了として開示して止める。迂回して手で埋めない。

**台帳の寿命。** 台帳は、同じ対象への review → 修正 → review の反復の間、run をまたいで続け、指紋が変わった単位を読み直す（[再レビューと持ち越し](#再レビューと持ち越し)）。

**退けた案。**
- 自己申告の読了：検査が無く、前からの見落としの根になった形。
- 読取りの印だけで読了とする：配達の確認にとどまる。
- 全てのファイルを別の検証役が読み直す：費用がおよそ 2 倍になる。確認は、全体の段が足したものと落としたものに絞る。
- 実行役が台帳の欄を直接書く：「欄だけを変えよ」を prompt に頼ると破られる。
- 役の出力を返り値で受け、次の役の prompt に埋め込む（今の plan と group）：埋め込みが写しになり、受理の照合を通らずに次の役へ渡る。
- 全ての役に台帳の全体を読ませる：範囲が大きいと文脈を超え、関係しない事実で想起が落ちる。`query` で要る分だけを引く。
- 今の運び方のまま再試行を増やす：長い値を写させる形そのものが原因で、再試行では直らない。
- 「該当なし」の理由を自由記述にする：言い換えで通り、検査できない。
- 既知の欠陥を常に本文に混ぜて「見た」の証拠にする：読む本文を変え、注入した欠陥は見つけやすい偏りがある。較正にだけ使う（[測り方](#測り方)）。
- harness の tool の呼び出しの記録で読了を証明する：runtime によって取れるかが違う。取れる環境では段 1 の補強として足せる。

下の層で決めるもの：報告と記録のスキーマ、引用の長さと数、引用がファイルの中に散らばることを求めるか、位置の ID の形式、指紋の方式、抜き取りの割合、再試行の回数。

## 観点の定義と持ち主

**定義の形。** 観点は確認項目の列挙でなく、次の欄を持つ小さな記録として書く。観点は一覧でファイルの段の全ての担当に渡すので、当てる対象を選ぶ欄は持たない。
- 目的：どの種類の欠陥を見つけるための観点か。理由もここに書く。
- 立場：誰の読み方か（作成者・テストの担当・利用者など）。
- 作るモデル：対象から取り出して作る中間の成果物の形。例は、状態と遷移の表、入力から出力への流れ、決定と前提の対応表、要求と検証方法の対応。各項目に対象の位置と短い引用を付ける。
- 答える問い：モデルを使わないと答えられない問いの列。答えは「指摘」か「該当なしと理由」のどちらか。
- 成果物の形：モデル、問いごとの答え、範囲外の気づき。

**持ち主。** 3 者に分け、ある対象に当てる観点は 3 つの和集合にする。呼ぶ側の観点だけを使うことは許さない。呼ぶ側の観点だけでは、呼ぶ側の死角を共有するため。
- 汎用の仕組み：定義のスキーマと検査、対象の種類に依らない少数の標準の観点。標準の 1 つは、観点を絞らない通読にする。固定した観点の外の欠陥を落とす副作用を、構造でも和らげるため。
- 呼ぶ側のスキル：領域に固有の観点の中身。例は、repo-review の REVIEW.md の観点、prd-spec の要求と仕様の責務。仕組みはこれを写さない。
- 計画役：対象を読んで、足りない観点を理由つきで提案する。呼ぶ側が観点を渡したときも、和集合を作るためにいつも行う。計画役は目標の照合と同じ 1 体で、照合で目標の穴が見つかれば needs_input にし、その回の計画は捨てる。

**観点の検証。** 和集合の観点は、計画役と別のモデルの観点の検証役 1 体が、計画の版を担当に全て確かめる。欠陥があれば計画の段に戻し、次の回は変わった観点だけを確かめ直す。観点ごとに体を分けないのは、分ける理由が独立でなく、独立は計画役と別のモデルにすることで足りるため（[モデルと費用](#モデルと費用) の起動の原則）。

**手続きに従ったかの確かめ。** 慣れると普段のやり方に戻るので、成果物で確かめる。
- CLI が決定的に確かめる：モデルの欄が埋まっているか、各項目の位置がそのファイルの中か、引用がその位置に実在するか、全ての問いに答えがあるか。欠けていれば、そのファイルの読みを未完に戻す。
- 判断が要るもの（モデルが対象と合っているか、該当なしの理由が妥当か）は、確かめる意図を持たない。全体の段と確認は意図と事実で判定し、観点の手続きを担当に付けないため。確かめていない範囲として扱い、見落としは全文レビューとファイルの段の重なりで補う。

**範囲外の気づき。** 成果物の別の欄で受ける。この欄は、網羅にも指摘の件数にも数えない。計画役が計画の版の担当を `claim` で取り、その id で `query` して引き、観点の候補にするか、理由つきで却下するかを決める。採った候補は、通常の観点と同じ検証を通る。

**改廃。** 観点ごとに安定した ID を付け、指摘への寄与と、注入した欠陥での再現率を観点ごとに測って見直す（[測り方](#測り方)）。改廃を自動で行うか、利用者の承認を挟むかは、[利用者に聞くこと](#利用者に聞くこと)。

**退けた案。**
- 確認項目の列挙として書く：通読と有意な差が無い（Hatton、Porter）。モデルを作らせないので、読んだかの検査もできない。
- 汎用の仕組みが全ての観点を持ち、呼ぶ側は選ぶだけにする：領域に固有の観点を写すと、写しが食い違う。決定 1 にも反する。
- 呼ぶ側だけが観点を持つ：呼ぶ側の死角を共有し、形の検査も呼ぶ側ごとに作り直しになる。
- 計画役が対象ごとに自由に作る：毎回の観点が変わり、観点ごとの再現率を測れない。提案の経路としてだけ残す。
- 全てのファイルで検証役が推論の過程まで読む：費用がファイルと観点の数に比例する。
- 範囲外の気づきをそのまま指摘として受ける：検証を通っておらず、網羅の数え方を汚す。

下の層で決めるもの：欄の型、引用の一致の厳しさ（空白の扱いなど）。

## 全体の段と確認

大きい単位でしか分からない欠陥、細かい単位の無意味な指摘、誤検出の 3 つへの対策。全体の段は、[skill-design-patterns](skill-design-patterns.md#探索グラフ) の探索グラフで進める。

**探索グラフを使う理由。** 全体の段で何を調べるかは、前の結果で変わる。ファイルの段の新しい指摘、名寄せで統合された主語、見つかった目標の抜けが、次に判定する組を作る。パターンの適用条件は 4 つともそろう。
- 出発点が分かっている：ファイルの段と静的な検査の事実、固定した目標。
- 完了を判定できる：目標を固定してあり、開いた意図の数と完了の照合で決まる。
- 試すものの集合が前の結果で変わる：上のとおり。
- 分岐を並列に試す価値がある：意図どうしは独立に判定でき、範囲が大きいほど 1 体に載せられない。ただし既定は判定役 1 体が順に処理し（起動の原則）、並べるのは `--workers` で上書きしたときだけにする。1 体の時間の上限に当たった残りは、次の呼び出しが取る。

前の版は、探索グラフを台帳と層も適用の条件も違う形として取り込まなかった。全体の段を固定の 1 回とし、名寄せと判定の結果で調べる組が増えることを扱っていなかったので、ここで改める。

**事実（グラフの点）。** CLI が受理したものだけを事実にする。
- 全文レビューの指摘（複数の単位の引用を持てる）
- ファイルの段の指摘と、保証・前提（主語・確信度・引用つき）
- 静的な検査の結果
- 名寄せの判定（同じ・別・不明）
- 全体の段の判定（指摘を残す・落とす、またぐ矛盾・境界、前提の消化、目標の支えと抜け）
- 確認の判定

**意図（次に調べること）。** CLI が事実から決定的に作り、根拠の事実の id を持つ。計画役は意図を出さない。

| 意図 | 作る条件 | 担当 | 受理されると足される事実 |
|---|---|---|---|
| 名寄せ | 名前が近く、同じとも別とも決まっていない主語の組 | 判定役 | 同じ・別・不明（引用つき） |
| 主語の照合 | 2 つ以上の単位にまたがる主語（名寄せの統合の後） | 判定役 | またぐ矛盾・境界の指摘、または問題なし |
| 指摘の判定 | 全文レビューの指摘、ファイルの段の指摘、静的な検査の結果の 1 件ごと | 判定役 | 残す・落とす（理由と引用） |
| 前提の消化 | 他の単位に満たす候補がある前提 | 判定役 | 満たされている（引用）、または満たされていない（指摘） |
| 目標の判定 | 目標・受け入れ基準の項目ごと | 判定役 | 支えの事実の id、または抜けの指摘 |
| 確認 | 全体の段が足した指摘の全件、全文レビューの指摘の全件（全体の段が残したものも落としたものも）と、他の落とした指摘（重いものは全件、他は抜き取り） | 確認役（判定役と別のモデル） | 確定・棄却・復活 |
| 束ね | 判定役の意図と確認の意図が全て閉じたとき（run に 1 つ） | 確認役（確認に続けて） | 確定した指摘の根本原因の群と原因の層 |

**境界の答え。** 対象が責務を対象の外に明示して預けている所と、対象に含めないと明示している所は、目標・要求・仕様がその責務を対象の中で果たすことを求めておらず、預け方が求めと食い違わないときに限り、抜けでなくその境界の答えとして、主語の照合と前提の消化が満たされたと判じる。求めがあって逐語で引けるときは、預け方が求めと食い違う指摘にする。確認役は境界の抜けの指摘への判定を確かめるとき、この明示を本文で探し、明示があって求めが無ければ、足した・残した判定を退け、落とした判定は認める。LLM は正しい対象を要求に満たないと判じがちで、本物の run では、明示して外に預けた責務と対象外と明示した範囲を、判定役が抜けとして足し、確認役も通したため（同じ文をファイルの段と全文レビューの役にも渡す）。

**順序と終わり。**
- 主語の照合の意図は、その主語に関わる名寄せの意図が全て閉じてから開く。統合の前に照合すると、同じ主語の別名どうしの矛盾を見落とすため。試行の上限で開示として閉じた名寄せの意図も、ここでは閉じたものに数える。
- 不明の名寄せは主語を統合しない。ただし CLI は、その組の主語の照合の意図を作り（主語が 1 つの単位にしか無くても作る）、不明の組の相手を関係する事実として一緒に引かせ、照合の役が判定する。不明のまま残った組は出来事として記録する。統合すると誤った統合が矛盾を作り、引かないと見落とすため。
- 試行の上限に達した名寄せの意図は、不明と同じに扱う。主語の照合の意図が作られずに終わることは無い。
- 意図は、全文レビューとファイルの段 → 全体の段 → 確認 → 束ねの向きにだけ作られる。確認の判定と束ねから作られる意図は無く、後ろへ戻る辺は無い。このため、開いた意図は有限の手順で 0 になる。

**割り振り。** 判定役 1 体が `claim` を繰り返して判定役の全ての種類の開いた意図を束で取り、`query` で束の根拠の事実と関係する事実だけを 1 回で引いて判定し、束の結果を 1 回の `submit` で足す（担当の単位は B1）。確認役 1 体も同じように確認の意図を束で取り、確認が全て閉じたら束ねの意図を取る。名寄せが閉じるまで主語の照合と前提の消化の意図は作られないので、束は意図が作られる波ごとに取られる。原文は判定に要る箇所だけ写し（`query` が返す写しの file と範囲）で開く。
- 1 つの意図の入力は、その意図に関係する分だけにする。前の版の設計レビューの HIGH（全体の段に全てのファイルの段の出力を渡すと、範囲が大きいと入りきらない）は、意図ごとに引くことで解く。1 体が束を重ねて処理すると、処理した分が 1 体の文脈に積もる。1 体の時間の上限に当たったら、その呼び出しを閉じ、残りの意図は次の呼び出しの新しい 1 体が取る（詰めきれない分だけ体数を増やす）。積もった文脈で判定が落ちないかは [未確認の前提](#未確認の前提)。近傍だけを比べる実践（[背景](#背景) の索引・グラフ）と、必要なときに引く実践に合わせた形。
- 意図は主語と目標の単位なので、またぐ矛盾が意図の境目で割れない。同じ主語を述べる事実は、どの単位のものでも同じ意図に入る。
- 1 つの意図の関係する事実が、それだけで 1 体の文脈を超えることはありうる（多くの単位にまたがる主語、支えの多い目標）。このときは、CLI の要約の上限と載せなかったものの宣言（B6）で入力を収め、役は宣言を見て id で細部を引き直す。それでも判定できず試行の上限に達した意図は、判定できなかった意図として開示して閉じ、開いた意図に数えない（[完了と止める条件](#完了と止める条件)）。run は他の意図を進める。

**独立。** ファイルの段は他の役の書き込みを読まない（`query` を許さない）。全文レビューの書き込みも読まないので、全文レビューの指摘に引きずられず、観点ごとの「見た」を独立に残す。全文レビューも他の役の書き込みを読まない（`query` で引けるのは目標と読む範囲だけ。B1）。全体の段の判定役と確認役は、全文レビューの指摘を他の事実と同じく、意図の根拠と関係する事実として `query` で引く。全体の段は事実を読むだけで、全文レビューにもファイルの段にも問い返さない。ファイルの段どうしも連絡しない。合議にしないためと、並列の段が順序に依存すると独立が崩れるため。

**完了と出来事。**
- 全体の段は、開いた意図が 0 になり、完了の照合（CLI の数の照合と、目標に照らす確認）を通ったときに終わる。試行の上限に達した意図は、判定できなかった意図として開示して閉じる。予算の上限に達したら、limit で開いた意図を開示して止める（[完了と止める条件](#完了と止める条件)）。
- 拒否・返らなかった役・確認での復活・不明のままの名寄せを出来事として記録し、`status` の `events` で返す。
- 振り返りは、対象の指摘と分ける。coverage-audit が単独で呼ばれたときは、1 体が全ての出来事を読み、結果を `status` の別の欄に出す。振り返りの結果は対象の指摘にせず、判定・確認・束ねの意図も作らない。coverage-build から呼ばれたときは振り返りを作らず、coverage-build の探索グラフが振り返る。混ぜると、仕組みの出来事が対象の欠陥として数えられ、起動も増えるため。

**確認。**
- 全体の段と別のモデルが、全体の段が足した指摘、全文レビューから残した指摘、落とした指摘を、確定か棄却で判定する。判定には引用を付け、CLI が実在を照らす。実在しない引用では棄却にできず、検証不能に倒す。
- 落とす側を厳しくする。全体の段が落とした指摘は、重いものは全件、他は抜き取りで確かめ（全文レビューの指摘は重さによらず全件。[段の構成](#段の構成) の全文レビュー）、誤りと判じたら復活させる。検証役を強くすると正しい指摘も落とすため（CriticGPT）、落とす判定を 2 つの役で確かめる。
- 落とした指摘と棄却した指摘も、理由と引用つきで台帳に残す。落とした数と復活した数を開示する。

**束ね。** 判定役と確認の意図が全て閉じたら、CLI が束ねの意図を 1 つ作り、確認役が確認に続けて同じ呼び出しで取る。確認役は確定した指摘を根本原因でまとめ、群と原因の層を付けて `submit` する。CLI は群の形と、群が持つ指摘の id の実在を照らす。上の層の群は、今まで通り needs_input で利用者が判断する。束ねには反証を置かない（退けた案）。

**条件の多様性。** 同じモデルは盲点を共有する（Song、抄録）。同じ範囲を重ねて読む代わりに、落とす・足す判定を確かめる段のモデルを変える。全体の段と確認は、別のモデルにする。全文レビュー・ファイルの段・全体の段は同じモデルでよい（試作で最も良かった組を使う）。全体の段が足した指摘、全文レビューから残した指摘、落とした指摘は確認が別のモデルで確かめるが、ファイルの段から残した指摘は、作った役と文脈だけが違う同じモデルの判定で確定する。全文レビューの指摘をこの経路に入れないのは、またぐ指摘は確認を通す規則に合わせ、同じモデルだけで確定する経路を増やさないため。残った誤検出が同じ盲点で通る危険はこれで残るので、run の記録の落ちた数と、後で誤りと分かった指摘の出どころで見る。予算は人数でなく条件の多様性に配る（Biffl）。

**退けた案。**
- 重ねた読みの指摘を、決定的なキーと二択の判定で統合し、票で優先度を付ける（前の決定）：同じ範囲を重ねないので票が無い。全体の文脈で残す・落とすを判定するほうが、無意味な指摘を落とせる。
- 同じ設定を n 回繰り返して和集合を取る：盲点を共有し、頭打ちが早い（Kim、Song）。
- 実行役どうしに討論・合議させる：会議での損失と、更新の送りすぎで性能が下がる。
- 確認を全体の段と同じモデルにする：落とす判定の盲点を共有する。
- 落とした指摘を根拠なしで捨てる：再現率を下げすぎ、全体の段の誤りが記録に残らない。
- 全体の段が落とした指摘を、全て確認にかける：費用が指摘の数に比例する。重いものに絞り、他は抜き取りで誤りの率を見る。
- 全文レビューの指摘を、落としたものも他の指摘と同じく重さで絞って確認にかける：全文レビューを足す価値はファイルの段の拾えなかった少数の指摘にあり、重くないものが確認を通らずに消えうる。全文レビューの指摘は 1 体の出力に限られ、全件にしても費用は全ての指摘の数に比例しない。
- 捕獲再捕獲で残りを推定し、止める条件に使う：前提を破り、過小に推定する。
- 全体の段の 1 体に、全てのファイルの段の出力を一度に渡す（前の版）：範囲が大きいと入りきらない。判定役は 1 体でも、意図ごとに要る事実だけを引く。
- 全体の段から新しい指摘を出す役を外し、ファイルの段と全文レビューの指摘の判定だけにする：ファイルをまたぐ矛盾は、主語の照合と前提の消化でしか拾えない。費用の元は意図ごとの往復で、役の数ではなかった（[モデルと費用](#モデルと費用) の起動の原則）。
- 全てのファイルの対を比べる：対の数が単位の数の 2 乗で増え、関係の無い対に費用を払う。主語と目標で近傍だけを比べる。
- 入りきらない意図を、判定を試みる前に「未判定」として別の区分に置く：判定できたかもしれない意図を試さずに外す。判定を試みて試行の上限に達した意図だけを、今の枡の開示と同じ形で開示して閉じる。
- 名寄せを CLI の文字列の一致や包含だけで行う：別名や言い換えを同じ主語と判じられない。包含し合っても別の主語の組も多い（本物の run の `expire` と `expiresAt` は別と判じられた）。名前が近い組を CLI が選び、型の決まった判定を判定役に任せる。
- 名寄せを小さいモデル（Haiku）の別の役にする（前の決定 13）：名寄せのモデルを小さくして減る費用より、別の役を起動する 1 体の前置きの費用の方が大きい。判定役は名寄せの直後に同じ主語の照合を判定するので、同じ体で続けて扱える。
- 全体の段を意図の種類ごとに、同時実行の数だけ並べる（前の版）：1 体が `claim` を繰り返して処理でき、並べた体数の分だけ前置きの費用が増える。
- 束ねの群ごとに反証を 2 体置く（前の版）：1 件ずつの指摘は確認で確かめてあり、反証が見るのは束ね方だけになる。束ね方の誤りは、上の層の群を利用者に返すことと、根本原因の照合（原因の層を作り直した後に同じ根本原因が再発したら原因の層の判定を見直す）で拾う。本物の run では、反証だけで 40 体を起動した。

下の層で決めるもの：抜き取りの率、全件を確かめる「重い」の線、判定の閉集合、落とす理由の語彙、「名前が近い」の判じ方、要約の上限の値。

## 再レビューと持ち越し

成果物を作り直した後の再レビューで、何を持ち越し、何を無効にするか。前の作業では、再レビューが「直した所だけ」と「全体」の間で回ごとにぶれ、前に何を見たかも引き継がれなかった。

**全体を覆う根拠を、毎回の作り直しに置く。** 再レビューのたびに、現在の対象からファイルの一覧を CLI が決定的に作り直す。全体を同じ検査で覆う根拠は、前の結果の持ち越しでなく、この作り直しに置く。これで「直した所だけ読む」を構造で不可能にする。持ち越しは、費用を減らすためだけに使う。

**持ち越せる条件。**
- ファイルの段の読みは単位ごとに、その単位の内容の指紋と、観点と検査の手続きの版が、どちらも前と同じときだけ CLI が持ち越す。同じ担当に詰めた他の単位が変わっても、変わらない単位の読みは持ち越す。ファイルの段は事実を単位ごとに書き、事実はそれを書く単位だけを引用して根拠に持つ。単位どうしの関係は全体の段の意図が受け持ち、全体の段が足した、複数の単位を引用する指摘は、その全てを根拠に持ち、どれかが変われば外れる（次の項）。このため詰め合わせの依存の指紋は要らない。
- 全文レビューの読みは、読む範囲（単位の組）と、その全ての単位の指紋と、目標の版が前と同じときだけ持ち越す。全文レビューは観点を受けないので、観点が変わっただけでは読み直さない（[段の構成](#段の構成) の全文レビュー）。どれかが変われば、新しい 1 体が今の読む範囲を読み直し、前の全文レビューの事実を今の根拠から外す（記録は消さない）。1 体が範囲をまとめて読むので、単位ごとには持ち越せないため。全文レビューの指摘は、引用した全ての単位を根拠に持ち、指摘の判定と確認の意図は全体の段の通常の依存の規則で開き直す。
- 全体の段は、事実の依存で開き直す。単位の指紋が変われば、CLI はその単位の事実を今の根拠から外し（記録は消さず、足す記録で外す）、その単位のファイルの段と、外した事実を根拠に持つ意図を開き直し、開き直した意図の前の判定も今の根拠から外す。ファイルをまたぐ意図（主語の照合・前提の消化）は、関わる全ての単位の事実を根拠に持つので、どちらの単位が変わっても開き直る。
- 無いことを根拠にした判定（目標の抜け、前提が満たされていない）は、根拠の単位を持たないので、どれかの単位の指紋が変われば開き直す。変わった単位が、抜けを埋めているかもしれないため。
- 変わった単位の新しい事実からは、新しい名寄せ・主語の照合の意図が CLI の通常の規則で作られる。変更で生まれた、ほかの単位との関係はここで拾う。
- 台帳は run をまたいで続け、前の結果を同じ台帳の記録として持つ。

**持ち越すものと持ち越さないもの。**
- 持ち越すもの：「見た」の結び付き、指摘の状態、保証と前提、根拠が変わらなかった意図の判定（閉じたまま）。
- 持ち越さないもの：前の reviewer の推論・文章・「問題なし」の理由。新しく見る reviewer には、前の中身を見せない。開き直した意図の役も、その意図の前の判定を `query` で引けない（前の判定は今の根拠から外れているため）。
- 持ち越したファイルは「持ち越し」と印を付け、新しく見たファイルと分けて数える。持ち越した「問題なし」は再現率の低い 1 回の読みに過ぎない。

**指摘の出どころの分類。** CLI が、指紋の照合だけで次の 2 つに分ける。
- 前からの見落とし：内容が変わっていないファイルで、前は「見た・指摘なし」だったもの。ファイルをまたぐ指摘と全文レビューの指摘では、関わるファイルがどれも変わっていないもの。
- 直しによる誤り：内容が変わったファイルで出たもの。ファイルをまたぐ指摘と全文レビューの指摘では、関わるファイルのどれかが変わったもの。

前の設計の 3 つ目の「依存を通じた波及」は、ファイルの段の事実が引用した単位だけを根拠に持つので無くなり、ファイルをまたぐ指摘の側に入る。判断でなく照合で決まるので、収束の評価をこの 2 つの run をまたぐ回ごとの推移で見られる。

**指摘の状態。** 前の指摘の ID と照らして決める。内容が変わったファイルで、前の指摘が新しい独立の読みでも出なければ、検証役が確かめて解消とする。解消した指摘が同じ ID で再び出れば、再発とする。却下は、関わるファイルの指紋が変わらない間だけ有効にする。

**run の中の再レビュー。** run の中で書き換えて見直す構成でも、run をまたぐ場合と同じ判定（指紋・手続きの版）を使う。

**壊れたときの扱い。** 前の記録が壊れている、成果物の基準の版と食い違う、手続きの版が違うときは、持ち越さずに全て無効にして最初から見る。損は費用だけで済む。持ち越したファイルの数と理由は、結果に開示する。

**退けた案。**
- 持ち越さず、毎回全体を最初から見る：網羅では最も安全だが、変わっていないファイルに毎回費用を払う。直しによる誤りと前からの見落としの区別も出せない。
- 直した箇所とその直接の影響だけを読み直す：前の作業で実際に取ったやり方で、前からの見落としが見つからなかった。範囲を決める判断も LLM に残る。
- 同じ reviewer に再レビューを続けさせる：新しい文脈で検証する規約と逆で、前の盲点を引き継ぐ。
- 影響の範囲を LLM に判断させる：決定 4 に反し、影響の見落としがそのまま見ないファイルになる。指紋の照合なら、見落としても無効にする側に倒れる。
- 持ち越した「問題なし」を新しい読みと同じ重みで数える：1 回の読みの再現率は低く、見落としが固定される。
- 全体の段を、変わったファイルの分だけ、依存を辿らずに読み直す：1 つの変更が他のファイルとの関係を変え、ファイルをまたぐ欠陥を見落とす。前の版はこれを避けて、どれかのファイルが変われば全体の段を全て読み直すとした。今の版は、またぐ判定が関わる全ての単位の事実を根拠に持ち、無いことの判定はどの変更でも開き直り、新しい事実からは意図が新しく作られるので、関係の変化を照合で拾える。
- どれかの単位が変われば、全体の段の意図を全て開き直す（前の版）：変更に関わらない判定にも費用を払う。上の依存の規則で足りる。

下の層で決めるもの：指紋の方式、再読の割合が高すぎるときに持ち越しを打ち切る閾値、持ち越した読みの数え方。

## 完了と止める条件

どの停止も、台帳の状態だけから CLI が決定的に判定し、判定の結果と開示を必ず返す。

**完了を 2 つに分ける。**
- 網羅の完了：全てのファイルが「ファイルの段で見た記録あり」か「見られなかった理由つきで開示済み」のどちらかで、全体の段の開いた意図が 0 になり（試行の上限で開示して閉じた意図は開いた意図に数えない）、完了の照合（CLI の数の照合と、目標に照らす確認）を通ったこと。数は CLI が台帳から数える。
- 受理：呼ぶ側のスキルの合格基準。網羅の完了を前提に、範囲内の必須の欠陥が残っていないことなどを足す。仕組みが返すのは網羅の完了と開示までで、受理の中身は呼ぶ側が決める。受理が呼ぶ側ごとに違い、仕組みが握ると決定 1 に反するため。

**飽和は完了の条件にしない。** run の中の周は 1 つで、束ねの結果から周を足さない。
- run をまたぐ回ごとの新しい指摘の数（飽和）は、根本原因でまとめた数で記録して開示するだけで、完了の判定に使わない。
- 新しい指摘が出なくなったことは、その観点とモデルの組では新しい発見が出ないという局所の事実で、残りが無い証拠ではない。

**安全網。** 予算の上限（起動数・token の量）と、試行の上限を置く。run の中の周は 1 つなので、周の上限は持たない。
- 上限は網羅の完了より前に当たりうる。そのときは完了にせず、見ていない単位と開いたままの意図を全て開示して止める。上限で止まったことを、完了と取り違えない形にする。
- 試行の上限：同じ意図の判定が、提出されない・照合に落ちるなどで試行の上限に達したら、CLI はその意図を「判定できなかった意図」として開示して閉じ、開いた意図に数えない。止める段は作らず、run は他の意図を進めて complete まで行く。開示の一覧に意図の id と理由を出す。今の実装で、枡が試行の上限で開示に倒れ、run が complete まで進む扱いと同じ。needs_input で止めないのは、利用者の回答で試行の数を戻しても同じ失敗に戻って抜けられず、止めた結果は呼ぶ側（coverage-build）が取り込めないため。
- 取ったまま出さなかった意図の数え方：その呼び出しで 1 件以上出した役の取り残しは、試行に数えずに手放す。1 件も出さなかった役の取り残しは、試行を 1 つ足す。束で取った後に 1 回時間切れになっただけで、束の全ての意図が判定できなかった意図に近づかないようにするため。1 件も出さなかった役でも、2 件以上の束なら試行に数えずに手放し、その役の種類の次の束の上限を、その束の量の半分にする。束が 1 件まで縮んで、なお 1 件も出さなかったときだけ試行を 1 つ足し、その種類で 1 件以上出た呼び出しの後は上限を `UNIT_MAX_BYTES` に戻す。submit が 1 回だけなので、時間切れはほぼ「1 件も出さない」形で起き、同じ束を繰り返すと束の全てが判定できなかった意図になるため。
- 上限で止まれた事例では、停止の理由と未達が開示されたので、止まった後に利用者が方針を決められた。

**人間への差し戻し。** script が判定できない価値判断が要る場合に限る。例は、範囲や基準を広げないと進めない場合、欠陥の原因が上の層にあり層を跨ぐ判断が要る場合。待たれる入力は、run の境界で止める既存の規則に従う。

**判定の優先順。** 続けられない失敗、人間への差し戻し、網羅の完了、上限の順にする。同時に成り立つときは先の種類で止める。網羅の完了と上限が同時に成り立ったら、網羅の完了として止め、上限に当たったことも開示する。

**止まったときに開示するもの。**
- 停止の種類と理由（どの上限か、どの条件が成り立ったか）。
- 単位ごとの状態の集計と、見られなかった単位の一覧。全文レビューの読まなかった範囲は、網羅と別の一覧で。
- 開いたままの意図の一覧（種類と根拠の事実）と、判定できずに開示して閉じた意図の一覧（id と理由）。
- 全体の段で落とした指摘の数と、確認で復活した数。
- run をまたぐ回ごとの増分の推移。
- 残った指摘を、根本原因と原因の層つきで。参考は別の一覧で。
- 再開の入口。

再現率や残りの欠陥の数の推定は、完了の根拠として返さない。

**既存の設計との関係。** [skill-design-patterns](skill-design-patterns.md#停止再開と人間の入力) の停止の種類（完了・乾き・needs_input・反復の上限・BLOCKED）と再開の規則は、そのまま使う。足すのは、完了を網羅の完了と受理に分けることと、乾きを完了の条件にしない位置づけだけ。全体の段の意図は CLI が事実から決定的に作るので、乾き（新しい事実も意図も出ない）の判定は使わず、開いた意図が 0 で完了の照合に進む。

**退けた案。**
- 「新しい指摘が 0 件」（または K 周続けて 0 件）を完了にする：検出が確率的で、0 件は見落としが無い証拠にならない。計画の段が収束しなかった原因そのもの。
- 乾きを網羅と組み合わせて完了にする：同じモデルは盲点を共有し、乾きは残りが無い証拠でない。完了と呼ぶと、開示された残りが読まれなくなる。
- 横展開の周を持ち、確定した欠陥の型を他のファイルに当てて読み直す（前の版）：ファイルの段が全てのファイルを全ての観点で読み、全体の段がファイルをまたぐ食い違いを照合し、束ねが全てのファイルの指摘をまとめるので、同じ型が他のファイルにあるかは束ねの結果に既に出る。本物の run（約 480 行・4 ファイル）では、型 20 × 他のファイル 3 の 60 体の起動を求め、そこで止めた。repo-review の横展開のモード（[既存のスキルへの組み込み](#既存のスキルへの組み込み) の組み込みの順 3）は、repo-review の側の事柄として残る。
- 捕獲再捕獲の推定で止める：前提を破り、過小に推定する。
- 回数の上限だけで止める：何も保証せず、止まった理由も区別できない。
- 担当の LLM が「十分か」を判断する：決定 4 に反する。
- 仕組みが受理まで判定する：受理は呼ぶ側ごとに違う。

下の層で決めるもの：上限の値、開示の形。

## モデルと費用

**起動の原則。** 何体を起動するかの判断は、ここに 1 か所だけ置く（決定 16）。coverage-audit にも、coverage-build の自分の Workflow にも当てる。
- 1 体の文脈に収まる範囲は 1 体に詰める。ファイル・単位・意図をまたいでよい。収まるかの判じ方は、大きいファイルを分ける基準と同じ 1 つ（今の実装の定数 `UNIT_MAX_BYTES`）で、新しい線を置かない（決定 9・11）。
- 1 体の中のやり取りの回数も費用になる。役は、やり取りのたびに伸びた文脈を読み直すため。受け渡しは詰められる分をまとめる（全体の段と確認の担当は意図の束。B1）。
- 詰めきれない分だけ体数を増やす。ファイルの段は文脈に収まる上限で担当を分け、全体の段と確認は 1 体の時間の上限に当たった残りの意図を次の呼び出しが取る（今の挙動のまま）。
- 分けるのは、独立と分離のためだけにする。
  - 判断を出す役と、それを確かめる役を別のモデルにする（観点の計画と観点の検証、全体の段の判定と確認）。
  - ファイルの段は、他の役の書き込みを読まない。守る独立はこれで、複数のファイルを読まないことではない。
  - coverage-build では、テストを書く役と実装する役を別の体にする（[台帳と見たの記録](#台帳と見たの記録) の「coverage-build の自分の Workflow にも当てる」）。

理由は、起動の数がそのまま費用になるため。1 体を起動するたびに約 8 万 token の前置きがかかる。本物の run（約 480 行・4 ファイル）では、止めるまでに 79 体を起動し、横展開を含めると 139 体を求めた。一方、試作では 1 体の全文のレビューが段をまたぐ欠陥を 30/31 件拾い（[試作の結果](#試作の結果)）、1 体の仕事を増やしても検出は大きく落ちなかった。ただしこれは約 500 行の 1 組の結果で、詰めた 1 体の入力が大きいときも同じかは [未確認の前提](#未確認の前提) に置く。

1 体の中のやり取りをまとめる理由も実測による。全文レビューを足した本物の run（約 480 行）で、判定役は 325 ターンで読み直した入力（cache read）が約 5,270 万 token、確認役は 181 ターンで約 2,650 万だった。2 体で全体の約 92% にあたり、全文レビューの 1 体（11 ターン、約 86 万）の約 90 倍になる。意図 1 件ごとに `claim` → `query` → 写しの Read → Write → `submit` を回し、伸びた文脈を毎回読み直していた。起動の数（9 体）は費用の元ではなかった。

**全文レビューの 1 体は、分けるのでなく足す。** 上の原則の「分ける」理由（独立と分離）と別に、拾える数を上げるために 1 体を足す（決定 17）。実測は次のとおり。
- 約 480 行・4 ファイル、正解 16 件の対象で、全文レビューを持たない設計の本物の run は、拾えた数が 13〜14/16、誤りが 1 件、起動が 6 体、token が約 65 万だった（その設計の既定は、小さい対象で 5 体、振り返りを含めて 6 体）。
- 前の試作の 1 体の全文レビューは、同じ対象で 16/16、誤り 0、約 9 万 token だった。
- 差は、ファイルの段の形が窮屈なことによる、と見ている。観点ごとに答えと逐語の引用を全て書かせ、引用を自分の単位に限るので、自由に読む 1 体より拾いにくい。

1 体の全文レビューだけで返さないのは、規模で段を分岐させないため（決定 9）と、観点ごとの「見た」（網羅の証拠）をファイルの段が残すため。足す体数はどの規模でも 1 体で、大きい対象では読む範囲が文脈に収まる分に限られるだけ（[段の構成](#段の構成) の全文レビュー）。

この原則で、小さい対象の coverage-audit の検査は、計画役・観点の検証役・全文レビュー・ファイルの段・判定役・確認役の 6 体で終わる（[段の構成](#段の構成)）。単独で呼ばれたときは、振り返りの 1 体が足されて 7 体になる（[全体の段と確認](#全体の段と確認) の完了と出来事）。

**値の正本。** 役ごとのモデルと effort の組の値は、1 か所にだけ置く。この文書は値の表を書かない。役の性質と初期値の方針は、[best-practices §3](../../plugins/skill-creator/skills/skill-creator-best-practices/references/best-practices.md) と [skill-design-patterns](skill-design-patterns.md#モデルeffortprompt) の既存の表を参照する。この仕組みの役（計画役・観点の検証役・全文レビュー・ファイルの段・全体の段の判定役・確認役）は、既存の役の性質へ対応づけ、同じ対応の役は同じ組を共有する。表は役だけで引く（重要度の軸は、重ねて読むのをやめたので要らない）。正本を置く場所は、[未決](#未決)。

**初期値の決め方。** 判断の重さ、誤ったときの波及、1 回に読む量、独立性の要否の 4 点で決める。方向は次のとおりで、具体の初期値は値の正本（今の実装では `roles.json`）に置き、run の記録で見直す。
- 上位のモデルの役は、中程度の effort にする。最も高い effort は、質の向上を測れた役にだけ使う（見直しの規則）。coverage-build の上位のモデルの役も同じにする。
- 計画役：上位のモデルと中程度の effort。目標の照合と観点の計画を 1 体で担う。
- 観点の検証役：計画役と別のモデル。判断を出す役と確かめる役を分けるため。
- 全文レビュー：上位のモデルと中程度の effort（試作の 1 体の全文レビューと同じ組）。起動はいつも 1 体。値の正本では、ファイルの段の読む役と別の役として引く（skill-design-patterns の分類ではどちらも実行役で、新しい種類の役ではない）。読む範囲・観点を受けないこと・引用の規則・`query` で引けるものが違い、prompt と照合が別になるため。値を読む役と同じにするかは値の正本で決める。
- ファイルの段：上位のモデルと中程度の effort。試作では、この組（Opus と中程度の effort）の 1 体の全文の読みが最も良かった。
- 全体の段の判定役：ファイルの段と同じ組。名寄せも担う（決定 13）。全体の判断と指摘を落とす判定を担うが、落とす判定は確認が別のモデルで確かめる（[全体の段と確認](#全体の段と確認) の条件の多様性）。
- 確認役：判定役と別のモデルで、effort を上げる。落とす側を厳しくするため。束ねも続けて担う。
- 回収役：小さいモデルと低い effort。

**Haiku の使い道。** 判断が薄く、型の決まった答えを返し、結果を CLI や検証役が後で確かめられる役に使う。ただし、他の役の体に続けて扱える判断のために別の体を起動すると、小さいモデルで減る費用より前置きの費用が大きい（起動の原則）。このため名寄せには置かず（決定 13）、それだけで起動する理由のある役（回収役など）に置く。名寄せの誤りは、不明の組を照合で一緒に引くこと（[全体の段と確認](#全体の段と確認) の順序と終わり）と、run の記録の名寄せの内訳で見る。小さいモデルで絞り込むときは、外した分から無作為に抜き取って上のモデルで精読し、偽陰性を測る。

**見直し。**
- 起動した agent のモデルと token を、役ごとに run の結果へ記録する。
- 見直す契機は、モデルの世代が変わったとき、注入した欠陥での再現率が役・モデルごとに下限を割ったとき、確定した指摘 1 件あたりの費用が上のモデルに寄せたほうが低くなったとき。
- 上げ下げはこの指標で決める。最も高い effort は、質の向上を測れた役にだけ使う。
- Codex runner で起動したモデルが記録に残らない環境では、指定が効いたかを確かめられない。その場合は、指定が効いていない前提で、体数の側で費用を抑える。

**Codex。** 同じ論理名を、runner の `modelMap` で Codex 側のモデルと effort の組に解決する。両者の品質が同等かは推測せず、実測で確かめる。別の系統は、確認を全体の段と別のモデルにする手段として使える。

**費用の見積もり。** CLI が起動の前に静的に見積もる。全体の段の意図の数は前の結果で決まるので、見積もりは 2 回に分ける。
- run の始まり：ファイルの段の起動数は担当（詰め合わせ）の数で決まる。計画役・観点の検証役・全文レビューの各 1 体を足す。全体の段は既定で判定役と確認役の各 1 体とし、続きの呼び出しは予算の上限の中で走る分として開示する。
- 全体の段の始まり：CLI が意図を作った時点で、意図の数から、1 体の時間の上限で続きの呼び出しが要るかを見積もり直す。確認と束ねは確認役の呼び出しに含める。
- 規模の桁は、run の記録（意図の数と段ごとの起動数）で見直す。
- 予算（最大の起動数と token の上限）は入力にし、どちらかの見積もりが超えたら、その段を始める前に止めて利用者に聞く。
- 最初の適用は、1 回のループで様子を見る。

**絞る順。** 網羅を保つ手段を先に、網羅を削る手段を後にする。
1. 網羅を保つ手段：持ち越しで変わらないファイルの読みを省く、共有の prompt を先頭にそろえてキャッシュを効かせる、本文の配達で冷読みの重複を減らす、同時実行を抑える。
2. 網羅を削る手段：ファイルの数や観点の数を削る。削った範囲は必ず開示し、「見ていない」を「問題なし」にしない。自動では削らず、利用者に聞く。

**退けた案。**
- この文書に値の表を書く：正本が 2 つになり、世代が変わるたびに食い違う。
- 独立と分離に要らない所で体を分ける（前の版の計画役 2 体、観点ごとの検証、全体の段の種類ごとの並列）：前置きの費用が体数分かかり、検出は 1 体に詰めても大きく落ちない（起動の原則）。
- 全ての役を最上位のモデルにそろえる：機械的な照合まで最上位にする意味が無く、週の上限に当たる。
- ファイルの段や全体の段を Haiku にする：読みと判定は判断で、見落としが増える。
- 全体の段をファイルの段より上位のモデルにする（前の版）：試作で最も良かった組を両方に使う。落とす判定の誤りは、確認を別のモデルにして拾う。
- run の始まりに、全体の段まで含めた起動数を 1 つの式で見積もる（前の版の「ファイルの数 + 3」）：全体の段の既定の体数は決まるが、続きの呼び出しの数は意図の数で決まり、始まりには分からない。
- 走らせてから使用量を見て止める：前に週の上限に達した規模で、事後では遅い。
- 費用が超えたらファイルや観点を自動で削る：「見ていない」が「問題なし」に見える。

下の層で決めるもの：具体のモデル名、effort の値、予算の上限の値、見直しの閾値。

## 測り方

測定は 3 つに分ける。どれも台帳の記録だけを読む。依存は測定から仕組みへの一方向にし、仕組みは測定を知らない。

| 測定 | 答える問い | 費用 | いつ |
|---|---|---|---|
| run の指標 | この run はどう進んだか | 追加なし | 毎回 |
| 較正 | 観点・モデル・effort の組は、どれだけ見つけ、どれだけ誤るか | 大きい（暫定で本番の 2 倍程度） | 観点・モデル・effort・prompt の指紋が変わったとき、利用者が求めたとき |
| 前の作業との比較 | 新しい方式は前より良いか | 小さい | 初回 |

1 つに寄せると、費用か妥当性のどちらかが崩れる。

**run の指標。** script とスキーマで決定的に集計し、LLM に集計させない。
- 周の数（reviewer を起動する 1 巡を 1 周とそろえる）。
- 指摘の内訳。前からの見落とし、直しによる誤り、新規に分ける（[再レビューと持ち越し](#再レビューと持ち越し)）。主な指標は、2 周目以降の前からの見落としと、直しによる誤りの数。網羅の仕組みが効けば前者が初回に出て周が減り、局所の直しをやめれば後者が減る、という仮説を直接確かめられる。
- ファイルの網羅（見たファイル、開示したファイル）。
- token と起動数（確定した指摘 1 件あたり、合格 1 件あたり）。
- 段ごとの寄与。指摘ごとの出どころ（全文レビューか、ファイルの段か、全体の段のどの種類の意図か）、全文レビューとファイルの段の指摘が同じ群に束ねられた数、全体の段で落ちた数、確認で復活した数、名寄せの内訳（同じ・別・不明）。
- 意図の数と、段ごとの起動数。
- 範囲の大きさ（単位の数・行数）。

**境目を run の記録から見る。** 範囲の大きさと、段ごとの寄与・落ちた数・復活した数・token を run ごとに並べると、ファイルの段が要らなくなる規模を後から見られる。たとえば、ファイルの段の指摘がほとんど全体の段で落ち、全体の段だけが確定の指摘を出す範囲が続けば、その大きさでは 1 体の全文の読みで足りていた可能性がある。測るための実験はしない（決定 10）。

**較正。** 正解の付いた対象を、本番と同じ経路で走らせて採点する。本番と違うのは、入力に正解の集合を付けることと、採点の段があることだけ。
- 正解の集合は 2 種類持つ。主は自然の欠陥で、このリポジトリで後から見つかり反証を通った指摘を、その時点の版に戻した対象。補助は注入の欠陥で、注入する役を検出側と別の系統のモデルにし、複数の種類と箇所に散らす。注入の欠陥は本物と分布が違い、LLM が注入したものは LLM に見つけやすいため、主にしない。
- 観点の間とモデルの間の相対の比較にだけ使い、絶対値は上限寄りの目安と明記する。改廃を決める集合と、確かめる集合を分ける。
- 再現率と誤指摘の率を両方測り、欠陥の無い対照のファイルも入れる。同じ組を複数回走らせ、ばらつきの区間が重なる差では改廃しない。
- 採点の照合は位置と種類で機械的に行い、曖昧なものだけ別のモデルの判定役に回す。判定役の誤りは採点の誤差として開示する。

**前の作業との比較。** relate の設計レビュー 4 回、取り込みの設計レビュー 2 回、計画の段の 6 回を、run の指標と同じ定義で事後に分類し直して比べる。
- 前の作業には台帳が無いので、周の数・指摘の内訳・token は比べられるが、ファイルの網羅は比べられない。比べられないことを開示する。
- 事例が少ないので、方向の目安にとどめ、合否の基準にしない。
- 同じ文書の前の版に新しい方式を走らせ直し、前の確定した指摘を正解にする比較は、条件がそろうので最も強い。行うかは、[利用者に聞くこと](#利用者に聞くこと)。

**結果の使い方。** 測定の結果は、観点の改廃・モデルと effort の割り当て・段の構成の変更の提案として台帳に出す。自動では切り替えず、人が承認する。少数の組と偏った正解で値を動かすと過適合するため。欠陥は原因の層へ戻す（観点が効かない → 観点の定義、モデルが落とす → 割り当て、段の構成が合わない → 方式設計）。測っていない初期値は「暫定・未測定」と開示する。

**初回の範囲。** 1 回のループで様子を見る方針に合わせ、run の指標と前の作業との比較から始める。較正を最小の規模で 1 回加えるかは、[利用者に聞くこと](#利用者に聞くこと)。

**退けた案。**
- 本番の run に常に既知の欠陥を混ぜる：利用者に出す指摘に混ざり、毎回費用が増える。
- 捕獲再捕獲を主な指標や完了の判定にする：前提を破り、過小に推定する。
- 注入の欠陥だけで測る：分布が違い、見つけやすい偏りがある。
- 測らずに初期値のまま固定する：観点の効果は割れており、決定 5 の見直しの根拠が得られない。
- 測定の結果で自動で切り替える：過適合する。
- 較正を毎回や定期の CI で回す：費用が大きい。
- 前の作業との比較だけで判断する：事例が少なく、網羅を比べられない。
- 境目を測る実験を走らせる：利用者の決定で行わない（決定 10）。本番の run の記録から見る。

下の層で決めるもの：指標の定義の細部、較正の規模と正解の集合の作り方、区間の計算。

## 既存のスキルへの組み込み

**渡すもの（宣言）。** 呼ぶ側は薄い宣言を渡す。静的に決まる部分は呼ぶ側の script とスキーマに、判断に属する部分は目的と理由で持つ。
- 対象のファイルの列挙の規則（差分の変更ファイル、監査の path など）。
- 観点の中身。
- 静的な検査に渡す ID の形。
- 重大度の名前と定義、裁定済みの論点（再び起票しないもの）。
- 成果物の層の対応。
- 規則の束（repo-review なら方針の束と pin）と、役ごとのモデルと effort の上書き。
- 止める条件の上限（正本は呼ぶ側の `meta.limits`）。
- 検証役の定義を差し替えるときだけ、その定義。

**受け取るもの。**
- 台帳（単位ごとの状態と、見られなかった理由、開いたままの意図）。
- 根本原因でまとめた指摘の一覧。各指摘は、1 つ以上の path、確信度、原因の層（必須）、出どころ、前からの見落としか直しによるかの印を持つ。
- 参考（義務に結べない指摘）の一覧。指摘と分けて受け取る。
- run をまたぐ回ごとの新しい指摘の数と、止まった理由。
- 出来事（`events`）と費用の実測。

**coverage-build との受け渡し。** 仕組みは修正をしない。今の実装では coverage-build が coverage-audit の結果を取り込む。受け渡しも台帳と同じく、司令塔が内容を写さない形にする。
- coverage-audit → coverage-build（取り込み）：coverage-audit は止まったときに `stateDir/status-<段>.json` を書く。coverage-build の `import-audit` は、そのファイルを path で読む。司令塔は `status` の出力を写さない。試行の上限で判定できなかった意図の開示を含む complete の結果も、そのまま取り込める。
- coverage-audit → coverage-build（段の位置）：coverage-audit は、init と reframe の時点で、段と段の始まり（`phase`・`phase_start`）を `stateDir/phase.json` に書く。coverage-build はこれを path で読み、同じ段の reframe を二重に発行しない判定（今の `framed`）に使う。二重に発行すると、途中の検査と coverage-audit の answer で足した `A<n>` が消える。止まったときだけ書く `status` のファイルでは、検査の途中の位置を読めないので代われない。
- coverage-build → coverage-audit：今と同じ。CLI が書いた argv を司令塔がそのまま渡す。呼び出しの境界で、渡すのは引数だけだから。
- 指摘の形が変わる（複数の path・確信度・原因の層の必須・参考の分離）ので、coverage-build の取り込みも同じ形に合わせる。
- 今の食い違い：coverage-build の CLI（`auditPosOf`）が coverage-audit の台帳（`ledger.json`）を直接読んでいる。coverage-build の SKILL.md の「coverage-audit を呼ぶ」は、coverage-build の CLI から coverage-audit のファイルを読まないとしている。段の位置は `phase.json`、止まった結果は `status-<段>.json` を読む形にそろえる。

**経路の無い作業への経路。** 設計レビューと計画には今スキルの経路が無く、即興のループで回して上限と差し戻しが当たらなかった。経路を与えるのは、仕組みを直接呼ぶ入口にする。
- 入口は、設計文書用と計画用の宣言の雛形を持つ。設計レビューは設計文書のファイルと方式設計の観点、計画は計画のファイルと計画の観点を渡す。
- [agent-work](../guidelines/agent-work.md) の既存の節（反復の収束と差し戻し）から、「スキルの経路が無い作業はこの入口を使う」と 1 行で指す。新しい司令塔の手順は増やさない。
- 入口の呼び出しそのものが上限・台帳・止める判定を持つので、規約を読んで自分のループに当てる必要が無くなる。
- 入口を仕組みのスキルと別のスキル（仮称 board-review）にするか、同じスキルの入口にするかは、[未決](#未決)。公開名と置き場は、[利用者に聞くこと](#利用者に聞くこと)。

**組み込みの順。**
1. 仕組みと、設計レビュー・計画の入口。経路が無くて発散した実例があり、既存の契約を壊さず、この方式設計自体の評価にも使えるため。
2. repo-review（差分・作業ツリー）。宣言を渡す形に変える。方針の束・pin・裏取り役は repo-review が持ち続ける。
3. repo-review の監査と横展開。review-mechanisms-import の「repo-review の中のモード」という置き場は変えない。モードが使う shard・本文の配達・読んだことの照合・run の状態は、この仕組みの契約に沿って作り、重複して持たない。
4. repo-implement の計画のレビューと実装のレビュー。計画のレビューは plan-reviewer の観点を宣言に写す。実装のレビューは既に repo-review を呼ぶので、2 の結果に乗る。
5. prd-spec。独自の run・保持規則・監査と改稿の輪を持ち、変える費用が最も大きいので最後にする。公開の後の仕組みだけを使える（[置き場と依存の向き](#置き場と依存の向き)）。

**退けた案。**
- 各スキルが自前で台帳・単位・止める判定を持つ：決定 1 に反し、正本が割れる。設計レビューと計画には経路が無いまま残る。
- 仕組みを repo-review の拡張にして、他のスキルが repo-review を呼ぶ：公開した prd-spec が依存できない。repo-review はリポジトリに固有で、汎用の核としては重い。
- 設計レビュー用と計画用に専用のスキルを個別に作る：規約を運ぶ経路がまた分かれる。入口 1 つで足りる。
- 規約の文だけで反復の収束を促す：規約を読んでも自分のループに当てなかった実例がある。
- prd-spec から先に組み込む：契約が実測で固まる前に着手すると、契約を prd-spec に合わせて歪める。

## 未確認の前提

| 前提 | 確かめ方 | 違ったときの扱い |
|---|---|---|
| 検証役が、層ごとの判定を引用つきで安定して返せる（独立の 2 回の一致率が十分高い） | 過去の設計レビューの実際の指摘から 10〜20 件の正解の集合を作り、独立に 2 回分類して一致率と、利用者が後で付けた原因との一致を測る | 3 回にして多数決にするか、方針・要求・方式設計を「上流」にまとめて利用者へ返す。それでも不安定なら、自動の分類をやめて利用者に確かめる経路を既定にする |
| 既存の成果物（docs/design、要求と仕様書、計画）が 5 つの層のどれかに対応づく | 既存の成果物を層に割り当て、どれにも入らない・複数に跨るものを数える | 層を増やす前に対応づけを見直す。入らない成果物の扱いを決める |
| 最も上流の原因を採っても、戻しの費用が過大にならない | 正解の集合の分類で、方針・要求まで戻る割合と、作り直しの規模を見る | 上流への戻しに利用者の確認を挟む |
| 同じ plugin の兄弟のスキルの CLI を、公開の前後とも、install 先でも呼べる | workflow plugin を install した環境で、prd-spec から仕組みの CLI を呼ぶ最小の run を通す。Codex でも試す | 呼び出しをスキルの呼び出しだけに限る。それでも解決しなければ、配り方を利用者に諮る |
| 全ての役が Bash で CLI（`claim`・`query`・`submit`）を流し、`stateDir`（repo の外）を読み書きできる。native の Workflow の subagent では確かめてあり、Codex の runner の worker では確かめていない | runner の最小の source で、役が CLI を流して `stateDir` へ書く run を通す。runtime の拒否条件を読む | `stateDir` を runner が許す範囲へ移す。それでも書けなければ、Codex では提出の無い呼び出しとして blocked で止め、開示する |
| 観点ごとの答えと引用を返させても、引用だけ正しく中身を読んでいない答えは多く出ない | 前からあった欠陥を含むファイルに段 1 の形で実行役を当て、欠陥の行を引用して「問題なし」と答えた数を数える | 段 1 を所在の確認としてだけ扱い、検出は全体の段と確認で担保する |
| 役が CLI に渡す短い ID の取り違えは稀で、拒否と冪等な再試行で回復できる | ID を故意に壊した `submit` のテストで、拒否と再試行での完了を確かめる | 未完了として開示して止める |
| 全文レビューを足すと、拾えた数が 1 体の全文レビュー（同じ対象で 16/16）に並ぶ | 次の本物の run で、同じ対象（約 480 行・4 ファイル、正解 16 件）の拾えた数を、出どころ（全文レビュー・ファイルの段・全体の段）ごとに数える | 全体の段か確認で正しい指摘が落ちていれば、落とす判定と確認の規則を見直す。全文レビュー自体が拾えていなければ、全文レビューの入力と形を見直す。規模で分岐はしない |
| 全文レビューを足しても、誤りが増えない（今の設計で 1 件、1 体の全文レビューで 0 件） | 次の本物の run で、確定した指摘のうち正解に無いものを、出どころごとに数える | 誤りの出どころの段の判定か確認を見直す |
| 文脈に収まる分の単位を 1 体に詰めて全文で読んでも、試作の 1 組（約 500 行）と同じく、細かく切るより文脈が落ちない | run の記録で、詰め合わせの大きさごとに、ファイルの段の指摘のうち全体の段で落ちた割合と、確定の指摘の数を見る | 詰める上限（`UNIT_MAX_BYTES` の値）を下げるか、ファイルの段の観点と出力の形を見直す。規模で分岐はしない |
| 文脈に収まる分を詰めたファイルの段の 1 体が、1 体の時間の上限の中で終わる。1 体で全ての意図を処理する全体の段と確認は、上限に当たっても次の呼び出しが残りを取って完了まで進む | 本物の run で、段ごとの呼び出しの時間と、時間の上限に当たった回数、続きの呼び出しの数を記録する | ファイルの段は詰める上限か時間の上限を見直し、全体の段は続きの呼び出しで足りるかを見る。体数は詰めきれない分だけ増やし、段は分岐させない |
| 1 体にまとめた全体の段（判定役・確認役）は、意図を順に処理して文脈が積もっても、後の意図の判定が落ちない | run の記録で、呼び出しの中の順番ごとに、落とした率・棄却した率・照合の拒否を見る。呼び出しの文脈の大きさも記録する | 1 回の claim で取る束の量の上限（`UNIT_MAX_BYTES`）を下げ、残りを続きの claim へ回す |
| 主語と目標で引いた近傍（意図の根拠と関係する事実）だけで、ファイルをまたぐ欠陥を拾える | run の記録で、確定したまたぐ指摘がどの種類の意図から出たか、確認で復活した指摘が近傍の外の事実に依っていたかを見る | 関係する事実の引き方（主語の近さ、前提の候補）を広げる。規模で分岐はしない |
| 1 つの意図の関係する事実が、要約の上限と id での引き直しで 1 体に収まる | run の記録で、意図ごとの入力の大きさと、試行の上限で開示して閉じた意図の数を見る | 意図の単位を細かくする（主語を観点や目標の項目で分ける）。収まらない意図は判定できなかった意図として開示する |
| 名寄せを判定役の型の決まった判定にし、主語の照合と同じ体で続けても、誤った統合と見逃しが少ない | run の記録の名寄せの内訳と、確認で復活した指摘のうち名寄せの誤りに由来するものを数える | 名寄せの閉集合と、一緒に引く事実を見直す |
| 反証を置かずに確認役が束ねても、根本原因の束ね方の誤りが少ない | run の記録で、上の層の群を利用者が退けた数と、作り直しの後に同じ根本原因が再発した数を見る | 束ねを確認役と別のモデルに移す |
| 意図の生成が有限の手順で 0 に至り、意図の数が単位の数に対して爆発しない | run の記録で、意図の数を単位の数と並べて見る | 意図を作る条件（「名前が近い」、前提の候補）を絞る |
| 保証と前提が、試作の契約の受け渡しのように情報を落とさず、全体の段の手がかりになる | 確定したファイルをまたぐ指摘の引用元が、保証と前提に挙がっていたか、全体の段が原文を開いて見つけたかを run の記録で見る | 保証と前提の形を見直す |
| 確認が、全体の段と別のモデル（全体の段より下位のモデルを含む）でも、全体の段の誤った落としと足しを拾える | 確認で復活した数と棄却した数、後で正しかったと分かった落としの数を run の記録で見る | 確認のモデルか effort を上げる |
| モデルを作らせる観点は、観点なしで読むより多く見つける | 注入した欠陥で、観点あり・なしの再現率と費用を比べる | モデルを必須の欄にするのをやめ、立場の多様性だけを与える軽い定義に縮める |
| 引用の実在を、CLI が安く決定的に確かめられる | 文書とコードで、改行や空白を崩した引用の偽陰性の率を数える | 正規化した一致に弱めるか、位置だけの検査にして標本の割合を増やす |
| 持ち越しで費用が減る（全体の段は毎回読み直しても、変わらないファイルの段の分が減る） | run の記録で、毎回読み直すファイルの割合と token を見る | 減らなければ持ち越しを使わない |
| 網羅の完了は、現実の予算の範囲で到達できる | 最初の run で、ファイルの数と 1 run の token・段ごとの起動数を記録する | 上限で止まるのが常態になるなら、未見のファイルの一覧を主な出力にし、絞る順を利用者に諮る |
| 根本原因でまとめた新しい指摘の数を、安定して数えられる | 前の周ごとの指摘の記録で、まとめた数の推移が収まるかを後ろ向きに確かめる | 飽和の記録は開示にとどめ、まとめる前の数も並べて出す |
| ファイルの段は、中位のモデルと中程度の effort で実用の再現率に届く | 最初の適用で、注入した欠陥での役・モデルごとの再現率と、確定の指摘 1 件あたりの token を測る | 上のモデルへ上げる |
| Codex runner で論理名を `modelMap` で解決でき、指定が効く | run の結果に起動したモデルが残るかを確かめる | 効いていない前提で、体数と段数で費用を抑える |
| 2 回の見積もり（run の始まりと全体の段の始まり）が、実際の起動数と token に近い | 最初の run で役ごとの起動数と token を記録し、見積もりと比べる | 見積もりの式を見直す。予算を超えるなら、網羅を保つ手段で絞り、それでも足りなければ範囲を絞って開示する |
| 前の作業の回ごとの指摘と確定の有無を、後から取り出せる | 該当の記録を開き、回ごとの指摘を列挙できるか確かめる | 取り出せない作業は比較から外し、その旨を開示する |
| token と起動数を、run ごと・役ごとに集計できる（native と Codex の両方） | 小さな run で、結果に使用量と agent の数が含まれるか確かめる | 起動数と入出力の文字数で代用し、概算と開示する |
| 前の作業の確定した指摘は、正解として使える程度に正確 | 標本を取り、利用者か別の検証役が実在を確かめる | 正解の集合を利用者が確かめたものだけに絞る |
| 薄い入口と agent-work の 1 行の参照で、経路の無い作業に実際に当たる | 入口の説明に、前の発散した事例の依頼文を当てて発火するかを確かめる | hook か AGENTS.md の必須項目で補う |
| review-mechanisms-import はまだ実装されておらず、置き場を変えても既存の実装を壊さない | repo-review の CLI に本文の配達・照合・shard の実装が無いことを確かめる | 実装済みの部分があれば、移す順序と互換の期間を、置き場の判断に戻して決める |

## 未決

論点どうしで食い違い、この文書では決めていないもの。決め方は、利用者の判断か、上の未確認の前提の実測による。

1. **Workflow source を共有するか、入口を別のスキルにするか。** 判定と集約を CLI に置き、source を役の起動だけにすることは B3〜B5 で決めた。残るのは、その薄い source を呼ぶ側ごとに持つか（案 A）、仕組みの核を 1 本の Workflow source にして runner がそのまま実行するか（案 B）。あわせて、設計レビューと計画の入口を、仕組みのスキル（仮称 coverage-board）と別のスキル（仮称 board-review）にするか、同じスキルにするかも決まっていない。A は、入れ子の workflow が無いことと公開の操作の制約に合わせた形。B を採るなら、両環境で同じ source を呼べる経路を示す必要がある。
2. **層の分類の形。** 案 A は、検証役が層ごとに閉集合の判定（正しく決めている・決めていない・誤り・越境・責務でない）を返し、独立に 2 回行い、script が最も上流を原因の層として導く。案 B は、検証役が層の閉集合（方針・要求・方式設計・詳細設計・実装・不明）から 1 つを選ぶ。A は判定を細かく検査でき、B は費用が小さい。分類の一致率の実測で決める。
3. **差し戻しを誰が実行するか。** 案 A は、汎用の部品が差し戻しの遷移（作り直し・下流の古い印・保留と分類し直し）を持つ。案 B は、仕組みは戻す先を示すだけで、作り直しは呼ぶ側が判断して行う。A は局所修正の経路を構造で塞ぐ範囲が広く、B は仕組みを小さく保つ。
4. **モデルの表の置き場。** 表は役だけで引く。正本を Workflow source（今の実装の `roles.json` はスキルの中）に置くか、CLI 側か共有の設定に置くかを決める。Workflow source を呼ぶ側ごとに持つ形（未決 1 の案 A）では、表が呼ぶ側ごとに分かれ、「1 か所」と食い違う。
5. **run の途中で観点を足すか。** 案 A は、観点を run の最初に固定し、途中で足さない（観点の偏りを防ぎ、分母を安定させる）。案 B は、計画役が途中でも観点の追加を提案でき、範囲外の気づきからも昇格させ、CLI が形式を検査して足す。B を採るなら、足した観点の読みを初期の分母と別に数えて開示する。
6. **ファイルの段が要らなくなる規模（境目）。** 全文レビューを先に置いたので、問いは「全文レビューの後の段（ファイルの段・全体の段・確認）が、拾える数と誤りの少なさをどれだけ足すか」になる。後の段が網羅の証拠のほかに足さず、費用だけを増やす範囲は残りうる（試作の 1 組では 1 体の全文の読みが良かった）。境目は測っておらず、測る実験もしない（決定 10）。規模による分岐は置かず（決定 9）、本番の run の記録から後で見て（[測り方](#測り方)）、構成を変えるかを利用者が決める。

## やらないこと

- 資産 × 観点の枡に分けない。1 体の文脈に収まるファイルを分けない。収まらないファイルも、構造の境目より細かく分けない。
- 階層の合成（契約の積み上げ・glossary・z3）を入れない。
- 規模による構成の分岐や、数値の線引きを置かない。
- 境目を測るための実験をしない。
- 担当どうしの合議・討論を置かない。
- 独立と分離に要らない所で体を分けない。横展開と束ねの反証を持たない。
- 「新しい指摘が 0 件」や乾きを、完了の条件にしない。
- 捕獲再捕獲などの残りの推定を、完了の判定に使わない。
- 指摘の箇所だけを直す経路を持たない。
- 全体の段の意図を計画役に出させない。
- 役の入力と出力を、返り値・args・司令塔の写しで運ばない。
- 測定の結果で、観点やモデルを自動で切り替えない。
- 費用が超えたときに、網羅を黙って削らない。
- この文書で、op の入出力・状態の欄・定数・閾値・モデルの値を決めない。
- この文書の確定の前に、既存の文書（skill-design-patterns・review-mechanisms-import・agent-work）を書き換えない。

## 利用者に聞くこと

各項の後ろの括弧は、答えを待っている節。

1. **層の順序と、利用者へ返す範囲。**（[層と差し戻し](#層と差し戻し)）
   - 依頼の並びは「方針・要求・方式設計・詳細設計・実装」だが、このリポジトリの design 文書は要求の前段で、方式設計が要求より前に来る使い方がある。層の順序をデータで持ち、既定は依頼の並びにして、方式設計 → 要求の順に並べ替えた一覧を渡せる形でよいか。実際にはどちらの順にしたいか。
   - 方針が原因の欠陥と、要求が複数の解釈を許す欠陥は、必ず利用者へ返して止める（自動で進めるのは方式設計より下だけ）という線引きでよいか。
   - 分類が食い違ったとき、上流の側を採る（費用より見落としの防止を優先する）既定でよいか。
   - agent-work の「必須欠陥は設計へ戻る」を、この設計の確定の後に層の一覧への参照へ置き換えてよいか。
2. **公開の時期と名前。**（[置き場と依存の向き](#置き場と依存の向き)、[既存のスキルへの組み込み](#既存のスキルへの組み込み)）
   - 仕組みを、develop の plugin ができる前に workflow plugin の一部として先に公開してよいか。公開しない場合、prd-spec への組み込みは公開の後になり、repo-review・repo-implement で先に実証する。
   - 仕組みのスキルと入口のスキルの公開名と置き場（workflow plugin の中か、新しい plugin か）。
3. **review-mechanisms-import との順序。**（[置き場と依存の向き](#置き場と依存の向き)、[既存のスキルへの組み込み](#既存のスキルへの組み込み)）
   - review-mechanisms-import の置き場の節（結論の表と共通する判断）を、実装の前に、この仕組みを使う形へ書き換えてよいか（取り込みの設計が 1 つ前に戻る）。
   - review-mechanisms-import の最初の単位（repo-review への横展開）を、この仕組みの契約が決まる前に進めてよいか。進めるなら重複を一時的に許して後で取り出し、止めるならこの設計の後にそろえる。
4. **司令塔の経路の塞ぎ方。**（[役と制御の境界](#役と制御の境界)）司令塔が成果物の本文を直す経路を、構造（受理の経路が script にしか無い）だけで塞ぐか、hook でも物理的に止めるか。後者は手間と確実さの価値判断がある。
5. **skill-design-patterns の更新。**（[台帳と見たの記録](#台帳と見たの記録)、[全体の段と確認](#全体の段と確認)、[再レビューと持ち越し](#再レビューと持ち越し)）
   - 「資産台帳」の「『見た』は検証を通さずに入れる」を、機械の検査を常に、モデルの確かめを全体の段と確認に持たせる形へ改めてよいか。費用は主に確認で増え、1 回のループの様子見に収まる見込み。
   - 「資産台帳」の「台帳の寿命は 1 run」と、「水準と未決事項」の run をまたぐ追跡の行を、この設計の後で持ち越しの形に書き換えてよいか。
   - 「状態の書き込み」と「探索グラフ」の運搬役の記述、「探索グラフ」の計画役が意図を出す形、「資産台帳」の担当の単位の行を、この設計を一般の規則として書き直すか、この仕組みの逸脱として各行に注記するだけにするか。
   - 持ち越しの信頼の方針。費用を抑えるなら、変更の無いファイルの読みを次の run にも持ち越す。網羅を優先するなら、一定の run ごとか、モデルが変わったときに全てのファイルを読み直す。初期値を「持ち越しを使い、モデルや手続きの版が変わったら全て無効」とする案でよいか。
6. **見られなかったファイルを残した受理。**（[完了と止める条件](#完了と止める条件)）見られなかったファイルが開示つきで残った状態を、呼ぶ側が受理として扱ってよいか。レビューなら指摘と未読の範囲を返して終わりでよいが、設計や計画の合格のように後の作業を許す場合に、未見のファイルが残ったまま進めてよいか。既定を 1 つ決めるか、スキルごとに決めるか。
7. **観点の改廃の承認。**（[観点の定義と持ち主](#観点の定義と持ち主)）測定で寄与の無い観点をやめるとき、自動で行うか、利用者の承認を挟むか。標準の観点は仕組みの持ち物なので、呼ぶ側の観点と違い、利用者の判断が要る。
8. **落とした指摘の開示の粒度。**（[全体の段と確認](#全体の段と確認)）全体の段が落とした指摘と、確認が棄却した指摘のうち重いものを、結果で一覧として見たいか。見たいなら理由と引用を載せ、見なくてよいなら件数の開示にとどめる。
9. **予算。**（[モデルと費用](#モデルと費用)）最初の適用の予算の上限（起動数と token）を、どの桁に置くか。週の上限との兼ね合いを判断してほしい。
10. **測定の範囲。**（[測り方](#測り方)）
    - 初回の測定に、run の指標と前の作業との比較に加えて、最小の規模の較正を 1 回（概算で本番の 2 倍程度）加えるか。較正を省くと費用は増えないが、Haiku とモデルの割り当てを見直す根拠が得られない。
    - 同じ文書の前の版に新しい方式を走らせ直す比較を行うか。条件がそろい最も強いが、ループ 1 回分の費用が増える。
    - 較正の正解に使う前の確定した指摘を、利用者が標本で確かめるか、反証を通ったものをそのまま使うか。
