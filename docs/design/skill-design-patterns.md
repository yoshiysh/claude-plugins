## 用語

複数の節で使う用語だけをここで定義する。1 つの節でだけ使う用語は、その節の初出で定義する。
- **項目**：1 つの段で処理する単位（ファイル・観点・意図など）。
- **段**：全ての項目を待ってから次へ進む区切りと、区切りの間の処理のまとまり。次の手順が全ての項目の結果を必要とするなら、そこが段の境界になる。
- **工程**：1 つの項目（`pipeline()` の 1 item）の中の手順。工程の間では他の項目を待たない。authoring が pipeline について言う "stage" は本書の工程に、"barrier" は全件の到着を待つ区切り（本書の段の境界）に当たる（本書の読み）。
- **反復**：段の並びを、結果に応じてもう一度回すこと。探索グラフの反復は**周**と呼ぶ。
- **形**：段と段の間の制御フロー。次の 3 つだけ（選び方は「形の判定」）。
  - 固定パイプライン型：段と段の間に、結果による戻りが無い（有限の分岐は列挙できるのでここに含める）
  - 固定集合の反復型：試すもの（項目・方向）の集合が事前に決まって結果で増えも減りもせず、段と段の間に結果による戻りがある
  - 探索グラフ型：試すもの（項目・方向）の集合が、前の結果で変わる
- **部品**：1 つ以上の段からなり、段と段の間に戻りの無い定型の並び。形の中に組み込む（例は「形の判定」）。
- **CLI**：状態（グラフ・台帳・ヒント）を検証つきで読み書きする唯一のコマンド。規則は「状態の書き込み」。
- **作業ファイル**：run のディレクトリに agent が置くファイル（実行の記録・大きな出力・各 agent の出力）。状態ではなく、CLI を通さずに書く。
- **needs_input**：人間の入力を待って止まったことを示す停止の種類。
- **BLOCKED**：失敗して続けられずに止まったことを示す停止の種類。
- **ヒント**：人間が状態に足す、待たれない入力（「停止・再開と人間の入力」）。
- **空振り**：何も見つからなかったという結果。
- **試行**：1 件の意図を、実行の工程から書き込みの工程まで 1 回流すこと（回収を含む）。
- **工程の欠け**：工程の agent が結果を返さずに終わること。試行については、実行の工程が欠け、回収でも受理が 1 件も出なかったことを指す（「実行役・回収役・検証役」）。
- **乾き**（暫定）：新しいものが 1 件も受理されず、全件失敗でもない反復。空振り・既知の事実・検証不能・却下（事実・完了の主張）は「新しいもの」に数えない。
- **全件失敗**：処理した項目が 1 件以上あり、その全てで工程が欠けた反復。探索グラフでは、実行した全ての意図で、試行が工程の欠けになった周。
- **未着手**：まだ結論の出ていない意図。試行の上限で外した意図（**打ち切り**）は含まない。

## 構成要素

Workflow script で組むスキルは、次の要素に分かれる。各要素は「持つもの」だけを持ち、「持たないもの」は他の要素に任せる。役の名前は探索グラフでのもので、他の形では使う役だけを置く。事実と意図は「探索グラフ」で定義する。

| 要素 | 持つもの | 持たないもの |
|---|---|---|
| script | 制御フロー、agent の起動と起動数の記録、受理の決定、停止の判定 | ファイルと shell（docs：script はどちらにも触れない） |
| 計画役 | 次に試す意図、完了の主張、人間の入力が要るという判断 | 実行、状態の書き込み |
| 実行役 | 1 件の意図の実行と、事実の候補（検証に要るものを添える） | 受理の判定、他の意図 |
| 回収役 | 工程が欠けた実行の記録から、確認済みの事実の候補を拾う | 新しい実行 |
| 検証役 | 生成と別の context で、事実の候補を受理・却下・検証不能に、完了の主張を受理か却下に分ける | 生成 |
| 運搬役 | 状態を書き込む CLI を呼び、その出力を script へ逐語で写して運ぶ役（規則は「状態の書き込み」） | 判断 |
| CLI | 状態、ID、要約、決定的な照合 | 意味の判定 |
| 人間 | 目標、ヒント、承認 | run の中で待たれる応答（docs：実行中の入力は受け取れない） |

```mermaid
flowchart LR
  H["人間"] -- "目標・承認（起動時）" --> S
  H -- "ヒント（いつでも）" --> CLI
  S["script"] -- 起動 --> PL["計画役"]
  S -- 起動 --> EX["実行役"]
  S -- 起動 --> VF["検証役"]
  S -- 起動 --> CN["運搬役"]
  S -- 起動 --> RC["回収役"]
  PL -- "意図・完了の主張" --> S
  EX -- "事実の候補" --> S
  EX -- "記録" --> WF[("作業ファイル")]
  WF --> RC
  RC -- "事実の候補" --> S
  VF -- "受理・却下・検証不能" --> S
  S -- "受理の決定" --> CN
  CN -- "読み書き" --> CLI[("CLI と状態")]
  CN -- "要約（逐語）" --> S
  PL & EX & VF -. "読み出し" .-> CLI
  S -- "停止の種類と理由、next_args" --> H
```

## 形の判定

軽い形から順に問う。前の問いは、後の重い形を選ぶ理由になる条件を含まないように書く。

```mermaid
flowchart TD
  A{"人間の入力が要るところを run の境界にできる（入力がほぼ全ての手順の間に挟まらない）"} -- いいえ --> T["Claude がターンごとに指揮する"]
  A -- はい --> Q1{"段と段の間に、結果による戻りが無い"}
  Q1 -- はい --> P["固定パイプライン型"]
  Q1 -- いいえ --> Q2{"試すもの（項目・方向）の集合が事前に決まり、結果で増えも減りもしない"}
  Q2 -- はい --> GV["固定集合の反復型"]
  Q2 -- いいえ --> Q3{"探索グラフの適用条件を満たす"}
  Q3 -- はい --> G["探索グラフ型"]
  Q3 -- いいえ --> T
  P --> Q4{"資産台帳の適用条件を満たす"}
  GV --> Q4
  G --> Q4
  Q4 -- はい --> L["資産台帳を足す"]
  Q4 -- いいえ --> S
  L --> S["部品を選び、Workflow script の制御フローとして組む"]
```

資産台帳の追加起動（「資産台帳」）は、形を決める戻りに数えない。追加起動は、決まった資産の集合の残りに同じ段を当てるだけで、試すものを変えないから。数えると、台帳を足しただけで形が変わる。

部品の例：
- 並列化：互いに独立な項目を同時に処理する段（項目ごとの処理は違ってよい）
- 観点ごとの検証、反証
- Judge panel：独立に N 案を作る段 → 並列に採点する段 → 最良を軸に他の案の良いところを取り込む段（authoring）
- 項目ごとの map：全ての項目に同じ処理を当てる段
- 項目ごとの until-pass：1 項目の工程を、通るまでその項目の中で繰り返す。繰り返しは有限で止め、通らずに止まったときは、その項目の結果として、通らなかったことと理由を返す

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| 待たれる人間の入力（承認・回答）が要るところは run の境界にし、Workflow script には入力を待たない区間だけを入れる（「停止・再開と人間の入力」）。入力がほぼ全ての手順の間に挟まるなら、run に切っても利点が無いので Claude がターンごとに指揮する | docs（Behavior and limits の表：実行中の入力は受け取れず、段階の間の承認は段階ごとに別の workflow として回す） | run の中では、入力を待ってから続けることができない |
| 図の順（軽い形から）に問い、重い形を選ぶときは、どの条件がそれを強いるかをスキルの設計の説明に書く | 本書 | 重い形が既定になり、決まった手順のスキルに探索の費用を払う |

例の着地（本書）：

| 例 | 着地 | 理由 |
|---|---|---|
| review（観点 fan-out → 反証 → 集約） | 固定パイプライン型＋観点ごとの検証・反証の部品 | 段と段の間に戻りが無い |
| 移行の map（各ファイルを通るまで直す場合も） | 固定パイプライン型＋項目ごとの map・until-pass の部品 | 改稿が他のファイルの結果を必要としないので、until-pass は各ファイルの工程の中にある |
| Judge panel で N 案から選ぶ | 固定パイプライン型＋Judge panel の部品 | 案を作る → 採点 → 取り込む、で戻りが無い |
| 1 つの文書の監査と改稿を通るまで回す | 固定集合の反復型 | 改稿が全ての観点の監査結果を必要とするので、監査と改稿の間が段の境界になり、そこに戻りがある |
| ゲートつきの要求文書の作成（人間の承認で止まって再開する） | 固定集合の反復型。各ゲートを run の境界にする | 上と同じ。ゲートの間の区間は、run の中で人間の入力を待たない |
| 情報源を辿る調査、原因調査 | 探索グラフ型 | 試すもの（調べる方向）の集合が前の結果で変わる |

## 目標の固定

どの形でも、入口で目標を固定する。探索グラフでは、完了の照合がこの目標に対して行われる。

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| 目標は「最終的に検証できる成果物」とし、調査・手段・検証の手順を入れない。成果物が互いに独立なときだけ分ける | 本書 | 手順を終えたことが完了と読まれる |
| 依頼文から範囲と禁止事項を先に抜き出し、指示語を固有名に置き換えて自己完結させる | 本書 | fresh な agent に渡った時点で指示語の意味が消え、範囲の外へ探索が漏れる |
| 目標に数値で判定できる条件（件数・閾値など。以下「数値条件」）があれば、目標と一緒に固定する | 本書 | 完了の照合で、決定的に確かめられる条件が無くなる |
| 固定した目標と出発点は、前提として状態に書き、最初の周の意図が根拠として指せるようにする。検証役による受理の規則の外に置く | 本書（生成した主張ではなく入力だから）・Cairn（origin と goal を特別な事実として作る） | 最初の周の意図が根拠の事実を指せず、CLI に拒否される |
| 依頼文に無い目標・制約は作らない | 本書・Opus 5（依頼の範囲を広げたり狭めたりしない） | 頼まれていない成果物に費用を払い、その完了を報告する |

## 停止・再開と人間の入力

形によらず、Workflow script に当てはまる。

- **next_args**：止まった run が返す、同じ状態から新しい run を起動するのに要るもの。
- **再開**：`next_args` で新しい run を起動すること。docs の relaunch（同じ run を保存した結果から再生すること）とは別で、本書は relaunch を使わない。
- **停止の種類**：完了・乾き・needs_input・反復の上限・BLOCKED（全件失敗の連続と、続けられない失敗）。形によっては使わないものがある。

人間の入力は 2 種類ある。
- **待たれる入力**（承認・質問への回答）：run の境界でだけ入れる。run は needs_input で止まり、人間が入力を足してから再開する。
- **待たれない入力**（ヒント）：run は止まらず、次に計画役を呼ぶときに取り込まれる。runtime 自体は実行中の入力を受け取らないが（docs）、状態は run の外にあり agent が CLI で読むので、この経路は runtime の制約に当たらない（本書）。

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| どの停止でも、理由と、未着手の意図と打ち切った意図の一覧を状態に書き、次の run の計画役がそれを読んで次の手を決める。完了は照合の証拠も返す | 本書・authoring（No silent caps：絞ったものを記録しないと「全部見た」と読まれる） | なぜ止まったか、どこから再開すればよいかが残らない。試していない方向が「試した」と読まれる |
| 待たれる入力が要るときは、needs_input と理由を返して止め、人間が入力を足し、再開する | docs（Behavior and limits の表：実行中の入力は受け取れない）・本書（next_args） | run の中で入力を待つ設計は組めない |
| ヒントは人間が CLI で状態に追記する。run の実行中も、完了以外で止まっている間も足せる | Cairn（ヒントはグラフの外の入力で、停止中のプロジェクトにも足せる） | 実行中に気づいたことを伝えるために run を止めることになる |
| スキルは run を起動したときに、ヒントの足し方を人間に示す | 本書 | 人間がヒントの足し方を知らず、待たれない入力の経路が使われない |
| 計画役が読んだヒントと、停止の判定が「読まれていないヒント」とするヒントを一致させる | 本書 | 読まれていないヒントが残ったまま乾きや却下で止まるか、読んだヒントを未読と数えて止まらない |
| 完了した状態へのヒントの追記は、CLI が拒否する | 本書（完了からは再開しないので、足しても読まれない。完了した項目を reopen できる Cairn とは事情が違う） | 人間が足したヒントが、誰にも読まれずに残る |
| 止めた run や途中で終わった run は relaunch せず、状態から新しい run として再開する。再開した run は状態をそのまま読み、途中の周で受理された事実・試行の回数・打ち切りも、そのまま使う | 本書（状態にあるのは検証を通ったものだけなので、捨てる理由が無い）・docs（relaunch では、prompt が変わった agent か失敗した agent から後ろが、完了済みでも再実行される） | 再実行の記録が前の記録と混ざる |
| 前の run の遅れた書き込みが、新しい run の状態を変えないようにする | 本書（新しい run の起動には relaunch の拒否のような保護が無い）・docs（止めた run の agent がまだ終わっていなければ relaunch は拒否される） | 前の run の遅れた書き込みが、新しい run が読んだ後の状態を変える |
| 完了以外の停止からは再開できる。乾き・反復の上限・needs_input は必要なら人間が入力を足してから、BLOCKED は原因を直してから再開する | 本書 | 止まった run の途中までの結果を捨てて、最初からやり直すことになる |
| 再開した run は必ず計画役から始め、止まっていた間に増えたヒントを読ませる | Cairn（ヒントの増加で計画役を呼ぶ）・本書 | 再開しても計画役が新しいヒントを読まない |
| 再開した run は、人間の入力が効く前に、前の run と同じ理由ですぐに止まらないようにする | 本書 | 乾きで止まって再開した run が、最初の周で再確認を待たずに止まる。人間の入力が効く前に却下でまた止まる |
| 再開した run では、台帳の結び付きとカバレッジを、対象の今の内容に基づかせる | 本書（前の run の後に対象が変わっていることがある） | 古い内容に基づく結び付きとカバレッジが残る |
| 再開をまたいで残す値（固定した目標・未着手の意図・試行の回数など）は run の外の状態に持ち、再開した run はそこから読む | 本書（再開は新しい run の起動なので、script の変数は残らない） | 人間の入力を挟むたびに、それまでの値が失われ、試行の回数が初期値に戻る |
| pipeline の外の agent が失敗しても、BLOCKED と理由を返して止める。状態を読み書きする agent も含む | docs（直接 await した agent は、失敗すると run を終わらせるか `null` を返す）・authoring（`agent()` は予算の超過などで throw する） | 停止の理由が残らないまま run が終わる |

## 体数と同時実行

形によらず当てはまる。

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| 探索グラフでは、実行役は全て script が起動し、周ごとの起動数を結果に残す | 本書 | 何体走ったかの記録が残らず、費用を追えない |
| fan-out の項目の件数は事前に決めない（探索グラフでは「計画役」の意図の件数の行） | 本書 | 件数を先に決めると、残りが次の反復に回って反復が増える |
| 同時に走る agent は 3 体まで（初期値。eval で測って決め直す）とし、残りは枠が空くまで待たせる。守らせ方（runtime の設定か script か）は実装で決める | 本書・docs（runtime の同時実行は既定で 16 体まで。`CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` で変える） | 同時に走る agent が増え、レート制限に当たる |
| 項目の件数が runtime の 1 回の呼び出しの件数の上限を超えるときは、呼び出しを分ける。切り捨てない | docs（上限を超える一覧はエラーで拒否される） | 呼び出しがエラーで拒否されるか、切り捨てた項目が「見た」と読まれる |

## モデル・effort・prompt

役ごとに求める性質が違うので、`agent()` の `model` と `effort` を役ごとに決める（本書。authoring は `model` を省略するのを既定とするので、本書はここで離れる）。model を指定しなければ、subagent と同じ順で決まり、他に割り当てが無ければセッションのモデルになる（docs）。値はモデルの世代で変わるので、本書は初期値だけを置き、eval で決め直す。

| 役 | 求める性質 | 初期値（暫定） |
|---|---|---|
| 計画役 | グラフ全体を読んで方向を選ぶ判断 | 最上位のモデル。effort はそのモデルの既定（Fable 5.1 は `high`、Opus 5.5 は `medium`） |
| 実行役 | 1 件の意図をやり切る持続力 | 課題に合わせる（Fable 5.1 を `low` で使うときは下の表の行） |
| 事実の検証役 | 表面的でない確認 | 実行役と同等以上のモデル。生成と別の context |
| 完了の照合の検証役 | 受理済みの事実を目標に照らす | 事実の検証役と同じモデル設定。誤って通すと run が完了して止まるため（Opus 5.5 は完了の照合に別の小さいモデルを使う選択肢も挙げるが、本書はこの理由でその選択肢を採らない） |
| 回収役 | 記録から確認済みのものだけを拾う | 小さいモデル・`low` |
| 運搬役 | 判断せず逐語で写す | 最小のモデル・`low` |

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| effort はモデルをまたいで同じ思考量を指さない。モデルを変えたら測り直す | Opus 5.5・Fable 5.1 | 前のモデルの設定を持ち込み、費用だけが増えるか、質が落ちる |
| `xhigh` と `max` は、質の向上を測れた役にだけ使う | Opus 5.5 | 1 周が長くなり、出力のトークンが増える |
| Fable 5.1 を `low` で使う役では、検索や読み出しの道具を使う場面を prompt に書く | Fable 5.1（`low` では検索と読み出しの道具を呼ぶ回数が減る） | 実行役が調べずに答え、検証役に却下され続ける |
| 実行役の prompt に「自分で検証せよ」「subagent で確かめよ」を書かない。検証は script の構造（検証役の工程）で持つ | Opus 5（検証の指示は過剰な検証を招く。subagent で自分の作業を確かめさせない）・本書（検証役は script が起動するので、Fable 5 が長い run に勧める subagent による検証の指示は要らない） | 実行役と検証役が同じ確認を二重に行い、費用だけが増える |
| 各役の prompt には、指示と一緒にその理由（何のための成果か）を書く。強い言葉や細かい手順の列挙で縛らない | Fable 5（理由を渡すとよく働く。前のモデル向けの細かすぎる指示は質を落とす）・本書（強い言葉で縛らない）・GPT-6（Astra は指示とスキルに敏感なので、矛盾を点検する） | 指示の字面だけに従い、目的に合わない結果を返す |
| 実行役は、返す事実ごとに、それを示したツールの結果（パス・URL・コマンド）を添える | Fable 5（進捗の主張をツールの結果に照らすと、作り話の報告がほぼ無くなる） | 検証役が何を再取得すればよいか分からない |
| Codex で GPT-6 Astra を使うときは、実行役に「依頼から意図を推定して完了まで進める」と書き、ユーザーの指示がスキルより優先されると書く | GPT-6（Astra は、追加の入力で結果が大きく変わるときに確認を求めて止まりやすく、指示とスキルに影響されやすい） | 実行役が確認待ちで止まり、工程が欠ける |

## 権限

permission rules は workflow の全ての subagent に同じく効き、agent ごとには変えられない（docs：workflow が起こす subagent はあなたの permission rules を使う）。下の役ごとの制限は、この前提のうえで組む。

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| auto mode では、script が `agent()` に渡す prompt はユーザーの依頼として扱われない。スキルの側からは変えられない前提で組む | docs（Claude Code が script の計算した文として印を付ける） | 権限確認で agent が止まり、run が人間の応答を待つ |
| agent が使う道具の許可は、run の前にそろえる。スキルは、必要な許可を利用者向けに書く | docs（長い run で確認を避けるには、agent が要る道具を allow rules に入れる） | 長い run の途中で確認が出て、その間 run が進まない |
| 許可は、CLI、run のディレクトリへの作業ファイルの書き込み、実行役が課題に要る道具に絞る | 本書（状態を書くのは CLI だけなので、状態の置き場への直接の書き込みを許す必要が無い） | 許可が広すぎ、意図しない書き込みが確認なしで通る |
| 役ごとに制限し、状態を書けるのは運搬役の経路だけにする | 本書 | 実行役が CLI で事実を直接書き、検証を飛ばす |
| 対象に書き込まない役は、対象を書き換えられないようにする（作業ファイルへの記録は許す） | 本書 | 記録を書く実行役が対象まで書き換える |
| 役ごとの制限が配布先で実際に効くかを確かめる。確かめられない分は、残る危険として run の結果に書く | subagents（plugin から読み込む agent では、frontmatter の設定の一部が無視される） | 役ごとの制限が、配布先で黙って効かない |

## 探索グラフ

**定義**：グラフの要素は事実と意図の 2 つ（Cairn）。
- 事実：分かったこと。グラフの点。
- 意図：次に試す方向。根拠にした 1 つ以上の事実から出る矢印で、試した結果が事実になると、その事実につながる。

ヒントはグラフの外から足す（「停止・再開と人間の入力」。Cairn もヒントを事実グラフの外に置き、誰でも足せる）。

グラフは状態の文書で、agent を持たない。script が計画役・実行役・検証役などを起動し、各役はグラフを読む。書き込みは運搬役が CLI で行う（「状態の書き込み」）。

1 周の流れは下の図のとおり。検証役と回収役の工程は、Cairn と違う本書の作り方（Cairn は reason の自己判定で完了し、欠けた実行の回収は同じ session の続きで行う）。

**適用条件**（本書。4 つ全てを満たすときだけ。1 つでも欠けると、グラフは重いだけになる）：
- 出発点が分かっている
- 完了を判定できる（「目標の固定」ができている）
- 試すもの（項目・方向）の集合が、前の結果で変わる
- 分岐を並列に試す価値がある

満たさないときは、試すものの集合が結果で変わるので固定の形にも収まらず、Claude がターンごとに指揮する（「形の判定」の図）。

1 体の agent が 1 回で解ける課題は対象にしない。Cairn は最初に 1 体で全体を解かせる段（bootstrap）を持つが、本書は持たない。1 回で解けるなら、スキルの形にする理由が無いから。

```mermaid
flowchart TD
  A["目標の固定"] --> P["計画役: 要約とヒントを読み、前提が満たされた意図の全てを順位付きで・完了の主張・人間の入力が要る、のどれかを返す"]
  P -- 意図 --> X["未着手の意図を順位の順に、意図ごとに 実行 →（欠けたら回収）→ 検証（空振りは除く）→ 書き込み"]
  P -- 完了の主張 --> C["完了の照合: ① CLI が事実 ID の実在と数値条件を確かめる ② 事実の受理とは別の検証役が目標に照らす"]
  C -- 通った --> E["停止: 完了（理由と証拠）"]
  C -- 通らない --> RJ["却下を理由つきで記録"]
  RJ --> R
  X --> R{"周の終わり"}
  R -- "全件失敗が続いた" --> B["停止: BLOCKED（理由）"]
  R -- "乾き・反復の上限・却下の繰り返し" --> H["停止: 種類と理由、未着手と打ち切った意図を状態に書く"]
  R -- "新しい事実かヒントが増えた、または未着手の意図が 0 件" --> P
  R -- "未着手の意図が残る" --> X
  P -- 人間の入力が要る --> H
  P -. 失敗 .-> B
  C -. 失敗 .-> B
  H -. "必要なら人間が入力を足して再開" .-> P
  B -. "原因を直して再開" .-> P
```

新しい事実が出続ける限り、周の終わりで止まるのは反復の上限だけ。完了は周の終わりではなく、完了の照合（C）を通ってだけ起きる。

### 計画役

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| 最初の呼び出しと再開を除き、計画役を呼ぶのは、新しい事実かヒントが増えたか、未着手の意図が無くなったときだけ。意図が増えただけでは呼ばない | Cairn（事実かヒントの数が増えたか、結論の出ていない意図が無くなったときだけ reason を呼び直す） | 自分の出力に反応して空回りする |
| 空振りは新しい事実に数えない。ここで Cairn から離れる | Cairn（explore は空振りでも 1 件の事実を書き、事実の数の増加で reason が呼び直される）・本書（離れる理由） | 空振りに反応して計画役が空回りする |
| 同時に走る計画役は 1 体（Cairn の lease は、計画役を走らせる排他の権利と本書は読む） | Cairn（reason の lease はプロジェクトごとに 1 つ）・本書（理由） | 同じ方向の意図が重複する |
| 1 回に出す意図は、グラフの今の状態から、前提が満たされ、互いに独立で重ならないものの全て。件数は事前に決めず、グラフの必要に応じて増減する | Cairn（reason は重ならない方向を出す）・本書（一度に全て出すと周が減り、費用を抑えて精度を保てる見込み。無駄は前提の行と重ならない規則で防ぐ） | 出し惜しむと周が増える。重なると同じ作業に二重に費用を払う |
| 未着手の意図が無く、完了でもないなら、意図か「人間の入力が要る」を返す | Cairn（結論の出ていない意図が無ければ意図を返す。本書は周の終わりで全ての実行を待つので、そこでの「結論の出ていない意図」は未着手と同じ）・本書（人間の入力） | 誰も次の手を出さないまま止まる |
| 計画役の prompt に、課題の複雑さと出す意図の件数の目安を書く（上限ではない） | research system（初期は単純な問いに 50 体を起動する誤りがあった。単純な事実の確認は 1 体、複雑な調査は 10 体を超えることもある、という目安を prompt に入れた） | 単純な問いに意図を出しすぎる |
| 前の出力に依存する直列の手順は、前提が満たされた 1 手順だけを意図にする | 本書・ARTEX（依存のある手順の一覧を周をまたいで持ち、前提の事実がそろった次の手順だけを出す） | 前提の無い手順まで並列に出て、空振りが費用になる |
| 「見つからなかった」は結論にしない。証拠が薄ければ、同じ方向に、回数を限って再確認の意図を出す | 本書 | 1 回の空振りで方向ごと捨てられる |
| 意図には順位を付ける。計画役は呼ばれるたびに、残っている未着手の意図も含めて順位を付け直す | 本書 | 同時実行の上限（「体数と同時実行」）で待つ意図を、どの順で始めるかが決まらない。別の呼び出しで付けた順位どうしを比べられない |
| 完了をもう一度主張するときは、前の却下の理由と、それに答える事実の ID を挙げ、なぜ今度は足りるかを書く | 本書・Opus 5.5（完了の条件を別のモデルが照らし、満たさないときは理由を返して続けさせる） | 同じ根拠で主張と却下を往復する |
| 計画役に渡すのは、状態の要約（「状態の書き込み」）と、その周で読むヒントだけ。計画役がヒントを読む範囲は、渡された分に限る | 本書（Cairn は reason にも explore にもグラフのスナップショットを渡すので、ここで離れる） | 全量を渡すと、周ごとに context が膨らむ |

### 実行役・回収役・検証役

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| 実行役は意図を 1 件だけ受け取る。返すのはグラフに無い差分だけで、大きな出力はファイルに置いて参照を返す | Cairn | 既知の内容の繰り返しでグラフが膨らむ |
| 空振りも返し、空振りの印を付けて残す。その意図は未着手に戻さない（方向の扱いは「見つからなかった」の行） | Cairn（返す）・本書（印） | 残さないと、同じ方向が繰り返し出される。印が無いと、乾きの判定で新しい事実に数えられる |
| 空振りは検証役に通さず、受理の規則の外に置く | 本書（調べた範囲の外まで含めた「無かった」は、どの検証方式でも確かめられない） | 受理の規則に入れると、乾きの判定で新しい事実に数えられる |
| 対象に書き込む実行役は、試行ごとに作り直す隔離した写しで動かす。試行の中の再起動で写しに残った変更が、事実の検証を誤らせないようにする | docs（移行の例：各ファイルを隔離した写しで変換し、編集の衝突を避ける。stall して再起動した試行の変更は残る）・本書（その変更が写しに残るという読み） | 並列の実行役どうしの書き込みが衝突し、やり直しの試行が前の試行の変更の上に重なる。再起動の前の変更が、検証される事実に混ざる |
| 写しは統合しない。実行役が返すのは事実だけで、成果物への反映は探索グラフの外で、探索の結果を入力にした別の run として 1 本の流れで行う | Cognition 続報（書き込みは 1 本の流れに保ち、並列の agent は読み取りで知見を足す形が実際に機能している） | 並列の実行役どうしの書き込みが衝突する |
| 実行役は、確認できた事実を見つけるたびに、意図ごとの記録ファイル（作業ファイル）へ、検証方式と検証に要るものを添えて追記する | context（context の外にメモを書き、後で読み戻す）・本書（回収の材料にするため） | 実行が途中で欠けたとき、それまでに確認したことが全て失われる |
| 実行の工程が欠けたら、回収役が記録ファイルだけを読み、確認済みの事実の候補だけを返す。候補は通常どおり検証役に通す | Cairn（timeout と出力の解析失敗のあと、同じ session で確認済みのことだけを要約させる）・docs（stall からの再起動は前の試行の transcript を持たない）・本書（`agent()` は同じ session を続けられないので記録ファイルで代える） | 長く走った実行役の成果が、最後の失敗 1 回で全て捨てられる |
| 実行役の時間に上限を置く | docs（`agent()` に経過時間の上限を指定する記載は無い） | 実行役が終わらず、周の終わりがその 1 件に引きずられる |
| 意図ごとに `pipeline()` の 1 item として流し、工程の間で item を待たせない。待つのは周の終わりだけ。同時実行の上限（「体数と同時実行」）で待つ item は、枠が空くたびに始める | authoring（pipeline は stage の間に barrier が無い。上限を超えた呼び出しは枠が空くまで待つ） | 工程ごとに全件を待たせると、最も遅い 1 件に全体が引きずられる |
| 周の途中で意図は足さない | 本書（計画役は周の終わりの状態を読んで意図を出す。途中で足すと、何を走らせるかが実行の速さで変わる） | 同じ状態から始めた run が、走らせる意図の違う run になる |
| 事実は、生成側と別 context の検証役が、下の検証方式で確かめたものだけを受理する | 本書（生成した本人には自分の誤りが見えない）・MAST（検証が無い・誤る失敗が観測されている）・Fable 5（fresh な context の検証役は自己批判より良い）。Opus 5 は別立ての検証の段を足す旧来の足場を外すよう勧めるが、本書はここで離れ、上の理由と MAST の観測から段を残す（Opus 5 にも、書き手と検証役の組をうまく回せるという能力の記述はある） | 自己申告がそのまま状態になり、後の手順がそれを前提に動く |
| 完了の照合は図の C の 2 つの手順で行う | 本書・MAST（表面的な検証に留まる失敗と、目標に照らす検証の効果）・Cairn（reason の自己判定だけで完了する。本書はここで離れる） | LLM だけの判定で、表面的な確認のまま完了が通る |

**検証方式**（本書）：実行役は事実ごとに方式を 1 つ選び、検証に要るもの（パス・URL・コマンド）を添える。検証役は方式に応じて確かめる。

| 方式 | 使うとき | 検証役がすること |
|---|---|---|
| 再取得 | 対象を読み直せる（ファイル・ページ） | 同じ出所を読み直し、事実と照らす |
| 再実行 | 実行の結果（コマンドの出力・計測値） | 同じ条件で実行し直して照らす。費用が高すぎるときは検証不能にする |
| 出典照合 | 他者の主張を引く | 出典を開き、主張がそこに書かれているかを確かめる |
| 検証不能 | 時間で変わる、再現の費用が高すぎる | 受理しない。検証不能の印を付けて記録し、計画役の要約に載せる |

検証不能の事実は根拠の事実として意図から指せない。確かめていない事実を根拠にすると、その上に積んだ意図と事実が全て未検証のものに依存するから。計画役は、それを確かめる別の方式の意図を出すか、人間の入力が要ると返す。

### 停止

停止の種類は「停止・再開と人間の入力」。ここには探索グラフでの止め方を置く。

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| 反復の数に上限を置き、達したら止める | 本書 | 新しい事実が出続ける限り止まらない |
| 全件失敗が、計画役が方向を選び直した後も続いたら、BLOCKED で止める | 本書 | 失敗は乾きに数えないので、止めないと反復の上限まで回り続ける |
| 完了の主張の却下が、新しい事実の受理を挟まずに繰り返され、読まれていないヒントが無ければ、needs_input で止め、却下の理由を返す | 本書 | 主張と却下の往復が、反復の上限まで続く |
| 乾き停止は K 周連続の乾きで、読まれていないヒントが無いときに判定し、K ≥ 2 とする | authoring（Loop-until-dry：K 周続けて新しいものが無くなるまで回す）・docs（例：2 周続けて新しいものが無ければ止める）・本書（K ≥ 2） | K = 1 だと、再確認の意図が出る前に止まる |
| 却下した完了の主張は、照合で足りなかった点を理由として記録し、新しい事実に数えない。理由は次の計画役の要約に載せる | 本書・Opus 5.5（満たさない理由を返して続けさせる） | 計画役が何を足せばよいか分からず、同じ主張を繰り返す |
| 工程が欠けた意図は、事実を書かず、試行の回数を記録して未着手に戻す。1 件の欠けだけでは、乾きにも BLOCKED にもしない | Cairn（失敗した explore は何も書かず意図を解放する）・本書（試行の回数を状態に持たないと、再開で 0 に戻り、試行の上限が効かない）・docs（pipeline の中の失敗は null になり run は続く） | 1 件の欠測で run 全体が止まるか、欠けた意図が失われる |
| 同じ意図の試行の回数に上限を置き、上限まで欠けたら打ち切りの印を付け、理由とともに記録し、未着手から外す。打ち切りは次の計画役の要約に載せる | Opus 5.5（自動の続行は同じ課題で 2〜3 回までにして、詰まった run を止めて見直せるようにする。本書はこの目安を試行の回数に当てはめる）・docs（agent 単位では、stall した agent を runtime が最大 5 回まで再起動する） | 壊れ続ける 1 件の意図が、反復の上限まで再試行される |

## 状態の書き込み

探索グラフと資産台帳に共通する。

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| 状態を書くのは CLI だけ。script はファイルに触れないので、run の中の agent では、書き込みの CLI を呼ぶのは運搬役。他の役は CLI で状態を読めるが、書き込まない。人間によるヒントの追記は例外（「停止・再開と人間の入力」） | 本書（CLI だけ）・docs（script はファイルにも shell にも触れない） | agent がファイルを直接書くと、検査を通らない内容が状態に入る |
| 受理を決めるのは script。運搬役は、その決定を CLI に渡すだけにする | 本書（受理の判定を生成側に持たせないため）・docs（script はファイルに触れない） | 受理を agent が決めると、検証を飛ばした書き込みを止められない |
| CLI の出力（要約・件数・ID）を script へ運ぶ運搬役は、schema のフィールドに逐語で写すか、パスだけを渡す | 本書 | 運ぶ agent の言い換えが、原典から drift した写しになる |
| CLI は、状態にある ID と、その書き込み自身が作る ID だけを受け付ける | 本書 | 存在しないものを根拠にした結果が状態に入る |
| ID は、再実行しても同じものを指し、別のものを指さないように決める | 本書 | 再実行で ID が変わるか、別のものが同じ ID になる |
| 既知の事実かどうかと、同じ指摘かどうかは、CLI の決定的な照合（既知のキー・ID との一致）か、検証役の閉集合からの選択で決める。生成した agent の申告や自由記述では決めない | 本書（言い換えを新しいものと数えないため） | 言い換えただけの既知が新しいものに数えられ、乾きも重複除去も壊れる |
| 状態の全ての書き込みは冪等にする。runtime が agent を再起動して同じ書き込みを繰り返しても、状態が変わらないようにする | docs（stall した agent は同じ prompt で再起動される）・本書 | 再実行された書き込みが、事実を二重に足し、連続数を二重に進める |
| 既にあるものと食い違う書き込みは、黙って受け付けず BLOCKED にする | 本書 | 状態と、実際に試したものが黙って食い違う |
| 事実は足すだけで書き換えない。状態の変化（指摘の状態の遷移を含む）は、新しい記録として足す | Cairn（結論の出た意図は書き換えず、状態の変化は新しい事実として足す）・本書（指摘の遷移） | どの事実を根拠に何を決めたかを、後から辿れない |
| agent に渡すのは状態の要約だけにし、細部は ID で必要なときに引かせる | context（パスやリンクのような軽い識別子だけを持ち、必要なときに読み込む。context は有限の資源） | 全量を渡すと context が膨らみ、想起が落ちる |
| 要約は CLI が決定的に作る | 本書 | agent が要約すると、原典から drift した写しが混ざる |
| 要約の大きさに上限を置き、載せなかったものは要約の中で宣言する | 本書・authoring（No silent caps） | 載らなかったものが「無い」と読まれる |

## 資産台帳

**定義**（本書）：台帳は、資産と各 agent の結果との結び付きの一覧である。資産は、検証や探索の対象のうち、CLI が決定的に安定した ID を付けられる単位を指す（ファイル＋行範囲・要求 ID・情報源 URL など）。
- 主張のように、同じかどうかが意味の判定になる対象は資産にしない（CLI が ID を決められない）。
- 資産 ID は、台帳を作り直しても、変わっていない資産を同じものと識別できるように決める。
- 対象がファイルの行範囲なら、台帳は、根拠を行番号つきで 1 回だけ抜き出して各 agent に配る束の、各行範囲に ID を付けた形になる。
- 台帳は run の中で agent が共有する資産の層で、探索グラフはタスクごとの探索の層。2 つを分けて持つ（ARTEX も、探索のグラフと資産のグラフを分け、意図と事実を資産に結ぶ）。
- 台帳の寿命は 1 run（再開したときの扱いは「停止・再開と人間の入力」）。

**適用条件**（本書）：fan-out した結果について、どこまで見たかを宣言する必要があるとき（宣言しないと壊れることは、下の skip 一覧の行）。

| 例 | 資産 | 結び付ける結果 |
|---|---|---|
| review / audit | ファイル・節・行範囲 | 「見た」の結び付き。指摘と「確認済みで問題なし」は検証役の結果 |
| 要求文書・仕様書の作成 | 要求 ID・仕様 ID | 検証結果、追跡リンク |
| 情報源を辿る調査 | 情報源 URL | その情報源で受理・却下・検証不能になった主張 |

「状態の書き込み」の原則は、台帳にも全て当てはまる。そのうえで、「見た」という結び付きは検証を通さずに入れ、指摘と「確認済みで問題なし」は検証役の結果として結び付ける。「見た」はカバレッジを数えるための記録で正しさを示さないので、検証に費用を払う理由が無い。

| 原則 | 出所 | 守らないと壊れること |
|---|---|---|
| 資産の ID と、同じ資産かどうかの判定は、CLI だけが決定的に決める。agent は生の情報を返すだけにする | 本書・ARTEX（資産の親子関係と重複除去のキーはプログラムが計算し、agent は生の情報だけを出す） | agent が判定すると、同じ資産が別 ID になり、カバレッジも重複除去も壊れる |
| カバレッジ（結果が 1 件以上結び付いた資産の割合）は CLI が数え、結果が結び付かなかった資産の一覧（skip 一覧）を結果に載せる | authoring（No silent caps） | 見ていない箇所が「問題なし」と読まれる |
| カバレッジは「見た」ことしか示さない。正しさは検証役が別に持つ | redesignhealth | 網羅率の高さが正しさの証拠として読まれる |
| skip 一覧に残った資産だけを渡して、その資産を見る役（review では検証役、調査では実行役）を追加で起動する | redesignhealth（カバレッジに穴があれば reviewer を 1〜2 体足す）・本書（skip 一覧を渡す形） | 全体を回し直すと、見終えた資産にも費用を払い直す |
| 追加の起動を行うのは script | 本書（起動数を記録するため） | 何体走ったかの記録が残らない |
| 追加起動は、新しく見た資産が無くなった回で止め、残った skip 一覧を返す | 本書 | 毎回残る資産について、回り続ける |
| agent に渡す担当の単位は、ファイルではなく、一緒に読まないと判断できない範囲にする | redesignhealth（変更ファイルを順に読むのではなく、実行の流れを単位にする） | ファイル単位で切ると、ファイルをまたぐ検査が誰の担当にも入らない |
| 担当の範囲は、CLI の決定的な規則で作るか、抽出役（範囲を選ぶ agent）が閉集合（ファイル一覧など）から選ぶ | 本書 | LLM が自由に範囲を作ると、範囲が run ごとに変わる |
| 担当は script が割り当てる。得意な agent が自分から名乗り出る形にはしない | 本書（起動と同じく割り当ても script が持ち、起動数を記録するため） | 得意な資産に名乗り出が集まって費用が重なり、苦手な資産は毎回 skip 一覧に残る |
| 指摘の ID は、回をまたいで同じ指摘を同じものと数えられるように決める | 本書 | 回ごとに ID が変わると、同じ指摘が別物として数えられる |
| run の中で対象を書き換えてから、もう一度見る構成（until-pass の部品、固定集合の反復型など）のときだけ、対象の内容が変わったら古い結果を無効にし、指摘を resolved / regressed まで追う | redesignhealth（前回の指摘を新しい差分と照らし、resolved / regressed / still open に分ける。原文は review の回をまたぐが、本書は run の中だけに当て、run をまたぐ追跡は「水準と未決事項」に残す） | 書き換わる run で追わないと、直った指摘と再発した指摘を区別できない |
| 対象が書き換わらない run では、指摘の状態は open / dismissed だけを持つ | 本書 | resolved / regressed が決まらない状態として残る |
| agent どうしが互いの作業過程を検索する専用の仕組みは作らない。各 agent の出力を run のディレクトリにファイルで残す | 本書（ARTEX は worker が他の worker の作業過程を検索する仕組みを持つが、足りるかどうか確かめる前に作らない） | 足りるかどうか確かめる前に、仕組みの保守費用を払う |

## 水準と未決事項

本書が決めるのは原則と初期値まで。「（暫定）」の印を付けた規則と値、CLI の形とキー・ID の作り方は、最初の実装でテストとともに決め、本書へ書き戻す。

未決事項：
- Codex runner との互換：本書は fan-out の件数に上限を置かないので、起動前に体数の上限を計算できず、runner はこの fan-out を拒否する。runner でどう動かすかは決まっていない
- 指摘の状態を run をまたいで resolved / regressed まで追うか。ゲートつきの課題のように run が分かれる場合も含む
