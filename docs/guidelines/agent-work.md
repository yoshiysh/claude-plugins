# エージェントの作業

目的を満たす最小の成果を、検証できる範囲で完成させるための規約。配置・配布・実行は [repository-operations.md](repository-operations.md)、コード・テスト・文書の共通基準は [README.md](README.md) を参照する。

## 目的と範囲を固定する

作業の最初に目的・合格基準・やること/やらないこと（触ってよいファイルを含む）・必要な証拠を固定する。依頼文と現在の作業文脈で明確なら、それを使い、新しい計画・契約ファイルを必須にしない。反復する作業には有限の反復上限を定める。レビューのたびに要求と修正範囲を増やすと、元の目的から離れて収束しなくなるため。上限は作業に応じて作業文脈の一箇所に置き、単純な一手の作業に数値予算の質問を追加しない。

追加すること自体を目的にせず、目的を満たす最小の成果物を選ぶ。既存箇所の更新・削除・正本への参照で足りるかを先に考える。必要な契約や検証まで省けば目的を満たせないので、短さだけで判断しない。触る範囲の重複や古い案内は正本へ戻す小さな修正で整理し、無関係な大掃除へ広げない。

## 設計・実装・レビューを進める

「設計 → 設計レビュー → 実装 → 実装レビュー」の順に進める。必須欠陥が出たら指摘を直接直さず設計へ戻り、根本原因を除去して実装し直す。注意書き・監視・例外条項だけでは、読まれない経路で再発する。正本参照・scriptによる配達・型/スキーマで防げるなら構造を直し、防御コメントを削除する。機械化する規約は検査可能な不変条件を選び、失敗時に違反箇所・理由・直し方を返す。検査を増やすこと自体は目的にしない。構造で防げず注意書きだけが唯一のガードとなる場合は、理由を一行で残す。

要求・仕様・実装の全てに形式検証を掛ける。検証対象と性質に合う手法を選び、モデルとの対応・探索範囲・未検証部分を明記する。対象外とする性質には理由を示し、軽い文面検査や一部の成功で全体の合格を代用しない。

生成と検証を分離する。生成者は自分の成果物・修正へ合格判定を出さず、別の fresh context が検証する。修正差分も独立再検証を通す。検証は決定的テストと独立監査、PRレビュー（人間）が担う。

検証を単一視点にしない。ただし観点は目的と合格基準に必要なものだけを選び、固定の全観点を毎回回さない。agent・subagentへの引継ぎは次節に従い、観点はagent自身が持つものを利用する。呼ぶ側の観点だけを指定すると、呼ぶ側の死角も共有されるため。

## 子agentへ明示して引き継ぐ

起動する側は、各子agentのpromptに次のbriefを必ず渡す。AGENTSや親の会話を継承しても、必要な規約を読んだとは限らないため。

- 目的・合格条件、対象/対象外と所有ファイル。
- 役割と許可/禁止（生成・修正・採点・外部への作用・再委譲の範囲）。
- 適用する正本のパスと節、または版を固定した束の節IDと元path/行範囲。作業前に読むことを明示する。
- 返答に必要な証拠、読んだ参照、読めなかった参照と理由、範囲内/逸脱/未確認の状態。

明確な依頼文や既存文脈を使い、別の契約ファイルは必須にしない。正本本文を毎回写さず、必要な参照と読む指示を渡す。ファイルを開けない環境では必要な本文を機械的に渡し、出典と版を示す。読む外部正本がない機械的な役は、その理由と完結した手順をpromptに置く。

既存の構造化プロトコルでは、読んだ節・根拠・limitations・判定理由など対応する欄と範囲の集計を使う。未読を当該agentの成功へ変換しない。検証役の一票が不足しても、残る独立した有効票で既存の合格条件を満たす場合の集計成功は妨げない。

管理する呼出側のpromptと、既存の未読・範囲違反の拒否経路を検査する。promptへの配達や束のtoken一致は、全節の読了・理解・遵守の証明ではない。リポジトリ外のhostが持つ起動APIを一律に制御できるとは扱わない。

## 反復を収束させる

指摘は固定した合格基準・適用規則との関係と証拠で分類する。指摘数や文章量、全レビュー担当の永続的な満足を終了条件にしない。

| 指摘 | 扱い |
|---|---|
| 範囲内の必須欠陥 | 合格基準または適用規則への違反が確認できたもの。設計へ戻し、修正後に独立再検証する |
| 範囲外の問題・追加要求 | 現作業へ混ぜない。固定基準の達成を妨げる依存問題なら未達として必要な判断を求める |
| 任意の改善・根拠未確認 | 必須欠陥に数えない。追加確認は固定基準に必要なものに絞る |

進展は、未達基準への新しい検証証拠、または同じ原因の欠陥の解消で判断する。同じ欠陥が再発するか新しい証拠が増えない反復では、そのまま続けず原因と方法を見直す。範囲内の代替案を試す場合も残予算を消費し、上限を自動更新しない。

全合格基準の必要な証拠と独立検証が揃ったら完了する。予算が尽きた場合、または範囲内の方法では進められない場合は、未達基準・試した方法・必要な判断を報告する。予算や非進展を理由に範囲を無断で広げたり、基準を緩めたり、完了と宣言したりしない。契約変更が必要なら元の契約を未達として判断を求める。

必要な作業は完了まで実行し、分割やIssue化で先送りしない。人間ゲート（マージ・公開）や上記の未達報告を、完了扱いにしない。

## 役割と正本を構造で守る

一役割一責務をmulti-agentループの内外で適用する。司令塔（メインセッション）は段の選択・agentへのdispatch・返り値のそのままのrelay・承認後の機械的コピーだけを行い、成果物本文（コード・hook・文書）の生成・修正・採点をしない。小さな修正でもbuilderへ渡す。実装タスクの「直接実行」は実行前固定の実験契約を組まない意味であり、司令塔が本文を書く意味ではない。

各役割のやること/やらないことを明示し、ループの出口も役割境界に合わせる。段の選択は司令塔が行うが、変更後の再検証は選択に任せず部品側で強制する。自己申告だけで未検証の変更が成果物へ届く経路を作らないため。

同じ値・列挙・上限は二箇所へ書かず、named constantか単一文書を正本にして参照する。写しは更新時に食い違うため。

## 検証の入力と証拠を絞る

fan-outするWorkflowはagentごとにmodelとeffortを明示する。省略はセッションモデルの継承となり、体数分の消費になる。enum判定・機械的照合には小さいモデルと低effort、最上位モデルは司令塔と統合判断に使う。

同じコーパスを各体に冷読みさせず、抽出役が行番号つきevidence packを一度作り、各体は引用箇所を再読する。共有部分はpromptの先頭でprefixを揃える。上位モデルへの入力も必要なdiff・抜粋・ファイルへ絞る。

絞り込みは閉集合（行範囲・enum・ファイル単位のverdict）からの選択とし、本文はscriptが正本から逐語コピーする。安いモデルの要約・書き直しを写しの正本にしない。見なかったものは除外・skip・fail-openとして開示し、可能ならskipから無作為サンプルを精読して偽陰性を測る。未読を「問題なし」へ変えないため。

不在・網羅の断定（「無い」「全て」「のみ」）は、閉集合の全列挙・全文読み・形を変えた複数回の検索で裏付けるか、「検索した範囲では」のように手段で限定する。rename・削除のsweep後はcommit前に再検索し、残り0を確かめてから網羅を主張する。

## 最小の成果を同じファイルで育てる

規範・ルール・スキル指示は、何をするかと「守られないと何が壊れるか」を組にする。理由があれば初めての状況にも適用できる。不可逆操作や壊れやすい手順は自由度が低いので、正確な手順を省略しない。

作業中は同じファイルを更新する。draft-v1など成果物全文の版コピーや、編集のたびのcommitを義務にしない。独立したレビュー記録・検証証拠は別の責務として保持する。変更履歴はGit、理由はcommit message / PR本文に置く。コードの説明的コメントは避け、コードから読めない制約・根拠だけを簡潔に書く。コメントを増やすことは目的にしない。

後方互換性は不要。保存データ・入力形式のmigrationや旧形式サポートは書かず、構造で形式を検証し、合わない旧データは失敗させる。marketplaceのplugin version bumpは配布機構なので対象外。

納品のcommitを作ったら同じ作業単位のうちにremoteへpushする。ローカルや一時worktreeだけのcommitは清掃で失われるため。マージ・公開の人間ゲートは保持する。
