# テスト

仕様ごとの検証と、実装全体のコードカバレッジを併用する。仕様IDの対応は検証漏れ、コードカバレッジは未実行部分を見つける入口であり、どちらも assertion の妥当性を代わりに判定しない。

## ケースの設計

- **仕様の入力条件・結果・状態遷移から必要なケースを先に決める。** 実装の分岐だけを写すと、実装自体にない要求もテストから落ちる。
  検査: レビューで仕様とケース計画を照合。
- **正常・準正常・異常・境界の観点を仕様ごとに検討し、不適用なら理由を残す。** ケースのない観点が、不要なのか未検討なのかを区別する。
  検査: ケース計画の構造検査とレビュー。

| 観点 | ケースとして検討するもの |
|---|---|
| 正常 | 契約どおりの入力と期待する主要な結果 |
| 準正常 | 契約が許す部分成功・再試行・重複・回復などの経路 |
| 異常 | 不正入力・依存先の障害・拒否・中断と、残る状態 |
| 境界 | 空・最小・最大・直前直後・遷移の境目・順序の違い |

正常・準正常・異常は応答の観点、境界は入力や状態の観点であり、互いに排他的ではない。正常かつ境界を検証する一つのケースは、複数の観点へ対応付けてよく、同じ実行を複製しない。不適用理由が仕様に照らして妥当か、ケース集合が十分かはレビューで確かめる。

- **列挙できる条件は、各ケースの入力と期待値を持つパラメタライズドテストにする。** 同じ検査を複製せず、ケースの抜けを表として比較できるようにする。
  検査: レビュー、ケース単位の実行結果。
- **期待値は仕様から決め、検査対象の処理で作らない。** 実装と同じ誤りを期待値へ持ち込まないため。
  検査: レビュー、誤った出力を拒否する負例。
- **assertion は返り値に加え、契約上重要な状態・副作用・失敗も確かめる。** エラーを返していても、壊れた状態を保存している可能性がある。
  検査: レビュー、作用の境界を通る結合テスト。
- **mock は外部との境界に置き、内部の呼出しだけで成功としない。** 実際の接続・形式・終了状態の食い違いを見つける結合テストも必要になる。
  検査: レビュー、実際の入口からの正常・失敗テスト。

## 仕様との対応と完了

仕様の検証方法がレビューや実機確認なら、その証拠を扱い、自動テストへ無理に置き換えない。未着手・作成中の仕様を追加することと、実装完了を宣言することを区別する。

- **テストを仕様IDとケース計画へ結び付け、不存在の仕様IDを参照しない。** 名前の付いたテストだけを数えても、どの仕様の何を確かめたかは分からない。
  検査: トレーサビリティ検査、ケースと assertion のレビュー。
- **成功・失敗・skip・未実行を区別し、未計画の仕様も一覧へ残す。** 実行されなかったテストや採用前の仕様を分母から隠さないため。
  検査: トレーサビリティレポート、レビュー。
- **仕様先行の不足は報告し、完了宣言では必要な検証の不足を失敗にする。** 開発途中の追加を妨げず、未着手を残したまま完了したことにもさせない。
  検査: 通常検査と完了検査の結果、レビュー。

## コードカバレッジ

- **実装の対象範囲を列挙し、テストで読み込まれなかったソースも報告する。** 計測に現れたファイルだけを分母にすると、未実装・未実行の経路を見落とす。
  検査: カバレッジレポートと対象ファイル一覧の照合。
- **行・分岐・関数を別々に示し、計測不能や除外には理由を残す。** 行を通っても分岐や期待結果を検査しているとは限らない。
  検査: カバレッジレポート、レビュー。
- **下限や除外の変更を、機能変更から独立した根拠で説明する。** 数値を下げたり難しい対象を外したりして、検証の後退を隠さないため。
  検査: レビュー、設定と対象一覧の差分。

規約を強制する検査ツール自身にも、不存在ID・未実行・skip・不正な計画・未計測ソースなどを使った負例を設ける。検査の成功ではなく、誤った成果物を拒否できることを確かめる。

## 検査の入口

[トレーサビリティツール](../../scripts/traceability/README.md)を、仕様ID・ケース計画・テスト名の対応付け・出力の正本とする。対象と除外の具体値は同文書が案内する設定へ置く。

| 入口 | 用途 |
|---|---|
| `make test` | 既存の合否検査に加え、同じ Node テスト実行から対応状況とカバレッジを出す |
| `make traceability` | bp の仕様・ケース計画・テスト・実装を計測する |
| `make traceability-complete` | bp 全体の完了を検査し、未計画・未完了を残した完了を拒否する |

結果は `.artifacts/verification/` へ出る。通常検査の成功と、対象全体の完了は別である。未採用の仕様も未計画として全件を表示し、計画した部分の率と全体の未完了を併記する。完了検査は全体が検証済みになるまで成功しない。

この導入範囲では、ほかの検証方法の証拠を自動収集する機能は持たない。レビュー・実機確認などが必要な仕様を、計画から外して自動テスト完了と数えず、未完了として残す。
