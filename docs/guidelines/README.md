# ガイドライン

コード・テスト・文書を変更するときの共通基準。テストで振る舞いを確かめられる構造にし、仕様からの検証漏れと実装からの未実行部分を別々に見つける。

[AGENTS.md](../../AGENTS.md) の作業ルールと配布の制約はここに写さない。スキル固有の設計は同文書が参照する best-practices、個別機能の振る舞いは要求・仕様文書を正本とする。

| 文書 | 扱うもの |
|---|---|
| [JavaScript](javascript.md) | `.js`・`.mjs` の責務、副作用、非同期、CLI・Workflow の境界 |
| [テスト](testing.md) | ケース設計、仕様との対応、実行結果、コードカバレッジ |
| [文書](documentation.md) | 簡潔さ、正本、理由、変更経緯 |

## 規約の書き方と検査

規約は決まりと理由を組にし、検査方法を添える。機械検査がないものは「レビュー」と書き、機械で保証されるように見せない。lint・スキーマ・設定で決まる値や列挙は、その正本へ参照し、本文へ転記しない。

検証コマンドの入口は [Makefile](../../Makefile)、レビュー時に読むものは [REVIEW.md](../../REVIEW.md)。数値の改善だけで、仕様の実装漏れがなくなったとは判定しない。意味を確かめるレビューと機械検査を併用する。

## 共通の設計原則

- **入力の解釈・判断・外部への作用を分ける。** 条件の組合せを外部環境なしで試せ、障害の発生箇所を切り分けられるようにする。
  検査: レビュー、[テスト](testing.md)のケース設計。
- **一つの部品が持つ変更理由をそろえる。** CLI の表示変更で判断処理まで変わるなど、無関係な変更の波及を抑える。
  検査: レビュー。
- **依存先は必要な入出力の契約を通して使う。** 相手の内部状態や配置を知る部品が増えると、単独で検証・変更できなくなる。
  検査: レビュー。plugin 間の境界は AGENTS.md の規則に従う。
- **同じ知識を共有するときだけ共通化する。** DRY の正本規則は AGENTS.md に従い、見た目が似るだけで別々に変わる処理を一つの抽象へ押し込まない。
  検査: レビュー。
- **テストで観測する結果を入出力や状態遷移で表す。** 内部の呼出順だけを固定したテストは、正しい改稿を妨げても誤った結果を見逃す。
  検査: レビュー、期待結果を変えた負例。
