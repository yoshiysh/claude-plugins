# 要求文書: 形式手法による検証

## 表記と用語

要求の区分は、必須を「しなければならない」、禁止を「してはならない」、許容を「してもよい」で表す。

本文書では、形式手法を使った検証を支援するスキルを「formal-method」、検証を依頼する人又は別のスキルを「依頼元」、検証対象の文書・コード・処理などを「対象」と呼ぶ。formal-method が依頼を受けてから完了又は停止するまでの処理を「run」と呼ぶ。形式モデルは、対象の性質を形式手法の道具で調べるために記述したモデル又は命題である。

## 背景と課題

BP によるスキルの作成・評価、要求文書の作成及びその他の開発では、目標までの状態・条件・失敗や再開の経路が抜けると、後続作業で手戻りが生じる。形式手法を適用できる性質を洗い出して機械的に検証し、何を確認できたかを後から辿れるようにする共通の能力が必要である。

形式検証には計算や実行環境の準備に時間がかかる。検証の範囲を黙って狭めずに、独立した検査の並列実行及び実測に基づく改善を行える必要がある。

## 想定する利用者と利用場面

| 利用者 | 利用場面 |
|---|---|
| 文書やコードを設計する人 | 要求や実装の性質を検証し、反例と未確認の範囲を得る |
| BP・要求文書作成などの呼び出し元 | 対象と検証したい性質を渡し、検証の結果と根拠を後続の処理に使う |
| 実行結果を見直す人 | 過去の結果、前提、未検証及び性能の記録を辿り、改善する |

## どう使われるか

1. 依頼元は、対象と目標、既知の要求・条件及び検証したい範囲を渡す。
2. formal-method は、対象・目標・性質・起こり得る出来事と結果を整理し、形式化できる性質と未確認を区別する。
3. formal-method は、対象に適した手法と道具を選び、モデル・性質・前提と要求の対応を定める。
4. formal-method は、検証の範囲と実行の計画を定め、独立した検査を必要に応じて並列に実行する。
5. formal-method は、結果を独立に確認し、検証できた範囲・反例・未検証・記録への参照を返す。
6. 依頼元は、結果を読み、対象の修正や後続作業に使う。止まった場合は、報告された理由と未確認の範囲から次の対応を決める。

## スコープとスコープ外

スコープ: 形式検証の対象の整理、手法と道具の選択、モデル化、検証、結果の確認、記録と受け渡し。BP や要求文書作成以外の対象にも利用できる。

スコープ外: 対象の変更自体、BP や要求文書作成の代行、法令・規格への適合性認証。対象の変更は依頼元の責務であり、形式検証の結果だけで利用者の意図への適合や対象の実装との一致を断定しない。

## 前提と依存

- 設計原則と対象スキルが備える性質は `docs/design/skill-design-patterns.md` と `docs/requirements/bp-designed-skill.md` を正とする。formal-method 自身の作業記録に適用する共通要求は PR-FORMALMETHOD-015 に定める。
- TLA+・TLC、Alloy、Dafny、Lean は候補の例である。Rust を実行基盤の第一候補とし、Z3 等の SMT ソルバを検証器の第一候補として評価する。いずれも、対象の性質に合う手法・道具を選ぶための候補であり、特定の道具を全対象で必須にしない。
- 形式検証の結果は、対象とモデルの対応、定めた性質、仮定及び検査した範囲に依存する。要求を満たす条件及び検証器・実行環境の詳細は後続の仕様で定める。

本文書は将来の formal-method が備える能力とその受入条件を定める。以下の run の完了条件は、formal-method が対象を検証するときに適用する。本文書の作成完了に、将来のスキルの実装や全能力の実行を要求するものではない。

## 要求一覧

欠番: PR-FORMALMETHOD-013

各要求の箇条書きは、その能力の受入条件である。

### 依頼と対象

#### PR-FORMALMETHOD-001 依頼範囲を確定して受け付ける

- formal-method は、人又は別のスキルから、検証対象と目標を受け取れなければならない。また、依頼に含まれる対象、目標、既知の要求・制約及び検証範囲を区別しなければならない。また、BP や要求文書作成スキルから呼ばれなくても、依頼された対象を検証できなければならない。
- 検証対象又は目標を特定できないならば、formal-method は不足を報告して止まらなければならない。また、依頼の範囲外の対象や利用者が指定していない目標を、検証済みの対象として報告してはならない。

### 性質とモデル

#### PR-FORMALMETHOD-002 検証すべき性質を網羅する

- formal-method は、依頼された対象について、要求、目標、状態、入力、出力及び制約から、依頼された範囲で検証すべき性質を全て洗い出さなければならない。
- 形式化できない性質があるならば、formal-method は、その性質と理由及び形式検証を適用できなかったことを記録しなければならない。別の方法で確認する場合は、性質を整理した context を持たない検証者が確認した方法と結果を区別して記録し、確認できない場合は未確認と理由を記録しなければならない。

#### PR-FORMALMETHOD-003 状態遷移の欠落と到達可能性を調べる

- 状態遷移を検証するならば、formal-method は、対象となる状態と出来事、成功・失敗・中断・停止及び適用される人の入力・再開を整理しなければならない。状態・出来事・結果を閉じた集合として定めるならば、formal-method は、その集合の各組合せについて、許される遷移、明示的に禁止された遷移及び対応できていない組合せを形式モデルに照らして機械的に確認しなければならない。対応できていない組合せは未検証として報告しなければならない。
- 状態遷移のモデルを検証するならば、formal-method は、依頼範囲の目標と、必要な完了・停止・再開先への到達可能性を確認しなければならない。検証する経路と対象外にした経路及び理由を記録し、経路を閉じた集合として定めたならば、その各経路の終点又は再開先への到達可能性も確認しなければならない。確認できなかった到達可能性と理由は、未検証として報告しなければならない。

#### PR-FORMALMETHOD-004 要求とモデルの対応を確かめる

- formal-method は、検証対象の要求・目標と、形式モデル及び検証する性質の対応を記録しなければならない。また、要求・目標とモデル・性質の対応を照合し、対応しない項目を報告しなければならない。検証が必要な項目に対応がない場合、形式化できる性質は未検証として分類し、形式化できない性質は PR-FORMALMETHOD-002 に従って扱わなければならない。
- formal-method は、要求とモデル・性質との結び付きが要求の意味を表すかを、結び付きの有無の機械検査とは別に確認しなければならない。

#### PR-FORMALMETHOD-005 適した検証方法と保証の範囲を定める

- formal-method は、対象の性質、実行環境、検査できる範囲、得られる保証及び取得可能な準備・実行の時間と資源の情報に応じて、形式手法と道具を選ばなければならない。また、選んだ手法・道具と、選択した理由を記録しなければならない。
- formal-method は、形式モデルが扱う対象、状態、出来事、前提、制約及び扱わない範囲を記録しなければならない。また、検証する性質ごとに、検査する範囲と、範囲を有限にしたときの境界を示さなければならない。
- formal-method は、有限の範囲又は遷移数に限った検査と、無界の範囲について証明した性質を区別しなければならない。
- 進行性を検証するならば、formal-method は、進行に必要な環境・公平性の前提を記録しなければならない。

#### PR-FORMALMETHOD-006 モデルに対応する図を提供する

- 形式モデルから図を導出できるならば、formal-method は、対象の流れ又は関係を読める図を用意しなければならない。図を作成するならば、formal-method は、図とその正本となる形式モデルの対応を確認し、図が省いた条件を示さなければならない。

### 依存関係に基づく分割

#### PR-FORMALMETHOD-007 依存関係から分割候補を導出する

- formal-method は、形式化した変数・遷移・性質とその参照関係から、依存グラフを機械的に導出し、各要素と依存関係を元の形式モデルへ辿れるようにしなければならない。導出できない関係と理由は未確認として記録しなければならない。
- formal-method は、依存グラフから、内部の依存関係が強い要素のまとまりを分割候補として機械的に導出し、導出を再現できるよう、依存関係の強さを判定する基準と分割の条件をグラフ及び候補に対応付けて記録しなければならない。候補と採用する分割単位及び採否の理由を区別して記録し、候補を得たことだけで独立に検証できるとみなしてはならない。

#### PR-FORMALMETHOD-008 境界を保って部分の結果を合成する

- 検証を分割するならば、formal-method は、分割単位の間に残る依存関係を全て保持し、各関係に対応する境界の契約と、その契約を満たすことを確認する責任を記録しなければならない。
- 検証を分割するならば、formal-method は、各部分の検証結果から全体の性質が成り立つための条件を明示して検証しなければならない。部分が置く前提を他の部分又は環境が満たすか確認できない場合や、相互の前提だけで結論を支える場合は、全体を検証済みとしてはならない。
- formal-method は、分割前の要求・変数・遷移・性質・依存関係と分割後の各部分及び合成の条件の対応を機械的に照合し、未対応・除外とその理由を記録しなければならない。部分の検証成功だけで依頼範囲全体を検証済みとしてはならない。

#### PR-FORMALMETHOD-009 要求の不足を切り分けて依頼元に確認する

- 未対応の組合せ又は反例があるならば、formal-method は、対象の要求の不足、形式モデルの欠陥及び分類処理の欠陥を根拠に基づいて区別し、区別できないものは原因未確認として報告しなければならない。形式モデル又は分類処理の欠陥だけを根拠に要求の不足と断定してはならない。
- 対象の要求に判断が必要な不足があるならば、formal-method は、不足する判断、影響する性質又は遷移及び選択肢を依頼元に問い、回答前に要求を推測で埋めてはならない。回答が必要な検証は止め、問いと未確定の範囲を PR-FORMALMETHOD-015 に従って報告しなければならない。完了の判定も同要求に従わなければならない。

### 検証と結果

#### PR-FORMALMETHOD-010 適用可能な性質を検証して結果を返す

- formal-method は、依頼された対象で形式検証を適用できる性質を、選んだ手法と道具で検証しなければならない。
- formal-method は、性質ごとに、検証に成功した範囲、反例、未実行、検証器の unknown、時間切れ及び実行失敗を区別しなければならない。また、未実行、unknown、時間切れ又は実行失敗を、検証の成功として扱ってはならない。
- 反例を得たならば、formal-method は、その反例が示す性質と対象の要求・目標を辿れる形で返さなければならない。
- 対象の必要な検証を実行できないか、必要な性質を満たさないならば、formal-method はその run を停止し、対象と理由を報告しなければならない。
- formal-method は、形式モデルで検証できた性質を、対象との対応及び検査した前提・範囲を超えて保証してはならない。また、完了したならば、作成した形式モデル、要求との対応、検査した性質・前提・範囲、結果・反例及び未検証を、依頼元が参照できる形で返さなければならない。

#### PR-FORMALMETHOD-011 検証結果と検出能力を独立に確認する

- formal-method は、形式モデルと検証結果について、決定的な検査と、モデルを作成した context を持たない検証者による意味の確認を区別して行わなければならない。
- 検証する性質に違反する例又は変異を用意できるならば、formal-method は、それを用いて検査が予め期待した違反を検出できるか確認しなければならない。用意できない場合は、性質と理由を記録し、別の方法による検出能力の確認結果又は未検証を示さなければならない。

### 並列実行と性能

#### PR-FORMALMETHOD-012 検証を計画して並列に実行する

- formal-method は、検証の対象・性質・前提・範囲と、検査を分けて実行する場合の単位を記録しなければならない。
- formal-method は、独立して検査できる性質又は検査を、並列に実行できなければならない。
- formal-method は、計画した各検査の結果と実行されていない検査を区別して集約しなければならない。検査が途中で停止したならば、formal-method は、完了した範囲と未完了の範囲を報告しなければならない。

#### PR-FORMALMETHOD-014 保証を保って性能を測定し改善する

- formal-method は、後から性能を見直せるよう、実行環境で取得できた所要時間、CPU、メモリ及び費用の情報を記録し、取得できなかった情報を区別しなければならない。また、実行環境の準備、ビルド及び検査の時間を区別して記録しなければならない。性能を測定するならば、formal-method は、ローカル又は CI の区別を記録しなければならない。
- formal-method は、手法や道具の性能を比較するとき、対象の性質、検査範囲及び前提が一致していることを確認しなければならない。比較条件の一致を確認できないならば、formal-method は、その結果から手法や道具の性能の優劣を断定してはならない。
- formal-method は、取得できた性能の記録から問題を見直すとき、検査範囲と保証を保ったまま改善できる候補を検討し、その結果を記録しなければならない。また、性能を改善する変更を採用する前に、変更後も必要な検査の対象・前提・範囲及び結果の扱いが保たれているか確認しなければならない。保たれていないか確認できないならば、formal-method は、その変更を改善として採用してはならない。

### 記録と停止

#### PR-FORMALMETHOD-015 記録を保持して停止を報告する

- formal-method は、作業記録、証拠及び参照について、`docs/requirements/bp-designed-skill.md` の PR-BPDESIGNEDSKILL-028〜036・038〜040・042 に従わなければならない。
- formal-method は、完了前に止まったならば、止まった段と理由、確認済み・未確認の範囲、生成済みと未作成の成果物及び保存できなかった記録を区別して報告しなければならない。依頼範囲で必要な検証又は独立した意味の確認に、未対応・未実行・unknown・時間切れ・実行失敗又は未確認が残るか、必要な記録を保存できないならば、formal-method は run を完了と報告してはならない。
