# 要求文書: 依頼者から見た振る舞い

## 表記規約

本文書の要求文は次の語尾で区分する。

| 区分 | 語尾 | 対応する英語 |
|---|---|---|
| 必須 | 〜しなければならない | shall / MUST |
| 推奨 | 〜することが望ましい | should / SHOULD |
| 許容 | 〜してもよい | may / MAY |
| 禁止 | 〜してはならない | shall not / MUST NOT |

本文書では、要求文書と仕様書を生成する仕組み全体を「システム」と呼び、その生成を頼む人間を
「依頼者」と呼ぶ。

本文書は次の文書と同じ一式として生成される。相互に参照する記述は、この一式が揃っていることを
前提とする。

- `docs/requirements/INDEX.md`
- `docs/requirements/requester.md`（本文書）
- `docs/requirements/consumer.md`（生成された文書を読む AI から見た要求）
- `docs/specifications/INDEX.md`
- `docs/specifications/flow.md`（全体の制御）
- `docs/specifications/elicitation.md`（事前分析と問いかけ）
- `docs/specifications/authoring.md`（生成される文書の記述仕様）
- `docs/specifications/verification.md`（生成物の検査と改稿）

本文書が参照する他文書の識別子は、これらのファイルにある。

本文書が「下位 agent」と呼ぶ対象を `docs/specifications/flow.md` は「内部の処理単位」と呼び、
両者は同一の対象を指す。

本文書では、システムが依頼者へ問いを示して回答を待つ地点を「中断点」と呼ぶ。文書を保存した後に
システムが依頼者へ示す報告を「事後報告」と呼ぶ。裁定が下っていない論点について、裁定が下るまで
何をしてはならないかを定める規範文を「保持規則」と呼ぶ（引き渡す文書での書き方は
`docs/requirements/consumer.md` の PR-CONSUMER-033 が正である）。

## 背景と課題

依頼者は、要求文書と仕様書を自分で書く代わりに、システムに生成させたいと考えている。
このとき依頼者が困るのは次の 2 つである。

- 依頼文だけでは決まらない事項があり、そこをシステムに推測で埋められると、後で作り直しになる。
- 生成物がファイルとして書き込まれ、既存のファイルを上書きする経路がある。

依頼者が最終的に受け取りたいのは、開いている未確定事項が残っていない文書である
（根拠: 回答 Q1「着手を止める未確定事項（blocking TBD）が 0 件」＋ 回答（人間ゲート③）Q2
「開いている未確定事項が 1 件でもあれば「完成しました」と言わず残りの件数と ID を示す」）。

**依頼者が決めていない事項は、問い直しても決まらない。** 依頼者は、決まっていない旨を答えた
時点でその事項が「今は決めない」と決まった状態になることを選んでいる。これにより、着手を
止める未確定事項を 0 件にして完了することと、同じ問いを繰り返さないことが同時に成り立つ
（根拠: 回答（人間ゲート②）決定 A「『決めない』も決定として扱う」）。

聞き返しには上限があり、上限に達してもなお決まらない論点は残りうる。依頼者は、そうした論点を
未確定事項のまま引き渡すのではなく、保持規則に変えて本文に残し、裁定そのものは Issue の文案として
受け取ることを選んでいる（根拠: 回答（人間ゲート③）Q2「回答の無い論点も保持規則と Issue の文案に
変え」）。一方、直せていない記述の欠陥が残る文書は、決まらない論点ではなく文書の欠陥であるため、
依頼者は保存せずに止まることを選んでいる。論点は保持規則にし、欠陥は止めるという分け方により、
決まらない論点があっても完了できることと、欠陥のある文書が後続の作業へ流れないことが両立する
（根拠: 回答（人間ゲート③）Q1「直せていない指摘か検査できなかった箇所が残る稿は blocked で止めて
保存しない」）。

## 想定する利用者と利用場面

| 利用者 | 利用場面 |
|---|---|
| 依頼者（個人が一人で使う） | 要求文書と仕様書を用意する |
| 依頼者（事業案件で複数の関係者がいる） | 要求文書と仕様書を用意する |

（根拠: 前回回答「個人が一人で使う。ただしスキル自体は個人開発専用ではない（事業案件でも
使える前提）」）

生成された文書の一次の読み手は AI である。その読み手にとっての要求は本文書の対象外であり、
`docs/requirements/consumer.md` が扱う（根拠: 依頼文「主に AI が作業を行うことを想定している」）。

## どう使われるか

依頼者から見た典型的な流れは次のとおりである。

1. 依頼者が、何についての文書を作りたいかを依頼文として渡す。改訂したい既存の文書があるなら、
   その所在をあわせて示す。
2. システムが、決まっていない事項を決めないまま初稿を作り、初稿までに出た問いをまとめて依頼者へ
   尋ねる。
3. 依頼者が回答する。決まっていない事項には「決まっていない」と答える。
4. システムが、回答を当てて文書を書き直し、検査と改稿を行う。決まらない論点は保持規則にし、
   その裁定を求める Issue の文案を作る。
5. システムが文書を保存し、書き込んだ先と内容、保持規則と Issue の文案を事後報告として示す。
   依頼者は事後報告を見て保存を覆せる。
6. 依頼者が承認した Issue の文案を、システムが起票する。

（根拠: 回答（人間ゲート③）Q6「回答待ちの論点は決めずに初稿を書くので推測は入らず」＋
回答（人間ゲート③）Q5「保存先が git で戻せる限り止まらず、事後報告で覆す。」）

上の流れは、依頼が対象の範囲にあり、実行基盤が要求を満たしている場合のものである。
それ以外の場合の扱いは PR-REQUESTER-001・PR-REQUESTER-069・PR-REQUESTER-041・PR-REQUESTER-024 が
定める。

## スコープとスコープ外

### この文書が扱う範囲

依頼者から見たシステムの振る舞い。何を尋ねられ、何を承認し、どこで止まり、何を持ち帰れるか。

### システムが行わないこと

| 行わないこと | 根拠 |
|---|---|
| 既存コードの挙動説明（「この関数の仕様を教えて」）に応じること | 回答 Q5〜Q9 |
| 文書を伴わない実装・修正を行うこと | 回答 Q5〜Q9 |
| 規格への適合性評価・認証取得の支援を行うこと | 回答 Q5〜Q9 |
| 生成した文書に基づく実装そのものを行うこと | 回答 Q5〜Q9 |
| 要求・仕様の体裁を取らない一般ドキュメント（提案書・意思決定文書・README・ブログ・議事録の要約）を執筆すること | スキルの説明（description）「要求・仕様の体裁を取らない一般ドキュメントの執筆（提案書・意思決定文書・README・ブログ・議事録の要約）や設計判断の壁打ちにも発火しない」 |
| 設計判断の壁打ちに応じること | スキルの説明（description）「設計判断の壁打ちにも発火しない」 |
| システム自身の検証資産（evals・回帰テスト）を整えること | 回答 Q3 |
| システム自身の配布（plugin 化・marketplace 登録・ランタイム互換）を扱うこと | 回答 Q3 |

実行環境の制約（動作しないランタイムがあること）は行わないことではなく、システムが備える
振る舞いとして扱う（根拠: 回答 Q3）。

### この文書が扱わない範囲

生成された文書そのものの品質（後続の AI が戻りなく進めるための要求）は
`docs/requirements/consumer.md` が扱う。引き渡す文書に未確定事項と保持規則をどう記載するかも、
そちらの関心事である。

生成文書における人物の表記（実在の氏名・アカウント名を書かないこと、人物を役割名で書くこと）は
`docs/requirements/consumer.md` の PR-CONSUMER-028 が正である。本文書は同じ規律を要求として
持たない。

依頼者が事後報告を見て保存を覆したときにシステムがどう振る舞うかは
`docs/specifications/flow.md` が定める。

要求文書の分量をどの水準で決めるかは `docs/requirements/consumer.md` の PR-CONSUMER-030 が
正である。

聞き返しの回数・検査と改稿の反復の回数・やり直しの回数・応答を待つ時間の上限の値は、本文書の
要求として持たない。上限の値の正は実装の定数であり、`docs/specifications/flow.md` がそれを参照する
（根拠: 回答（人間ゲート③）Q3「script の定数と進展なしでの停止を正とし、文書は値を書き写さず
定数名で参照する」）。

### 判定に迷う場合の共通の扱い

本文書には、字句の一致では決まらない判定が複数ある。対象外の依頼かどうか、問いの中身が
変わったかどうか、応答が承認の意思を示すかどうかがそれに当たる。これらの判定は実行主体の
言語理解によって行われ、迷う場合の扱いは PR-REQUESTER-037・PR-REQUESTER-040・PR-REQUESTER-042 が
共通に定める。個別の要求文はこれらを参照し、迷う場合の扱いを重ねて持たない
（根拠: 回答（人間ゲート②）B「実行主体の言語理解に委ね、判定に迷う場合は同一・該当と
みなさず、依頼者に確認する」）。

#### PR-REQUESTER-037 判定に迷う場合に結論を定めない
実行主体の言語理解による判定に迷う場合、システムはその判定の結論を定めてはならない。
（根拠: 回答（人間ゲート②）B「判定に迷う場合は同一・該当とみなさず」）

#### PR-REQUESTER-040 判定に迷う場合に依頼者へ確認する
実行主体の言語理解による判定に迷う場合、システムは判定の対象を依頼者へ示して確認しなければ
ならない。
（根拠: 回答（人間ゲート②）B「判定に迷う場合は…依頼者に確認する」）

#### PR-REQUESTER-042 作成に入った後の確認を次の中断点の問いにする
文書の作成に入った後に判定に迷う場合、システムは PR-REQUESTER-040 の確認を、確認のためだけに
実行を止めて待つのではなく、次の中断点で示す問いとして依頼者へ示さなければならない。
（根拠: 回答（人間ゲート③）Q7「確認のための独立の待ち状態は作らず、推測で決めずに次のゲートの
問いとして聞く。」）

### 起動と対象の見極め

作成する文書の種別を依頼文の語から判定することは、目的から導いたものではなく依頼者が決めた
事項であるため、PR-REQUESTER-003 はその決定をそのまま要求として持つ。依頼者は、種別を尋ねる
問いを増やさずに依頼文だけで判定することを選んでいる（根拠: 回答（人間ゲート②）決定 C・D）。

#### PR-REQUESTER-001 対象外の依頼で作成に入らない
依頼文が、既存コードの挙動説明・文書を伴わない実装や修正・規格への適合性評価・生成文書に
基づく実装・要求や仕様の体裁を取らない一般ドキュメントの執筆・設計判断の壁打ちのいずれかを
求めているならば、システムは文書の作成に入ってはならない（依頼がこれらに当たるかどうかの判定は
実行主体の言語理解によって行われ、迷う場合の扱いは PR-REQUESTER-037 および PR-REQUESTER-040 が
定める）。
（根拠: 回答 Q5〜Q9 のスコープ外 4 項目 ＋ 回答（人間ゲート②）B ＋ スキルの説明（description）
「要求・仕様の体裁を取らない一般ドキュメントの執筆（提案書・意思決定文書・README・ブログ・議事録の
要約）や設計判断の壁打ちにも発火しない」）

#### PR-REQUESTER-069 空の依頼文と単語だけの依頼文で作成に入らない
依頼文が空であるか単語のみであるならば、システムは文書の作成に入ってはならない。
（根拠: スキルの説明（description）「空入力・単語のみの入力では作成に入らず、何の文書かを尋ねて
終了する」）

#### PR-REQUESTER-070 空の依頼文と単語だけの依頼文では何の文書かを尋ねる
依頼文が空であるか単語のみであるならば、システムは何についての文書を作るかを依頼者へ
尋ねなければならない。
（根拠: スキルの説明（description）「空入力・単語のみの入力では作成に入らず、何の文書かを尋ねて
終了する」）

#### PR-REQUESTER-003 作成する文書の種別を依頼文の語から判定する
依頼文を受け取ったとき、システムは作成する文書の種別を、次の対応に従って判定しなければ
ならない（PR-REQUESTER-069 に当たる依頼文は、この判定の対象にしない）。

| 依頼文に現れる語 | 作成する文書 |
|---|---|
| PRD / 要件定義 / 要件 / 要求 | 要求文書 |
| 仕様書 / spec / specification / 設計書 | 仕様書 |
| いずれの語も現れない、または双方の語が現れる | 要求文書と仕様書の両方 |

（根拠: 回答（人間ゲート②）D「この表を唯一の根拠とし、実行のたびに語を足さない」）

#### PR-REQUESTER-038 種別の判定に用いる語を足さない
システムは、PR-REQUESTER-003 の表が挙げる語以外を、種別の判定に用いてはならない。
（根拠: 回答（人間ゲート②）D「実行のたびに語を足さない」）

#### PR-REQUESTER-033 所在が示されなければ新規作成として扱う
依頼者が既存の文書の所在を示さなかったとき、システムはその依頼を新規作成として扱わなければ
ならない。
（根拠: 回答（人間ゲート②）決定 C「所在が示されていなければ新規作成として扱う」）

### 問いかけと回答

#### PR-REQUESTER-005 着手を止める論点を尋ねる
決まっていないと文書の作成に着手できない論点がある間、システムは
`docs/specifications/flow.md` が定める聞き返しの上限に達するまで、初稿の後の中断点を含めて、
その論点を依頼者へ尋ねなければならない（PR-REQUESTER-045 に当たる論点を除く）。
（根拠: 回答 Q1「着手を止める未確定事項（blocking TBD）が 0 件」＋ 回答（人間ゲート③）Q6
「回答後もなお着手できない事項は、聞ける回数の上限まで後のゲートで聞き直す。」）

#### PR-REQUESTER-007 同じ論点を繰り返し尋ねない
依頼者が既に回答した論点について、問いの中身が変わっていないならば、システムは同じ論点を
再度尋ねてはならない（ここで言う回答には決まっていない旨の回答を含む。問いの中身が変わった
かどうかの判定は実行主体の言語理解によって行われ、迷う場合の扱いは PR-REQUESTER-037 および
PR-REQUESTER-040 が定める。PR-REQUESTER-048 に当たる場合を除く）。
（根拠: 前回回答「再質問: 問いの中身が変わったときだけ行う」＋ 回答（人間ゲート②）B）

#### PR-REQUESTER-008 「分からない」と答える権利
依頼者が問いに対して決まっていない旨を答えたとき、システムは、問いの言い回しを変えて尋ね直す
場合を含め、同じ問いへの回答を改めて求めてはならない（PR-REQUESTER-048 に当たる場合を除く）。
（根拠: 回答（人間ゲート②）決定 A「同じ問いを繰り返さない」）

#### PR-REQUESTER-029 決まっていない旨の回答を着手不能から外す
依頼者が問いに対して決まっていない旨を答えたとき、システムはその事項を着手を止める未確定
事項として扱ってはならない。
（根拠: 回答（人間ゲート②）決定 A「依頼者が『決まっていない』と答えた時点で、その事項は
着手を止める未確定事項ではなくなる」）

#### PR-REQUESTER-009 未回答の事項を推測で埋めない
依頼者が回答していない事項がある間、システムはその事項を推測で埋めた記述を文書に
書いてはならない。
（根拠: 回答 Q9「依頼文・依頼者の回答・依頼者が所在を示した既存文書だけを根拠にする」）

#### PR-REQUESTER-048 回答の記録が欠けた問いを尋ね直す
依頼者の回答の記録が失われたか、回答の記録に問いへの回答の欄が無いならば、システムはその問いを
改めて依頼者へ尋ねなければならない。
（根拠: 回答（人間ゲート③）Q8「回答の記録が失われた・欠けた場合だけ再質問禁止の例外として同じ
問いを聞き直す。」）

#### PR-REQUESTER-049 空のまま渡された回答を尋ね直さない
依頼者が問いへの回答の欄を空のまま渡したならば、システムはその問いを改めて尋ねてはならない
（その問いの事項は未回答の事項として扱われ、PR-REQUESTER-009 と PR-REQUESTER-055 が適用される）。
（根拠: 回答（人間ゲート③）Q8「答えなかった問い（空の回答行）は未回答として進む。」）

#### PR-REQUESTER-050 検証に落ちた回答の反映を文書に書かない
依頼者の回答を当てた記述が、作成した者とは別の検証に落ちたままであるならば、システムはその
記述を文書に書いてはならない。
（根拠: 回答（人間ゲート③）Q8「依頼者の言葉と違う決定が検証を通らずに文書に入らない。」）

#### PR-REQUESTER-051 修正後も検証に落ちる裁定・問い・保持規則で止まる
論点の裁定・依頼者への問い・保持規則のいずれかが、修正の後も作成した者とは別の検証に落ちる
ならば、システムは文書の作成を完了せずに実行を止めなければならない。
（根拠: 回答（人間ゲート③）Q8「裁定・問い・保持規則が直しても検証に落ちれば止める。」）

### 保存と持ち帰り

本節は、未確定事項について 3 つの別の義務を置く。PR-REQUESTER-015 は、着手を止める未確定
事項の**内容**を依頼者へ示すことを求める。PR-REQUESTER-014 は、開いている未確定事項が残って

（根拠: 追加要求カテゴリ「下位 agent の失敗・タイムアウト・契約 JSON 違反時の再試行と
打ち切り、および部分成果の扱い」）

#### PR-REQUESTER-060 検査の結果を得られずに止めた実行を途中から続けられるようにする
検査を担う下位 agent から規定の形式の結果を得られずに実行を止めたとき、システムは、止めた段から
実行し直せる状態を保たなければならない。
（根拠: 回答（人間ゲート③）Q4「run は止まり、依頼者は next_args で同じ段から呼び直す。」）

#### PR-REQUESTER-061 途中から実行し直せるかを示す
文書の作成を完了できなかったならば、システムは、止めた段から実行し直せるか、最初からやり直す
必要があるかを依頼者へ示さなければならない。
（根拠: 回答（人間ゲート③）Q10「段から再実行できる停止（next_args あり）と最初からやり直す停止
（なし）を区別して書く。」）

## リスクと影響

本案件のドメイン分析 10 観点の判定を、根拠とともに全件置く。

| ID | 観点 | 判定 | 根拠 |
|---|---|---|---|
| RK-001 | 個人情報・機微情報の取扱い | 該当 | 回答「個人情報は検出しない。常に役割名へ置き換える」。生成文書中の人物表記の規律が入力から確定している |
| RK-002 | 不可逆な操作（削除・送信・課金・公開） | 該当 | 版管理で元に戻せる保存先へは承認を待たずにファイルを保存し、事後報告で覆せるようにする。版管理の外への保存と不変のものに触れる保存は承認を要する。既存文書を意図的に上書きする経路がある。Issue の起票はリポジトリの外から見える |
| RK-003 | 外部システム・第三者への提供・連携 | 該当 | 実行基盤に依存し、特定のランタイムでは動作しない。工程は多数の下位処理単位の呼び出しで構成され、応答が得られない場合の扱いが要る |
| RK-004 | 利用者の範囲 | 該当 | 個人が一人で使う場合と、複数の関係者がいる事業案件の双方が想定範囲に入る |
| RK-005 | 法令・業界規制・契約上の義務 | 非該当 | 回答 Q4「設計文書としてのみ使う。規制適合も監査記録も想定しない」 |
| RK-006 | 第三者監査・当局報告・社内統制 | 非該当 | 回答 Q4「実装・テスト設計の入力であり、監査記録は想定しない」。したがって承認の記録欄を置かない |
| RK-007 | 人の生命・身体・健康に影響しうるか | 非該当 | 成果物は Markdown 文書であり、機器制御・臨床判断・物理系への作用を含む記述が入力に無い |
