# 要求文書: create・update が作るスキルが備える性質

表記規約と用語は [bp-operations.md](bp-operations.md) に従う。本文書の「対象スキル」は create が作るスキルと update が作り直したスキルを指す。

## 背景と課題

利用者は、目的に必要な形を選び、生成者の自己評価に頼らず検証でき、中断しても根拠と作業を失わないスキルを得たい。create・update と review が同じ基準で判断できるよう、本文書は必要な能力・品質と上位の設計制約を定める。

## 想定する利用者と利用場面

- スキルを作る人は、create・update で設計方針に沿うスキルを得る。
- スキルを評価する人は、review のフローの観点で同じ基準による結果を得る。
- スキルを実行する人は、Claude Code・Codex で制限の実効性と未確認の範囲を知り、中断後も作業を続ける。

## どう使われるか

利用者の目的から必要な形と部品を選び、上位の設計制約に沿って作る。create・update は成果物を独立に検証して返し、review は同じ性質に照らして評価する。実行時には進み・判断・根拠を保存し、停止後の再開と後からの検証に用いる。

## スコープとスコープ外

対象は、対象スキルの設計方針への適合、形式検証、実行の記録、配布先での制限、起動数の上限と再開である。run をまたぐ指摘の状態の追跡は裁定の対象であり、裁定までの保持規則は bp-operations の PR-BPOPERATIONS-022 が定める。内部 CLI の操作名、状態の保存形式、ID の符号化など、依頼者または上位文書が指定しない実現方法は要求に含めない。

## 前提と依存

- [設計方針文書](../design/skill-design-patterns.md) は、形・部品・役割・状態更新・証拠・記録の上位制約の正本である。各要求が参照する節を適用し、本文書に記した裁定済みの例外を優先する。
- 配布先は Claude Code と Codex（Codex runner）である。host によって制限を確認・強制できる範囲が異なる。
- 外から観測する条件・結果と検証方法は [bp-conformance.md](../specifications/bp-conformance.md) などの BP 仕様が具体化する。

## 要求一覧

### 目的に合う形と設計制約

#### PR-BPDESIGNEDSKILL-001 必要な形と部品の選択
create・update は、設計方針文書の「形の判定」を軽い形から適用し、目的に必要な形と部品を選ばなければならない。ターンごとの指揮には Workflow script を持たせず、Workflow を持つ形は同節の部品で組み、資産台帳は同節の適用条件を満たす場合だけ持たせなければならない。資産台帳の有無は PR-BPDESIGNEDSKILL-029 の記録台帳を免除しない。重い構成を既定にして不要な探索や管理の費用を増やさないためである。

#### PR-BPDESIGNEDSKILL-002 重い形を選ぶ根拠
対象スキルは、固定集合の反復型または探索グラフ型を選ばせた条件を設計の説明に残さなければならない。run を分ける場合は該当する各 run の条件を残し、形が目的に必要かを後から判断できるようにしなければならない。

#### PR-BPDESIGNEDSKILL-006 目標の固定
対象スキルは、入口で設計方針文書「目標の固定」の原則に従い、最終的に確かめる成果物、範囲、禁止事項、数値条件と指示語の対象を固定しなければならない。手順を終えたことを目的の達成と取り違えないためである。

#### PR-BPDESIGNEDSKILL-007 停止・再開と人間の入力
Workflow を持つ対象スキルは、設計方針文書「停止・再開と人間の入力」に従い、人間の入力が必要な境界で止まり、判断材料と再開に必要な情報を返して続行できなければならない。中断を完了と扱わず、同じ作業を続けるためである。

#### PR-BPDESIGNEDSKILL-008 体数と同時実行
Workflow を持つ対象スキルは、設計方針文書「体数と同時実行」に従い、必要な項目を切り捨てず、同時実行を制限できなければならない。実行資源の制限と未処理の黙った除外を区別するためである。

#### PR-BPDESIGNEDSKILL-009 モデル・effort・prompt
Workflow を持つ対象スキルは、設計方針文書「モデル・effort・prompt」に従い、全ての役のモデルと effort を明示し、判断に必要な prompt を渡さなければならない。適合の判定ではモデル・effort の値自体、初期値の表、モデル変更時の effort の測り直し、xhigh・max を使える役の限定には照らしてはならない（依頼者の裁定）。prompt の内容の原則は適用する。

#### PR-BPDESIGNEDSKILL-010 権限
Workflow を持つ対象スキルは、設計方針文書「権限」に従い、役に許す操作と許さない操作を分けなければならない。生成・検証などの役割分離を権限の抜けで失わないためである。

#### PR-BPDESIGNEDSKILL-011 探索グラフと実行時間
探索グラフ型の対象スキルは、設計方針文書「探索グラフ」の原則を満たし、実行役の時間の上限を自ら決めて明示しなければならない。Codex runner ではその値で実行を制限し、Claude Code では強制できないことを run の結果に残さなければならない。値の明示だけを強制の証拠にしないためである。

#### PR-BPDESIGNEDSKILL-012 状態更新の信頼性
探索グラフまたは資産台帳を備える対象スキルは、設計方針文書「状態の書き込み」に従い、状態を検証して更新し、同じ更新の再送・競合・中断によって記録の意味が変わらないようにしなければならない。CLI だけが共有状態を更新すること、運搬、受理の分離、追記と決定的な照合は同節の上位制約とする。

#### PR-BPDESIGNEDSKILL-013 資産台帳
資産台帳を備える対象スキルは、設計方針文書「資産台帳」に従い、対象と結果を対応させ、確認した範囲と未確認の範囲を区別できなければならない。台帳の件数を判断の正しさの証拠にしてはならない。

#### PR-BPDESIGNEDSKILL-051 AI の自由な判断とその限界の説明
対象スキルは、設計方針文書「配置の原則」の AI の判断に渡す知識の層に置いた判断点と、硬い層へ置けない理由を設計の説明に残さなければならない。判断点が無い場合もそう示さなければならない。create・update と review は、列挙または不存在の記述と、判断点・理由の対応を機械で照合することだけで適合を判定し、最も硬い層か、理由の意味が妥当か、他の層にも理由があるかを適合の条件にしてはならない。照合範囲は create・update が設計の説明、review が対象スキルの全ファイルとする（依頼者の裁定）。列挙の網羅を機械では確認していないことを、create・update は残る危険、review は未検査として示さなければならない。

### 形式検証

#### PR-BPDESIGNEDSKILL-024 検証すべき性質の特定
create・update は、対象スキルの要求・状態・遷移・入出力・制約から検証すべき性質を洗い出し、形式化できない性質には理由と別の確認結果または未確認の理由を残さなければならない。形式化の難しさによって必要な確認が黙って落ちないためである。

#### PR-BPDESIGNEDSKILL-025 性質に応じた形式検証
create・update は、形式検証を適用できる性質を、その性質に必要な手法と道具で検証しなければならない。TLA+ や SMT は性質に応じた道具の例であり、一律に使わせるための指定ではない。

#### PR-BPDESIGNEDSKILL-026 検証の範囲と限界の説明
create・update は、形式検証の対象・手法・道具・前提・探索範囲・結果・未検証範囲と、形式化できない性質の確認を記録しなければならない。確認した範囲を超えて「検証済み」と読まれないためである。

#### PR-BPDESIGNEDSKILL-027 形式検証の失敗で停止
必要な形式検証を実行できないか性質が成り立たなかった場合、create・update はその run を止め、対象と理由を報告しなければならない。修正または環境の復旧と再検証は別の run で行ってよい。形式検証以外の書き直しは PR-BPOPERATIONS-011 に従う。

### 実行の記録と保持

#### PR-BPDESIGNEDSKILL-028 作業と判断の監査可能性
対象スキルは、run の各担当について、担当・段・対象・入力・実行内容・結果・根拠・失敗・未確認を後から辿れる記録を残さなければならない。段の境界が無い場合は段が無いと示し、どの入力と作業が判断を生んだかを特定できるようにしなければならない。

#### PR-BPDESIGNEDSKILL-029 記録と証拠への到達
対象スキルは、各 run の作業記録と証拠を実行環境に保存し、記録台帳から辿れるようにしなければならない。資産と指摘の対応を持つ資産台帳だけでは、この能力を満たしたことにしてはならない。各担当は共有の記録台帳へ直接書き込んではならない（上位の設計制約）。

#### PR-BPDESIGNEDSKILL-032 記録の正本
対象スキルは、同じ内容を複数の記録の正本にしてはならない。責務または対象で記録を分ける場合も、同じ内容が必要な箇所は正本を参照しなければならない。記録間の食い違いで判断の根拠が決まらなくなることを防ぐためである。

#### PR-BPDESIGNEDSKILL-034 記録と過去の判断の保持
対象スキルは、保存できた作業記録・証拠・記録台帳と過去の判断を、利用者が削除を指示するまで保持し、新しい run で更新しても過去へ辿れるようにしなければならない。

#### PR-BPDESIGNEDSKILL-035 保存失敗で停止
記録・証拠・記録台帳を保存できない場合、対象スキルは止まり、保存できたものを保持して、保存できなかった範囲と理由を報告しなければならない。この場合に完了と報告してはならない。

#### PR-BPDESIGNEDSKILL-036 性能を見直せる記録
対象スキルは、run ごとの所要時間・人の介入・再試行と取得できた費用を記録し、取得できなかった情報と区別しなければならない。後から実行条件と費用を比較するためである。

#### PR-BPDESIGNEDSKILL-040 記録に適用した文書規約
対象スキルは、作業記録に文書の一般規約を適用し、実行先でその正本を参照できるようにしなければならない。各 run で適用した版を不変の参照で特定できるようにし、後から同じ基準で読めるようにしなければならない。

### 配布先での制限

#### PR-BPDESIGNEDSKILL-014 役ごとの制限の実効性
create・update は、役ごとの制限が Claude Code と Codex で効くかを確認できなければならない。Claude Code では、設計方針文書が plugin agent で無視される frontmatter 設定を名前で挙げた記述を一覧として照合し、一覧の版が古くなる危険は受け入れる（依頼者の裁定）。文書を読めないか、その記述が無い場合だけ一覧を読めないと扱わなければならない。一覧を読めない場合、Claude Code の全ての役ごとの制限を未確認とし、その未確認だけで検証不合格としてはならない。

#### PR-BPDESIGNEDSKILL-015 確認できない制限の開示
create・update は、制限が配布先で効くかを確かめられなかった範囲と理由を、残る危険として検証の結果に示さなければならない。Claude Code の一覧に照らした制限を同 host の未確認として報告してはならない。Codex で確認できなかった範囲は別に示さなければならない。

#### PR-BPDESIGNEDSKILL-046 効かない制限の修正
create・update は、配布先で効かないと確認した制限を不適合とし、効く形に直すまで検証合格としてはならない。未確認の危険と既知の不適合を混同しないためである。

### 起動数の上限と再開

#### PR-BPDESIGNEDSKILL-016 起動数の上限の受け取りと遵守
fan-out を持つ対象スキルは、1 run の起動数の上限を入力として受け取り、その上限内で実行できなければならない。起動数には結果を返さなかった呼び出しも含めなければならない。

#### PR-BPDESIGNEDSKILL-019 未処理の保持と再開
起動数の上限で処理できない項目がある場合、対象スキルは、項目を順位付きの未着手として残して止まり、再開した run はその残りから続けなければならない。未処理を切り捨て、確認済みと読まれる結果にしてはならない。

#### PR-BPDESIGNEDSKILL-021 上限を渡さない場合
起動数の上限を渡さない場合、対象スキルは、fan-out の項目件数と 1 run の起動数に入力に依存しない固定上限を置いてはならない。同時実行・反復・周・試行の上限はこの制約に含めない。

#### PR-BPDESIGNEDSKILL-022 host に合う上限の受け渡し
fan-out を持つ対象スキルは、Codex runner では起動数の上限を渡し、Claude Code の native Workflow では渡してはならない。host が課す総起動数の制約を守り、上限が不要な host で対象を黙って切り詰めないためである。
