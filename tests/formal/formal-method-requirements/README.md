# formal-method の要求の形式検証

対象は要求文書 `docs/requirements/formal-method.md` である。仕様書（`docs/specifications/formal-method.md`）の判定の規則は `tests/formal/formal-method-spec/` のオラクルが扱い、ここでは扱わない。範囲は検証計画（`.agents/skills/formal-method/references/verification-plan.md` の「要求の形式検証の作り直し」）に従う。

## 実行

リポジトリの根で実行する。Z3 の実行体は環境変数 `Z3`（絶対 path）だけから読み、既定値は持たない。

```bash
Z3=/absolute/path/to/z3 python3 -I tests/formal/formal-method-requirements/check.py
```

- 1 ケースごとに JSON を 1 行、標準出力に出し、最後に集計の行を出す。期待と違うケースが 1 つでもあれば exit 1（仕様で決める点のケースは数えない）。
- 最初に `PRD.sha256` の指紋と、要求文書・仕様書の今の指紋を照合する。違えば、どの query も回さずに exit 1。
  - 指紋は、模型・性質・対応を確かめた上でだけ更新する。新しい要求に古い結果を流用しないためである。
  - 今の値は、未 commit の変更を含む作業ツリーの 2 文書から作った。
- CI では `verification.yml` の `formal-method-z3` job が、版と SHA-256 を固定した Linux の Z3 で走らせる。

## 何をどう確かめるか

要求の文 1 つを、名前付きの assert 1 つにする。名前は `PR<番号>_<箇条>` で、どの文かを示す。文の字面に無い読みは `I_` を頭に付けて分ける（下の表）。

各 query で、次を確かめる。

- **A**: 入力と整形の条件だけで sat。入力そのものが起こりうることを示す。
- **B**: 要求の規則を加えて sat。規則と入力が矛盾しないことを示す。
- **C**: 確かめたい命題を加えて、期待（`sat` か `unsat`）と一致する。
- **M**（変異）: 命題を支える規則を外すと、C の結果が反転する。規則を外しても通る、空虚な成功でないことを示す。

| 対象 | 性質 | query |
|---|---|---|
| PR-001・009・010・011・015 の完了・停止・報告の条件 | 条件どうしが矛盾せず、完了に到達できる入力がある | `R1_complete_reachable` |
| 同上 | 停止の条件（対象・目標の不足、反例、実行できない）と完了が重ならない | `R2_*` |
| 同上 | 未対応・未実行・unknown・時間切れ・実行失敗・未確認のどれか、意味の確認の未確認、記録の未保存、回答待ちの問いが残れば、完了と報告しない。未実行などを検証の成功にしない | `R3_*` |
| PR-003 の組合せの 3 区分 | 3 区分が閉じた集合を分割する（重ならず漏れない）。対応できていない組合せは未検証。許される遷移と禁止された遷移の重なり、未検証が残る run の完了は仕様で決める点（下の結果） | `R4_*` |
| PR-012 の途中の停止 | 計画した検査は、完了・未完了・未実行のどれか 1 つに入る | `R5_*` |
| PR-004 の対応の無い項目 | 形式化できる性質は未検証で成功にならず、形式化できない性質は PR-002 の扱い。2 つは重ならない | `R6_*` |
| PR-008 の合成の条件 | 前提を確認できない、相互の前提だけで支える、部分の成功だけ、の場合に全体が検証済みにならない。全体を検証済みにできる入力はある | `R7_*` |
| 全ての PR と SP・AC の対応 | 各 PR に SP と AC が 1 つ以上結び付き、仕様に無い番号・欠番を参照しない | `traceability`（決定的な照合） |

**解釈（`I_`）**

| 名前 | 読み | 理由 |
|---|---|---|
| `I_PR009_2b_answer_blocks_*` | 回答が必要な検証は、止めた結果として成功にならず、未実行か未確認として残る | 要求は「止め」「PR-015 に従う」とだけ書く。止めた検証が PR-015 のどの区分になるかを書かない |
| `I_PR010_cex_unsat_*`・`I_PR010_notrun_cannot_*` | 「必要な性質を満たさない」は反例、「必要な検証を実行できない」は未実行か実行失敗 | PR-010 の停止の条件を、同じ要求の区分の語に写す |
| `I_PR003_1b_unhandled_def_*` | 対応できていない組合せは、許される遷移でも明示的に禁止された遷移でもない組合せ | 要求は 3 つの区分を並べるだけで、関係を定めない |
| `I_PR012_3a_*` | 完了＝始めて終わった、未完了＝始めて終わっていない、未実行＝始めていない | PR-012 は区分の名前だけを書く |
| `I_PR004_unverified_not_success_*` | 「未検証」は検証の成功でない | 語の意味。要求は未検証と成功の関係を書かない |

**形式化しない要求**: PR-002・005・006・007・014。

- 理由: どれも、何を記録し区別するかという能力を述べる要求で、条件の組合せから判定や遷移を導く文を持たない（検証計画のとおり）。
- 例外として、PR-002 の未確認の記録は `R6_unmapped_nonformal_pr002` の入力の事実として現れる。PR-005 の進行性の前提は、ここでは扱わない。
- これらは、仕様の AC での確かめに委ねる。

## 結果（macOS arm64、Z3 5.3.3）

38 ケース（指紋 2、トレーサビリティ 1、query 35）。query のうち 33 は期待どおりで、2 つは「仕様で決める点」として一致・不一致に数えない（exit 0）。

**仕様で決める点**（依頼者の決定。要求文書は変えない）

| query | 結果 | 理由 |
|---|---|---|
| `R4_partition_allowed_forbidden` | sat（重なりうる） | 要求の文は、1 つの組合せが「許される遷移」と「明示的に禁止された遷移」の両方になることを禁じない。区分の決め方は仕様 SP-006 が定める |
| `R4_unhandled_not_complete` | sat（完了しうる） | PR-015 の列挙に「未検証」が無いので、対応できていない組合せが残る run が完了しないことは要求からは導けない。完了の条件は仕様 SP-015 が定める |

- この 2 つは、結果を JSON に `kind: "spec_decides"`・`match: null`・`reason` で残し、変異も回さない。
- 前の版にあった解釈 `I_PR015_unhandled_is_unmapped_*`（対応できていない組合せは PR-015 の未対応に当たる）は、要求の文に無い読みなので外した。

query の結論が何に依るかは、C の unsat core で分かる。各ケースの JSON の `rests_on_interpretation_only` が true のものは、要求の文（`PR` の規則）を 1 つも使わず、解釈（`I_`）と定義だけから導けた結論で、要求からの結論ではない。

| 依るもの | query |
|---|---|
| 要求の文だけ（と整形・入力） | `R2_*`（`R2_stop_excludes_complete_cex` を除く）、`R3_*`（`R3_question_not_complete` を除く）、`R4_unhandled_reported_unverified`、`R6_unmapped_formal_unverified`、`R6_unmapped_nonformal_pr002`、`R7_premise_unconfirmed`・`R7_mutual_only`・`R7_parts_only`・`R7_parts_only_unmapped` |
| 要求の文と解釈 | `R2_stop_excludes_complete_cex`（`I_PR010_cex_unsat_p1`）、`R3_question_not_complete`（`I_PR009_2b_*`）、`R6_unmapped_formal_not_success`（`I_PR004_unverified_not_success_*`） |
| 解釈と定義だけ | `R4_partition_cover`・`R4_partition_allowed_unhandled`・`R4_partition_forbidden_unhandled`（`I_PR003_1b_*`）、`R5_*`（`I_PR012_3a_*`）、`R6_unmapped_two_treatments_disjoint`（恒真） |
| sat（到達できる） | `R1_complete_reachable`、`R7_whole_reachable` |

- **2 つの経路**: 未実行・実行失敗が残る run が完了にならないことは、PR-015 と PR-010 の停止（実行できない）の 2 つの経路で導ける。片方の規則だけを外しても C は反転しないので、変異は 2 つを同時に外す。
- 完了に到達できること（`R1`）は、要求が完了の必要条件だけを書くので「許される」までを示す。十分条件は仕様の SP-015 が定める。

## 未検証の範囲

- 性質は 2 つ、組合せは 2 つ、検査は 2 つの記号で書いた。命題は性質・組合せ・検査ごとに独立なので、数を増やしても形は変わらない。
- 要求の文から assert への写しが文の意味を表すかは、機械では確かめていない。独立した読み手による確認が要る。
- `PRD.sha256` の一致は、要求の意味が模型に忠実なことの証明ではない。
