# BP 要求の形式モデル

`BP.tla` は `bp-designed-skill.md` と `bp-operations.md` の一部、および設計方針の停止・再開とヒントを手動で抽象化した TLA+ の状態機械である。TLC で、指定した有限範囲の到達状態、遷移上の安全性と公平性を前提とする進行性を調べる。PRD からモデルを自動生成するものではない。

## 状態遷移

次は TLC の到達状態グラフを `phase` に射影し、同じ始点・終点の遷移をまとめた図である。状態変数の違いや遷移のガードは省略している。`check.sh` は毎回 TLC の DOT 出力からこの図を Rust の `project_graph.rs` で導出し、以下と比較する。開始状態も DOT の初期ノードから読み、初期ノードの欠落・複数は拒否する。図には到達可能な実行時遷移だけが含まれ、破線の時間経過（stuttering）や変異は含まない。

```mermaid

    blocked --> blocked: AddHint, Delete, Repair, Report, RequestDelete, StopSave, StopSaveFail
    blocked --> planning: Resume
    done --> done: Delete, RequestDelete
    dry --> dry: AddHint, Delete, Repair, Report, RequestDelete, StopSave, StopSaveFail
    dry --> planning: Resume
    limit --> limit: AddHint, Delete, Repair, Report, RequestDelete, StopSave, StopSaveFail
    limit --> planning: Resume
    needs_input --> needs_input: AddHint, Answer, Delete, Report, RequestDelete, StopSave, StopSaveFail
    needs_input --> planning: Resume
    planning --> blocked: PlanFailed
    planning --> dry: DryStop
    planning --> limit: LimitStop
    planning --> needs_input: NeedsInput
    planning --> planning: AddHint, Delete, Deliver, DryRound, RequestDelete
    planning --> running: AcceptPlan
    running --> blocked: SaveFail, VerifyFail
    running --> done: Complete
    running --> limit: LimitStop
    running --> needs_input: NeedsInput
    running --> planning: ReplanForHint
    running --> running: AddHint, Delete, PartialSave, RequestDelete, SavePass, VerifyPass
```

- `planning`: 計画役が未読ヒントを受け取り、出力が CLI に受け付けられたときだけ既読にする。計画役が失敗した場合は未読に戻して停止する。新しいものが受理されない周（`DryRound`）が 2 周続き、未読・配達中のヒントがないときだけ乾きで止まる。周の連続数は計画の受理と再開で 0 に戻る。
- `running`: 検証と保存は順不同。部分保存後に保存が失敗する場合を含む。部分保存と全体の保存成功は別の状態である。保存に成功すると現在の run の記録が完全に保存済みになる。実行中に届いたヒントは計画段階に戻ってから受け付け、戻るときに検証と保存を未実施に戻し、現在の run を完全に保存済みの印から外す。保存した記録そのものは保持する。
- `blocked`: 失敗理由を記録し報告する。原因が解消され、報告済みで run の上限内なら、次の run は `planning` から始まり、検証と保存を再び未実施に戻す。停止中にもヒントを追加できる。ヒントだけで BLOCKED の原因が解決したとは扱わない。
- `dry`・`limit`: 乾き、反復上限による停止。報告後に、利用者側の再開操作を受けると次 run を計画から開始する。停止中にもヒントを追加できる。
- `needs_input`: 待たれる人間の回答が必要な停止。報告と回答の後、上限内なら次の run は計画から始まり、検証と保存を再び未実施に戻す。ヒントと回答は別の入力として扱う。
- `done`: 最後に受理された計画の後で検証と保存が成功し、未読・配達中のヒントがない。完了後はヒントを追加しない。保存済み記録の削除は利用者から指示された場合だけ行う。

停止した run の記録が部分保存を含め完全に保存できていなければ、停止状態で残りを保存するか、保存失敗として未保存範囲に加える。いずれかの結果を得てから停止理由・未保存範囲を報告する。未保存範囲は run 単位に、保存失敗の理由は `storage` の1種類に抽象化する。未保存範囲は後の run でも残り、減らない。元の停止理由とは別に報告した保存失敗理由を保持し、未保存範囲があるときの理由の欠落・誤りを検査する。

停止と理由の報告は有効な到達先であり、常に完了まで進むことは要求していない。停止後の原因解消や利用者の入力は外部環境の行動とし、自動的に起こるとは仮定しない。停止報告には元の停止理由、保存失敗理由と、run 番号の集合に抽象化した未保存範囲を載せ、一致を検証する。停止理由は停止中の状態に保持し、再開時にクリアする。過去の run の理由の本文と実際の記録の対応はこのモデルでは扱わない。

## 実行

TLC `v1.7.4` の `tla2tools.jar`、Java 11 以降、Rust (`rustc`)、`shasum` が必要。TLC は公式リリースから取得する。jar の SHA-256 は `check.sh` の `expected_jar` を正とする。

```bash
gh release download v1.7.4 --repo tlaplus/tlaplus --pattern tla2tools.jar --dir /path/to/tools
TLA2TOOLS=/path/to/tools/tla2tools.jar JAVA=/path/to/java RUSTC=/path/to/rustc tests/formal/bp-prd/check.sh
```

`JAVA` と `RUSTC` は省略すれば PATH の `java` と `rustc`。指定した jar の SHA-256 が違えば停止する。各検査の TLC 作業ディレクトリは repo 外の一時領域に置く。終了時と中断時に削除する。図の投影元である状態全体の DOT を保存するには、出力先の**絶対パス**を指定する。

```bash
TLC_DOT=/path/to/state-graph.dot TLA2TOOLS=/path/to/tools/tla2tools.jar tests/formal/bp-prd/check.sh
```

`TLC_DOT` の図は到達した状態変数の組を含むため大きい。Graphviz の `dot -Tsvg state-graph.dot -o state-graph.svg` で描画できる。README の射影は `project_graph.rs` の出力を囲みの内側に置き、`check.sh` の比較を通す。図だけを編集しても検査は通らない。

各検査は互いに独立した TLC の起動であり、`tlc_cases.sh` が並列に走らせる。同時に走らせる数は `TLC_JOBS` で指定し、既定は CPU 数（`getconf _NPROCESSORS_ONLN`）。正の整数以外（0 を含む）を指定すると jar を読む前に停止する。先頭の 0 は落として渡す。各 TLC は `-workers 1` で走る。TLC は標準 module を `java.io.tmpdir` に展開してそこから読み、終了時に消すので、各検査は spec と cfg の写し・`java.io.tmpdir`・metadir を自分だけの作業ディレクトリに持ち、並列の検査とファイルを共有しない。判定は全ての起動が終わってから宣言順に行い、出力の順序は並列数によらない。期待した終了コードと出力のメッセージが一致しない最初の検査で、その検査のラベルと TLC のログを出して非 0 で止まる。

`check.sh` は、`MaxRuns` が記録の型に反映されることも、3 run で記録を残す限定経路を使って検査する。主モデルの範囲は後述のとおりである。

### 対応する要求・設計の節の固定

モデルが対応する要求 2 文書と設計方針文書の節を `PRD.sections` に列挙し、節ごとの SHA-256 と照合する。各行は SHA-256、repo 内のパス、見出し行のタブ区切りである。節は見出し行から、同じかそれより上のレベルの次の見出しの直前までとし、コードフェンスの中の `#` で始まる行は見出しとして扱わない。見出しが文書に無いとき、複数あるときは停止する。一覧の外の節が変わっても照合は通る。

要求の「形式検証」「run の記録」の節は、導入文で設計方針の「機械で確かめる」「記録と改善」の節の原則を取り込むので、その 2 節も固定する（PR-BPDESIGNEDSKILL-007 が取り込む「停止・再開と人間の入力」と同じ扱い）。固定した設計の節の各行とモデルの対応は「固定した節の行ごとの対応」に名指しで書く。

照合に落ちると、`prd_sections.sh` が変わった文書・見出しと、再検証の手順、固定し直すコマンドを出して止まる。手順の正本はその出力であり、ハッシュだけを更新せずにその順に従う。

対応する節を増やすときは、`PRD.sections` に SHA-256 を 64 桁の `0` にした行を足す。照合はその行で落ちるので、出た手順に従って固定する。

`.github/workflows/verification.yml` の `formal-bp-prd` ジョブは、pull request では `PRD.sections` に載る文書、`tests/formal/bp-prd/` 配下、`verification.yml` のいずれかが変わったときだけ走る。変更ファイルとの照合は `prd_sections.sh affected` が行うので、文書の一覧は `PRD.sections` だけに書く。main への push と `workflow_dispatch` では常に走る。

## 性質と要求

| 性質 | 内容 | 対応 |
|---|---|---|
| `CompletionAfterChecksOfAcceptedPlan`・`CompleteRequiresVerifiedAndPersisted`・`CompleteHasCurrentRunRecord` | 最後に受理された計画の後で形式検証と現在の run の記録保存がともに成功するまで完了しない。再計画の前の成功は数えない | PR-BPDESIGNEDSKILL-025・027・035。記録は run 単位に丸め、028・029・039 の担当ごとの作業記録・記録台帳・保存先は区別しない |
| `RecordedPassHappened` | 記録された検証・保存の成功は、受理された計画の後に実際に成功したものに限る。失敗を成功として記録しない | PR-BPDESIGNEDSKILL-027・035 |
| `StopMatchesCause`・`VerificationFailureStops`・`SaveFailureStops`・`StopHasReason` | 計画役・形式検証・記録保存の失敗は BLOCKED、待たれる入力の不足は needs_input、乾き・反復上限はそれぞれの停止で止まり、起きた事象を停止理由として残す | PR-BPOPERATIONS-005・013、PR-BPDESIGNEDSKILL-027・035、設計方針「用語」「停止・再開と人間の入力」 |
| `StopReportHasRecordedOrMissing`・`ReportAccurate`・`SaveFailureReasonConsistent` | 停止報告は、停止した run の記録を保存できたか未保存範囲に入れたかが決まってから出す。報告の元の停止理由・保存失敗理由・未保存範囲は状態と一致し、未保存範囲があるときだけ保存失敗理由を持つ | PR-BPDESIGNEDSKILL-035・038 |
| `SavedOrMissingExclusive`・`StopReportReflectsCurrentSave` | 同じ run を保存済みと未保存範囲の両方に入れない。停止報告が保存済みとする記録は、最後に受理した計画以後の保存に基づく。再計画の前の保存を根拠に「未保存なし」と報告しない | PR-BPDESIGNEDSKILL-035・038 |
| `RetentionWithoutDeleteRequest` | 削除指示の前は、部分保存を含め保存できた記録を保持する | PR-BPDESIGNEDSKILL-034・035・038 |

| `RunningRequiresAcceptedPlan`・`HintReadOnlyAfterAccept`・`NoUnreadHintOnCompletion`・`ResumeOnlyAfterReportAndRepair`・`ResumeStartsNewRun` | 計画が CLI に受理されるまで実行段階へ進まない。ヒントは計画の受理の時点で既読にし、未読のヒントを残して完了しない。報告と原因解消の後で再開する。再開は前の run の記録と混ざらない新しい run として計画役から始まる | 設計方針「停止・再開と人間の入力」、PR-BPDESIGNEDSKILL-007、bp-operations の用語「run」 |
| `DryStopWithoutUnreadHint`・`WitnessDryAfterReadHint` | 未読・配達中のヒントが残っている間は乾きで止まらない。読んだヒントを未読と数えて乾き停止を拒むこともない（既読のヒントがある状態で乾き停止に到達する） | 設計方針「停止」の K ≥ 2 の行の後半、「停止・再開と人間の入力」の計画役が読んだヒントと停止の判定の未読ヒントを一致させる行 |
| `DryStopAfterTwoDryRounds` | 乾きで止まるのは、計画の受理または再開の後に乾きの周が 2 周続いたときだけ。再開した run は最初の周で乾きと判定しない | 設計方針「停止」の K ≥ 2 の行、「停止・再開と人間の入力」の再開した run がすぐに止まらない行 |
| `Progress`・`StopReported`・`ResumeProgress` | 後述の公平性の下で、稼働中の run はいずれ完了か停止へ到達し、停止理由はいずれ報告され、報告と修復が済んだ再開は計画へ進む | 設計方針「停止・再開と人間の入力」 |

記録に関する行（`CompletionAfterChecksOfAcceptedPlan` の行の記録保存、報告・保持の行）は、PR-BPOPERATIONS-051 により best-practices 自身の run にも同じ扱いが課される。モデルの run は対象スキルの run と best-practices の run を区別しない抽象なので、051 との対応はこの表の行の範囲に限る。051 が引く要求のうち表に無いものは「対象と限界」のとおり対象外である。

PR-BPOPERATIONS-010 の「検証」は 009 の生成と別の context による検証を指し、このモデルの `verification`（形式検証）とは別物なので、対応に含めない。PR-BPDESIGNEDSKILL-027 の、形式検証を実行できない場合と失敗した場合は、どちらも停止して報告する同じ扱いなので `VerifyFail` 1 つに抽象化する。検証の対象は 1 つにまとめ、報告の「失敗した対象」は停止理由 `verify` が示す形式検証という区分までで、対象ごとの名前は持たない。

`Spec` は通常の遷移と弱公平性を持つ。計画・再計画・検証・保存・完了・停止中の記録保存（成功または失敗）・停止報告・準備済みの再開が、実行可能なままなら、いずれ実行されると仮定する。乾きの周には公平性を置かない。停止中に利用者が入力することや、永久障害が自然に直ることは仮定しない。

### 補助変数と要求側の性質

`stopCause`・`passed`・`dryRoundsObserved` は、起きた事象を記録するだけの補助変数で、遷移のガードには使わない。`stopCause` は現在の run で停止の原因になった事象、`passed` は最後に受理した計画以後に成功した検証・保存（停止時の保存を含み、再計画と再開で空にする）、`dryRoundsObserved` は計画の受理または再開から数えた乾きの周を持つ。要求側の性質で確かめる変異は、遷移のガードか `phase`・`reason`・`verification`・`persistence`・`planAccepted`・`run`・`fullySaved`・`dryStreak` を変え、補助変数は変えない。このため上の表の性質は、遷移の書き方を写した `EventContract`・`OutcomeContract` を外しても、それらの変異を反例として返す。`check.sh` は、`OutcomeContract` で検出する変異のうち報告の内容を誤る 4 本を除く全てと、乾き・ヒントの 3 変異について、要求側の性質 1 本だけを検査に入れた TLC が反例を返すことを `requirement-side counterexample` の行で確かめる。報告の内容を誤る 4 本は `ReportAccurate` を検査する行で確かめる。

性質が空虚に成り立っていないことは、前件の状態への到達で確かめる。停止中でないときに足したヒントを読んだ後の完了（`WitnessCompleteAfterHint`）、再開した run の乾き停止（`WitnessDryInResumedRun`）、既読のヒントがある状態での乾き停止（`WitnessDryAfterReadHint`）は到達可能である。

## イベントの欠落検査

`EventContract` は各イベントの有効条件を遷移のガードから写して列挙し、条件を満たす到達状態では、そのイベントに対応する遷移が `Next` に含まれることを検査する。ガードの写しなので、要求から独立した仕様ではない。役割は、遷移を `Next` から除いた変異の検出器である。対象はヒント追加・配達・計画受理・計画失敗・入力待ち・乾きの周・乾き・反復上限・再計画・検証成功/失敗・部分保存・保存成功/失敗・完了・停止時の保存成功/失敗・停止報告・修復・回答・再開・削除指示・削除である。`check.sh` はそれぞれを `Next` から除いた変異に対して、同じ契約の反例を確認する。

`OutcomeContract` は各イベントの主要な事後条件を遷移から写したもので、遷移の結果を変えた変異の回帰検出器である。事後条件は主要な状態変数に限り、補助変数と書込みの完全なフレーム条件は含まない。結果の誤りを要求の側から捉えるのは前節の性質である。対象の変異は `check.sh` の `OutcomeContract` を検査するループが定める。

`NoUnspecifiedTransitions` は、定めたイベントのいずれにも該当しない遷移を禁止する。計画未受理のまま実行へ進む未定義の遷移を追加した変異が、この契約と `RunningRequiresAcceptedPlan` の両方で別々に検出されることを確かめる。

これは列挙したイベントとガードに限る。イベントの列挙や条件自体が PRD・設計から欠けている場合は検出できないため、設計の原文との照合が必要である。ガードに合わない入力の拒否応答もモデル化していない。

## 負例と到達可能性

`check.sh` は、検証失敗や保存失敗で止まらない、未検証・未保存のまま完了する、現在の run と異なる記録を保存したまま完了する、停止した run の記録を保存できたか未保存と報告したかを確認せず報告する、部分保存だけで完全保存と見なして報告する、部分保存済み記録の破棄、指示なしの削除、担当による台帳書き込みなどの変異が各不変条件の反例になることを確かめる。さらに、元の停止理由の誤り、保存失敗理由の誤り・省略や未保存範囲を欠いた報告、理由を持たない停止、未読のヒントを残した完了、保存失敗の理由を記録しない保存失敗、ヒントを CLI の受理前に既読にする変異、報告や修復を待たずに再開する変異を検出する。要求側の性質では、計画役の失敗を入力待ちに、入力待ちを BLOCKED に誤分類する変異、計画受理を記録しない変異、検証・保存の失敗を成功と記録する変異、再計画で検証・保存をやり直さない変異、再計画で保存済みの印を外さない変異、1 周の乾きで止まる変異、未読のヒントを残して乾きで止まる変異、乾きの連続数を再開に持ち越す変異、再開で run 番号を進めない変異を検出する。未保存範囲は最大2 run の run 番号集合に抽象化している。

BLOCKED・needs_input・乾き・反復上限で停止中に追加されたヒントを次の run で受け付ける状態、部分保存した run が保存に失敗して停止する状態、部分保存のまま入力待ちに移った後に残りの保存が成功または失敗して報告する両方の状態、2 run の記録を共に保持する状態、停止中でないときに足したヒントを読んだ後の完了、再開した run の乾き停止、既読のヒントがある状態での乾き停止が**到達可能**であることも確認する。ヒントの停止中追加・再開をそれぞれ無効化した変異では前者が、部分保存を除いた変異では部分保存した run の保存失敗が、既読のヒントでも乾き停止を拒む変異（`dry_blocks_read_hint`）では既読のヒントがある状態での乾き停止が到達不能になることを確認し、経路の欠落を空成功として扱わない。公平性を取り除いた検査は進行性の反例を返す。

## 対象と限界

- モデルは最大2 run・ヒント1件・記録2件に限定する。`deleteRequested` は対象ごとの削除指示を区別せず、指示後に作成した記録への効力も区別しない。
- 正常モデルの遷移規則には要求を織り込んでいる。結果はモデル内の性質についての確認であり、PRD からモデルへの翻訳の完全性、要求が利用者の意図を満たすこと、実装がモデルに従うことの証明ではない。
- 実際の通信、永続化、破損、並行実行、遅延した書き込み、失敗理由の具体的な内容や run ごとの詳細の対応、指示の認証、削除対象の粒度、形式化対象の洗い出しの網羅は検査していない。モデルに書かれていない出来事の欠落も自動では検出できない。ガードに合わない操作は遷移として無効であり、実装が明示的な拒否応答を返すことは検査していない。
- 再開時と、実行中のヒントで計画へ戻ったときは、検証・保存を常にやり直す安全側のモデルであり、依存条件が一致する結果の再利用はモデル化していない。各 run の保存は run 番号を単位として抽象化しており、担当や証拠ごとの保存は区別しない（PR-BPDESIGNEDSKILL-028 の担当ごとの記録は run 単位に丸める）。`fullySaved` は、最後に受理した計画以後に現在の run の記録を完全に保存したことを表し、再計画で現在の run を外す。再計画の後に止まったときは、停止時に保存し直すか未保存範囲に加える。
- このモデルの `verification` は形式検証を表す。形式検証が失敗した run は停止し、原因解消後に新しい run から再開する。PR-BPDESIGNEDSKILL-027 が許容する、別の run を開始してから原因を修正・復旧して再検証する経路はモデル化していない。PR-BPOPERATIONS-009〜012 の、生成と別の context での検証、それを通るまでの完了の扱い、書き直しと再検証、通らずに止まるときの返しもモデル化していない。
- 乾きの周は計画段階の自己遷移に抽象化し、周の中身（事実の受理・全件失敗・工程の欠け・検証不能）は持たない。新しいものの受理による連続の中断は計画の受理で代表させる。K は設計の下限の 2 に固定する。
- 次の要求は、記録・報告の内容や構造を扱い、run の停止・完了・保存の有無だけを持つこの状態遷移では表せないので対象外とする。
  - PR-BPDESIGNEDSKILL-024・037・041：検証すべき性質の洗い出し、形式化できない性質と理由の記録、別の方法での確認。洗い出しの網羅と記録の内容は状態に無い。
  - PR-BPDESIGNEDSKILL-026：形式検証の対象・手法・道具・前提・範囲・結果・未検証の範囲の記録。`verification` は結果の 3 値だけを持つ。
  - PR-BPDESIGNEDSKILL-031・032・033・040・042：作業記録の分割、正本の一意性、書き方、文書の一般規約の参照と版。記録の内部構造と書式を持たない。
  - PR-BPDESIGNEDSKILL-036：性能の見直しに使う所要時間・人の介入・再試行・費用の記録。これらの量を持たない。
  - PR-BPOPERATIONS-041：止まったときに報告する、書いたファイルの検証済み・未検証の範囲と止まった段。報告は停止理由・保存失敗理由・未保存範囲だけを持つ。
- 検証・保存・計画・報告自体の実行が永遠に拒まれる環境は進行性の前提外。TLC の到達状態の探索にはハッシュ衝突のごく小さな可能性がある。`CHECK_DEADLOCK FALSE` は停止・完了を有効な終端とするためで、停止後に外部入力なしで再開する保証を意味しない。

### 固定した節の行ごとの対応

`PRD.sections` が固定した要求の節の各要求は、ID を名指しして「性質と要求」の表か上の対象外の項に載せている（「形式検証」「run の記録」の節の 024〜042、PR-BPDESIGNEDSKILL-007、PR-BPOPERATIONS-005・009〜013・041・051）。設計方針と用語の節は、導入の文を除き、行ごとに次のとおり対応させる。行は冒頭の語句で示す。

| 節 | 行 | 対応 |
|---|---|---|
| 設計「用語」 | 反復（周）・CLI・needs_input・BLOCKED・ヒント・乾き | モデルの語として使う。周は `DryRound`、CLI は計画を受理する主体、needs_input・BLOCKED・乾きは停止の種類、ヒントは `hint` |
| 設計「用語」 | 項目・段・工程・形・部品・作業ファイル・空振り・試行・工程の欠け・全件失敗・未着手 | 対象外。モデルは段・工程・意図・試行を持たず、周の中身を抽象化している |
| 設計「停止・再開と人間の入力」 | next_args | 対象外。再開に渡す値の中身を持たず、再開は `Resume` 1 つ |
| 同 | 再開 | `ResumeStartsNewRun` |
| 同 | 停止の種類 | `StopMatchesCause`・`StopHasReason`。BLOCKED のうち全件失敗の連続による停止は対象外（周の中身を持たない） |
| 同 | 待たれる入力 | `NeedsInput` から報告・`Answer`・`Resume` へ進む経路。`StopMatchesCause`・`ResumeOnlyAfterReportAndRepair`・`WitnessNeedsInputResume` |

| 同 | 「needs_input で止めるときは、理由だけでなく、人間が判断に要る材料」 | 対象外（判断の材料を持たない） |

| 同 | 「ヒントの既読は、計画役が出力を返し、CLI がその書き込みを受け付けた時点で」 | `HintReadOnlyAfterAccept`（変異 `premature_hint_read`）。完了の主張の却下理由を記録することを受け付けに含める部分は対象外（完了の主張と却下を持たない） |
| 同 | 「完了した状態へのヒントの追記は、CLI が拒否する」 | `AddHint` は `done` で無効。完了後に追記できると `NoUnreadHintOnCompletion` が破れる |
| 同 | 「止めた run や途中で終わった run は relaunch せず」 | 新しい run としての再開は `ResumeStartsNewRun`。記録・未保存範囲・ヒントは再開をまたいで残る。受理済みの事実・試行の回数・打ち切りの再利用は対象外（事実・意図・試行を持たない） |
| 同 | 「前の run の遅れた書き込みが、新しい run の状態を変えない」 | 対象外（遅延した書き込みと並行実行を持たない） |
