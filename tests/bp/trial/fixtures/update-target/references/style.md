# リリースノートの規則

## 文体の規則

- 1 項目は 1 文で書き、文末は「〜した」「〜できるようになった」のように、利用者から見えた変化で終える。
- 内部の関数名・ファイル名・PR 番号を本文に書かない。PR 番号は項目の末尾の括弧にだけ書く（例: 「（#123）」）。
- 利用者が操作を変える必要がある項目は、文の後に「移行: 」で始まる 1 文を足し、何をどう変えるかを書く。
- 同じ機能への複数の PR は 1 項目にまとめ、括弧に全ての PR 番号を並べる。
- 否定の言い方（「〜できなくなった」）は、機能を取り除いた項目にだけ使う。

## 分類の規則

分類は次の 4 つだけとし、上から順に当てる。最初に当たった分類に入れる。

| 分類 | 当てる PR |
|---|---|
| 互換性のない変更 | 利用者が設定・呼び出し方・入力の形を変えないと、前と同じ結果が得られなくなる PR |
| 新機能 | 利用者が新しくできることが増えた PR |
| 修正 | 前のリリースで期待どおりに動かなかったことを直した PR |
| その他 | 上のどれにも当たらない PR（文書・内部の整理など） |

- 「その他」の項目はリリースノートに載せず、件数だけを末尾に書く（例: 「ほか 4 件の内部の変更」）。
- 1 つの PR が 2 つの分類に当たるときは、上の分類に入れる。
- 分類に迷ったときは、利用者に分類の候補 2 つを見せて選んでもらう。
