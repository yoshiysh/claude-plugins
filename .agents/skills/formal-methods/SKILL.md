# formal-methods（形式手法の適用設計と運用）

要求・仕様・実装の各層で、ミスが入り込まないことと、入ったミスが下流へ流れ出ないことを、
機械の検査で担保する範囲を設計し運用する。形式手法は全体に均一に広げるものではなく、
層ごとに「その層のミスが一番安く死ぬ検査」を選んで置く。

## 1. 目的と位置づけ

- 思想の正本は `docs/design/skill-design-patterns.md` の「機械で確かめる」の節である。
  このスキルは原則を複写せず、手順と判断基準だけを持つ（複写すると正本とずれたときに
  どちらが正か分からなくなるため）。
- 対象スキルへの要求としての正本は `docs/requirements/bp-designed-skill.md` の
  PR-BPDESIGNEDSKILL-024〜027・037・041 である。洗い出し・実施・記録・失敗時の扱いは
  この 6 件に帰着させる。
- このスキルが決めるのは「何を・どの範囲で・どの手法で形式化するか」と
  「形式化しなかった残りをどう扱うか」である。検証済みの範囲の外へ保証を広げない
  （範囲外まで「検証済み」と読まれると、残りの問題の居場所が見えなくなるため）。
- （未定：このスキルの実行形態。単独の手順として回すか、skill-creator-best-practices の
  create・update の段に組み込むか）

## 2. 対象の選定基準

形式化に向く対象（次の条件が重なるものを優先する）:

- 状態・遷移・入出力・制約として書き下せるもの。書き下す試み自体が、到達できない遷移や
  条件の重なりといった抜けを露出させる
- 順序・失敗・再開の交差など相互作用が濃いもの。標本のテストでは組み合わせを
  踏み尽くせない場所ほど全数探索の利得が大きい
- 下流への fan-out が大きいもの。要求 1 件のミスが仕様・実装・導出物へ増幅される場所は、
  上流で潰す費用対効果が最も高い
- 要求が安定しているもの。変わる前提の要求を網羅的に固めると、変更時に検証ごと捨てる
  費用が発生する

形式化に向かない対象:

- 状態を持たない文面・書式・内容の要求（報告の文面、文書の体裁、判断材料の中身など）。
  対象外として除外するのではなく、理由つきで記録し別の確認方法に回す
  （黙って外すと、形式化しなかったこと自体が後から追えなくなるため）
- 意味の妥当性そのものが問いのもの（目標が利用者の意図に合うか、観測が現実を十分に
  表すか）。機械の整合では決まらないので、レビュー等の別の層の担当にする

## 3. 手順の骨格

### 段 1: 検証すべき性質の洗い出し

- 対象の要求・状態・遷移・入出力・制約から、検証すべき性質を全て列挙する
  （PR-BPDESIGNEDSKILL-024）。洗い出しの漏れは後の全段で回復できないため、
  対象文書の節・項目を走査元にする。
- 件数・ID・カバレッジのように決定的に計算できるものは、性質として宣言し機械に数えさせる。
  agent の申告を数値の根拠にしない。

### 段 2: 形式化できる／できないの仕分け

- 洗い出した性質ごとに、形式化できるか否かを決める。
- できない性質は、その性質と理由を記録する（PR-BPDESIGNEDSKILL-037）。記録しないと、
  形式化の対象を選んだ理由が残らず、未対象が「存在しないもの」として扱われる。
- できない性質は別の方法で確認し、方法と結果を記録する。確認できない場合は未確認である
  ことと理由を記録する（PR-BPDESIGNEDSKILL-041）。

### 段 3: 抽象化の決定

- 何を丸めるかを明示する（例: データの中身を有無に丸める、失敗理由を区分に丸める、
  記録の単位を粗くする）。丸めたものはモデルに現れないため、段 8 の記録に残す。
- 有限範囲の切り方とその根拠を決める（要素数・反復回数・状態数の上限）。
  範囲の境界値そのものが仕様の下限・上限に当たる場合は、その旨を記録する
  （境界ちょうどでしか確かめていない性質は、範囲を広げたときの成否が別途の話になるため）。
- 前提と公平性の置き方を決める。環境の行動（利用者の入力、障害の回復など）を自動的に
  起こると仮定しない。進行性の性質は、どの遷移に公平性を置くかの宣言とセットにする。

### 段 4: モデル・仕様の作成

- 選んだ手法でモデルまたは形式仕様を書く。手法の候補と使い分けは設計方針文書
  「機械で確かめる」の「形式化の対象と手法」の表を参照する（このスキルには複写しない）。
- 既存のテストや eval のケースは、常時成り立つべき性質に変換できるものを性質として
  固定する（ケースの追加・削除で保証範囲が黙って変わらないようにするため）。

### 段 5: 忠実さの検証（モデルと対象文書の対応）

- 対象文書の節・項目と性質の対応表を作る。固定した節の各行は「対応する性質」か
  「対象外（理由つき）」のどちらかに名指しで割り当てる。対応表に載らない行を残さない
  （載らない行は、モデルの欠落か対象外の判断漏れか区別できないため）。
- 固定した節は、文書が変わったら照合が落ちる仕組みで固定する（節ごとのハッシュ照合など）。
  照合が落ちたら、ハッシュだけを更新せず、変わった節について段 1〜4 をやり直す
  （固定の更新だけで済ませると、文書変更がモデルへ伝播しないため）。
- 状態遷移を持つモデルは、到達状態の投影（状態図など）を機械的に導出して文書側の図と
  照合する。図だけを手で直しても照合が通らない形にする。
- イベント・遷移の列挙そのものの欠落は機械では検出できない。この限界を段 8 に記録し、
  原文との照合は人の確認として残す。

### 段 6: 検査の実施

- 段 4 で選んだ手法・道具で検査を実行する。閉じた有限の対象は全数列挙で確かめ、
  標本のテストで済ませない。
- 検査は再実行できる形（コマンド・設定・前提）で残す。再実行できない検査は、
  結果を後から検証できないため記録としての価値を持たない。

### 段 7: 検出力の確認

- 性質が飾りでなく効いていることを確かめる。意図的な変異（ガードの反転、遷移の削除、
  結果の誤記録など）を入れ、性質が反例を返すことを確認する。変異を検出できない性質は、
  成り立っているのではなく検査が届いていないものとして扱う。
- 性質が空虚に成り立っていないことを、前件の状態への到達可能性（witness）で確かめる。
  前件が到達不能な性質は、満たすべき場面がそもそも現れないため保証にならない。
- 遷移の欠落を検出する契約（イベントの有効条件と事後条件の写し）を置く場合は、
  それが対象文書から独立した仕様ではないことを明示する。写しは回帰検出器であり、
  結果の誤りを要求の側から捉える性質と二重にする。

### 段 8: 範囲と限界の記録

- 対象、手法、道具、前提、検証した範囲、結果、未検証の範囲を記録する
  （PR-BPDESIGNEDSKILL-026）。性質ごとに、性質・検査器・前提と範囲・機械では
  確かめられない残りを宣言する。
- 対象外にした要求・性質は、ID を名指しして理由とともに列挙する。
- 記録は「検証済み」を主張できる範囲の境界そのものである。記録に無い範囲は
  未検証として扱う。

### 段 9: 失敗時の扱い

- 必要な形式検証を実行できないか検証に失敗した場合は、その run を停止し、失敗した対象と
  理由を報告する（PR-BPDESIGNEDSKILL-027）。失敗したまま完了として扱わない。
- 修正と再検証は別の run で行う。同じ run の中で失敗を握りつぶして進めない。

## 4. 合成の規律

- 検証済みのブロックを組み合わせて全体を表す場合、ブロックは「環境への仮定」と
  「自分の保証」の契約でつなぐ。契約に書かれていない相互作用は、合成の保証に含めない。
- 状態を共有する継ぎ目では、状態の積が戻る前提で設計する。継ぎ目に当たる性質
  （共有する状態・返り値・順序についての性質）を名指しで列挙し、ブロック単体の
  検証とは別に確かめる（合成の費用は消えず継ぎ目へ移動するため）。
- 個別に検証したブロックの保証を、合成した全体の保証に読み替えない。
  全体について言えるのは、継ぎ目の性質まで確かめた範囲に限る。

## 5. 実例

- 唯一の実例は `tests/formal/bp-prd/`（BP 要求の形式モデル、TLA+/TLC）。
  段 5 の節の固定（`PRD.sections`）、性質と要求の対応表、段 7 の変異・負例・witness、
  イベント欠落検査、段 8 の「対象と限界」の書き方はこの実例から型を取っている。
- この実例が写しているのは PRD 全体ではない。`docs/requirements/bp-designed-skill.md` と
  `docs/requirements/bp-operations.md` の一部、および設計方針の節を固定した一覧の範囲であり、
  手で抽象化したもので自動生成ではない。ディレクトリ名の `bp-prd` は由来を示す通称であり、
  保証の範囲は README の「対象と限界」が正である。
- 実例の範囲: run の停止・再開、ヒントの配達と既読、記録の保存と停止報告。
  有限範囲は最大 2 run・ヒント 1 件・記録 2 件に切っている。

## 6. 取り込み候補

次は正本ではなく参照であり、候補であること、このスキルでの検証済みを意味しないことを
断ったうえで取り込みを検討する。

- 原子的な要求への分解、要求単位の肯定・否定テストの生成、テストと要求のトレーサビリティ、
  失敗を特定の要求へ帰属させての局所修正（VeriSpecGen、
  https://arxiv.org/abs/2604.10392 ）。段 5 の忠実さの検証に、対応表の人手照合に加えて
  要求単位の否定テストを持ち込む候補。ただし元の手法は参照実装をテストの正解の
  オラクルにしており、要求段階にはオラクルが無いため、整合性の確認への格下げが要る。
- 要求同士の衝突検出（NASA FRET の realizability 解析）。モデル化した範囲の外でも、
  要求の集合自体の矛盾を要求段階で検出する候補。

## 7. 停止条件と完了条件

停止条件:

- 段 9 のとおり、必要な形式検証が実行できないか失敗した場合は報告して止める。
- 段 5 の固定の照合が落ちた場合は、そのまま進めず固定し直しの手順に従う。
- 対象文書との対応で、モデルの欠落か文書側の誤りか判断が付かない項目が出た場合は、
  勝手にどちらかへ倒さず、判断が付かない項目として報告して止める。

完了条件:

- 段 1〜8 の記録が揃い、形式化した性質の検査結果と、形式化しなかった性質の
  理由・別の確認の結果（または未確認の記録）が残っていること。
- 対応表に未割り当ての行が無く、対象外が全て名指しで列挙されていること。

正常終了の変種:

- 段 2 の仕分けで形式化の対象が 1 件も無い場合は、「対象なし」とその内訳
  （向かない理由の記録）を残して正常終了する。形式手法を無理に適用しない
  （状態を持たない対象への適用は、保証の無い「検証済み」を生むだけであるため）。
