## 前提と依頼者の決定

依頼者の決定は次のとおり。下の各節に実現する場所を示す。

| 決定 | 実現する場所 |
|---|---|
| D1: 反例が出た後、又は回答を待つ問いがある間も、それと独立な検査は時間の上限内で最後まで続ける | [段と処理の順序](#段と処理の順序)、[時計と資源](#時計と資源)の scheduler |
| D2: 回答に依存しない検証も続ける | [段と処理の順序](#段と処理の順序)、[判定の集約](#判定の集約) |
| D4: 再開・再利用・道具の再実行は持たない | 構成の全体 |

D4 の「道具の再実行」は、失敗した検査を同じ run の中でもう一度動かすことと読む。そのため、検査の再試行の回数は持たない。

SP-012 が決定的な検査として求める「反例の再実行」は、反例を確かめる別の確認として残す（[段と処理の順序](#段と処理の順序)の実行の段）。依頼者はこの読みを確認した。

依頼者が確認事項に答えて決めたことは次のとおり。

- 文書の一般規約は同梱する。正本は `docs/guidelines/documentation.md` とする（[作業記録と記録台帳](#作業記録と記録台帳)）。
- 配布先は、今は Claude Code だけとする（依頼者の決定）。Codex での動作は未検証として記録し、公開のときに実測して扱いを決める（[未検証と限界](#未検証と限界)）。
- CPU とメモリの上限は持たない（要求と仕様の対象外。上限を守れるかが実行環境に依存するため）。
- 初回とキャッシュの区別は持たない。要求・仕様からは外した。

## 構成と役割

| 役割 | 実体 | 書いてよい場所 | 禁止 |
|---|---|---|---|
| 司令塔 | このスキルを読む session | 無し（CLI の出力を次の呼出しへ渡すだけ） | 成果物の本文・判定・状態を作る、直す、採点する |
| 決定的な処理 | `scripts/formal-method-cli.mjs` と `scripts/lib/`（Node）。run ごとに 1 つの background の `run-daemon` と、前景の client のコマンド | `run-daemon` は run の領域の全て。client は受け箱と依頼のファイルの排他作成だけ。salvage は salvage の印・結果・追補台帳だけ | 意味の判断（モデルの意味、原因の分類） |
| 作成役 | Workflow が起動する agent（抽出役・モデル作成役・分割作成役・計画作成役）。claim・query・submit で CLI と受け渡す | 自分の attempt の領域だけ | 自分の成果物を確認済みとする、道具を実行する |
| 独立検証者 | Workflow が起動する agent（抽出・形式化でない確認・忠実さ・合成の各検証者、原因の分類役）。claim・query・submit で CLI と受け渡す | 自分の attempt の領域だけ | 作成側の作業記録・会話を読む、成果物を直す |

**決めたこと: 判断のうち決定的に書けるものを全て CLI に置き、司令塔は中継だけにする。**

- 理由: 判断を自然文の手順に置くと、読む者ごとに実行が変わり、停止条件や期限の確認が漏れる（`docs/guidelines/agent-work.md`「役割と正本を構造で守る」、`skill-design-patterns.md` の最も硬い層に置く原則）。CLI に置けば、判断を単体テストと形式モデルで確かめられる。
- 退けた案: 1 つの Workflow script に run 全体を置き、決定的な処理を agent に CLI で実行させて結果を写させる。Workflow script はファイルを読めず process も起動できないので、決定的な結果が LLM の書き写しを経て制御に入る。写し間違いを検出できない。

**決めたこと: CLI の実装は Node とする。**

- 理由: 配布物の `.mjs` がそのまま動き、合否ゲート（`make test`）が `scripts/*.test.mjs` を実行する。
- 退けた案: Rust。子 process の制御とメモリの制限は Rust の方が強いが、利用者の環境で build が要り、build できない環境では run が始まらない。
- SP-007 の「実行基盤の候補に Rust を含める」は、性質ごとの道具の選択の記録として結果に出す（[結果の構造](#結果の構造)の `method`）。この選択とは別の事柄である。

**決めたこと: 独立検証者の役を、観点ごとに分ける。同じ観点の unit は 1 体に詰める。**

- 理由: SP-012 の意味の確認と SP-004 の別の方法による確認は、それぞれ別の資料を読む。1 体に全観点を持たせると、作成側の資料を読ませない境界を観点ごとに作れない。
- 同じ観点の unit（忠実さならモデルごと）は、1 体の資料の和集合のバイト数が `UNIT_MAX_BYTES` に収まる分を 1 体に詰める（[担当の起動](#担当の起動)の起動の理由）。観点の境界は守ったまま、体の数だけを減らす。
- 性質ごとの保証の観点は持たない。前提と保証の範囲のうち機械で決まる型（前提だけで結論が出る、性質が自明、範囲の変数が現れない、計画の欠け、変異が規則を変えない）は [静的な確認](#静的な確認) が決め、機械で決まらない型（節の役の付け方、保証の範囲が出所を超えないか、判断を要する項目）は忠実さの検証者がモデルごとに確かめる。
  - 理由: 前の稿では、保証の検証者を性質ごとに 1 体起動していた。性質 40 件で 40 体になり、どの体も同じ依頼・モデル・計画を読み直した。指摘の多くは機械で判定できる型だった。
  - SP-012 の「意味の確認は、全ての形式化した性質について、制約を規則・前提・否定に分けた付け方が出所と一致するかを含む」は、忠実さの検証者がモデルの全ての性質の節の役を照らすことで満たす。
- 退けた案 1: 検証者を 1 体にする。観点の境界が無くなる。
- 退けた案 2: 保証の検証者を、判断を要する項目だけを読む新しい確認役（confirmer）にする。判断を要する項目は節の付け方の判断で、節の役の照合と同じ資料（出所・モデル・query）を読む。別の体にすると同じ資料を 2 体が読み、判断を要する項目の無い性質では起動の理由が無い。形式化できない性質の確認（`nonformal`）は別の資料を読むので、保証の検証者の役（`assurance-reviewer`）はその観点だけに縮めて残した。

## 段と処理の順序

段は `docs/design/skill-design-patterns.md` の「用語」の定義（全ての項目を待ってから次へ進む区切り）に従う。

段の名前は作業記録の段の欄（PR-028）と停止の報告の段（SP-015）に同じ値で使い、値の正本は `artifact-formats.md` の `Stage` で、`scripts/lib/schemas.mjs` の `STAGES` はその写しである。

| 段 | CLI の決定的な処理 | 起動する担当（項目） | 次の段へ進む条件 |
|---|---|---|---|
| 受付 | 依頼の検査（SP-001）、保存先の確認、対象の取得と版の固定、文書規約の版の固定 | 無し | 依頼が受け付けられた |
| 洗い出し | 走査範囲・出所・引用の指紋の照合（coverage） | 抽出役（対象ごと） | 全ての対象の抽出を回収した |
| モデル化 | 対応表の照合、状態×出来事の組合せの分類、経路の照合、図の導出と突き合わせ、query の構文の検査 | モデル作成役（1 体） | モデルを回収して照合した |
| 計画 | 依存グラフと分割候補の導出、分割の照合、計画の照合、道具の候補表の作成（計画の `selection` から結果の `method` を作る。道具の名前と adapter の id の関係は `artifact-formats.md` の plan と mutations の「道具の名前」） | 分割と計画を順に担う 1 体（分割の担当は候補が 2 つ以上のときだけ。計画の担当は分割の担当が閉じた後の claim で返る） | 計画を照合した |
| 実行 | 道具の実行の全て（性質の検査、部分の契約の検査、合成の条件の検査、確認用の実行＝前提の整合・変異・反例の再実行・[静的な確認](#静的な確認)の節を切り取った実行）を、同じ同時実行の数と時間の上限の下で行う。その後、決定的な検査（SP-012。静的な確認を含む）を行い、断定できない節の付け方を判断を要する項目にする | 無し | 全ての検査が終わった、又は時間の上限に達した |
| 確認 | 確認の unit の組立てと詰め合わせ（観点ごとに `packByUnion`）、判断を要する項目の記録（モデルごと） | 抽出・形式化でない確認・忠実さ・合成の各独立検証者（観点ごとに、詰めた束 1 つにつき 1 体）、原因の分類役 1 体（反例・`対応できていない` 組合せ・作成役の問いの主題を束で取る） | 全ての unit と主題を回収した |
| 集約 | 判定の集約、完了の条件、性能の記録、結果・報告・作業記録・記録台帳の保存と再読込 | 無し | 結果を保存した、又は結果をその場で返した |

**順序の規則**

- 段は表の順に 1 度ずつ進む。戻るのは、同じ段の中の修正の巡（下記）だけである。
- 反例・問い・独立検証者の不合格を受け取っても、次の段へ進む（D1・D2）。止めるのは次の場合だけで、その場で[停止の手順](#停止の手順)へ移る。
  - 時間の上限に達した
  - 保存できない記録があった
  - 依頼を受け付けなかった
  - CLI の内部の誤り
- 問いに依存する性質（作成役が `blocked_by_question` に挙げたもの）は、挙げた段より後の段の対象から外す。挙げた段までに作った成果物は残す。
  - 抽出役が挙げた性質（`Inventory.properties[].blocked_by_question`）: モデル化と計画の対象から外す。モデル作成役の task の `context.property_ids` に入れないので、mapping の行を持たない。
  - モデル作成役が挙げた性質（`AuthorReturn.blocked_by_question`）: 計画の対象から外す。その性質の mapping の行は残り、形式化 の行は `check_ids` が空で `reason`（回答を待つ問いの id）を持つ。
  - 計画作成役が挙げた性質: その性質の検査を書かない。mapping の 形式化 の行は同じく `check_ids` が空で `reason` を持つ。
  - どの段で外しても、`depends_on_questions` に問いの id を持つ。その他の性質の処理は続ける（D2）。外した性質の判定は、[判定の集約](#判定の集約)で `未確認` になる（SP-011 の「回答を待つ問いに依存する」場合）。
- **修正の巡**: 作成役の成果物に機械の照合が欠陥を見つけたら、同じ段で同じ担当（同じ体・同じ task）に、欠陥の一覧を submit の応答で返して作り直させる。
  - 照合は submit ごとに流す。欠陥があり、提出の回数が `REVISE_ROUNDS_MAX` + 1 に達しておらず、欠陥が前の提出より減っていれば、`ok: false` と欠陥を返して出し直させる。そうでなければ、残った欠陥ごと受理する。
  - 理由: 新しい task を巡ごとに出すと、同じ資料を読み直す担当を巡の数だけ起動する。同じ体なら、読んだ資料と前の成果物を文脈に持ったまま直せる。
  - 退けた案: 巡ごとに新しい task を出す（前の稿）。起動の数と tokens が巡の数に比例する。
  - 上限は 2 巡（提出は `REVISE_ROUNDS_MAX` + 1 回まで）で、定数は `scripts/lib/schemas.mjs` に置く。
  - 前の提出の欠陥が 1 件も減らなければ、上限の前でも打ち切る。
  - 残った欠陥は、関係する性質の未検証・未確認の理由として結果に残す。止めずに次の段へ進む。欠陥の残った計画の要素は実行せず、結果の検査にも数えない（正本は `artifact-formats.md` の検査の節）。
  - 理由: 形の誤り（span の不一致、未定義の参照）は、作り直せば直ることが多い。上限を持たずに直させると収束しない（`agent-work.md`「反復を収束させる」）。
  - 退けた案 1: 欠陥で run を止める。D1・D2 の方針に反し、他の性質の検証まで失う。
  - 退けた案 2: 独立検証者の不合格でも作り直す。検査をやり直すことになり、D4 に反する。
- **原因の分類は、確認の段で、停止の前に行う。**
  - 対象は、反例・`対応できていない` 組合せ（SP-006）・作成役の問いの全てである。
  - 理由: SP-011 は反例と `対応できていない` 組合せの原因を結果に示すことを求め、AC-08 はそれを同じ結果の中で観測する。分類を別の run に回すと、同じ結果に原因が載らない（退けた案: 再開した run で分類する。再開は持たない、D4）。
  - 作成役の問いを分類役に通すのは、作成役が自分の欠陥を `要求の不足` に付け替えるのを防ぐためである（SP-011、AC-08）。分類が `要求の不足` でない問いは問いとして返さず、分類した原因を、その性質の `未確認` の理由にする。
- 独立検証者の unit は、分類役を含めて、確認の段でまとめて起動する。同時に起動する数の上限（`AGENT_BATCH_MAX`）を超える体は、順に次の呼び出しで起動する。
  - 理由: どの観点も検査の結果か固定した成果物だけを読むので、互いの結果を待たない。
  - 原因の分類役は、1 体が主題を束で取る。`claim` ごとに、残りの主題を並びの順に、束の資料の和集合のバイト数が上限に収まる所まで取る（next-fit。上限の初めは `UNIT_MAX_BYTES`）。束を取ったまま 1 件も出さずに呼び出しが閉じたら、その束は試行に数えずに手放し、次の呼び出しで、束の上限をその束の量の半分にして出し直す。1 件だけの束を出さなかったときは、その主題を `担当の失敗` にする。主題が残る間は呼び出しを開き直し、主題も上限も減らない呼び出しの後は打ち切る。
    - その呼び出しで 1 回以上 `submit` した分類役の後は、次の呼び出しの束の上限を `UNIT_MAX_BYTES` に戻す（出せる大きさだったので、半分にした上限を持ち越さない）。取ったまま出さなかった主題は、その呼び出しで手放す（`cli-contract.md` の閉じた呼び出しの担当）。
    - 理由: 束を抱えたまま期限に当たると、0 件の提出で全てを失う。同じ大きさの束を繰り返しても同じことが起きるので、束を小さくする（coverage-audit の束の上限の半減と同じ型）。
    - 終わることの根拠: 呼び出しごとに、残りの主題の数か束の上限のどちらかが減る。1 回以上 `submit` した呼び出しでは、提出した主題は受理か `担当の失敗` に決まって手放されないので、主題の数が 1 つ以上減る（上限は `UNIT_MAX_BYTES` に戻るが、主題の数は戻らない）。1 回も `submit` しなかった呼び出しでは、2 件以上の束なら上限が半分になり（主題の数は変わらない）、1 件だけの束ならその主題が `担当の失敗` に決まって主題の数が減る。どちらも減らない呼び出しの後は打ち切る。主題の数は有限で、同じ主題の数のまま上限は半分ずつしか減らないので、呼び出しの数は有限である。
  - 退けた案: 忠実さの確認をモデル化の直後に置く。不合格でも検査は続けるので（D1）、早く知っても止め方が変わらない。段が 1 つ増えるだけになる。

## 司令塔と CLI の分担

**決めたこと: run の状態を書くのは、run ごとに 1 つの background の process（`run-daemon`）だけにする。**

- `run-daemon` は、run の領域を作る時点から終わりまで、run の lock を持ち続ける。
- 前景のコマンドは client で、次のことしかしない。
  - lock を取らない、`state.json` を書かない。
  - 書くのは、受け箱（`inbox/`）と依頼（`requests/`）のファイルの排他作成だけである。
  - 読むのは `status.json` だけである。
- 段の進行・決定的な照合・検査の実行・集約・保存は、全て `run-daemon` が行う。
- 理由: lock を 1 つの process が最初から最後まで持てば、lock の引き渡しが無い。引き渡しの隙間に salvage が入って結果が 2 つできる経路が、構造として無くなる。
- 退けた案 1: 前景の `next` が段を進め、実行の段だけ background の `run-checks` に lock を引き渡す。引き渡しの手順（職務の記録の排他作成 → 受け手の lock → 完了の印）と、隙間の salvage の扱いが要る。守る手順と状態の組合せが増える。
- 退けた案 2: 前景の CLI だけで段を進める（前々の稿）。検査が長いと、ホストのコマンドの時間の上限で殺される（H5）。

**コマンド**

司令塔が呼ぶコマンドは次の 4 つで、担当が呼ぶコマンドは `claim`・`query`・`submit` の 3 つである。入力は依頼の項目（`start`）と、CLI が前に返した値だけである。依頼以外の入力の口は作らない（仕様の外部インタフェースと検証方法の節）。正本は `references/cli-contract.md` に置く。

| コマンド | 入力 | すること | 出力 |
|---|---|---|---|
| `start` | 依頼（SP-001 の項目）。作業ツリーは `start` を呼んだ process の現在のディレクトリとし、入力に含めない | 保存先の能力を確かめ（一時のディレクトリを作って書込みと fsync を試し、消す）、`run-daemon` を detach して起動し、[起動の手順](cli-contract.md#起動の手順)に従って待つ | `status`（下記）、又は `terminal` の結果（保存先に書けない、起動に失敗した、起動の途中で落ちた） |
| `close` | `run_dir`、`call_id`、`workflow_output_path`（又は `timed_out: true`） | 受け箱を「一時ファイル → link」で公開する（下記）。既にあれば何もせず `duplicate` を返す | `accepted` か `duplicate` |
| `wait` | `run_dir`、前に受け取った `status_seq` | `status.json` の `seq` が増えるか、`run-daemon` の終了を観測するまで、`CALL_MAX_MS` を上限に待つ | 新しい `status`、又は `still_waiting` |
| `salvage` | `run_dir` | [保存と排他](#保存と排他)の salvage の規則 | `terminal` |
| `claim`・`query`・`submit`（担当） | `run_dir`、`call_id`、`worker`（`query` は `task_id` と任意の `refs`） | 依頼を「一時ファイル → link」で公開し、`run-daemon` の応答を `WORKER_CALL_MAX_MS` まで待つ（[担当の起動](#担当の起動)） | `run-daemon` の応答 |

誤り（`ok: false`）の code と、どのコマンドがどの場合に返すかは、[CLI 契約の誤りと終了コード](cli-contract.md#誤りと終了コード) が正本である（`start` も、[起動の手順](cli-contract.md#起動の手順) の 5-1 で `E_BUSY` と `E_RESULT_UNREADABLE` を返す）。

`status.json` は `run-daemon` が rename で置き換える。持つ欄は次のとおり。

- `seq`
- `action`: `run_agents`（`call`: `call_id`・`args_path`・`deadline_wall_ms`・`workflow_script`）、`working`、`terminal`（結果）のいずれか
- `daemon`: 保持者の識別

`wait`・`salvage` が `run-daemon` の生死と終わりを判定するときに読むものは、`status.json` と `run.lock` の 2 つだけである。

- `status.json` の `action` が `terminal` になった。
- `run.lock` に書かれた保持者の process が終了したと観測した（[保存と排他](#保存と排他)の生死の判定）。
- `start` は、client がこの 2 つを読める状態（最終の名前の run の領域に `run.lock` がある）になるまで返らない（[起動の手順](cli-contract.md#起動の手順)）。そのため、`wait` が呼ばれる時点では `run.lock` が必ずある。

**起動の手順**（`start`。正本は `cli-contract.md`）

`start` は依頼を検査しない。依頼の検査・対象の取得・版と指紋の照合と一覧の保存は、全て `run-daemon` が同じ読み込みのバイト列で行う（照合と一覧の指紋の間に内容が変わる余地を無くすため。対象の写しは作らない。[対象の固定](#対象の固定)。受付で止めた run の記録も lock の下で保存できる）。`run-daemon` を起動せずに `start` が返す結果（保存先に書けない、起動の失敗、rename の前の crash）は保存せず、`run_dir: null`・`seq: 0` で返す。

`start` は `run_id` と nonce を決め、一時の領域に依頼を置き、引数として渡して `run-daemon` を detach で起動する。`run-daemon` の引数と標準入出力の扱いは `cli-contract.md` の呼び方と入力の口が正本である。自分が起動した process の pid と開始時刻を控え、その process の終了を親として観測する。次の順に評価する。

1. 起動そのものに失敗した（spawn の誤り）か、`run-daemon` が終わったと観測した。
   - 最終の名前の run の領域があれば、salvage と同じ規則で結果を作り、`terminal` で返す（rename の後、最初の `status.json` の前に落ちた場合）。
   - 無ければ、受付の段の `停止` の結果を、`start` 自身が標準出力の `terminal` で返す（起動の失敗、又は rename の前に落ちた場合）。理由は「`run-daemon` の起動に失敗した」で、`records.unsaved` に全ての記録を載せる。
2. 最終の名前の run の領域と `status.json` が現れたら、その `status` を返す。
3. `START_WAIT_MS`（`CALL_MAX_MS` − `CLEANUP_BUDGET_MS`）まで待っても 2 に当たらないとき:
   - 最終の名前の run の領域（`run.lock`）があれば、`action: working`、`status_seq: 0`、`run_dir` を返し、`wait` に任せる。`status.json` の `seq` は 1 から始まるので、`wait` は `seq` が 1 以上の `status.json` が現れたときに返る。`status.json` が遅いだけの `run-daemon` を落ちたものとみなさないためである。生死は、以後 `run.lock` で判定できる。
   - 最終の名前の run の領域が無ければ、`start` は自分が起動した process（pid と開始時刻が控えと一致するもの）の group を止め、終了を観測してから 1 に戻って評価し直す。
     - 終了を観測した後は rename が起きないので、run の領域の有無で返す結果が 1 つに決まる。
     - 止める前に rename が済んでいれば、1 の前半（salvage と同じ規則）になり、結果は 1 つのままである。
- **残った `.tmp-*`**: `start` は、自分が起動して終了を観測した process の一時の領域（`.tmp-<run_id>-<nonce>`。名前は `start` が決めたもの）だけを消す。
  - 他の `.tmp-*` は消さない。その process が生きているかを `start` は知らないからである。
  - `.tmp-*` は run の索引に載らず、run としても結果としても扱わない。
  - 消せなかったものは、結果の `unverified[]` に path と理由を書く。
- 理由: `start` は起動した process の識別を確実に知る唯一の者なので、起動の失敗と途中の crash は `start` が引き受ける。最終の名前の run の領域が現れた後は、`run.lock` で誰でも判定できる。
- 退けた案: `start` が起動したらすぐ返し、`wait` に `start` の控えた識別を渡す。client が生死の判定に読むものが 3 つに増える。

**1 回の呼出しの時間の上限**

- 前景の 1 回の呼出しは、定数 `CALL_MAX_MS` 以内に返す（定数の値と関係の正本は `cli-contract.md` の定数）。
  - 前景のコマンドが待つのは、`CALL_MAX_MS` − `CLEANUP_BUDGET_MS` までとする。残りは、待ち終えた後の処理（`start` の process の停止と終了の観測、salvage と同じ規則での結果の組立て、出力）に使う。`wait` は、待つ上限で `still_waiting` を返す。
  - この関係（`CLEANUP_BUDGET_MS` < `CALL_MAX_MS`）は `schemas.mjs` の unit で検査する。
- 不変条件: `CALL_MAX_MS` + `CALL_MARGIN_MS`（30000ms）≤ 司令塔がホストに指定するコマンドの timeout ≤ ホストの上限。`CALL_MARGIN_MS` が CLI の後始末と出力の時間を含むので、左の等号を許す。
  - Claude Code の Bash の上限は 600000ms である。
  - Codex のコマンドの上限は、`docs/guidelines/repository-operations.md` の「実行と環境」に記載が無い。確かめられていない。
  - この不変条件の左辺がホストの上限以下であることと、`WAIT_POLL_MS` < `CALL_MAX_MS` は、`schemas.mjs` の unit で検査する。
- 司令塔がホストに指定する timeout は、SKILL.md の [CLI の呼び方と timeout](../SKILL.md#cli-の呼び方と-timeout) が正本である。
- 長い処理（担当の呼び出しと検査）は、`run-daemon` と Workflow が background で行う。前景は待つだけである。

**司令塔の手順**: 正本は SKILL.md の [手順](../SKILL.md#手順)・[誤りと止まり方](../SKILL.md#誤りと止まり方)・[結果の提示](../SKILL.md#結果の提示) である。

**決めたこと: 担当の受理は submit の照合で決め、司令塔の close は呼び出しを閉じるだけにする。**

- `close` は、`inbox/.tmp-<nonce>` に内容を書いて fsync し、`inbox/<call_id>.json` へ link する。link が既にあれば失敗し、`duplicate` を返す。最後に一時ファイルを消す。
  - 理由: 排他作成してから書くと、書く途中の受け箱が見え、`run-daemon` が途中の内容を読む。link で公開すれば、見える受け箱は常に書き終えたものである。
- `run-daemon` は受け箱から Workflow の返り値（`{agents, tokens}`。ホストの完了通知の包みは外す）を読み、起動の記録と tokens だけを記録する。受け箱が読めない・`timed_out: true`・期限で閉じた場合も、submit で受理した担当はそのまま残る（条件と記録の正本は `cli-contract.md` の受け箱）。
  - 理由: 担当の成果物は submit ごとに照合して受理しているので、返り値の形で受理を覆す理由が無い。前の稿では、受け箱と Workflow の返り値の形が合わないと batch の全ての返り値を捨てていた。ホストの完了通知が返り値を包むと、期限内に書いた担当の成果物まで全て失われた。
  - 退けた案: 返り値の形で batch ごと拒否する（前の稿）。上の理由で退けた。
- `run-daemon` は、開いている呼び出しの `call_id` の受け箱だけを読む。
- 理由: 書く者が 1 つなので、書き手どうしの競合が起きず、それを防ぐ番号・所有札・lease が要らない。

## 担当の起動

- `run-daemon` は担当の呼び出しを 1 つ開くたびに、`calls/<call_id>/args.json`（Workflow の args）と `calls/<call_id>/tasks.json`（呼び出しの記録）を書き、`status.json` を `run_agents`（`call`）にする。
  - args は `{state, callId, stage, workers}` だけで、`workers` の行は `{id, role, model, effort}`。task・資料・前の担当の出力は args にも prompt にも載せない。担当が `claim` と `query` で CLI から引く。
  - 1 つの worker は 1 つ以上の task を持つ。行の `role` は、その worker の task の役を出てくる順に `+` でつないだもの（分割と計画なら `partition-author+plan-author`）。1 体の task の model・effort は同じでなければならない（違えば CLI の内部の誤り）。同時に起動する数は `AGENT_BATCH_MAX` 体までで、超える分は次の呼び出しにする。
  - worker に結ぶ task の決め方は 3 つある。
    - 作成役（抽出役・モデル作成役）: 1 体に 1 task。
    - 分割と計画: 1 体に 2 task。計画の task は分割の task に依存し、分割の task が閉じる（受理か失敗）まで `claim` に出さない。分割の結果は閉じた時点で `run-daemon` が受け取り、計画の task の資料と照合に使う。分割の task が閉じないまま呼び出しが閉じたら、計画の task は出さず `担当の失敗` にする。
    - 確認役: 観点ごとに、unit の並びのまま `packByUnion`（詰めた unit の資料の和集合のバイト数が `UNIT_MAX_BYTES` に収まる所まで前から詰める。next-fit）で束にし、束ごとに 1 体。観点をまたいで混ぜない。1 件で上限を超える unit は単独の束になる。原因の分類役は 1 体が束を順に取る（[段と処理の順序](#段と処理の順序)）。
    - 1 体の量は、その体の unit の `input_refs` が指すファイル（ディレクトリはその下の全て。範囲を渡す対象のファイルは渡す行だけ）の和集合のバイト数である。同じ束の unit が共有する資料（同じ行・inventory の写し・モデルなど）は 1 度だけ数える。理由: 1 体が読む量は和集合で、共有の資料を unit ごとに足すと、資料が大きい run で全ての unit が 1 体ずつに分かれる（autonoia の run 20261122T040551Z-ba04a7 では、確認の段が 11 体で、どの体も 1 unit だった）。
    - `claim` は、同じ応答で返す 2 つ以上の task が共有する資料を `shared_inputs` に 1 度だけ挙げる。担当は共有の資料を 1 度だけ読む。渡した資料の指紋は、task ごとの最初の `query` の時点で task ごとに固定する（共有の資料でも task ごとに記録する）。
  - 上限 `UNIT_MAX_BYTES` の値と根拠（実測の手順・余裕・余裕の限界）の正本は [CLI 契約の定数](cli-contract.md#定数) の `UNIT_MAX_BYTES` の根拠で、ここには写さない。
- 担当は、`<run_dir>/formal-method-cli.mjs`（呼び出しのたびに `run-daemon` が書く入口。本物の CLI を絶対パスで import するだけで、台帳に登録しない）で `claim` を流し、`query` で資料を引き、成果物と返り値を attempt の領域に書いて `submit` を流す。落ちたら直して同じ `submit` を流し直し、`claim` が `done` を返すまで続ける。
  - `claim` は、呼び出しと worker を照らし、その worker の出し終えていない担当の task（[claim の Task](artifact-formats.md#claim-の-task)）を全て `tasks` で返す。task は指示ファイル（`agents/<role>.md` と `agent-obligations.md`）の絶対パス、`attempt_dir`、`result_path`、`query_cmd`・`submit_cmd` を持つ。
  - `query` は、その担当の `input_refs` の資料の path だけを返し、担当の外の資料を拒む。`refs` は `.` と `..` を畳んでから照らし、畳んだ後に run の領域の外を指す ref と絶対の path は担当の外とする。最初の `query` の時点で資料の指紋（`expandRefHashes`）を固定し、これを渡した資料（SP-012）として記録する。`query` を流さなかった担当の渡した資料は空である。
  - `submit` は、返り値を書いた task（前の照合から attempt の領域が変わったもの。無ければ出し終えていない全ての task）の `result_path` の返り値を照合し（[担当の返り値](artifact-formats.md#担当の返り値)と各段の照合）、task ごとに `{ok, problems, done}` を返す。受理したものは、呼び出しを閉じた後に台帳に足す。期限の後と閉じた後の `submit` は拒む。
  - 担当が見ていない前の `submit` の応答（依頼の公開から `WORKER_CALL_MAX_MS` 近くの後に書いた応答か、書けなかった応答）があり、その後に取った task の attempt の領域が 1 つも変わっていなければ、照合し直さず前の応答をそのまま返す（期限の後でも返す）。前の応答を見た後の同じ提出は、直せなかった提出として照合する（欠陥が減らなければ残った欠陥ごと受理する）。
  - 理由: `no_response` の後に同じ `submit` を流し直すと、照合が 2 度走って提出の回数が増え、作成役は欠陥を見ないまま出し直しの機会を失い、束の worker は返り値を書いていない task まで照合されて `担当の失敗` になる。見た応答の後の同じ提出まで前の応答を返すと、直せない作成役が受理にも失敗にも決まらず、依存つきの task（計画）が出ないまま期限まで待つ。
- 依頼と応答（正本は `cli-contract.md` の依頼と応答）: client は依頼を `requests/<call_id>/<req_id>.json` に link で公開し、`responses/<call_id>/<req_id>.json` を待つ。`run-daemon` は呼び出しが開いている間、依頼を届いた順に 1 つずつ処理し、応答を `guardedWrite` で書く。
  - 理由: 台帳と run の状態を書くのは `run-daemon` だけという規則（[保存と排他](#保存と排他)、`Lock.tla`・salvage の前提）を保ったまま、担当が CLI と直接受け渡せる。照合の関数は `run-daemon` の記憶（前の段の成果物）を前提にしている。
  - 退けた案: 担当が台帳を直接書く（coverage-audit の `ledger.lock` の型）。書き手が増え、lock の引き渡しと salvage の扱いを作り直すことになる。
- 呼び出しの期限は、担当の呼び出しの期限（`AGENT_BATCH_DEADLINE_MS` と検査に使える期限の早い方）とする。期限までに `close` が届かなければ、`run-daemon` が期限で閉じる。
- 閉じた呼び出しの担当のうち、受理していないもの（取らなかった・取ったまま出さなかった・照合に落ちたまま閉じた）は、停止の理由 `担当の失敗` をその task の `context.stage` を段として記録する。受理した担当の成果物は捨てない。
  - 受理した後に attempt の領域のファイルが書き換わった担当は、受理のまま登録しない（`担当の失敗`）。閉じた時点で結果を渡した担当（分割と計画）は、渡した受理を取り消す: その担当の記録を台帳に足さず、その担当の query の登録を外し、成果物を `artifacts_not_created` に載せる。分割を取り消したら分割を採らず、計画の契約・合成の条件の検査を欠陥の残った要素として実行しない。出し直しの欠陥を返した後に提出が無いまま閉じた担当は、ファイルが変わっていなければ前の提出を残った欠陥ごと受理する。
  - 呼び出しを開く前に担当を出さないと決めた（中断の理由・期限・呼び出しの記録を書けない）ときも、閉じた時点で結果を渡す担当には、出さなかった結果を渡す（分割・計画・変異を `artifacts_not_created` に載せる）。
  - 依存つきの task を出さなかったときは、依存する task が呼び出しの間に閉じたかで理由を分ける（閉じる前に呼び出しが閉じた、又は閉じた後に worker が `claim` しなかった）。
- 役ごとの model・effort の正本は `scripts/lib/roles.mjs` の 1 箇所とする。担当に与える権限（台帳の `permissions`）の正本も同じ module の `AGENT_PERMISSIONS`（`["fresh-thread", "workspace-write"]`）とする。
  - Workflow script（`scripts/formal-method-agents.js`）は CLI の module を import できないので、`meta.requirements` に同じ値を書く。一致は unit（`scripts/lib/roles.test.mjs`）が照らす。`AGENT_PERMISSIONS` は import する。Workflow script は import せず、ファイルの本文を次の規則で読む。
    1. `meta` の範囲は、行頭の `export const meta = {` の行から、次の `}` だけの行まで。
    2. その範囲の行のうち、`^\s*requirements:\s*\[([^\]]*)\],?\s*$` に当たる行がちょうど 1 つある。
    3. 捕まえた中身を `,` で分け、各要素の前後の空白を除いたものが全て `^'[a-z-]+'$` に当たる。引用符を除いた並びを値とする。
    4. 1〜3 のどれかが成り立たなければ不一致とする。値が `AGENT_PERMISSIONS` と順も含めて等しいときだけ一致とする。
  - 理由（import しない）: import すると本文が実行され、ホストの global（`args`・`agent` など）が無いので落ちる。
  - 理由: 台帳の値が Workflow script の宣言と食い違わないようにする。実際に起動した担当の権限との一致は保証しない（ホストが宣言どおりに与えたかを CLI は観測できない）。
  - 理由: `agent-work.md`「検証の入力と証拠を絞る」が、fan-out の agent ごとの明示を求める。
- **起動の理由**（体の数と model・effort。coverage-audit の `docs/design/coverage-ledger-method.md` の起動の原則に合わせる）
  - 1 体の文脈に収まる範囲は 1 体に詰め、分けるのは独立と分離のためだけにする。体を起動するたびに前置き（指示・依頼・共通の資料）を読み直すので、体の数がそのまま費用になる。前の稿の確認の段は、性質ごとに保証の検証者を起動し、4 体の呼び出し 1 つで約 50 万 tokens、run で約 40 体になった。
  - 分けるもの: 作成役と確認役（生成と検証の分離）、確認の観点（読む資料の境界）、`UNIT_MAX_BYTES` に収まらない束。分けないもの: 分割と計画（同じモデルを読み、計画は分割の結果を使う。同じ体なら読んだモデルを文脈に持ったまま書ける）、同じ観点の unit、原因の主題。
  - 作成役（抽出役・モデル作成役・分割作成役・計画作成役）は、上位のモデルの中程度の effort にする。上位のモデルの最も高い effort は、質の向上を測れた役にだけ使う（coverage-audit の初期値の方針と同じ）。
  - 確認役（抽出・忠実さ・形式化でない確認・合成の検証者）と原因の分類役は、作成役と別のモデルで、effort を作成役より上げる。作る役と確かめる役を別のモデルにすると、同じモデルが共有する盲点を減らせる。effort を上げるのは、通す側より落とす側を厳しくするためである。
  - 原因の分類役を確かめる役に数えるのは、反例と `対応できていない` 組を、作成役の成果物の欠陥（`形式モデルの欠陥`・`分類処理の欠陥`）か `要求の不足` かに分ける役だからである。作成役と同じモデルにすると、作成役の読み違いを `要求の不足` や `対象が性質を満たさない` に付け替える盲点を共有する（SP-011、AC-08）。作る役と確かめる役が別のモデルであることは `scripts/lib/roles.test.mjs` が照らす。
  - 値の正本は `scripts/lib/roles.mjs` の 1 箇所で、この文書は方針だけを書く。上げ下げは run の記録（`performance.agent_calls`）と、注入した欠陥での検出で見直す。確認役のモデルで、作成役のモデルより検出が落ちないかは確かめていない（[未検証と限界](#未検証と限界)）。
- Workflow script は判断しない（coverage-audit の `coverage-audit.js` の起動部の型）。
  - `workers` の行ごとに担当を 1 体、行の model・effort で起動し、手順（claim → query → 書く → submit → 直して同じ submit → done まで）だけを prompt に置く。
  - 返すのは `{agents, tokens}` だけである。`tokens` は本体の始めと終わりの `budget.spent()` の差で、取れなければ null。担当の結論は Workflow の返り値に載らない。
- 実行環境: 担当は native の Workflow で起動する。native の `Workflow` が無い環境では、司令塔は担当を起動せずに `close` に `timed_out: true` を入れる（`SKILL.md` の担当の起動）。その呼び出しの担当は取られないので `担当の失敗` になり、成果物は未作成になる。`workflow:dynamic-workflow-runner` への切り替え（`repository-operations.md`「実行と環境」）は実装しておらず、検証もしていない（[未検証と限界](#未検証と限界)の配布先）。
- 独立検証者への入力は、原典・固定した成果物・検査の記録の参照だけにする。作成役の作業記録・attempt の領域のディレクトリは渡さない（「独立した確認」の定義）。
- 担当の返り値が欠けた、形が違う、期限の後に届いた場合は、成功に数えず、停止の理由 `担当の失敗` をその task の `context.stage` を段として記録する（正本は `artifact-formats.md` の担当の返り値）。
  - その担当が作るはずの成果物は未作成になる。
  - `context.perspective` が非 null の task なら、その確認は `result: "確認できず"` の `Confirmation` として結果に残る。原因の分類役の task なら、`原因未確認` の `Cause` になる（正本は `artifact-formats.md` の確認と担当の返り値）。
  - 理由は作業記録の失敗の欄と結果に残す。

## 対象の固定

- 対象は run の間固定している前提とする（依頼者の決定）。正本が run の途中で変わるなら、formal-method を流す意味が無い。
- 受付は対象の写しを作らない。`targets/<target_id>/manifest.json` に、ファイルごとの元の絶対パス・作業ツリーからの相対パス・受付で読んだ指紋を残し、台帳の `target_snapshot` はこの一覧だけにする。担当には元のファイルの絶対パスを渡す（`query` の `path`）。
- 固定の前提を確かめるのは、集約の段の 1 か所だけにする。集約の段の始めに、次の 2 つを受付の指紋と照らす。途中の `submit` ごとには照らさない。
  1. 全ての対象のファイルを読み直した指紋。
  2. 担当ごとの最初の `query` で固定した、対象のファイルの指紋（`materials` と台帳の `input_refs` に記録される `expandRefHashes` の値）。
  - 違うファイルがあれば、停止の理由 `対象の変化`（段は `集約`）を 1 度だけ足す。集約が 2 度走っても（内部の誤りの後の集約）、照らすのは 1 度だけである。
  - 違うファイルは結果の `verified_scope.targets[].files` から外し、`unverified[]` に `対象の変化: <target_id> の <FilePath>` と理由で載せる。`extraction_coverage.complete` は false にする。そのファイルを、性質を支える出所（`run.mjs` の `propertyScopeOf`。性質の `source_ids` と、その性質を扱うモデルの性質の `modelScope`: inventory の性質・節・遷移・禁止・入出力の契約の `source_ids`、対応表の行の location、節の外部の依存の `source`）に持つ性質か、その性質の確認の担当が `query` で受けた資料（`materials`）にそのファイルを持つ性質と、それを親に持つ契約の判定は、`検証済み`・`別手段で確認済み` なら `未確認` に落とす（SP-001 の「版又は内容を特定できない対象を、検証済みの対象として報告してはならない」）。
  - 理由: 担当は元のファイルを読むので、途中で変われば担当の読んだ内容と受付の指紋が食い違いうる。照らす場所を 1 つにすれば、途中の段の照合の手順を増やさずに、破れた run を `完了` にしない。
  - 洗い出しの照合（網羅・出所・引用の指紋）は、受付で読んだバイト列で行う。
  - 固定の範囲は、受付で集まりに入れたファイルだけである。受付の後にディレクトリの対象へ足されたファイルは照らさない（集まりの外で、担当にも渡さない）。受付で読めなかったファイル（`unreadable`）は、読み直しても読めなければ変わっていないとし、読めるようになれば変わったとする。受付で読めたファイルが読めなくなれば変わったとする。
  - 限界: 照らすのは集約の段の読み直しと `query` の時点の指紋だけなので、途中で変わって元に戻り、その間に `query` が無ければ見つけられない（[未検証と限界](#未検証と限界)。結果の `unverified[]` にも載せる）。`query` の後に担当が読んだ時点の内容は記録に残らない。`run-daemon` は途中から再開しないので、再開の時点で照らす場所は持たない。
- `revision` を添えた対象は、作業ツリーのファイルがその版の内容と一致するときだけ受け付ける（一致しなければ `revision_mismatch`）。担当に作業ツリーの元のファイルを渡すためである。
  - 版の内容は、checkout と同じ変換（`.gitattributes` の `eol`・`text`、`core.autocrlf` などの filter）を通した形（`git cat-file --filters <commit>:<path>`）で取る。照合・記録する指紋・集約の段の照合は、全てこの形のバイト列で行う。理由: blob をそのまま比べると、変換を通った正しい checkout を拒む。
  - 版の tree にあるファイルの blob を読めなければ、受付で `target_unavailable` として拒む。理由: 読めないファイルとして受け付けると、集約の段で作業ツリーの指紋と食い違い、変わっていない対象を `対象の変化` にする。
- 作業ツリーの外の絶対パスの対象も受け付ける。担当が読めなければ、その担当の確認は `確認できず` になる。
- 退けた案: 写しを作り続ける。担当（抽出役・モデル作成役）には写しの本体が渡っておらず、担当は一覧から推して元のファイルを読んでいた（指示と食い違っていた）。写しは run ごとに対象の全体を複製し、確認役の資料を膨らませていた。

## 担当に渡す資料

- 担当には、要るファイルと行の範囲だけを渡す（形は `artifact-formats.md` の担当に渡す資料）。範囲は役ごとに次から決める。
  - 抽出役・モデル作成役・抽出の確認役: 依頼の範囲。
  - 形式化できない性質の確認役: 性質の出所の要素。
  - 忠実さの確認役: そのモデルの性質を支える出所（`modelScope`: 対応表の行、そのモデルが扱う inventory の性質・節・遷移・禁止・入出力の契約の出所、節の外部の依存の出所）に、そのモデルの inventory の全ての外部の依存の出所と、どの性質にも結ばれない要素の出所を足したもの。結果の `対象の変化` の判定（`propertyScopeOf`）も同じ `modelScope` を使う。
  - 原因の分類役: 主題から辿れる出所に、全ての対象の依頼の範囲を足したもの。`要求の不足`・`形式モデルの欠陥` は「出所に無いこと」「モデルが出所を落としたこと」で決まり、主題の出所だけでは無いことを確かめられないため（抽出の確認役と同じ）。
- inventory は、忠実さと形式化できない性質の確認役にはその unit の分だけを `views/<unit_id>.json` に写して渡す。忠実さの view は、このモデルの性質に結ばれた要素と、どの性質にも結ばれない要素を分けて持ち（他のモデルの性質にだけ結ばれた要素は入れない）、その inventory の外部の依存（文と出所）を持つ。
- 担当は渡された範囲だけを読む。範囲の外の文脈が要れば、要った範囲を作業記録の `unconfirmed` に書き、確認役はその点を `確認できず` にし、作成役は推測で埋めない（`agent-obligations.md`）。範囲の外を読まずに `成り立つ` にしない。
- 範囲の指紋は `quote_hash` と同じ求め方で取り、ファイル全体の指紋も併せて記録する（SP-012 の渡した資料）。
- 理由: run ba04a7 では、確認役の 1 回の要求の入力が最大で約 204k token になり、共有の資料（2 つの文書の写しと 2 つの inventory）だけで約 124KB あった。範囲で渡せば、1 体の資料が判断に要る分に縮み、詰め合わせが効く。
- 限界: 範囲を絞ると、範囲の外にある出所を確認役が読まない。
  - 忠実さの確認役には、このモデルの性質に結ばれた要素とどの性質にも結ばれない要素の本文を範囲で渡すので、節に出所の無い性質（モデルが落とした要求）と、どの性質にもならなかった要素の漏れを本文で判断できる。他のモデルの性質にだけ結ばれた要素は渡さないので、このモデルが扱うべき要求を他のモデルの性質に誤って結んだ形は、忠実さの確認役からは見えない。
  - 抽出の確認役と原因の分類役は依頼の範囲の全体を読むので、洗い出しの漏れと「出所に無いこと」の判断はそこで行う。
  - 範囲の外を読まない義務は担当だけで守り、CLI は機械では止めない（結果の `unverified[]` の `担当の読む範囲`）。

## 保存と排他

- **保存先**: `<workspace>/.formal-method/runs/<run_id>/` とする。`run_id` は UTC の時刻と乱数から `start` が作る。
  - 依頼の項目に保存先は無い（SP-001）。依頼以外の入力の口を作らないため、保存先は内部で決める。
  - 退けた案: 環境変数で保存先を変える。入力の口が増え、検証方法の節の「依頼の項目以外に入力の口を設けない」に当たる。
- **run の索引**: 過去の run を辿れるよう（PR-034）、`<root>/index/<run_id>.json` を run ごとの別ファイルで置く。
  - 理由: 共有ファイルへの追記が無いので、run どうしの書込みが衝突しない。
- **不変の記録**: 証拠は `writeEvidence` で、一時ファイル・fsync・rename・ディレクトリの fsync を通して書く。
  - 同じ path を別の内容で上書きしない。
  - 保存の直前に秘密値の形を走査し、見つかれば書かない。走査の型（秘密鍵など誤検知の少ない 4 つ）の閉じた集合の正本は `cli-contract.md`。対象の写しは作らないので、対象のファイルは run の記録にならず、走査の対象でもない。
- **状態**: `state.json` は `run-daemon` が rename で置き換える。保存済みの範囲は、rename が終わった `state.json` だけで決まる。
- **run の領域の作成と lock**（引き渡しを持たない）:
  1. `start` が、一時の名前（`<root>/.tmp-<run_id>-<nonce>/`）にディレクトリを作り、`request.input.json` を書く（`.tmp-*` を作るのは `start` だけ。`cli-contract.md` の構造の契約）。
  2. `run-daemon` が、その中に `run.lock` を排他作成する。
  3. `run-daemon` が、ディレクトリを最終の名前へ rename する。
  - これで、run の領域は、lock を持った状態でだけ現れる。lock の無い run の領域が見える時点が無いので、salvage が入る隙間も無い。
  - lock の中身は、保持者の識別（pid、OS が報告する process の開始時刻、乱数の nonce）と役（`run-daemon`）である。
  - 消すのは `run-daemon` 自身が、自分の nonce が書かれていることを確かめてからだけである。消す関数は `lib/store.mjs` の `releaseOwnLock` の 1 つに限る。他の process は、どんな条件でも lock を消さない、奪わない、上書きしない。
  - 理由: 保持者でない手順が lock の path を消せると、その間に別の操作が取り直した lock まで消し、結果が 2 つ確定しうる。再開を持たないので、止まった run を引き継ぐ者が要らず、消す・奪う手順そのものを持たない。
  - 退けた案: 番号付きの lock と解放の印。正しいが、守る相手（回収者）が存在しない。
- **保持者の生死**: 生きているのは、その pid の process があり、その開始時刻が lock の記録と一致する場合だけとする。
  - pid だけで判定しないのは、pid の再利用で、終わった保持者を生きていると誤るためである。
  - `kill(pid, 0)` が「無い」なら死んでいると確定する。開始時刻を読めない場合は、判定できない（`liveness: "unknown"`）として生きている側に扱う。理由: 止まっている側に倒すと、結果が 2 つできることはない。判定できない状態が `LIVENESS_UNKNOWN_MAX` 回続いたら、司令塔は結果を作らずに終える（`ps` が使えない環境で待ち続けないため）。
- **salvage の印**: `run-daemon` は、`state.json`・`status.json`・結果・台帳を書く直前に、毎回 `salvage.mark` が無いことを確かめる。あれば何も書かずに終わる。
  - 生死の判定が正しければ、salvage が動くときに `run-daemon` は終わっている。この確認は、判定が誤った場合の防御である。
- **salvage の規則**: lock を取らず、`state.json`・`status.json`・`ledger.json` を書かない。規則の正本は `cli-contract.md` の「salvage の手順」で、要点は次のとおり。
  1. lock の保持者が生きていれば `E_BUSY`（役 `run-daemon`）。
  2. `result.json` があれば、それを返す（`state.json` は判定に使わない）。
  3. `status.json` が `terminal` なら、その結果を返す。
  4. `salvage.mark`（識別を書いた一時ファイルからの link）で勝者を決める。勝者が生きていれば `E_BUSY`（役 `salvage`）。
  5. 保存済みの範囲だけから決定的に結果を作り、追補台帳 → `result.json` の順に公開する。`result.json` は `run-daemon` と同じ名前で、既にあれば負けとし、既にある結果を返す。
  - 退けた案: 結果を 2 つの名前（`result.json` と `salvage-result.json`）に公開し、`salvage.mark` の確認で重ならないようにする。生死を誤判定すると、印の確認と書込みの間の隙間で両方が公開され、結果が 2 つになる（形式検証の `lock-mut-two_names`）。1 つの名前への link なら、確認と書込みが 1 つの不可分な操作になり、誤判定があっても公開される結果は 1 つになる。
  - 退けた案: 印の確認を lock で守る。salvage は lock を取らない（保持者が死んでいれば lock は解けない）ので、守れない。
  - salvage の作業記録と結果には時刻を入れない。そのため、salvage の所要時間と run 全体の所要時間は、`performance` に `取得できず` と理由で記録する。
  - 台帳（PR-029）: salvage は `ledger.json` を書かない。結果の `records.ledger_refs` は、その結果を登録した台帳を指す。PR-032 は、同じ内容の正本を 1 つにする限り、記録の分割を許す。
- **結果と台帳の保存の失敗**（正本は `cli-contract.md` の同じ名前の節）
  - 公開の順は、台帳 → 結果。結果は、`run-daemon` も salvage も `result.json` にだけ link で公開する。
  - 状態を決める順序: 集約の段は、公開が成功すると仮定して完了の条件を評価し、結果 R を作って公開する。台帳か結果の公開に失敗したら（負けと、結果の link の後の失敗を除く）、R を捨てる。そして状態 `停止`（`保存の失敗`・`記録の未保存`）の R' を作り直し、公開せずに返す。そのため、`完了` が返るのは R の `result.json` への link に成功したときだけである（SP-015 の「記録を全て保存した」）。link の後に fsync か再読込が失敗した場合は `cli-contract.md` の「link の後の失敗」（[未検証と限界](#未検証と限界)）。公開の前に `完了` を返す変異は、形式検証の `lock-mut-complete_before_publish`・`run-mut-complete_before_publish` が拒む。
  - 結果の中では、結果のファイル自身と台帳を参照だけで持ち、指紋を持たせない（指紋が循環するため）。
  - `status.json` は記録に数えない。client への受け渡しの口なので、書けなければ `run-daemon` は終わり、salvage が結果を返す。
- **ホストに殺されたとき**:
  - `run-daemon` は自分の process group で動き、道具の process group を起動し、標準入力（query）を渡す前に `children/` に記録する（記録できなければ入力を渡さずに止め、起動の失敗とする。正本は `cli-contract.md` の Z3 の adapter）。
  - 前景の CLI がホストに殺されても、状態を書く者ではないので何も壊れない。
  - `run-daemon` が殺されたら lock が残り、`wait` は保持者の終了を観測して `E_STALE` を返す。salvage の規則 5-1 が、残った道具の process を止める。
  - 道具は検査ごとの時間の上限（`-T`）を持つので、回収されなくても有限の時間で終わる。
- **担当の書込み範囲**: 担当は Workflow の `workspace-write` で動き、ホストの権限で書込みの範囲を分けていない。
  - `run-daemon` は、attempt の領域の外のファイルを成果物として登録しない。
  - 台帳・状態・他の担当の領域に担当が書かないこと（PR-029）は、担当の義務（`agent-obligations.md`）で守る。これは構造で守れない限界である（[未検証と限界](#未検証と限界)）。
  - 登録した成果物は、読むたびに指紋を照合し、一致しなければ使わない。

- **契約への記載**: 次の 4 つを、`references/cli-contract.md` に契約として書く。`tests/formal/formal-method-skill/Lock.tla` は、この 4 つをモデルにする（[検証計画](verification-plan.md#内部の設計に当てる形式手法)）。
  - run の領域の作成の手順（一時の名前 → lock → rename）
  - 保持者の生死の判定
  - salvage の印の確認
  - salvage の規則 1〜5
  - 起動の手順（起動の失敗、rename の前後の crash、遅い `run-daemon` の扱い、`.tmp-*` の扱い）
  - 受け箱と依頼の公開の手順

## 停止の手順

止める理由は次の 4 つに限る。それ以外の失敗（反例、問い、独立検証者の不合格、担当の欠測、作成役の欠陥）は、関係する項目の判定・未確認として記録し、段を進める。

| 理由 | 起きた時点の処理 | 結果の返し方 |
|---|---|---|
| 依頼を受け付けない（SP-001） | 検証を始めない。対象の取得より前の不備なら、何も取得しない | 結果を保存できれば保存し、`status.json` の `terminal` で返す。`stop_report.stage` は受付 |
| 時間の上限に達した（SP-010） | 実行中の道具の実行（確認用も含む）を止める。始めていない実行と担当を始めない。開いている呼び出しは期限で閉じる | 集約の段の処理を、得た範囲だけで行う。確認の段より前に達したら確認の段に入らない（意味の確認を作らず、反例と組合せの原因は `原因未確認` で作る）。確認の段の中で達したら、組み立てた unit のうち出さなかったものを `artifact-formats.md` の確認の「担当を出さなかったとき」で扱う |
| 保存できない記録があった（SP-014） | 新しい書込みを始めない。保存できたものはそのまま残す | 集約の段で結果を作り、保存を 1 度だけ試す。下の「保存先に書けないとき」 |
| `run-daemon` の内部の誤り | 途中まで書き換えた状態を捨て、前回の `state.json` から集約する | 同上 |

**全ての段を終えた run の扱い**

- 集約の段が完了の条件（SP-015）を評価する。成り立たなければ、結果の状態を `停止` とする。
- この場合の停止の理由は、条件ごとの未達（反例、未実行、未確認、問い、`対応できていない` 組合せ、記録の未保存、保持規則）の全てとする。

**`stop_report.stage`（SP-015 の「止まった段」）の決め方**

- 停止の理由ごとに、それを生んだ処理の段（作業記録の段の欄と同じ値）を記録する。
- `stop_report.stage` は、中断の理由（`依頼の不備`・`起動の失敗`・`時間の上限`・`保存の失敗`・`内部の誤り`・`処理の中断`）があれば、最初に記録されたものの段とする。中断の理由が無く完了の条件で止まった場合だけ、理由の段のうち最も上流の段とする（正本は `artifact-formats.md`）。
  - 理由: AC-19 は「段の分かっている処理で失敗を起こし、停止の報告の段がその処理の作業記録の段と一致する」ことを観測する。終わった段（集約）を返すと、失敗を起こした段と一致しない。
  - 退けた案: 常に run が終わった段を返す。
- `stop_report.checks_running`・`checks_aborted` には、性質・部分の契約・合成の条件の検査だけでなく、確認用の実行（sanity・mutation・replay・静的な確認の ablation）も入れる。

**保存先に書けないとき（AC-13）**

- `start` は、`run-daemon` を起動する前に、保存先の root の作成・書込み・fsync を試す（能力の確認）。試しに作ったものは消す。
- できなければ、`run-daemon` を起動せず、次の結果を標準出力の `terminal` で直接返す。
  - 状態は `停止`、段は受付である。
  - `records.saved` は空、`records.unsaved` には、結果のファイル自身を含む全ての記録と理由を載せる。
- run の途中で書けなくなったら、`run-daemon` は集約の段で結果を作り、`result.json` と `status.json` への保存を試す。
  - 保存できなければ、`run-daemon` は結果を返す経路を持たないまま終わる。前景の client と `run-daemon` の間に、ファイル以外の経路を持たないためである。
  - `wait` は保持者の終了を観測して `E_STALE` を返し、司令塔が salvage を呼ぶ。salvage は、rename まで終えた記録から `停止` の結果を作り、標準出力で返す。
    - `records.saved` には、再読込で指紋が一致した記録だけを載せる（例外は結果のファイル自身の link の後の失敗。`cli-contract.md` の「link の後の失敗」）。
    - salvage の結果と追補台帳を書けなければ、それも `records.unsaved` に載せる。
  - 退けた案: `run-daemon` が結果を保存先の外（OS の一時領域）にも書く。保存先として依頼元が辿れない場所に、記録の写しが残る。
- 結果は、保存できたかどうかによらず、標準出力の `terminal` で返る。結果のファイル（`result.json`）は、記録の 1 つとして `records.saved` か `records.unsaved` に載る。
  - 理由: 受け渡しの方法を表す専用の欄を持つと、`records` と同じ事実を 2 箇所に書く。
  - 退けた案: 受け渡しの方法を表す欄（`delivery`）を結果に持つ。
- 保存したと示すのは、再読込で指紋が一致した記録だけとする。例外は結果のファイル自身の link の後の失敗である（`cli-contract.md` の「link の後の失敗」）。

## 時計と資源

**時間の上限**（依頼の秒）

- run の期限は、受付の時刻にその秒を加えた時点とする。
- process をまたぐ判定には、壁時計と OS の起動からの経過時間を併用する。どちらかが期限を過ぎた、又は時計が戻ったら、期限切れとする。
- 1 回の呼出しの中の待ちは、`process.hrtime` で測る。
- 担当の呼び出しの期限は、run の期限から集約の予備時間を引いた時点とする。
  - 予備時間の定数は `schemas.mjs` に置く。
  - 理由: SP-015 は停止の報告を求めるので、報告を作る時間を残す。
- 時間の上限が渡されなかったときは、run の期限を持たない。
- 検査ごとの道具の時間の上限（Z3 の `-T`）は計画作成役が検査ごとに決め、CLI が定数の上限で抑える。この上限に達した検査は「道具自身の時間の上限」に当たり、`時間切れ` になる（SP-011）。
  - 理由: 時間の上限の無い依頼で、終わらない検査が run を終わらせなくなるのを防ぐ。
  - 退けた案: 検査にも上限を置かない。
- 担当の呼び出しにも、時間の上限の有無によらず内部の期限（定数。`schemas.mjs`）を置く。依頼の時間の上限があれば、早い方を使う。
  - 期限までに受理されなかった担当は欠測として扱う（[担当の起動](#担当の起動)。期限の後の `submit` は拒む。期限内に受理した担当は、`timed_out` の close でも残る。正本は `cli-contract.md` の依頼と応答と受け箱）。run は止めずに次の段へ進む。
  - 理由: 担当が返らないと、run が終わらない。担当の応答に公平性は仮定できない。
  - 退けた案: 時間の上限が無ければ担当を待ち続ける。

**期限と道具の終わりが重なったとき**

検査の終わり方は、scheduler が 1 つの event loop の中で先に観測した出来事だけで決める。

- `-model` を渡した実行では、答えの行の読み終わりを「出力の読み終わり」とする。答えの後のモデルを読んでいる間に期限か停止の要求が来たら group を止めるが、検査は止めていないものとして答えで判定する（`stopped_by` は null。正本は `cli-contract.md` の答えの後の停止）。
- 道具の終了（close）と出力の読み終わりを、期限か停止の要求より先に観測した場合:
  - その検査は止めていない（`stopped_by` は null）。
  - 実行中に依頼元の時間の上限には達していない（`time_limit_hit` は null か `道具`）。
  - 後から来た期限は、その検査に作用しない。
- 期限か停止の要求を先に観測した場合:
  - `stopped_by` を記録し、その後に届いた出力は判定に使わない（`tool_result` は `なし`）。
- 理由: SP-011 の「始めた後、道具の結果を得る前に formal-method が中止した」と、網羅表の WF1（道具が返りを報告した後は止める対象が無い）・L138（依頼元の時間の上限では実行中の検査を止める）に合う。この規則は、網羅表で許される終わり方だけを作る。
- `classifyCheck` の例外（[判定の集約](#判定の集約)）は、この規則の外れ（scheduler の欠陥）を見つけるためにだけ残す。

**scheduler の unit の入口**（内部）: `scripts/lib/scheduler.mjs` の `runExecution(execution, io)`

道具の 1 回の実行の始めから終わり方（`End`）までを決める関数で、上の規則の正本の実装である。scheduler の同時に動かす数と依存（D1）の処理は、実行ごとにこの関数を呼ぶ。依頼元から見える入力の口ではなく、テストは module を直接 import して呼ぶ（`cli-contract.md` の unit の入口と同じ扱い）。

```text
ExecutionSpec = {
  execution_id: Id, kind: ExecKind,
  query: Uint8Array,                       // 標準入力に渡すバイト列（checks/<execution_id>/input.smt2 の内容）
  with_model: boolean,                     // -model を渡すか（property・composition だけ true）。kind から決まる値を呼び手が入れ、runExecution は kind を見ない
  expected: "sat" | "unsat",                // cli-contract.md の「答えと tool_result の対応」の expected。mutation は MutationsFile.mutations[].expected_violation
  tool_time_limit_seconds: int≥1,
  deadline_ms: int | null                  // 検査に使える期限（clock.now() と同じ時間軸）。期限が無ければ null
}
ExecutionIo = {                            // 作用の境界。本番は node の timer・adapter の execute・停止の関数、テストは差し替える
  clock: { now(): int, setTimer(at_ms: int, cb: () => void): unknown, clearTimer(handle: unknown): void },
  spawn(execution: ExecutionSpec): ProcessHandle,   // 本番は group を作って起動し、標準入力を渡す前に children/ に記録する
  signal: AbortSignal                      // 停止の要求。scheduler の停止の関数が abort する
}
ProcessHandle = {
  onStdout(cb: (chunk: Uint8Array) => void): void,
  onStderr(cb: (chunk: Uint8Array) => void): void,
  onClose(cb: (exit_code: int | null) => void): void,   // 道具の終了と、標準出力・標準エラーの読み終わりの両方。killGroup の後も 1 回だけ来る
  killGroup(): void,                       // process group を止める
  readonly startFailure: string | null     // 起動の失敗の原因（spawn の失敗か、children/ に記録できず入力を渡さなかった）。無ければ null。close の時点で確定している
}
ExecutionOutcome = { execution_id: Id, end: End, stdout: Uint8Array, stderr: Uint8Array, exit_code: int | null,
  model_cut: "none" | "truncated" | "stopped_after_answer",   // 答えの後のモデルを読み切らなかった理由。下の規則
  start_failure?: string }                 // 起動の失敗のときだけ持つ。値は ProcessHandle.startFailure
```

- 戻り値は `Promise<ExecutionOutcome>`。`stdout` は受けたバイト列（`TOOL_OUTPUT_MAX_BYTES` までに切り詰めたもの）、`stderr` は受けたバイト列で、どちらも証拠として保存するためのもの。判定には使わない部分を含みうる。
- `model_cut`: 答えの行を読み終えた後に標準出力が `TOOL_OUTPUT_MAX_BYTES` を超えたら `truncated`（その後に答えの後の停止が起きても `truncated`）、超えずに答えの後の停止が起きたら `stopped_after_answer`、他は `none`。`none` 以外なら、呼び手は証人を読めないものとする。`truncated` のときだけ、呼び手は `Check.reason`・replay の `Confirmation.reason` に固定の語「標準出力を TOOL_OUTPUT_MAX_BYTES で切り詰めた」を書く（`cli-contract.md` の出力の上限）。理由: 出力がちょうど上限で終わった場合と切り詰めた場合は `stdout` の長さで区別できず、答えの後の停止は `end` が通常の close と同じになる。
- **起動の失敗**: close を受けた時点で `startFailure` が非 null なら、観測の順（期限・停止の要求が先に来たかを含む）によらず、`End` は `started: false`（他の欄は既定）、`model_cut: "none"`、`start_failure` はその原因とする。呼び手は原因を `Check.reason` か `Confirmation.reason` に書く（`cli-contract.md` の Z3 の adapter）。理由: 道具は入力を受けておらず、始めていない実行である。道具の異常終了（`abnormal_exit`）と混同しない。
- **始める前**: 呼ばれた時点で `deadline_ms` が非 null かつ `clock.now() ≥ deadline_ms`、又は `signal.aborted` なら、`spawn` を呼ばずに `started: false` の `End`（他の欄は既定）を返す。それ以外は `spawn` を呼び、`deadline_ms` が非 null なら `clock.setTimer(deadline_ms, …)` を置く。
- **観測の順**: 終わり方を決める出来事は、close（`onClose` の callback）、期限（timer の callback）、停止の要求（`signal` の `abort` の事象）の 3 つ（加えて、下の出力の上限で止める場合）で、callback が呼ばれた順を観測の順とする。close を受けたときに `clock.now()` と期限を比べない。最初の出来事で終わり方が決まり、後の出来事は終わり方を変えない。
  - close が最初: timer を外し、`killGroup` を呼ばない。`stdout`・`stderr`・`exit_code` を `cli-contract.md` の「読む順」に当てて `End` を作る（`stopped_by: null`、`time_limit_hit` は null か `道具`）。
  - 期限が最初（`with_model: false`、又は答えの行を読み終える前）: `killGroup` を呼ぶ。`End` は `started: true`・`tool_result: "なし"`・`abnormal_exit: false`・`unreadable_output: false`・`stopped_by: "時間"`・`time_limit_hit: "依頼元"`。それまでに受けた出力によらない。
  - 停止の要求が最初（`with_model: false`、又は答えの行を読み終える前）: `killGroup` を呼ぶ。`End` は期限と同じで、`stopped_by: "その他"`・`time_limit_hit: null`。
  - 止めた後に来た close の `exit_code`（0 以外や null を含む）は `abnormal_exit` にしない。止めた後に受けた出力は判定に使わない。
- **止めた後も close を待つ**: 止めた場合も、`onClose` が来てから戻る。テストの偽の process は、`killGroup` の後に close を出す。
- **答えの後の停止**（`with_model: true`）: 標準出力の最初の空でない行を改行まで受けた時点（行が複数の chunk にまたがれば、改行を含む chunk を受けた時点）で、その行が `sat`・`unsat`・`unknown`・`timeout` のどれかなら、答えの行を読み終えたとする。その後、close より先に期限か停止の要求が来たら（上の「期限が最初」「停止の要求が最初」に当たらない）、`killGroup` を呼び、`End` は `cli-contract.md` の「答えの後の停止」のとおり（`stopped_by: null`、`time_limit_hit` は答えが `timeout` なら `道具`、他は null、`abnormal_exit`・`unreadable_output` は false、`tool_result` は答えの行で決める）。
- **出力の上限**: 標準出力が `TOOL_OUTPUT_MAX_BYTES` を超えたときは `cli-contract.md` の出力の上限のとおりで、group を止める場合（`with_model: false`、又は答えの行を読み終える前に超えた）は、それを close・期限・停止の要求より先の出来事として `killGroup` を呼び、`End` は `started: true`・`tool_result: "なし"`・`abnormal_exit: false`・`unreadable_output: true`・`stopped_by: "その他"`・`time_limit_hit: null` とする。答えの行を読み終えた後に超えた場合は止めず、出来事にしない（`model_cut: "truncated"`）。答えの行を読み終えたかと上限を超えたかの前後は、chunk でなくバイトの位置で決める。答えの行の改行が標準出力の先頭から `TOOL_OUTPUT_MAX_BYTES` バイト以内にあれば、同じ chunk の中で上限を超えても、答えの行を読み終えた後に超えたとする。

**同時に動かす数**（内部の選択）

- 仕様は CPU とメモリの上限を定めない（依頼の資源は時間の上限だけ。SP-001・SP-010）。同時に動かす道具の実行の数は、内部で決める。
- 数は、実行環境の `os.availableParallelism()` と、互いに依存しない実行の数の小さい方とする。1 つの実行が使う CPU は、adapter の宣言（Z3 は 1）とする。
- この数は、外から観測できる振る舞いにも、結果の欄にもしない。上限に達したという理由も結果に出さない。
- 理由: SP-010 は、互いに依存しない検査を並列に実行できることを求める。実行環境の CPU の数より多く動かしても速くならず、時間の上限に余計に近づく。
- 退けた案: 依頼から同時実行の数を受ける。依頼の項目に無い入力の口になる。

**数える単位**

- scheduler が同時に動かす数と時間の上限を当てて数える単位は、道具の実行の全てである。部分の契約の検査と確認用の実行（sanity・mutation・replay・静的な確認の `ablation`）も、性質の検査と同じ数と上限の下で動く。
- 時間の上限で止めた確認用の実行も、`stop_report` の実行中・中止した検査の一覧に、`kind` を付けて出す。
- 理由: 確認用の実行も時間を使う。時間の上限（SP-010）の「実行中の検査を止め、始めていない検査を始めない」を、確認用の実行にも当てないと、上限の後に道具が動き続ける。

**互いに独立な検査（D1）**

- 反例・失敗が出ても、互いに依存しない検査は止めずに最後まで動かす。依存先の検査が成功でなかった検査だけを始めず、`未実行` とする。

**formal-method が止めた検査**

- 中止は、全て scheduler の停止の関数を通して行う。`runExecution` が自分で group を止める場合（期限・停止の要求・出力の上限）は、`runExecution` がこの停止の関数の役を持つ。その検査の終わり方を「formal-method が止めた（時間・その他）」として記録する。
- 判定は、[判定の集約](#判定の集約)の終わり方の分類で決める。道具の異常終了（`実行失敗`）と混同しない。
- 理由: 外から止めた process を signal の異常終了として数えると、formal-method が止めた検査が `実行失敗` になり、`未実行` と区別できない。

**adapter の出力の規則**

- Z3 の結果の行が `unknown` なら、「判定できない」と読む。判定は `unknown` である。`unknown` の理由（`(get-info :reason-unknown)`）は取らず、メモリなどを理由にしていても同じに読む（SP-011、オラクルの Q20）。
- Z3 の結果の行が `timeout` なら、「道具自身の時間の上限に達した」と読む。判定は `時間切れ` である。
- 出力の流れと終了コードは、adapter の契約（`cli-contract.md`）に分けて書く。実測（macOS arm64、Z3 5.3.3）は次のとおり。

  | 場合 | 標準出力 | 標準エラー | 終了コード |
  |---|---|---|---|
  | メモリ不足 | （答えの行なし） | `(error "out of memory")` | 101 |
  | 構文の誤り | `(error …)` の行 | — | 1 |

- 読み方の規則の正本は `cli-contract.md` の読む順で、要点は次のとおり。
  - `(error` の行は「判定以外のエラー」、答えの行が 1 つで終了コードが 0 ならその答え、それ以外で終了コードが 0 でなければ「異常終了」、残りは `tool_result` を「なし」とし、SP-011 の受け皿の `実行失敗`（どの返りも無く、他の値の条件にも当たらない）で拾う。
  - `-model` を渡した実行（性質と合成の条件の検査）では、最初の空でない行が `sat`・`unsat`・`unknown`・`timeout` のどれかなら、それを答えの行とし、続く行はモデルとして答えの読みに使わない（反例の再実行の証人にだけ使う）。
  - 標準エラーは証拠として保存するだけで、読み方には使わない。
  - メモリ不足は異常終了に、構文の誤りは判定以外のエラーに当たる。どちらも formal-method が止めていない道具なので、`実行失敗` になる（SP-011）。
  - 理由: 標準エラーの文面で読み分けると、道具の版で文面が変わったときに黙って読み違える。
- `(error …)` は、Z3 が `check-sat` の答え（sat・unsat・unknown）の代わりに出す診断である。SP-011 の `unknown` の条件「道具が判定できないと返した」は、答えとしての `unknown` に当たる。メモリ不足の `(error "out of memory")` は答えではないので、`unknown` と読まない。
  - 退けた案: `(error "out of memory")` を `unknown` と読む。答えではない出力を答えとして扱うことになる。
- 偽の z3 も実測どおりに返す。メモリ不足は、標準エラーに `(error "out of memory")` を出して終了コード 101。構文の誤りは、標準出力に `(error …)` を出して終了コード 1。
- Linux では未測定である（[未検証と限界](#未検証と限界)）。

**道具の並列の設定**

- 1 つの実行の CPU は adapter の宣言で数える。そのため、query が道具の並列の設定（Z3 の `parallel.enable`、`(check-sat-using (par-or …))` など）を書いていたら、計画の照合（`planCheck`）が拒む。
- 理由: 宣言より多くの CPU を使うと、同時に動かす数の内部の選択が意味を失い、時間の見積りも外れる。

**メモリの記録**

- 常駐メモリは、性能の記録（SP-013）のためにだけ、process group を一定の間隔で標本化して最大値を記録する。標本化で道具の実行を止めることはしない。

**`models[].behavior`**（SP-006。ここでいう再開は、検証する相手の状態遷移の再開である）

- `outcomes`: 成功・失敗・中断・停止の各状態の一覧と、モデルの要素への参照
- `human_inputs`: 適用される人の入力（出来事）の一覧と、受け付ける状態
- `resumptions`: 再開の遷移と、その再開先
- 対象に当てはまらない項目は、空の配列と理由で示す

**検査の終わり方（`end`）**

- 判定の入力となる、検査の終わり方の記録である。持つ欄は次のとおり。
  - `started`
  - `tool_result`（`満たす`・`反する`・`判定できない`・`判定以外のエラー`・`なし`）
  - `undecided_cause`（`時間`・`その他`・null）
  - `abnormal_exit`
  - `unreadable_output`
  - `stopped_by`（`時間`・`その他`・null）
  - `time_limit_hit`（`依頼元`・`道具`・null）
- 欄は `tests/formal/formal-method-spec/` の網羅表の入力の語彙（`endstates.py` の `RET`・`STOP`・`TL`）と 1 対 1 に対応させる。この対応で、オラクルと照合できるようにする（[検証計画](verification-plan.md#判定のオラクル照合)）。

**人向けの表示**

- `report.md` は結果の JSON から決定的に導く。
- 表示にある成功は、全て構造の該当する欄から引く。表示の関数は構造を引数に取り、成功の語を構造の外から作らない（SP-003）。

`stop_report` 以外の項目は、`完了` の結果も `停止` の結果も全て持つ（AC-21）。該当が無い項目は空の配列か、理由を持つ値で表し、キーを省かない。

## 判定の集約

判定は 3 つの純粋関数に分け、入出力だけで単体テストとオラクルの照合ができるようにする（`docs/guidelines/README.md` の、判断と作用を分ける原則）。

**1. `classifyCheck(end) → 検査の判定`**（SP-011 の検査の規則）

- 各値の条件を、仕様の表の「使う条件」どおりの述語として別々に書く。
  - `成功`: 道具が満たすと返し、他のどの条件も成り立たない。
  - `反例`: 道具が反すると返した。
  - `時間切れ`: 始めた後に、依頼元の時間の上限か道具自身の時間の上限に達した。
  - `実行失敗`: 止めていない道具の異常終了・読めない出力、判定以外のエラー、又はどの返りも無く他の条件にも当たらない。
  - `未実行`: 始めていない、又は始めた後、道具の結果を得る前に formal-method が止めた。
  - `unknown`: 道具が判定できないと返した。
- 2 つ以上の条件が成り立てば、`反例`・`時間切れ`・`実行失敗`・`未実行`・`unknown` の順で先の値を返す。順の正本は 1 つの定数に置く。
- 仕様が起こらないとする終わり方（網羅表の `unsat` と `除外` の行）を受けたら、例外で拒む。拒んだ検査の判定は付けず、内部の誤りとして停止の手順へ移る。
  - 理由: 成り立たない入力に判定を付けると、scheduler の欠陥が判定の値に紛れる。

**2. `aggregateProperty(facts) → 判定の集合`**（SP-011 の性質の規則）

- 入力は、性質の検査の判定と、次の事実である。
  - 形式化できるか
  - SP-005 の対応・意味の確認
  - 合成の条件（SP-009）
  - SP-012 の決定的な検査・意味の確認・検出能力の確認
  - 回答を待つ問いへの依存
  - SP-007 の道具が無い・準備できない
- 次の順に評価し、最初に当たった段で判定を返す。右の列は、その段を確かめるオラクルの Q である。

| 段 | 条件 | 返す判定 | オラクル |
|---|---|---|---|
| 1 | 検査が 1 件以上あり、成功でない検査がある | 成功でない検査の判定の全て（重複を除き、SP-011 の表の順） | Q1・Q3・Q7・Q15〜17・Q19c・Q20・Q22〜28 |
| 2 | 検査が 1 件以上あって全て成功し、形式化できる性質である | `検証済み` の条件が全て成り立てば `[検証済み]`。条件は、回答を待つ問いに依存しない、SP-005 の対応と意味の確認、合成の条件、SP-012 の決定的な検査と意味の確認、行った検出能力の確認の検出 | Q10c（成り立つ）、Q2・Q4・Q19b（成り立たない → 段 5） |
| 3 | 形式化できない性質である（検査の有無によらない） | 回答を待つ問いに依存せず、別の方法による独立した確認が成り立てば `[別手段で確認済み]` | Q11・Q13b・Q21a・Q21b（成り立つ）、Q12・Q13a（成り立たない → 段 5） |
| 4 | 検査が 0 件で、形式化できる性質に適した道具が無いか準備できない（SP-007） | `[未実行]` | Q14・Q18 |
| 5 | 上のどれにも当たらない | `[未確認]`（受け皿） | Q2・Q4・Q9・Q12・Q13a・Q19a・Q19b |

- 段 1 は、形式化できない性質にも当てる。成功でない検査がある性質を `別手段で確認済み` にしないためである（SP-011 の「成功でない検査があるならば」は性質の区別を置かない）。
- `未確認` は段 5 でだけ付くので、他の成功でない値と同じ集合に入らない。
- 問いに依存して検査を作らなかった性質（[段と処理の順序](#段と処理の順序)）は、検査が 0 件で SP-007 の場合でもないので、段 5 で `未確認` になる。オラクルの Q6 は、計画した検査を始めなかった入力を扱う（r11 では答えが未確定）。この設計ではその入力が生じない。
- 性質の検査に数えるのは、`kind` が `property` と `composition` の検査だけである。`kind: contract` の検査は、部分の契約（内部の性質）の判定にだけ数える（入力の正本は `artifact-formats.md` の契約の判定）。
  - `sanity`（前提の整合・初期状態の存在）、`mutation`（変異）、`replay`（反例の再実行）は、SP-005・SP-012 の確認の記録として `confirmations` に入れる。
  - これらが成り立たなければ、`検証済み` の条件が成り立たない（`未確認` の受け皿になる）。
  - 理由: 前提の矛盾を見つけた検査を `実行失敗` や `反例` に数えると、仕様の値の意味（道具の異常、性質に反する例）と食い違う。
- `検出能力未確認` は判定に混ぜず、`properties[].detection.status` に置く（SP-012、用語定義）。

**3. `decideStatus(global) → 完了 | 停止`**（SP-015）

- SP-015 の完了の条件の箇条は 6 つある。そのうち 6 つ目（「下の 2 つの保持規則のいずれにも当たらない」）は保持規則を指すので、述語は次の 9 つとする。
  - 5 つの条件: 全ての必要な性質が検証の成功、SP-012 の確認に未実行・失敗・未確認が残らない、`対応できていない` 組合せが残らない、回答を待つ問いが残らない、記録を全て保存した
  - 2 つの保持規則: 必要な性質が 0 件、`検出能力未確認` の性質が残る
  - 2 つの停止の規則: 反例、実行できない検査（必要な性質）
- それぞれを別の述語にする。
- 全てが成り立つときだけ `完了` を返す。
- 成り立たなかった述語の一覧を `stop_report.reasons` にする。

D2 の実現: 問いに依存する性質は、問いの ID を `depends_on_questions` に持ち、`検証済み` にならない。他の性質の判定は、問いと無関係に同じ規則で決まる。

## 静的な確認

SP-FORMALMETHOD-012 の静的な確認の表を、CLI の決定的な確認として行う。担当の確認役が読んでいた指摘のうち機械で判定できる型を、性質ごとの LLM の起動から外すためである。

**節の印**（モデル化の段）

- モデル作成役は、性質の query のトップレベルの assert を全て `(assert (! <項> :named <name>))` にし、`ModelFile.properties[].clauses` に名前ごとの役（出所の規則 `rule`・前提 `premise`・性質の否定 `goal`）を書く（形は `artifact-formats.md` の model）。
- モデル化の照合は、全ての assert の名前、名前の集合と `clauses` の一致、`goal` の有無、規則の出所、前提の根拠、外部の依存の id、範囲の変数の宣言を照らし、違反を修正の巡の欠陥にする。計画の照合は、変異が同じ名前の集合を持つことを照らす。
- 理由: 役を名前で結べば、CLI は項を読まずに節を切り取れる。役の付け方が出所と一致するかは機械で決まらないので、意味の確認が確かめる（SP-012）。

**実行**（実行の段。`kind: property` の欠陥の残らない検査ごと）

| 実行 | 残す節 | 期待 | 確認の kind |
|---|---|---|---|
| 否定だけ | `goal` | sat | `goal_trivial`（unsat なら性質が自明） |
| 前提と否定だけ | `premise`・`goal` | sat | `premise_only`（unsat なら前提だけで結論が出ている） |
| 規則と否定だけ | `rule`・`goal` | — | `premise_load`（sat なら結論は前提に支えられる） |
| 前提を 1 つ外す | 外す前提の他の全て | — | `premise_load`（sat ならその前提が効いている） |

- 切り取りは `checks/ablation.mjs` の `ablate` が、検査の入力（`input_refs` をつないだもの）からトップレベルの assert の form を位置で除く。宣言・`define-fun`・`(check-sat)` は残す。実行は `kind: ablation`、`-model` を渡さず、時間の上限はその検査の値で、他の実行と同じ同時実行の数と期限の下で動く。
- 前提が無ければ、前提と否定だけは否定だけと同じ query なので実行せず、否定だけの答えで決め、規則と否定だけも実行しない。
- 前提を 1 つずつ外す実行は、規則と否定だけが sat のときだけ、反例の再実行と同じ波で出す。3 つと前提の数の和が `ABLATION_PER_PROPERTY_MAX`（`cli-contract.md` の定数）を超えれば出さず、全ての前提を判断を要する項目にする（和がちょうど上限なら出す）。
- 前提を 1 つずつ外して unsat だった前提が 2 つ以上あり、全ての前提ではなければ、それらをまとめて外した実行を、前提ごとの実行の後の波で出す（一部だけ重なって効く前提を見つけるため）。この 1 つも `ABLATION_PER_PROPERTY_MAX` に数えない。
- 前提と否定だけが unsat で、前提に `basis: "外部の依存"` があれば、外部の依存の前提を外した実行（外部の依存でない前提と否定だけ）を同じ波で出す。外部の依存でない前提が無ければ、否定だけの答えを使う。この 1 つは `ABLATION_PER_PROPERTY_MAX` に数えない。
- 節を役ごとに切り取れない検査は実行せず、3 つの kind を決定的な確認の `確認できず`（未実行）にする（`checks/ablation.mjs` の `clauseShapeProblem`）。切り取れないのは、性質の否定の節が無い、名前の無い assert がある、名前の集合が `clauses` と合わない、宣言した記号を本体に（他の `define-fun` を通しても）含む `define-fun` を役の違う節が参照する、のどれかである。最後のものはモデル化の照合の欠陥（`other`）にもし、作成役に出し直させる。性質の否定の節が無いことは `syntax` の欠陥にする（受理されても `syntax` の確認が成り立たない）。道具が無ければ組み立てない（性質の検査も `未実行` になる）。
  - 理由: 切り取れない入力に静的な確認を流すと、空の否定が sat になって `goal_trivial` が成り立ち、共有した定義の本体の制約が切り取りから外れる。これを判断を要する項目にして意味の確認に回すと、決定的な検査を意味の確認で代えることになる（SP-012）。SP-012 の「静的な確認の道具が判定できなかった場合」は、組み立てた実行に道具が答えなかった場合（unknown・時間切れ・失敗）であり、組み立てられない入力は含めない。
  - 計画の照合は、`kind: property` の検査の `input_refs` が性質の `query_ref` を含むことを照らす（含まなければ欠陥の残った要素として実行しない）。静的な確認は性質の query の節の印で検査の入力を切り取るためである。

**道具を使わない確認**: `plan_coverage`（モデルの性質ごとに、欠陥の残らない計画の検査・前提の整合の確認・変異又は `unavailable`。検査の欠けの正本は `checkGaps`）、`scope_variables`（`範囲を限った検査` の `scope_variables` が検査の入力で宣言され、`rule` か `goal` の項に現れる）、`mutation_scope`（欠陥の残らない変異ごとに、検出役の検査の最後の入力と比べて、`rule` の節の項が 1 つ以上変わり、`goal`・`premise` の節の項と assert でない form（宣言・`define-fun` など）が変わらない）。
- 理由（`mutation_scope`）: 否定や前提、宣言を同時に変えた変異は、出所の規則を壊さなくても自明に違反を作れるので、検出の確認にならない。

**判定への写し**

- 成り立つ・成り立たないと断定できた確認は `confirmations.deterministic` に入れる。成り立たない確認が 1 つでもあるモデルの性質は `deterministic_confirmed` が false で、検証の成功にならない（`確認が終わっていない` でも止まる）。
- 次は断定せず、判断を要する項目（`confirmations.judgments`）にする。項目そのものは判定の入力にも `confirmations_unresolved` にも数えず、項目ごとの意味の確認（下の判定への写し）が数える。
  - 前提と否定だけが unsat で前提に外部の依存があり、外部の依存の前提を外した実行が sat のとき（`外部の依存`）。外したのに unsat なら、外部の依存によらず前提だけで結論が出ているので `成り立たない` と断定する
  - 前提を外すと sat になる前提（`効いている前提`）と、上限で再検査しなかった前提（`上限を超えた`）
  - 規則と否定だけが sat なのに、前提を 1 つずつ外した実行が全て unsat のとき（前提が重なって結論を支える。`効いている前提の組`。`clause_names` は全ての前提）。規則と否定だけが sat なら、判断を要する項目が少なくとも 1 つ出る
  - 1 つずつ外して unsat だった前提が 2 つ以上あり、全ての前提ではないとき、それらをまとめて外した実行（規則・他の前提・否定を残す）が sat なら、その組（`効いている前提の組`。`clause_names` はまとめて外した前提）。unsat なら組は結論を支えていないとして `成り立つ` の確認にし、答えが無ければ `道具が判定できない`。組の作り方は 1 つだけで、unsat だった前提の全ての部分集合は調べない
  - 道具が unknown・時間切れ・失敗・未実行で答えを返さなかった実行（`道具が判定できない`）
- 理由: 外部の依存に支えられる前提で結論が出るのは正しいモデルでも起こり、前提が結論を支えること自体は欠陥でない。道具が答えなかったことを成り立たないと数えると、静的な確認の道具の失敗だけで性質が検証の成功にならない。
- 退けた案: 判断を要する項目を `確認できず` の確認として `deterministic` に入れる。`confirmations_unresolved` で完了を妨げ、意味の確認で確かめる経路が無くなる。

**判断を要する項目の意味の確認と、性質の意味の確認**

- CLI は確認の段の始めに、モデルごとに、そのモデルの性質の判断を要する項目を `judgments/<model_id>.json` に書き、そのモデルの忠実さの検証者の資料に入れる（項目の道具の実行の記録も入れる）。
- 忠実さの検証者は、返り値の `judgments` に、そのモデルの全ての項目に 1 つずつ答える。足りない・余る・重なる返り値は形の違いとして拒む（出し直せる）。CLI は項目ごとに、`kind: judgment`・`item` = 項目の `id` の意味の確認を作る。確認した者と渡した資料は、その忠実さの確認と同じである。
- inventory の性質の `meaning_confirmed` は、次の 3 つが全て成り立つときだけ true である（SP-012。判定の入力の正本は `artifact-formats.md` の確認）。
  1. その性質を持つモデルの忠実さの確認が 1 つ以上あり、全て `成り立つ`。
  2. その性質の判断を要する項目が無いか、全ての項目の意味の確認が `成り立つ`。
  3. その性質のモデルの性質の静的な確認（決定的な検査の記録）が 1 つ以上あり、全て `成り立つ`。結果の `reason` では、この条件の欠けを意味の確認の名前で書かず、決定的な検査の静的な確認として書く。
- 理由: 決定的な検査の成功で意味の確認を代えない（SP-012）。静的な確認が全て成り立っても忠実さの確認が要り、判断を要する項目が無くても忠実さの確認が要る。判断を要する項目が 0 件の性質を未確認にしないため、2 だけは空を成り立つとする（1 と 3 は空なら成り立たない）。
- 静的な確認が成り立たない性質は `deterministic_confirmed` も false である。3 と重なるが、決定的な検査の記録と意味の確認の記録を別々に判定する規則（SP-012）を、判定の入力でも保つ。

## 依存グラフと合成

依存グラフと分割は、次の 3 つを守る。

1. 状態遷移の辺は構文から導き、推定しない。
2. 分割前後の要素の対応を照合する。
3. 環境の前提は、依頼の既知の要求・制約で確かめる。

**グラフを構文から導く（SP-008、AC-06）**

- モデル作成役は、状態遷移の guard と update を SMT-LIB の項として書く。update は `{変数, 項}` の代入の一覧とする。形の正本は `artifact-formats.md` の model（モデル作成役）の節で、`schemas.mjs` の `MODEL` はその検査器である。
- CLI は `sexpr.mjs` で項を読み、読む変数（guard と代入の右辺の記号）と書く変数（代入の左辺）を構文から導く。全ての辺が構文から導かれるので、推定の辺は無くなる。
- SMT の query の依存は、`lib/adapters/z3.mjs` の `dependencies` で読む。
- 各ノードと辺は `location` を持つ。`model.json` の中の JSON Pointer か、`.smt2` の中の form の番号と文字の範囲である。
- 導けない関係は辺にせず、`graph.unconfirmed[]` に理由とともに入れる。例は、宣言の無い記号、配列の添字や関数の値で決まる参照など、実行時にしか決まらないもの。
- 理由: 辺を文字列の正規表現で推定すると、推定の辺が成分を跨ぐ分割を拒むことになり、成分の間に辺が 1 本でもあれば分割を採れない。境界の契約の経路が実際に動かなくなる（退けた案: 辺を推定する）。

**候補の導出と基準の出力（SP-008、AC-06）**

- 候補の導出は `lib/checks/graph.mjs` の `deriveCandidates` で行う。
  1. 書く変数とその遷移を同じ組にする。
  2. 読み込みの辺で強連結成分に縮約する。
  3. 名前の辞書順で決定的に並べる。
- 結果の `decomposition.criteria` には、適用し直せる形の基準を出す。
  - 組にする規則
  - 縮約に使う辺の種類
  - 同点の並べ方
  - 依存の強さの定義（成分の間の辺の数）
- AC-06 の検査は、この基準を別の実装で当て直し、候補が一致することを確かめる。
- 候補ごとに、他の候補との依存の強さを示す。

**採否**

- 候補が 2 つ以上あるときだけ、分割作成役が候補ごとの採否と理由、採る分割の契約を書く。
- CLI が機械的に照合し、合成の検証者が意味を確かめる。
- 採らないときも、採らなかった理由を `decomposition.decisions` に残す。
- 候補を得たことだけでは、独立に検証できると示さない。採否と照合の結果を分けて出す。

**分割したときの性質の扱い**

- 各部分の契約は、親の性質から作る内部の性質（`derived_from` に親の ID を持つ）とする。
  - 内部の性質は、部分のモデルの上で通常の検査（`kind: contract`。`checks[]` に入る）と判定を持つ。判定は同じ `aggregateProperty` で決める。入力の各欄の取り方は `artifact-formats.md` の契約の判定が正本で、親の性質の合成の条件を入力にしない（循環させない）。
  - 内部の性質は依頼元の「必要な性質」に数えない（SP-015 の完了の条件は親の性質で評価する）。
  - 結果では `properties[]` に入れず、`decomposition.contracts[]` に置く。理由は、`properties[]` を読む側（別のスキル、AC-02・AC-14 の検査）が、必要でない性質を必要な性質と読まないためである。
- 親の性質の検査は、合成の条件の検査（`kind: composition`）である。合成の条件も、契約と同じく `derived_from` に親の性質を持つ（形の正本は `artifact-formats.md`）。
  - 部分の契約の連言から親の性質を導く含意の検査と、横断する性質の合成後の検査がある。
  - これらが反する例を返せば、親の性質の `反例` になる。原因の分類役が、`形式モデルの欠陥`（契約が弱い）か `対象が性質を満たさない` かを根拠付きで分ける（SP-011）。
- 親の性質が `検証済み` になるのは、次の全てが成り立つときだけである（SP-009）。
  - 合成の条件の検査が全て成功した
  - 内部の性質が全て `検証済み`
  - 境界の契約の前提が全て満たされた（下記）
  - 分割前後の照合に対応の無いものが残らない
- 理由: 親の性質に部分の検査の成功を直接数えると、部分の成功だけで全体を検証済みとすることになる（SP-009 が禁じる）。
- 退けた案: 合成の義務の反例を `未確認` に読み替える。性質に反する例を返した検査の判定が、値の意味と食い違う。

**分割前後の対応の照合（SP-009、AC-07）**

- CLI は、分割前の要素を全て列挙する。要素は、要求・目標、性質、変数、遷移、依存グラフの辺である。
- 各要素を、分割後の部分・境界の契約・合成の条件のどれかに対応付ける。
- 結果の `decomposition.correspondence` には、次の 3 つを出す。
  - `matched[]`: 要素と対応先
  - `unmatched[]`: 対応の無い要素
  - `excluded[]`: 除外した要素と理由。ここで使う除外は、`verified_scope.exclude` のうち出どころ（`origin`）が `依頼元` のものに限る。`origin: "formal-method"` の除外（`.git`・保存先）は対象の定義の外なので、分割前の要素に現れない
- 対応の無い要素があれば、それに関係する親の性質を `検証済み` にしない（`未確認` の理由にする）。
- 理由: 一覧を結果に出すと、AC-07 が結果を外から突き合わせられる（退けた案: 件数だけを報告し、不一致を作り直しの欠陥にする。外から突き合わせられない）。

**境界の契約と前提（SP-009）**

- 分割単位の間に残る依存の辺ごとに、境界の契約（前提と保証）と、それを確かめる責任を負う契約（その `check_ids` の検査）を 1 つ以上持つ。CLI が辺の全数と照合する。
- 前提の出どころは、次の 3 つに限る。
  - 他の部分の保証（その部分の内部の性質の検査）
  - 環境
  - 共同不変条件（初期での成立と全遷移での保存を確かめる検査を持つ）。ただし今の版では、検査の作り手と id を決める経路が無いので受け付けず、分割の照合の欠陥とする（正本は `artifact-formats.md` の分割と合成）
- 環境の前提にできるのは、依頼の既知の要求・制約にあるものだけである。前提ごとに、その要求・制約の識別子を持つ。
- それ以外の環境の前提は「確認できない前提」とし、関係する親の性質を `検証済み` にしない。`verified_scope.external_assumptions` に挙げただけの外部のものも、これに含める。
  - 理由: `external_assumptions` は formal-method が対象から読み取ったものである。依頼元が与えた事実ではないので、それを根拠にした前提は、他の部分や環境が満たすと確認できたことにならない（SP-009）。
  - 理由: 環境の前提を確かめずに基底にすると、確かめていない前提で親の性質が `検証済み` になる（SP-009）。
  - 退けた案: `external_assumptions` も前提の根拠にする。
- 前提どうしの依存は DAG として照合する。循環は、共同不変条件の検査を持つときだけ許す（今の版では共同不変条件を受け付けないので、循環は常に欠陥）。相互の前提だけで結論を支える分割は、親の性質を `検証済み` にしない。
- 分割を採った計画の検査も、互いに依存しない限り並列に動かす。
  - 依存は、前提がその保証の検査を待つ関係として、計画の `depends_on` に書く。

## 性能の記録・比較・改善

**記録（SP-013、PR-036）**

- CLI は run と検査ごとに、次の値を `performance` に書く。
  - 準備（道具の発見と版の取得）・ビルド・検査・確認・保存の所要時間
  - 子 process の CPU 時間
  - 常駐メモリの最大値と標本の間隔（記録のためだけに測る）
  - 費用
  - 人の介入の回数
  - 再試行の回数
- 取得できなかった値は、`{"value": null, "status": "取得できず", "reason": …}` とし、0 と区別する。
  - 道具にビルドが無い場合も、0 ではなく `該当なし` と理由を書く。
  - 費用は CLI から観測できない。ホストが値を渡す口は作らず、`取得できず` とする。
  - 再試行は持たないので、常に 0 で、理由を添える。
- 実行の場所（`ローカル`・`CI`）は、環境変数 `CI` の有無で記録する。記録するだけで、振る舞いは変えない。
- 起動した担当の数と消費量（SP-013）は `performance.agent_calls` に、呼び出しごと・段ごと・全体で書く。値は `close` の受け箱が指す Workflow の返り値（`agents` と `tokens`）から作る。
  - 受け箱が無い・`timed_out`・形が違う・期限で閉じた呼び出しの起動の数と、`tokens` が null の呼び出しの消費量は `取得できず` と理由にする。
  - 段と全体の和は、含む呼び出しの値が全て取れたときだけ数で示し、1 つでも取れなければ `取得できず` にする。理由: 一部の和を示すと、0 や下限が全体の値に見える（SP-013 の「0 と区別」）。
- 初回とキャッシュの区別は記録しない。キャッシュを持たず（D4）、依頼者が仕様の側でこの区別を外すと決めたためである。

**道具の候補の比較（SP-007・SP-013）**

- 性能を比べる場面は、SP-007 の道具の候補の比較だけとする。run の外の結果どうしを比べるコマンドは持たない（[司令塔と CLI の分担](#司令塔と-cli-の分担)）。
- 候補の比較で性能（準備・実行の時間と資源の見積り、又は同じ run の中で測った値）の優劣を示すときは、`properties[].method.comparison_conditions` に、比べる実行の次の項目が一致するかを確かめた結果を書く。項目は、性質（ID と文の指紋）・前提・検査範囲・保証の種類と境界・判定の規則の版である。
- CLI が決定的に照合する。一致を確かめられない組には `一致を確認できず` と理由を書き、優劣を示さない（`method` の選んだ理由にも、性能の優劣を使わない）。
- 理由: SP-013 は、手法や道具の性能を比較するときに条件の一致を確かめることを求める。formal-method が比較する場面は SP-007 の候補の比較なので、そこに条件の照合を付ける。
- 退けた案: 2 つの結果を受け取る `compare` コマンド。依頼の項目以外の入力の口になる（仕様の外部インタフェースの節、検証方法の節）。

**改善の候補**

- 集約の段で、CLI は性能の記録から測定上の問題を決定的に挙げる。例は、時間の上限への接近、道具自身の時間の上限、道具の `unknown`。
- 問題ごとに、検査範囲と保証を保つ改善の候補を、定数の一覧から結び付ける。例は、検査を分ける、道具の時間の上限を上げる、単独で動かす。
- 検討の結果は「この run では採用しない」として記録する（D4。run の中で計画を変えない）。
- 結果は、条件の一致を確かめていない改善・優劣を示さない。結果に現れる優劣は、`comparison_conditions` で一致を確かめた組のものだけである。
- 改善の採用は run の外の判断（スキルの開発、又は依頼元の次の依頼）であり、formal-method は行わない。

## 作業記録と記録台帳

- 担当（作成役・独立検証者）は、自分の attempt の領域に作業記録を書く。欄は PR-028 の 9 項目（担当、段、対象、入力、実行内容、結果、根拠、失敗、未確認）である。
- CLI の決定的な処理も担当（`cli`）として、段ごとに同じ欄の作業記録を書く（PR-028 の「担当ごと」）。
- 記録台帳（`ledger.json`）は CLI だけが書く（PR-029）。各記録の参照・指紋・段・担当・model・effort・渡した資料の参照と指紋を持つ。
- 同じ内容を複数の記録に正本として書かない（PR-032）。
  - 判定の正本は結果。
  - 検査の生の入出力の正本は `checks/<id>/` の証拠。
  - 他の記録は参照で指す。
- 文書の一般規約（PR-040）は、配布物に同梱した写し `references/document-rules.md` を使う（依頼者の決定）。
  - 正本は `docs/guidelines/documentation.md` である。同梱の写しが正本と一致するかを、`make test` の検査が確かめる。
  - 作業ツリーにある正本を優先する経路は持たない（依頼者の決定）。理由: 実行する場所によって適用する規約が変わると、run ごとの記録の書き方が揃わない。
  - 受付で写しのバイト列の指紋を版とし、不変の写しを run の領域に保存する。各作業記録は、その版と写しへの参照を持つ（PR-040）。
  - 依頼の項目に規約の場所は無いので、依頼から受け取る口は作らない。
- 保存できた記録は、利用者が消すまで残す（PR-034）。CLI は run の領域を消す手順を持たない。

## 未検証と限界

- **CPU とメモリ**: 上限を持たない（要求・仕様の対象外）。同時に動かす数は内部の選択で、実行環境の CPU の数を超えない。メモリの使い方は記録するだけで、守らない。
- **ホストの時間の上限**: 前景の 1 回の呼出しは `CALL_MAX_MS` 以内に返る。ホストの上限が `CALL_MAX_MS` + `CALL_MARGIN_MS` より短い環境は対象外とする。Codex の上限は確かめていない。
- **配布先と detach**（設計の前提）:
  - 配布先は、今は Claude Code だけとする（依頼者の決定）。
  - 確かめた範囲: Claude Code（デスクトップ、macOS arm64、2026-11-08）の Bash で、Node から `detached: true` と `unref()` で起動した process は、前景のコマンドが終わった後も生き続けた。親は pid 1、process group は自分の pid だった。
  - 確かめていない範囲: session の終了やアプリの終了の後も生きるか、Linux での振る舞い。終了で殺される場合は、`wait` が `E_STALE` を観測し、salvage が保存済みの範囲で結果を作る（設計の範囲内の振る舞い）。
  - **Codex**: 未検証である。コマンドの時間の上限と、detach した process の扱いを、公式の文書でもリポジトリ内の記述でも確かめられなかった。公式でない資料には、コマンドの timeout で process group に SIGKILL を送る修正が見えるが、既定の上限の値は食い違う。公開のときに実測して扱いを決める（依頼者の決定）。
- **ホストに殺された `start` の `.tmp-*`**: `start` がホストに殺されると、自分が起動した process の一時の領域を消す者がいない。残った `.tmp-*` は誰も消さない。`.tmp-*` は run としても結果としても扱わないので、結果は増えない。
- **Z3 の出力の実測**: macOS arm64・Z3 5.3.3 だけで測った。Linux では未測定である。
- **salvage の所要時間**: salvage の結果を決定的に作るため、salvage の所要時間と run 全体の所要時間は `取得できず` と理由で記録する。
- **結果を返す経路**: `run-daemon` と前景の間はファイルだけでつなぐ。保存先に全く書けなくなった後の結果は、salvage が保存済みの範囲から作る。`run-daemon` がメモリに持っていた、保存前の判定は失われる。
- **macOS の時計**: `os.uptime()` は単調時計ではない。壁時計との併用で期限が延びる経路は塞ぐが、判定は最大 1 秒遅れうる。
- **担当の書込み範囲**: 担当は `workspace-write` で動くので、attempt の領域の外（状態・台帳・他の担当の領域）を書けてしまう。台帳に書かないこと（PR-029）と作成側の作業記録を読まないこと（独立した確認）は、担当の義務だけで守る。
  - CLI は、登録した成果物の改ざんを指紋で見つけるが、登録の前の書換えは見つけられない。
  - この限界は結果の `unverified[]` に載せる。
- **記録した model・effort**: 記録は、CLI が workers の行に書いた値である。ホストが実際にその値で動かしたかは確かめられない。
- **担当の応答の待ち**: 担当の 1 回の `claim`・`query`・`submit` は `WORKER_CALL_MAX_MS` まで `run-daemon` の応答を待つ。`run-daemon` の照合が重く上限に当たると、担当は `no_response` を受け取り、同じ命令を流し直す。上限に当たる重さは実測していない。
- **tokens**: Workflow の返り値の `tokens` は `budget.spent()` の差である。autonoia での実測（run 44032e）では、script の `tokens` の合計は約 32 万で、Workflow の完了通知の subagent tokens（cache の読み込みを含む）の合計の約 154 万の約 2 割しかなかった。`tokens` は担当の消費の下限であり、通知の値より小さい。値の取り方は変えず、下限として記録する。
- **詰め合わせ**:
  - 1 体に詰めると、同じ体の中で前の unit の判断が後の unit に影響しうる。unit ごとにその unit の資料だけで判断する義務（`agent-obligations.md`）だけが守りで、機械では止められない。
  - 上限の 1 token あたりのバイト数は 1 つの run（日本語の文書 2 つ）の実測で、他の言語やコードの対象では比が変わりうる。往復による増分も、同じ run の担当 15 体で見ただけである。
  - 判断を要する項目の検査の記録（`checks/<id>/`）が多いモデルでは、忠実さの 1 unit が上限を超え、1 体に 1 unit のままになる（run ba04a7 の数え直しでは m-apply の unit が約 160KB）。
  - 確認役を作成役と別のモデル（値は `scripts/lib/roles.mjs`）にして、検出が作成役のモデルより落ちないかは確かめていない。
  - 節の役の付け方が偽られたときに止めるのは、忠実さの検証者だけである。
- **`define-fun` の本体の制約**: 静的な確認は assert だけを切り取るので、`define-fun` の本体に置いた制約は、参照する節が残る限り切り取られない。CLI が止めるのは、宣言した記号を本体に含む定義を役の違う節が参照する形だけである。1 つの役の節だけが参照する定義の本体に別の役の制約（例: 前提にすべき制約を規則の節が参照する定義に置く）を書いた形、定数や引数だけの関数の定義で値を固定して範囲を狭める形は、機械では止められず、忠実さの検証者が本体を参照する節の役の制約として読んで確かめる（`agents/fidelity-reviewer.md`）。
- **秘密値の走査**: 誤検知の少ない 4 つの型に絞ったので、それ以外の形の秘密値（`password=` の代入など）は見逃す。対象のファイルは写さないので走査しない。
- **対象の固定**（[対象の固定](#対象の固定)）:
  - 固定の前提は、集約の段の読み直しと、担当の `query` の時点の指紋でしか確かめない。途中で変わって元に戻り、その間に `query` が無ければ見つけられない。この限界は結果の `unverified[]` に載せる。
  - 写しをやめたので、`revision` の無い対象は、run の後に変わると、担当が読んだ内容を記録から取り戻せない（指紋で不一致は分かる）。`revision` つきの対象は、記録の版と指紋から git で辿れる。SP-014 の記録の範囲に対する限界で、依頼者の決定（対象は固定している前提、写しを持たない）を優先した。
  - 担当が範囲（`spans`）の外を読まない義務は、CLI が機械では止めない（`agent-obligations.md`）。
- **子 process**: 子 process が別の process group へ移ると、group ごとの停止が届かない。
- **結果の link の後の失敗**（依頼者の決定）: 結果の link に成功した後に fsync か再読込が失敗した `result.json` を、R の `records.saved` に保存したものとして示す（`cli-contract.md` の「link の後の失敗」）。
  - `reread_io` の場合、後の salvage の読み出し（規則 2）が `E_RESULT_UNREADABLE` になりうる。
  - 再読込で中身が食い違う（corrupt）場合、形に合えば、誰も作っていない中身を結果として返しうる。
  - SP-014 の「保存できなかった記録を保存したと示さない」と、SP-015 の「記録を全て保存した」に対する限界である。結果を常に 1 つにすることを優先した。
- **生死を判定できない環境**: `ps` が使えず、pid が再利用された場合は、生死が分からないまま待つことになる。司令塔は `LIVENESS_UNKNOWN_MAX` 回の後、結果を作らずに「生死を判定できない」誤りとして終える（依頼者の決定。形式検証の `lock-termination`）。この場合、結果は返らない。
- **仮の結果**: 保存できない状態で返した `停止` の R' は `provisional: true` の仮の結果である。あとで別の salvage が `result.json` を公開すると、受け取った仮の結果と公開された結果が食い違う（形式検証の 4 ケース。生死の誤判定が無くても、`status.json` が読めないだけでも起こる）。依頼者の決定で、公開された `result.json` を正とする。公開される `result.json` は常に 1 つである。
- **`run-daemon` の異常終了**: 保存の途中で落ちた run は続けない。`salvage` が、rename を終えた `state.json` の範囲だけで停止の結果を作る。
