## 構成（ブラックボード）

| 部品 | 実体 | 持つもの |
|---|---|---|
| ボード | `stateDir/ledger.json`（`hints.jsonl` と写しの `snap/` は別ファイル） | 目標・受け入れ基準・制約・決定の記録・計画・資産・枡・指摘・出来事・束・起動の記録 |
| 知識源 | Workflow source の役（`scripts/roles.json`） | 1 体 1 単位の判断だけ。ボードも対象も書かない |
| 制御 | `scripts/ledger-cli.mjs`（`next` と `ingest`） | 次の 1 手の決定、受け入れ、止める判定 |

探索グラフの事実は台帳の記録（受け入れた読み・確かめた指摘・束・出来事）で、意図は `next` が台帳から導く次の 1 手（読む枡・横展開の観点）。出来事 → 束（根本原因と層）→ 横展開の観点、の辺は ID で辿れる（`events[].ref`・`groups[].keys`・`lenses[].origin`）。

## 段と、script と LLM の分け方

| 段 | LLM がすること | script がすること |
|---|---|---|
| init | なし | 目標・基準・制約の各項目に引用があり、引用が依頼文か決定の記録に逐語であるか（`readGoalFiles`）。通らなければ台帳を作らない。照合済みの印（`--goal-checked coverage-build`）があれば照らさない |
| plan | 目標の照合（依頼文と決定の記録が求める成果を引用つきで挙げ、受け止める項目の id を付ける。照合済みの印があれば流さない）、独立な計画役 2 体（別のモデル）が観点を切る、統合、観点ごとの反証 | 照合役の成果の引用の実在・項目の id の実在、受け止められていない成果を人間に返す（`checkGoalMap`・`goalGaps`）。対象の索引の写し、観点の形・ID の重複・基準と制約の受け皿・source_map・欠陥への応答の網羅、観点の同一性（中身の hash） |
| review | 枡ごとに読む役、枡ごとに別のモデル・反証側の検証役 | 枡の生成、写しの hash の照合、区画ごとの読んだ証拠の照合、指摘の引用の照合、判定の網羅、偽の引用での判定を検証不能にする |
| retro | review と同じ（資産が出来事、観点が R1〜R4） | まだ振り返っていない出来事を段ごとに 1 行 1 件で並べ、`MAX_ASSET_LINES` 行ごとの資産に分ける。区画は通常の資産と同じ式 |
| group | 根本原因で束ねる、別のモデル 2 体で反証 | 全件の写し、全 key がちょうど 1 つの群に入るか、層の値、横展開の観点の追加 |

静的な照合の正本は Workflow source の `// <checks>` 区間だけで、CLI は同じ文を読み込んで `ingest` で照らし直す（runner の source は import できないので、写しを持たずに 1 か所にするため）。Workflow は本文を持たないので、Workflow の中では形だけを照らして 1 回やり直させ（`checkReadShape`）、引用の逐語と区画の照合は `ingest` が写しに対して行う（`checkRead`）。目標の照合役の引用（依頼文・決定の記録）と、前の計画の観点への検証役の引用も同じく、Workflow は形と id だけを照らし、逐語かは `ingest` が照らす。引用が合わない読みは試行に数え、次の呼び出しで読み直す。目標の照合の静的な部分（`// <goalmap>`）は coverage-build の Workflow source と同じ文を置き、一致は `tests/coverage-build-goalmap.test.mjs` が照らす（2 つのスキルは互いのファイルを読まないため）。照合役には、項目が依頼に無いものを足したか・範囲を狭めたかを判定させない（判定が回ごとに揺れたので）。足していないことは init の引用の照合が、落とした要求は対応の無い成果が示す。呼び出し側が args を運ぶので、source は args の FNV（`argsSum`）を照らし、合わなければ役を起動せずに止まる。

## 写しと ID と持ち越し

- 写し: `next` は対象のファイルを読んだその内容を `stateDir/snap/<内容の hash>.txt` に書き、args にはその path・行の範囲・範囲の hash だけを載せる。担当は Read で自分の範囲だけを読む。索引（計画役）と指摘の全件（束ね役）も同じ形で渡る。担当が読む文（目標・基準・制約・依頼文・決定の記録・ヒント・回答・前の計画・計画の欠陥・観点の手続き）も、呼び出しごとの束（brief）の写しで渡り、args には id・件数・役の設定と写しの参照だけが残る（args の大きさは文の長さや件数に比例しない）。`ingest` は args が指す写しの範囲の hash を照らし、違えば台帳を変えずに拒否する。写しの名前は内容で決まるので、同じ状態の `next` は同じ `call_id` を返す。
- 資産: Markdown は見出しの経路（`path#親/子`）、それ以外は `CHUNK_LINES` 行の塊（`path#cN`）。1 体が読む範囲は `MAX_ASSET_LINES` 行まで。見出しだけの塊は資産にしない。
- 区画: 資産の本文をおよそ `BLOCK_LINES` 行ごとに、`MAX_BLOCKS` 個までの窓に分け、各窓から 1 つ以上の逐語の引用を求める。
- 枡: `資産|観点|p回`。回は 1..k で、全ての枡に同じ k を使う。
- 指摘: `枡#hash(引用+主張)`。同じ枡の別々の指摘は潰れない。
- 持ち越し: 台帳は run をまたいで残る。`next` のたびに対象を読み直し、資産の hash か観点の版（名前・手続き）が変わった枡だけを未読に戻す。前の指摘は superseded にする。消えた資産の枡は gone。その周の振り返りと束ねが済んだ後に読む枡が出たら、`next` は新しい周を開き、新しい指摘も振り返り・束ね・横展開を通す（持ち越しも周を使うので `max_cycles` に数える）。
- 試行の回数（枡・観点の検証・束ね）と周の数は台帳にあり、再開しても 0 に戻らない。

## 止める条件

`next` が返す `stop` の種類と、その条件。上から順に判定する。

| stop | 条件 | 再開のしかた |
|---|---|---|
| blocked（cause: input） | 台帳を作った後に対象のファイルが読めなくなった（init の時点で読めなければ台帳は作られず、init からやり直す） | 置き場を直して `next` |
| blocked（cause: failure） | 全ての役が欠けた呼び出しが `MAX_FAIL_STREAK` 回続いた | 環境を直して `next` |
| limit | 周が `max_cycles` を超えた、起動数が `max_agents_total` に達した | `config` で上限を上げて `next` |
| needs_input | 依頼文・決定の記録が求める成果を、どの項目も受け止めていない（`goal_gaps`）／試行の上限まで欠けた段がある／計画の欠陥が統合のやり直し `PLAN_ROUNDS` 回で消えない／利用者への質問がある | `answer`（`goal`・`criteria`・`constraints`・`decisions` は `--file`、質問の id・`attempts:<キー>` は `--text`）を足して `next` |
| blocked（cause: target / failure） | 枡が 0 件／読みを受け付けた枡が 1 つも無い | 対象を直すか、原因を直して `next` |
| needs_input | 上の層（方針・要求）が原因の指摘（`upper`）・束（`upper_groups`）、検証不能の指摘（`unverifiable`）が残る | 指摘の id か束の id で `answer` |
| complete | 読み直す枡が 0、この周の振り返りと束ねが済み、上の全てに当たらない | 対象が変われば、同じ台帳で `next` が変わった枡だけを読み直す |

- 枡の状態: unseen →（読みを受け付け、指摘があれば全て検証役が判定）settled、欠けが `MAX_ATTEMPTS` 回で disclosed。指摘の無い settled の枡は検証役を通っていない（見ただけ）ので、`coverage.settled_no_findings` として別に数える。
- 全ての役が欠けた呼び出しの試行は別に数え、blocked（failure）から再開したときに戻す（環境の失敗で枡を開示に倒したままにしない）。
- 束ねの段で反証役の枠を超えた群は unverified のまま残し、横展開の観点も作る（絞らないため）。`status` の `groups` で状態が分かる。
- 振り返りは、その周までにまだ振り返っていない出来事を全て拾う。振り返りの後に起きた出来事は次の周で拾い、最後まで拾えなかったものは `status` の `events_not_in_retro` に残る。
- 飽和（周ごとの新しい確かめた指摘の数）は `status` の `saturation` に記録するだけで、止める条件に使わない（新しい指摘が 0 件でも見落としが無いとは言えないため）。

## 記録

- 起動ごとに役・label・指定した model・effort・成否（`agents`）、呼び出しごとに起動数・欠け・token（`calls`）。token は native の `budget.spent()` が読めるときだけ数で、runner では null と理由を残す。model は指定値で、実際に効いたかは確かめられない。
- 観点の外の気づきは枡ごとに残し、`status` の `outside_notes` で返す。効果の根拠は無い（開示して使う）。
- 較正: `init --seeds` に既知の欠陥（`[{path, quote, lens?}]`）を渡すと、`status` の `calibration` が観点 × 読む役（回）ごとの再現率を返す。仕込んだ欠陥を入れた対象は利用者が用意する。

## 汎用の設計の型から変えた点

このリポジトリの Workflow の設計の型（状態を CLI だけが書き、run の中では運搬役が CLI を呼んで出力を script へ運ぶ形）から、次の点を変えている。

- 運搬役を置かない。状態を書くのは CLI だけという点は守り、CLI は Workflow の外で呼び出し側が流す。1 回の Workflow は 1 段を 1 回だけ流し、ループは台帳と `next` が持つ。運搬役の失敗・写し違い・競合の種類の欠陥を作らないため。
- 状態の寿命を 1 run でなく、run をまたぐものにする（利用者の決定）。対象が変わっても新しい状態から始めず、同じ台帳で変わった枡だけを読み直す。
- 重要度で枡を絞らない。全ての枡を同じ扱いにし、独立は別のモデル・別の枠組み（反証側）・新しい context で作る。Anthropic のモデルどうしなので盲点の重なりは減りにくく、結果にそう開示する。
