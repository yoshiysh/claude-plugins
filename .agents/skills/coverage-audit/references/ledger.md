## 構成（ブラックボード）

| 部品 | 実体 | 持つもの |
|---|---|---|
| ボード | `stateDir/ledger.json` | 目標・受け入れ基準・制約・決定の記録・段（`phase`・`phase_start`・`phase_records`）・観点・計画・単位・事実（`facts`）・意図の試行・横展開の型・束・出来事・起動の記録 |
| ボードの周りのファイル | `stateDir` の下 | 写し（`snap/`）、ヒント（`hints.jsonl`）、呼び出しの args（`call-<callId>.json`）、役の結果（`results/`）、段の位置（`phase.json`）、止まったときの status（`status-<段>.json`。段の無い台帳は `status.json`）、役の入口（`ledger-cli.mjs`）、lock（`ledger.lock`） |
| 知識源 | Workflow source の役（`scripts/roles.json`） | 1 体 1 担当の判断だけ。台帳を直接書かず、対象も書かない |
| 制御 | `scripts/ledger-cli.mjs` | 次の 1 手の決定（`next`）、呼び出しを閉じる（`ingest`）、役の読み書き（`claim`・`query`・`submit`）の受け入れ、意図の生成、票の集約、止める判定 |

台帳を書くのは CLI だけで、役の出力は返り値・args・prompt で運ばない。役は `claim` で担当を取り、`query` で入力を引き、`submit` で結果を出す。運ぶ工程を無くせば、長い値の写し違いと、照合を通らずに次の役へ渡る経路が構造として無くなるため。

`ledger.json` は今の形の欄（目標の項目・段の記録・事実・意図の試行・横展開の型など）を持たなければ、init 以外のコマンドが読み込みで拒否する。形の違う台帳は新しい `stateDir` で init からやり直す。

## 呼び出しと役の読み書き

- 呼び出しを開く: `next` は次の段を決め、args `{state, callId, stage, workers}` を `call-<callId>.json` に書いて、その path（`args_path`）を返す。`workers` は役の行 `{id, role, model, effort}` の配列で、段と担当から役の名前への対応は ledger-cli.mjs の `stageTasks`・`INTENT_ROLE`、役のモデルと effort は台帳の役の設定（`roles.json` に `init --roles` の上書きを重ねたもの）が決める。`estimate_agents` は行の数。ファイルの段と横展開の行は 1 単位に 1 体で、読む単位の数を `meta.limits.maxAgents` と残りの起動数の予算（`max_agents_total`）に収めた数にし、残りは次の呼び出しで読む。`config --workers` が決めるのは、全体の段の名寄せ・判定・確認の行の数だけ。
- 冪等: 開いた呼び出し（`pending`）がある間の `next` は、同じ `call_id` と `args_path` を返す。対象の読み直し（変わった単位を読み直しにする）だけは流す。Workflow が途中で落ちても、`next` からやり直せば同じ呼び出しに戻る。
- Workflow: `scripts/coverage-audit.js` は args を照らし、行ごとに役を 1 体起動する（`meta.limits.maxAgents` まで）。prompt には担当を取る命令と手順・結果の形だけを置き、命令は `stateDir/ledger-cli.mjs`（init と next のたびに CLI が書き直す、本物の CLI を流すだけの入口）を使う。args で CLI の置き場を運ばないため。返り値は起動の記録と token（`{agents, tokens}`）だけ。
- 閉じる: `ingest --call <callId> --result <返り値のファイル>` は、その呼び出しを閉じるだけ。返り値から読むのは `agents` と `tokens` で、役の出力は既に `submit` で台帳にある。取ったまま提出されなかった担当は試行に数え、反証の票はここで集める。待っている呼び出しと違う `--call` は拒否する。
- `claim --call --worker`: 今の呼び出しの行の worker からだけ受け付ける。担当を 1 つ（`tasks`）と、提出の命令 `submit_cmd` を返す。出し終えていない担当を持つ worker には、それを同じ形で返し直す。取る物が無ければ `done`。返す前に結果の path（`results/<call>/<worker>/` の下）の古いファイルを消す。
  - ファイルの段: まだ読んでいない単位を 1 つ取り、単位（写しの file と行の範囲）・観点の一覧・義務（目標と受け入れ基準）・ヒントを返す。1 worker は 1 単位だけを読み、出し終えた（受理か開示）後の claim は `done` を返す。同じ文脈で次の単位を読ませないため。横展開の意図も同じ。
  - 全体の段: 行の種類の開いた意図を 1 つ取る。
  - ほかの段: 行に結んだ担当を返す。
- `query --call --worker --task [--fact <id> ...]`: 担当の入力を台帳から引く。全体の段は、意図の根拠（`basis`）と関係する事実（`related`）と、載せなかった事実の宣言（`omitted`。目標の判定は `omitted_ids`・`omitted_more`）だけを返し、`--fact` で事実を id で引き直せる。ほかの段は、その担当に要る文（目標・依頼文・索引・案・欠陥・回答・観点・指摘）だけを返す。ファイルの段の担当は拒否する。他の単位の書き込みを読まずに独立に読ませるため。
- `submit --call --worker`: その worker が取って出し終えていない担当のうち、結果のファイルがある担当を全て照らし、担当ごとの `results`（`ok`・`problems`・`dropped`）と、ファイルの無い担当の `missing` を返す。照合に落ちた担当は理由を返して試行に数え、結果のファイルを消す（直さずに流し直しても missing になり、同じ中身で試行を重ねない）。`MAX_ATTEMPTS` で、単位は開示（disclosed）、意図は判定できなかった意図（undecided）に倒し `dropped` を返す。今の呼び出しと違う call・行に無い worker は、台帳を変えずに終了状態 2 で拒否する。
- lock: 台帳を書くコマンドは load から save までを `stateDir/ledger.lock`（`openSync` の `wx`）で囲む。待つのは `LOCK_WAIT_MS` までで、超えたら台帳を変えずに拒否する。lock は古さによらず自動で消さない（自動で奪うと 2 つの process が同時に台帳を書く窓ができる）。mtime が `LOCK_STALE_MS` より前なら、CLI が動いていないことを確かめてから手で消すよう案内する。lock には取得ごとの token を書き、自分の token のときだけ消す。
- `call_seq` は呼び出しを開くたびに進み、`callId` に入る。閉じた呼び出しへの遅れた claim・submit は拒否される。

## 段と、script と LLM の分け方

`next` が段を決める。目標の照合 → 観点の計画 → ファイルの段 → 全体の段 → 振り返り → 束ねと反証の順で、横展開の型が出たら次の周に進む。

| 段 | LLM がすること | script がすること |
|---|---|---|
| init・reframe | なし | 目標・基準・制約の各項目に引用があり、引用が依頼文か決定の記録に逐語であるか（`readGoalFiles`）。通らなければ台帳を作らない・変えない。照合済みの印（`--goal-checked coverage-build`）があれば照らさない |
| goal_check | 照合役が、依頼文と決定の記録が求める成果を引用つきで挙げ、受け止める項目の id を付ける。印のある台帳では流さない | 引用の実在・項目の id の実在（`checkGoalMap`）、どの項目にも受け止められていない成果を人間に返す（`goalGaps`） |
| plan・integrate | 独立な計画役 2 体（別のモデル）が、既にある観点（query の `given_lenses`。呼ぶ側の観点と標準の観点）に足す観点・受け持つ目標の部分（`goals`）・制約の受け皿（`constraint_map`）・質問を作り、次の呼び出しで統合役が 1 つにする（見直しでは前の計画と欠陥・回答から） | 観点の形・id の重複・既にある観点の定義し直しの拒否・part の逐語と、呼ぶ側の観点が無いときだけ目標と基準の被覆（`checkGoals`。呼ぶ側の観点があれば、目標の項目は全体の段の goal の意図が受け止める）・制約の受け皿・source_map・欠陥への応答の網羅（`checkPlan`）。計画役・統合役の落ちた提出は 1 回出し直させ、出し直しでも残る外れは案に添えて受け取る（統合役の外れは計画の欠陥 `P<n>`）。呼ぶ側の観点があるときの提案が試行の上限まで出なければ、出来事 `plan_skipped` を残して、呼ぶ側と標準の観点で読み進める（提案は足すだけなので止めない） |
| unit_verify | 観点の検証役が観点ごとに閉じた問い（Q1: 何を列挙するか、Q2: 何と照らすか、Q3: `goals` の要素ごとにその部分が果たされたかを確かめられるか）だけに yes/no と引用で答える | 答えの過不足・yes/no・引用の逐語と自由な欠陥の拒否（`checkUnitVerdict`）、no の答えだけを計画の欠陥にする（`unitDefects`） |
| file | 読む役が単位を 1 つずつ取り、全文を全ての観点で読み、観点ごとの「見た」・指摘・参考・保証と前提を書く | 結果の照合（`checkFileResult`）: 観点ごとにちょうど 1 つの答え（閉じた集合）と逐語の引用、指摘の義務・確信度・原因の層、found の観点の指摘。受理した読み（本文の版・観点の組の版・役の条件・答えと引用）を単位に置き、事実を足す（`factsOf`） |
| global | 全体の段の役が意図を 1 つずつ取り、根拠と関係する事実だけを引いて判定する（下の「全体の段」） | 意図の生成、判定の閉じた集合と引用の照合（`intentProblems`）、受理した判定と足した指摘を事実にする |
| retro | なし（Workflow を起動しない） | まだ振り返っていない出来事を段ごとに 1 行 1 件で並べ、`UNIT_MAX_BYTES` に収まるよう行の境目で分けて振り返りの単位にする（`retroAssets`）。この単位は次のファイルの段で、振り返りの観点（R1〜R4）で読まれる。印のある台帳では単位を作らず、出来事を `status` の `events` で返す（振り返りの探索グラフを coverage-build の 1 つに寄せるため） |
| group | 束ね役がこの周に確定した指摘を根本原因で束ね、群ごとに既にある横展開の型の例（`extends`）か新しい型（`pattern` と当たる単位 `applies_to`）かを返す。確定した指摘が無い周は起動しない | 全 key がちょうど 1 つの群に入るか、層の値、`extends` が今ある横展開の型の id か、新しい型の `applies_to` が実在する単位か（`checkGroups`）。`extends` を持ち層が `UPPER` でない群（`linkOnly`）は反証に回さない |
| refute | 反証役 2 体（別のモデル）が群の根本原因の主張を反証する | 票を `ingest` で集め、群の状態（kept・split・refuted・unverified・linked）を決め、反証されていない新しい型だけを横展開の型にする |

静的な照合の式の正本は Workflow source の `// <checks>` 区間で、CLI（ledger-core.mjs）は同じ文を読み込む（runner の source は import できないので、写しを持たずに 1 か所にするため）。ファイルの段の結果の照合（`checkFileResult`）と意図の判定の照合は CLI だけが持つ。目標の照合の静的な部分（`// <goalmap>`）は coverage-build の Workflow source と同じ文を置き、一致は `tests/coverage-build-goalmap.test.mjs` が照らす（2 つのスキルは互いのファイルを読まないため）。照合役には、項目が依頼に無いものを足したか・範囲を狭めたかを判定させない（判定が回ごとに揺れたので）。

観点の検証役に閉じた問いだけを聞くのは、大きさ・層・制約との矛盾などを自由に判定させると、統合のやり直しのたびに新しい欠陥が出て `PLAN_ROUNDS` で止まったため。手続きの細部の良し悪しは、読んだ結果（見落とし・判定できなかった意図・振り返り）で直す。統合役が閉じた問いから作った欠陥に `rejected` と応答しても、その観点は検証済みにならず、次の検証で同じ問いに答え直す。計画の欠陥の id `P<n>` は台帳の連番で、前の番号を使い回さない（`answer --id P<n>` が今の欠陥だけを指すため）。

引用の規則の文 `QUOTE_RULE` は `<checks>` 区間の定数で、照らす関数（`quoteProblem`）と同じ字数の定数から作り、本文を引く段（unit_verify・file・global）の prompt だけに載せる。`CITE_RULE`（`<goalmap>` 区間）は目標の照合役に載る。食い違う規則を 2 つ並べないため。

## 単位と観点と持ち越し

- 単位: 対象のファイル 1 つを 1 単位にし、id はファイルの path にする。本文のバイト数が `UNIT_MAX_BYTES` を超えるファイルだけを、構造の境目で同格の単位に分け、ファイルを隙間なく覆う（`splitAssets`）。細かく切ると文脈が落ち、無意味な指摘が増えるため。
  - Markdown は最も上の階層の見出しの境目で分けて上限まで詰め、1 つの節で収まらなければ下の階層の見出しで分ける。code fence の中の `#` は見出しにしない。
  - JS・MJS はトップレベルの文の境目（宣言の直前のコメントを含む）で分けて詰める。
  - 境目の無い所は空行、それでも収まらなければ行の境目で分ける。
  - 分けた単位の id は `<path>#<位置>`（見出しの経路・宣言の名前・`c<n>`。同じ位置は `~<k>`）。位置を構造から決めるので、大きさを変えない書き換えでは、書き換えた単位の外の id と hash は変わらない。
- 写し: `next` は対象のファイルを読んだ内容を `snap/<内容の hash>.txt` に書き、単位は写しの file と行の範囲と hash を持つ。役は写しを Read で開く。`submit` は写しの hash が台帳と違えば受け付けない。
- 観点: 呼ぶ側が `--lenses` で渡した観点、仕組みの標準の観点（`STANDARD_LENSES`。観点を絞らない通読を含む）、計画の観点の和を、一覧で全ての単位に渡す。呼ぶ側の観点だけでは呼ぶ側の死角を共有し、固定した観点の外の欠陥を落とすため。当てる単位は選ばない（当たらない観点には、読む役が not_applicable と引用を書く）。振り返りの単位には振り返りの観点だけを渡す。`reframe --lenses` は利用者の観点を差し替え、渡さなければ今の利用者の観点を保つ。
- 持ち越し: 台帳は run をまたいで残る。`next` のたびに対象を読み直し、本文の hash か観点の組の版（渡す観点の id・名前・手続き）が変わった単位だけを読み直しにし、消えた単位は外す。止まった後に対象が変わったら新しい回（`round_start`）を始め、前の回の読みは持ち越し（`status` の `units[].carried`）として新しい読みと分けて数える。読み直した単位は前の読みの hash と周（`prior`）を残し（手続きが変わって全てを読み直す reframe でも残す）、確定した指摘の出どころ（`provenance`: new・missed・fix・carried）を指紋の照合だけで決める。関わる単位は指摘の場所の単位で、全体の段が足した指摘では、それを足した意図の根拠と関係する事実の単位も含める。周の上限は今の回の始まりから数える。
- 意図の開き直し: 意図の鍵は根拠の事実と、それを足した読み（か判定）の組なので、単位を読み直せば、その単位の事実を根拠に持つ意図は開き直る。無いことを根拠にした判定（目標の gap・前提の unsatisfied）は、どれかの単位の読みが変われば開き直る。変わった単位が抜けを埋めたかもしれないため。
- 段と reframe: 台帳は呼ぶ側の段（`phase`）をまたいで 1 つ。`reframe` は照合済みの印のある台帳だけを受ける。
  - 同じ段で手続きの指紋（利用者の観点・目標・基準・制約・決定の記録・link）が前と同じなら `kept: true` で、対象だけを差し替え、`phase_start` の `reframes` を 1 つ増やす。読み直すのは次の `next` で内容の変わった単位だけで、止まった後なら新しい回を始める。
  - それ以外は、出ていく段の節（`findings`・`groups`・`events`）を `phase_records[<段>]` に写し、計画・回答・横展開の型・束・試行・pending を捨て、全ての単位を読み直しにし、周を 1 つ進めて `phase_start`（周・起動数・出来事の数）を置く。中身が同じでも読み直すのは、手続きを変えたら全体を検証し直すため。
  - init と reframe は段の位置（`phase` と `phase_start`）を `phase.json` に書く。呼ぶ側は台帳を読まずにこれを読み、`phase_start` が変わったことで reframe が流れたと判じる。
- 試行の回数と周の数は台帳にあり、再開しても 0 に戻らない（reframe は段を始め直すので試行を捨てる）。

## 全体の段（探索グラフ）

事実（グラフの点）は CLI が受理したものだけ: ファイルの段の指摘・参考・保証・前提、静的な検査の結果、全体の段の判定と、判定が足した指摘。意図（次に調べること）は、今の根拠の事実から CLI が毎回決定的に導く（`board`）。役は意図を出さない。何を調べるかは事実の種類で決まり、判断に任せると意図の漏れが run ごとに変わるため。

| 意図 | 作る条件 |
|---|---|
| alias（名寄せ） | 保証・前提の主語の正規化した名前が近い組（片方がもう片方を含む） |
| subject（主語の照合） | 2 つ以上の単位にまたがる主語（名寄せで統合した後）と、名寄せが不明のまま残った組。その主語に関わる名寄せが全て閉じてから作る |
| finding（指摘の判定） | ファイルの段の指摘・静的な検査の結果・横展開の読みの指摘の 1 件ごと |
| premise（前提の消化） | 他の単位に同じ主語の保証がある前提ごと |
| goal（目標の判定） | 目標と受け入れ基準の項目ごと。関係する事実は、その項目を義務に持つ事実。担当と query は単位の索引（`units`: id・path・写しの file と範囲）を持ち、載せなかった事実を件数（`omitted`）と id（`omitted_ids`。上限 `OMITTED_IDS_MAX` を超えた件数は `omitted_more`）で宣言する。支え（`support`）には `omitted_ids` の id も使え、引用と抜けの場所には全ての単位を使える。義務に結ばれた事実が無くても判定できるようにするため |
| confirm（確認） | 全体の段が足した指摘の全件と、落とした指摘（重いものは全件、他は抜き取り。`sampled`） |
| lateral（横展開） | 横展開の型ごとに、型の当たる単位で読みのあるもの |

- 判定の閉じた集合は ledger-core.mjs の `VERDICTS`・`ALIAS_ANSWERS`、意図の種類から役への対応は `INTENT_ROLE`。全体の段の行は、開いた意図のある種類の組ごとに、名寄せ・判定・確認は `workers` 体まで、横展開は意図 1 つに 1 体で、呼び出しの中で受理された事実から増えた意図も、行のある組なら同じ呼び出しで取る。
- 意図は、ファイルの段 → 全体の段 → 確認の向きにだけ作られ、後ろへ戻る辺は横展開だけ（周の上限で抑える）。このため、新しい型が出ないかぎり、開いた意図は有限の手順で 0 になる。
- 試行: 同じ根拠の鍵で、照合に落ちるか取ったまま提出されない試行が `MAX_ATTEMPTS` に達した意図は、判定できなかった意図（undecided）として理由つきで閉じ、開いた意図に数えない。止めずに他の意図を進め、complete まで行く。利用者の回答で試行を戻しても同じ失敗に戻り、止めた結果は呼ぶ側が取り込めないため。
- 引用: 判定の引用は、根拠と関係する事実の単位の本文に逐語であることを照らす。確認の判定の引用が逐語でなければ、拒否せずに検証不能（unverifiable）として受け取る。
- 確定: 指摘を確定にするのは、義務（目標か受け入れ基準の id）と原因の層の両方を持つものだけ（`deriveFindings`）。結べないものは参考（`references`）にし、指摘の件数にも網羅にも数えない。
  - ファイルの段・静的な検査・横展開の指摘は、指摘の判定が keep なら確定。drop で、確認が disagree なら復活して確定。確認が検証不能なら検証不能の指摘として出す（黙って落とさない）。
  - 全体の段が足した指摘は、確認が agree なら確定、検証不能なら検証不能の指摘。
- 静的な検査: `--link <正規表現>`（id の型。枠の一部で、`--link` の無い reframe は null に戻す）があれば、範囲で書いた参照（例: `U1〜U3`）を 1 件ずつに展開し、どの単位の本文にも無い id を事実にする（`staticFacts`）。単独の参照は、存在する id と見分けられないので照らさない。結果は指摘の判定にかけ、それだけで確定にしない。
- 束ねと横展開: 束ね役は既にある横展開の型（`lat-<群>`）の一覧を受け、同じ型なら `extends` に型の id を返し、新しい型のときだけ `pattern` を返す。新しい型（反証されていない群）だけが横展開の型になり、次の周を開く。新しい型が 0 件なら周を進めない。今の周が上限の周（段の始まりから `max_cycles` 周目）なら新しい型を展開せず、群を needs_input の `lateral_groups` で返す（同じ型を周ごとに展開し直して周を使い切らないため）。上限を下げた台帳では、`next` が上限の周以降の束ねが作った型を外し、周を上限の周に戻す。束ねが試行の上限に達した周は、開示して閉じて進める。
- status の指摘: `findings.confirmed` と `findings.unverifiable` は、判定・path の組・norm した quote と claim・layer が同じ指摘を 1 件にまとめ、`id`（最初の指摘）と全ての `ids` を持つ。確定した指摘は `paths`・`obligation`・`confidence`・`origin`・`provenance` と、結ばれた群の id（`groups`）を持つ。

## 止める条件

`next` が返す `stop` の種類と、その条件。上から順に判定する（`decide`）。どの停止の出力にも、開いたままの意図（`open_intents`）、判定できなかった意図（`undecided`）、status のファイルの path（`status_path`）が載る。上限で止まったことを完了と取り違えないため。

| stop | 条件 | 再開のしかた |
|---|---|---|
| blocked（cause: input） | 台帳を作った後に対象のファイルが読めなくなった（init の時点で読めなければ台帳は作られない） | 置き場を直して `next` |
| blocked（cause: failure） | 全ての役が欠けた呼び出しが `MAX_FAIL_STREAK` 回続いた（ファイルの段で提出が 1 件も無い呼び出しと、全体の段で claim が 1 度も無い呼び出しを含む） | 環境を直して `next`（環境の失敗に数えた試行は戻る） |
| limit | 今の回の始まり（`round_start`）からの周が `max_cycles` を超えた（持ち越しで周が進んだとき。横展開では超えない）、今の段の始まり（init か、`kept` でない reframe）からの起動数が `max_agents_total` に達した | `config` で上限を上げて `next` |
| needs_input | 依頼文・決定の記録が求める成果を、どの項目も受け止めていない（`goal_gaps`）／目標の照合・計画・観点の検証が試行の上限まで欠けた（`stuck`。キーは `goal`・`plan`・`unit:<観点の id>`）／計画の欠陥が統合のやり直し `PLAN_ROUNDS` 回で消えない（`plan_defects`）／利用者への質問がある（`questions`） | `answer` を足して `next` |
| blocked（cause: target / failure） | 単位が 0 件／読みを受け付けた単位が 1 つも無い | 対象を直すか、原因を直して `next` |
| needs_input | 上の層（方針・要求）が原因の確定した指摘（`upper`）・束（`upper_groups`）、検証不能の指摘（`unverifiable`）、上限の周で展開しなかった新しい型の群（`lateral_groups`）が残る | 指摘の id か束・群の id で `answer`。展開を続けるなら、回答せずに `config --max-cycles` で上限を上げて `next` |
| complete | 全ての単位を見たか見られなかった理由を開示し、開いた意図が 0 になり、この周の振り返りと束ねが済み、上の全てに当たらない | 対象が変われば、同じ台帳で `next` が変わった単位だけを読み直す |

- 単位の状態: unseen →（読みを受け付けた）seen。取ったまま提出されないか照合に落ちる試行が `MAX_ATTEMPTS` に達したら、理由つきの disclosed（`status` の `skip`）。
- 止まるたびに `status` と同じ中身を今の段の `status-<段>.json` に書く。呼び出しを開くときと reframe（入ってくる段のファイル）で消すので、今の段のファイルがあるのは止まっている間だけ（呼ぶ側が前の停止の status を取り込まないため）。
- 飽和（周ごとの新しい確定した指摘・群・横展開の型の数）は `status` の `saturation` に記録するだけで、止める条件に使わない。新しい指摘が 0 件でも見落としが無いとは言えないため。

## 記録

- 起動ごとに役・label・指定した model・effort・成否（`agents`）、呼び出しごとに起動数・欠け・提出の数・token（`calls`）。token は Workflow source が本体の始めと返す直前に読んだ `budget.spent()` の差で、どちらかが読めなければ（runner など）null と理由を残す。`budget.spent()` が何を数えるかは確かめていないので、同じ経路の差どうしだけを比べる。model は指定値で、実際に効いたかは確かめられない。
- run の指標（`status` の `metrics`）: 確定した指摘の出どころの内訳、新しく読んだ単位と持ち越した単位の数、全体の段で落とした数と確認で復活した数。止まるたびに `run_records` に 1 件足す。
- 出来事（`events`）: 拒否（`rejected_*`）・返らなかった役・取ったまま提出されなかった担当・開示・判定できなかった意図・確認での復活・不明のままの名寄せなど。振り返りの単位に入らなかった出来事は `events_not_in_retro` に残る。
- 較正: `init --seeds` に既知の欠陥（`[{path, quote, lens?}]`）を渡すと、`status` の `calibration` が観点ごとの再現率を、ファイルの段の指摘で返す。仕込んだ欠陥を入れた対象は利用者が用意する。

## 汎用の設計の型から変えた点

このリポジトリの Workflow の設計の型（状態を CLI だけが書き、run の中では運搬役が CLI を呼んで出力を script へ運ぶ形）から、次の点を変えている。

- 運搬役を置かない。状態を書くのは CLI だけという点は守り、役が `claim`・`query`・`submit` を Bash で直接流す。`next`・`ingest` は Workflow の外で呼び出し側が流し、1 回の Workflow は 1 段を 1 回だけ流す。運搬役の写し違いと、照合を通らずに次の役へ渡る経路を作らないため。競合は lock で直列にし、遅れた書き込みは `callId` で拒否する。native Workflow の subagent が Bash で CLI を流せることは確かめてある。Codex の runner の worker が `stateDir` に書けるか・CLI を流せるかは確かめていない。
- 状態の寿命を 1 run でなく、run をまたぐものにする（利用者の決定）。対象が変わっても新しい状態から始めず、同じ台帳で変わった単位だけを読み直す。呼ぶ側の段が変わるときも台帳は 1 つのままで、`reframe` で枠を差し替えて全体を読み直す。
- 重要度で単位を絞らず、同じ範囲を重ねて読まない。独立は、全体の段と確認・束ね役と反証役を別のモデルにし、新しい context で読むことで作る。Anthropic のモデルどうしなので盲点の重なりは減りにくく、結果にそう開示する。
