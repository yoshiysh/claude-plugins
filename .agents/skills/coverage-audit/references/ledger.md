## 構成（ブラックボード）

| 部品 | 実体 | 持つもの |
|---|---|---|
| ボード | `stateDir/ledger.json`（`hints.jsonl` と写しの `snap/` は別ファイル） | 目標・受け入れ基準・制約・決定の記録・段（`phase`・`phase_start`・`phase_records`）・計画・資産・枡・指摘・出来事・束・起動の記録 |
| 知識源 | Workflow source の役（`scripts/roles.json`） | 1 体 1 単位の判断だけ。ボードも対象も書かない |
| 制御 | `scripts/ledger-cli.mjs`（`init`・`reframe`・`next`・`ingest` と、review の worker が流す `claim`・`submit`） | 次の 1 手の決定、受け入れ、止める判定。台帳を書くコマンドは `stateDir/ledger.lock` で直列にする |

探索グラフの事実は台帳の記録（受け入れた読み・確かめた指摘・束・出来事）で、意図は `next` が台帳から導く次の 1 手（読む枡・横展開の観点）。出来事 → 束（根本原因と層）→ 横展開の観点、の辺は ID で辿れる（`events[].ref`・`groups[].keys`・`lenses[].origin`）。

## 段と、script と LLM の分け方

| 段 | LLM がすること | script がすること |
|---|---|---|
| init | なし | 目標・基準・制約の各項目に引用があり、引用が依頼文か決定の記録に逐語であるか（`readGoalFiles`）。通らなければ台帳を作らない。照合済みの印（`--goal-checked coverage-build`）があれば照らさない |
| plan | 目標の照合（依頼文と決定の記録が求める成果を引用つきで挙げ、受け止める項目の id を付ける。照合済みの印があれば流さない）、独立な計画役 2 体（別のモデル）が観点・当てる資産（`applies_to`）・受け持つ目標の部分（`goals`）と、除く資産（`excluded`）を切る、統合（`applies_to`・`goals`・`excluded` も併せる）、観点の精査役（統合の後、検証の前。N1: 当てた資産ごとに、手続きが列挙するものがあるか、N2: 他の計画の観点ごとに、同じものを列挙し同じものと照らすか）、観点ごとの閉じた問い（Q1: 何を列挙するか・Q2: 何と照らすかを手続きが書いているか、Q3: `goals` の要素ごとにその部分が果たされたかを確かめられるか） | 照合役の成果の引用の実在・項目の id の実在、受け止められていない成果を人間に返す（`checkGoalMap`・`goalGaps`）。対象の索引の写し、観点の形・ID の重複・基準と制約の受け皿・source_map・欠陥への応答の網羅、`applies_to` と `excluded` の照合（`checkAppliesTo`）、`goals` の照合（`checkGoals`）、閉じた問いの答えの過不足・yes/no・引用の逐語と自由な欠陥の拒否（`checkUnitVerdict`）、no の答えだけを欠陥にする（`unitDefects`）、精査の答えの過不足・yes/no・引用の逐語（N1 は資産の本文、N2 は両方の手続き。`checkLensReview`）、N1 の no の資産を `applies_to` から外し、残らない資産を `excluded` に、空になった観点を落とす、落とした観点だけが受け皿だった項目と N2 の yes を欠陥にする、計画の欠陥への `P<n>` の id、観点の同一性（中身の hash） |
| review | 読む役の worker が資産を 1 つずつ取り、観点ごとの枡の結果を書いてから、資産ごとに 1 回出す。全ての読む役の worker が終わった後、別のモデル・反証側の検証役の worker が指摘のある枡を 1 つずつ取る | 枡の生成（観点が当たる資産との組だけ）、待ち行列（`claim`）、関係する資産（`related`）の列挙、提出（`submit`）の写しの hash の照合、区画ごとの読んだ証拠の照合、指摘の引用の照合、判定の網羅、偽の引用での判定を検証不能にする、提出されなかった枡の戻し |
| retro | review と同じ（資産が出来事、観点が R1〜R4）。照合済みの印（`--goal-checked coverage-build`）のある台帳では流さない | まだ振り返っていない出来事を段ごとに 1 行 1 件で並べ、`MAX_ASSET_LINES` 行ごとの資産に分ける。区画は通常の資産と同じ式。印のある台帳は資産を作らず、出来事を `status` の `events` で返す（振り返りの探索グラフを coverage-build の 1 つに寄せるため） |
| group | 根本原因で束ね、群ごとに既にある横展開の観点の型の例（`extends`）か新しい型（`pattern` と当たる資産 `applies_to`）かを返す、別のモデル 2 体で反証（既にある型に結ぶだけの群は反証しない） | 全件・対象の索引・既にある横展開の観点の一覧の写し、全 key がちょうど 1 つの群に入るか、層の値、`extends` が今ある横展開の観点の id か、新しい型の `applies_to` が空でなく実在する資産か（`checkGroups`）、新しい型だけの横展開の観点の追加、`extends` を持ち層が `UPPER` でない群（`linkOnly`）を反証役に渡さず `linked` にする |

静的な照合の正本は Workflow source の `// <checks>` 区間だけで、CLI は同じ文を読み込んで `ingest` で照らし直す（runner の source は import できないので、写しを持たずに 1 か所にするため）。Workflow は本文を持たないので、plan と group では Workflow の中で形だけを照らして 1 回やり直させ、引用の逐語は `ingest` が写しに対して照らす。review の読みと検証は、worker が出すたびに `submit` が写しに対して全てを照らし（`checkRead`・`checkVerify`）、落ちた理由を worker に返して出し直させる。目標の照合役の引用（依頼文・決定の記録）と、前の計画の観点への検証役の引用も同じく、Workflow は形と id だけを照らし、逐語かは `ingest` が照らす。引用が合わない読みは試行に数え、次の呼び出しで読み直す。目標の照合の静的な部分（`// <goalmap>`）は coverage-build の Workflow source と同じ文を置き、一致は `tests/coverage-build-goalmap.test.mjs` が照らす（2 つのスキルは互いのファイルを読まないため）。照合役には、項目が依頼に無いものを足したか・範囲を狭めたかを判定させない（判定が回ごとに揺れたので）。足していないことは init の引用の照合が、落とした要求は対応の無い成果が示す。呼び出し側が args を運ぶので、source は args の FNV（`argsSum`）を照らし、合わなければ役を起動せずに止まる。

引用の規則の文は `<checks>` 区間の定数で、照らす関数と同じ字数の定数から作り、その引用を返す役の prompt だけに載せる（食い違う規則を 2 つ並べないため）。`QUOTE_RULE`（`quoteProblem` が照らす引用）は review の worker（読む役・検証役）・観点の精査役（N1・N2）・観点の検証役（Q1〜Q3）に、`CITE_RULE`（`<goalmap>` 区間。引用元の 1 件を引く規則）は目標の照合役に載る。束ね役・反証役・計画役・統合役には載らない。

## 写しと ID と持ち越し

- 写し: `next` は対象のファイルを読んだその内容を `stateDir/snap/<内容の hash>.txt` に書き、args にはそのファイル名・行の範囲・範囲の hash だけを載せる（写しの置き場 `snapDir` と、資産・枡の id と path の基準にする対象の共通のディレクトリ `targetBase` は args に 1 回だけ載り、Workflow source が結合する。args の長さを path の長さと枡の数の積にしないため。台帳の id は絶対 path のまま）。担当は Read で自分の範囲だけを読む。索引（計画役）と指摘の全件・既にある横展開の観点の一覧（id・型・根本原因。束ね役）も同じ形で渡る。担当が読む文（目標・基準・制約・依頼文・決定の記録・ヒント・回答・前の計画・計画の欠陥・観点の手続き）も、呼び出しごとの束（brief）の写しで渡り、args には id・件数・役の設定と写しの参照だけが残る（args の大きさは文の長さや件数に比例しない）。`ingest` は args が指す写しの範囲の hash を照らし、違えば台帳を変えずに拒否する。写しの名前は内容で決まるので、同じ状態の `next` は同じ `call_id` を返す。
- 資産: 中身の境目で切り、id は中身の位置から決める。前に行が増えても、同じ中身は同じ id と hash のまま持ち越せる。

  | 対象 | 資産の単位 | id |
  |---|---|---|
  | Markdown の frontmatter（1 行目が `---` で、閉じる `---` があるときだけ） | frontmatter の全体 | `path#_frontmatter` |
  | Markdown の節の中 | 段落・箇条書き・表・コードブロック（種類は `p`・`list`・`table`・`code`） | `path#<見出しの経路>/<種類><序数>`。序数は節の中で種類ごとに 1 から数える。最初の見出しより前は `_top` |
  | JS・MJS のトップレベルの宣言（function・class・const・let・var・export） | 直前のコメント行から宣言の終わりまで | `path#<宣言の名前>`（`export default` は `default`） |
  | JS・MJS の宣言の無い所（import・名前の無い export・文）と、その他のファイル | `CHUNK_LINES` 行の塊 | `path#c<n>` |

  - Markdown のブロックの範囲に、見出しの行と前後の空行は入れない。code fence は開きと閉じの行を含め、fence の中の `#` の行は見出しにしない（閉じない fence は文書の終わりまで）。空行を挟んでも、次の空でない行が箇条書きの項目なら同じ list にする。
  - 目次（入れ子を含め、リンクだけの箇条書きだけの節）、見出しだけの節、本文の無い節は資産にしない。読む中身が無く、枡を増やすだけなので。
  - JS は、テンプレート文字列・ブロックコメント・括弧の中の行では切らない。
  - 1 体が読む範囲は `MAX_ASSET_LINES` 行まで。超える資産は `/c<n>` で切り、同じ id が重なれば `~<k>` を付ける。見出しの `|` は経路から除く（枡の id の区切りと衝突させないため）。
- 索引: 計画役・統合役・束ね役に渡す対象の索引は、1 行 1 資産のタブ区切りの 6 欄（id・写しのファイル・`<start>-<end>`・見出しの経路・種類・先頭の数語）。細かい資産から当てる資産を選べるようにするため、本文を開かずに中身の見当が付く要約を載せる。経路の無い資産（frontmatter・`_top`・JS）は経路の欄を空にし、先頭の数語は norm した本文の先頭から取る。欄の中にタブを残さない。
- 関係する資産（`related`）: `init`・`reframe` の `--link <正規表現>` を台帳の `link` に置く（正規表現として作れなければ台帳を変えずに拒否する）。link は枠の一部で、`--link` の無い reframe は null に戻す。資産ごとに、本文に現れる link の一致の語を 1 つ以上共有する、`excluded` でない他の資産を、共有する語の数の多い順（同じなら資産の並びの順）に、行の合計が `MAX_ASSET_LINES` までを `related` にし、入らない資産は `related_not_given` に id で残す。振り返りの資産は関係の元にも先にもしない（出来事の文は指摘の id を含むため）。link が null なら空。作る側と使う側（定める節と使う節）を 1 体 1 枡のまま同じ枡で確かめさせ、片側だけを見た不在の主張を減らすため。読む役の evidence と findings の quote は今のまま資産の本文だけに照らし（指摘の場所は資産に置く）、検証役の判定の quote は資産か related のどれかの本文に逐語なら効く。
- 区画: 資産の本文をおよそ `BLOCK_LINES` 行ごとに、`MAX_BLOCKS` 個までの窓に分け、各窓から 1 つ以上の逐語の引用を求める。
- 枡: `資産|観点|p回`。回は 1..k で、全ての枡に同じ k を使う。枡を作るのは観点が当たる資産との組だけ。計画の観点は `applies_to` の資産に、横展開の観点は束ね役が返した `applies_to` の資産に当たる。利用者の観点は全ての資産に当たる（利用者の観点を渡すと計画を作らないので、除く資産も無い）。目的と層の見方は、要るときだけ計画の観点として切られ、ほかの計画の観点と同じく `applies_to` の資産に当たる。
- 除いた資産: `excluded` の資産には、横展開を含めどの観点の枡も作らない。`applies_to` と両方に入っていても `excluded` を優先し、既にある枡は gone にする。`status` の `excluded` で理由と共に開示する（見ていない所）。
- 当てる資産と除く資産の照合（`checkAppliesTo`）: `applies_to` と `excluded` の id が資産に実在する、どの計画の観点も 1 つ以上の資産に当たる、`excluded` の各件に理由がある、全ての資産が「計画の観点の `applies_to` を合わせたもの」か `excluded` のどちらか一方にちょうど 1 回入る。どの観点も関係しない資産を当てさせると、関係の無い組が枡になって膨らむため、当てずに除いたことを開示させる。外れは計画の静的な欠陥になり、統合のやり直しに戻る。ingest に加え、持ち越しで資産が変わった `next` でも照らし、そこで欠陥を足したときは統合のやり直しの数（`PLAN_ROUNDS` に照らす数）を 0 に戻す。
- 受け持つ目標の照合（`checkGoals`）: 計画の観点の `goals` は `[{id, part}]` で、id が目標・受け入れ基準に実在する、part が空でなくその本文に逐語である、どの観点の `goals` も空でない、全ての目標・受け入れ基準がどれかの計画の観点の `goals` に入る。制約は `constraint_map` で受ける。複合の目標は部分ごとに別の要素にでき、Q3 は要素ごとに問うので、1 つの観点が目標の全体を確かめられなくても no が残らない。外れは計画の静的な欠陥になる。逐語かは本文を持つ `ingest` が照らす（Workflow は形・id・被覆だけ）。
- 観点の検証役に閉じた問いだけを聞く理由: 大きさ・問いの数・層・制約との矛盾・当てる資産の当否を自由に判定させると、統合のやり直しのたびに新しい欠陥が出て `PLAN_ROUNDS` で止まった。静的に決まること（`goals`・`applies_to`・`excluded`・`constraint_map`）は script が照らし、手続きの細部の良し悪しは枡を読んだ結果（見落とし・検証不能・振り返り）で直す。
- 観点の精査（N1・N2）: 統合の後、検証の前に、統合役と別の context の精査役が観点ごとに答える。精査役と検証役は、当てた資産の行を索引の写しから読む（統合しない呼び出しでは、args の `reviewUnits` に観点・当てた資産・他の観点の id だけを載せ、手続きは束に入れる）。
  - N1 の no は、script がその資産を観点の `applies_to` から外す。統合に戻さないので往復しない。どの計画の観点の `applies_to` にも残らない資産は、理由に N1 を書いて `excluded` に移す。台帳の `plan` は外した後の計画で、見直しの統合役はそれを前の計画として読む。外したことは出来事（`lens_n1_removed`）に残す。
  - `applies_to` が空になった観点は計画から落とし（`constraint_map` の `handled_by` からも外す）、検証にかけず、`status` の `dropped_lenses` で開示する。落とした後の計画の静的な照合の外れ（受け皿を失った目標・基準・制約）は計画の欠陥にする。
  - N2 の yes は、観点の組ごとに 1 件の計画の欠陥にする（両方向の yes も 1 件）。
  - 統合のたびに全ての観点を精査し直す（計画を変えたら全体を検証し直す）。静的な欠陥のある計画には精査を当てない。受け付けなかった精査は `attempts:lens:<観点の id>` に数え、`MAX_ATTEMPTS` で `stuck` になる。精査を終えていない観点が残る間は枡を読む段に進まない。
- 計画の欠陥の id: `plan_defects` の各件は台帳の連番の `P<n>` を持つ。統合をやり直して欠陥を戻しても前の番号を使い回さないので、`answer --id P<n>` は今の欠陥だけを指す。統合役が閉じた問いの答え（Q1〜Q3 の no、N2 の yes）から作った欠陥に `rejected` と応答しても、欠陥を退けたことにはならない。その観点は検証済みにならないので次の検証で同じ問いに答え直し、yes なら欠陥が消え、no ならまた欠陥（新しい `P<n>`）になる。
- 指摘: `枡#hash(引用+主張)`。同じ枡の別々の指摘は潰れない。
- 持ち越し: 台帳は run をまたいで残る。`next` のたびに対象を読み直し、資産の hash・渡した related の hash の組・観点の版（名前・手続き・`applies_to`）のどれかが変わった枡だけを未読に戻す。`applies_to` から外れた資産の枡と、`excluded` に移った資産の枡は gone。前の指摘は superseded にする。消えた資産の枡は gone。その周の振り返りと束ねが済んだ後に読む枡が出たら、`next` は新しい周を開き、新しい指摘も振り返り・束ね・横展開を通す（持ち越しも周を使うので `max_cycles` に数え、持ち越しで周が上限を超えたら limit）。
- 待ち行列: 読む役の待ち行列は、その回の unseen の枡を資産ごとにまとめて渡す。claim は資産（写しの範囲と、資産ごとに 1 つの提出の命令 `asset.submit_cmd`）・`related`・`related_not_given` と、枡ごとの `cell_id`・`lens`・観点の束・`result_path` を返す（枡ごとの命令は持たない。worker に枡の id を組み立てさせないため）。検証の待ち行列は、受け付けた読み（`cells[].read`）に指摘があり status が seen の枡を 1 つずつ、その枡の指摘だけと共に渡す。取れるのは claim の無い枡と、試行が `MAX_ATTEMPTS` に届いていない枡だけで、取った枡には `claim: {call, worker}` を残す。本文と他の枡の指摘は渡さない（前の観点の指摘を次の観点に持ち込ませないため）。その worker がその呼び出しでまだ提出していない枡を持つ間は、claim は新しく取らずにその枡を同じ形で返し直す。結果の path（`results/<call>/<queue>/<worker>/`）は待ち行列と worker ごとに分け、claim は返す path に既にあるファイルを消す（読む役の古い結果を検証役が受け取らないため）。
- 提出と拒否: `asset.submit_cmd`（`--cell` と `--result` を持たない submit）は、その worker がこの呼び出しで取ってまだ出していない枡のうち、`result_path` にファイルがある枡を全て出し、枡ごとの `{ cell, ok, problems, dropped }` の `results` と、ファイルの無い枡の `missing` を返す。missing の枡は試行に数えず、取ったままにする。照合に落ちた枡の結果のファイルは CLI が消すので、直さずに流し直しても missing になり、同じ中身で次の試行に数えない。`--result` だけを渡す submit は拒否する。`--cell` と `--result` を組で渡す 1 枡の submit は、1 枡だけ出し直す口として残る。`submit` は枡を取った worker からだけ受け付ける。今の呼び出し（`pending.call_id`）と違う call・review でない段・args の workers に無い worker・claim の無い枡・別の worker の枡・写しの hash の食い違いは、台帳を変えずに終了状態 2 で拒否する（中身の照合に落ちた提出は終了状態 0 の `ok: false` で、試行に数える）。
- 取りの戻し: 取られたまま提出されなかった枡は、その呼び出しの `ingest` が戻す。`ingest` を経ずに `next` が来たら `next` が戻す。読む役の枡は unseen のまま、検証の枡は読みを保ったまま claim を外し、どちらも試行に数えて出来事（`missing_read`・`missing_verify`）を残す。`call_seq` は review の `ingest` と、1 件以上を戻した `next` で進み、`call_id` に入るので、前の呼び出しの遅い claim・submit は拒否される。
- lock: 台帳を書くコマンド（init・reframe・next・ingest・answer・config・hint・claim・submit）は load から save までを `stateDir/ledger.lock`（`openSync` の `wx`）で囲む。待つのは `LOCK_WAIT_MS`（ledger-cli.mjs）までで、超えたら台帳を変えずに拒否し、生きた lock は消さない。mtime が `LOCK_STALE_MS` より前の lock は落ちた process の残りとして消して取り直す。
- 試行の回数（枡・観点の精査・観点の検証・束ね）と周の数は台帳にあり、再開しても 0 に戻らない（reframe は段を始め直すので、試行を捨てる）。
- 段と reframe: 台帳は呼ぶ側の段（`phase`）をまたいで 1 つで、置き場を増やさない。`reframe` は照合済みの印のある台帳だけを受け、印を残して目標の冒頭の文・目標・基準・制約・依頼文・決定の記録・対象と段を差し替える。出ていく段の節（`findings`・`groups`・`events`）を `phase_records[<段>]` に写し、計画・回答・横展開の観点・束ね・試行・pending を捨て、全ての枡を unseen に戻し、今の指摘を superseded にし、周を 1 つ進めて `phase_start`（周・起動数・出来事の数）を置く。中身が同じでも読み直すのは、計画を変えたら全体を検証し直す形に揃えるため。
- 段ごとの status: 上の階層の `findings`・`groups`・`events`（`{id, stage, kind, text}`）は今の段のもので、`phases` は `phase_records` に今の段の節を足したもの。止める判断の `upper`・`upper_groups`・`unverifiable` も今の段の指摘と束だけで決まる。`findings.confirmed` と `findings.unverifiable` は、判定・資産（指摘の id の最初の `|` の前）・norm した quote と claim・layer が同じ指摘を 1 件にまとめ、`id`（最初の指摘）と全ての id の `ids` を持つ（同じ指摘が観点の数だけ並ばないため。layer が違えば直す層の判断が違うのでまとめない）。`by_verdict`・`by_layer` はまとめた後の件数を数える。言い換えはまとめず、`findings.confirmed` の各件の `groups` に、`ids` のどれかを keys に含む、refuted でない群の id を載せて結ぶ。

## 止める条件

`next` が返す `stop` の種類と、その条件。上から順に判定する。

| stop | 条件 | 再開のしかた |
|---|---|---|
| blocked（cause: input） | 台帳を作った後に対象のファイルが読めなくなった（init の時点で読めなければ台帳は作られず、init からやり直す） | 置き場を直して `next` |
| blocked（cause: failure） | 全ての役が欠けた呼び出し（review では提出が 1 件も無い呼び出しを含む）が `MAX_FAIL_STREAK` 回続いた | 環境を直して `next` |
| limit | 今の段の始まり（init か reframe）からの周が持ち越しで `max_cycles` を超えた（横展開では超えない。下の収束を見る）、同じく起動数が `max_agents_total` に達した | `config` で上限を上げて `next` |
| needs_input | 依頼文・決定の記録が求める成果を、どの項目も受け止めていない（`goal_gaps`）／試行の上限まで欠けた段がある／計画の欠陥が統合のやり直し `PLAN_ROUNDS` 回で消えない／利用者への質問がある | `answer`（`goal`・`criteria`・`constraints`・`decisions` は `--file`、質問の id・計画の欠陥の id `P<n>`・`attempts:<キー>` は `--text`）を足して `next` |
| blocked（cause: target / failure） | 枡が 0 件／読みを受け付けた枡が 1 つも無い | 対象を直すか、原因を直して `next` |
| needs_input | 上の層（方針・要求）が原因の指摘（`upper`）・束（`upper_groups`）、検証不能の指摘（`unverifiable`）、上限の周で展開しなかった新しい型の群（`lateral_groups`。横展開が収束しない）が残る | 指摘の id か束の id で `answer`（`lateral_groups` の群は展開せずに記録し、全てに回答があれば complete）。展開を続けるなら、回答せずに `config --max-cycles` で上限を上げて `next`（今の周の未回答の群を展開して次の周を開く） |
| complete | 読み直す枡が 0、この周の振り返りと束ねが済み、上の全てに当たらない | 対象が変われば、同じ台帳で `next` が変わった枡だけを読み直す |

- 枡の状態: unseen →（読みを受け付けた。指摘が無ければ settled）seen →（全ての指摘を検証役が判定）settled、欠けが `MAX_ATTEMPTS` 回で disclosed。指摘の無い settled の枡は検証役を通っていない（見ただけ）ので、`coverage.settled_no_findings` として別に数える。
- 全ての役が欠けた呼び出し（review では提出が 1 件も無い呼び出し）の試行は別に数え、blocked（failure）から再開したときに戻す（環境の失敗で枡を開示に倒したままにしない）。
- 束ねの段で反証役の枠を超えた群は unverified のまま残し、新しい型なら横展開の観点も作る（絞らないため）。`extends` を持ち層が `UPPER` でない群は反証せず `linked` にする（観点を作らず、上の層の判定にも使わないので、反証しても結果が変わらない）。上の層の `extends` の群は今のまま反証し、`upper_groups` の判定は変わらない。`status` の `groups` で状態が分かる（`lateral` は横展開の観点があるか、`extends` は結んだ観点）。
- 横展開の収束: 束ね役は、既にある横展開の観点（`lat-<群>`）の一覧を写しで受け、群ごとにその型の例なら `extends` に観点の id を返し、どれとも違う新しい型のときだけ `pattern` を返す。`extends` のある群は観点を作らず、指摘をその群に結ぶだけにする（`pattern` が一緒に来ても `extends` を優先する。層が上の層でなければ status は `linked`）。新しい型（`extends` が無く `pattern` があり、反証されていない群）だけが横展開の観点になり、次の周を開く。新しい型が 0 件の束ねの後は次の周に進まず、complete に向かう。今の周が上限の周（段の始まりから `max_cycles` 周目。既定 2）なら新しい型を展開せず、群を残して needs_input の `lateral_groups` で返す。同じ型を周ごとに展開し直して周を使い切らないため。上限を今の周より小さく下げた台帳では、`next` が上限の周以降の束ねが作った横展開の観点を外し（その枡と指摘は gone）、周を上限の周に戻して、元の群を `lateral_groups` で返す。展開しなかった群は当たる資産（`applies_to`）を群に残し、上限を上げた後の `next` が、今の周の未回答の群を横展開の観点にして次の周を開く。
- 振り返りは、その周までにまだ振り返っていない出来事を全て拾う（照合済みの印のある台帳では流さず、出来事は `status` の `events` で呼ぶ側に渡る）。振り返りの後に起きた出来事は次の周で拾い、最後まで拾えなかったものは `status` の `events_not_in_retro` に残る。
- 飽和（周ごとの新しい確かめた指摘の数）は `status` の `saturation` に記録するだけで、止める条件に使わない（新しい指摘が 0 件でも見落としが無いとは言えないため）。

## 記録

- 起動ごとに役・label・指定した model・effort・成否（`agents`）、呼び出しごとに起動数・欠け・token（`calls`）。token は Workflow source が本体の始めと返す直前に読んだ `budget.spent()` の差（この呼び出しの消費量）で、どちらかが読めなければ（runner など）null と理由を残す。`budget.spent()` が何を数えるか（司令塔・担当の入力・出力のどれか）は確かめていないので、同じ経路の差どうしだけを比べる。model は指定値で、実際に効いたかは確かめられない。
- 観点の外の気づきは枡ごとに残し、`status` の `outside_notes` で返す。効果の根拠は無い（開示して使う）。
- 較正: `init --seeds` に既知の欠陥（`[{path, quote, lens?}]`）を渡すと、`status` の `calibration` が観点 × 読む役（回）ごとの再現率を返す。仕込んだ欠陥を入れた対象は利用者が用意する。

## 汎用の設計の型から変えた点

このリポジトリの Workflow の設計の型（状態を CLI だけが書き、run の中では運搬役が CLI を呼んで出力を script へ運ぶ形）から、次の点を変えている。

- 運搬役を置かない。状態を書くのは CLI だけという点は守り、`next`・`ingest` は Workflow の外で呼び出し側が流す。1 回の Workflow は 1 段を 1 回だけ流し、ループは台帳と `next` が持つ。運搬役の失敗・写し違い・競合の種類の欠陥を作らないため。例外は review の worker で、資産を 1 回読んで枡ごとに出すために、Workflow の中から `claim`・`submit` だけを流す。競合は lock で直列にし、写し違いは `submit` が hash で拒否する。native Workflow の subagent が Bash で CLI を流せることは確かめてある。Codex の runner の worker が `stateDir` に書けるか・CLI を流せるかは確かめていない。
- 状態の寿命を 1 run でなく、run をまたぐものにする（利用者の決定）。対象が変わっても新しい状態から始めず、同じ台帳で変わった枡だけを読み直す。呼ぶ側の段が変わるときも台帳は 1 つのままで、`reframe` で枠を差し替えて全体を読み直す。
- 重要度で枡を絞らない。作った枡は全て同じ扱いにし（関係の無い観点と資産の組は枡にしない）、独立は別のモデル・別の枠組み（反証側）・新しい context で作る。Anthropic のモデルどうしなので盲点の重なりは減りにくく、結果にそう開示する。
