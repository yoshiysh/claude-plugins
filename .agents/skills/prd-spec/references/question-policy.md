# 質問と既定の判定（question policy）

このファイルが**唯一の正**である。「ユーザーに聞くか、既定で進めるか」の判定手順と、
決定ログ（decisions）の書式を定める。intake（既定選定係）・司令塔（統合ゲート）・
fabrication-auditor（[DECISIONS] の受理）がここを見る。

## なぜ質問を最小化するか

質問のコストは 1 問あたりの往復時間ではない。**質問が多いほど 1 問あたりの回答の質が
下がり、結局どれも決まらない**。「依頼者にしか決められない」と分類された質問でさえ、
再検査すると依頼文に答えがあるか上位互換候補を持つものが大半である。**自分の
分類を信用せず、下の判定手順で機械的に落とす。質問 0 件が目標値である。**

一方、推測で埋めることの害は「間違えること」ではなく**「間違いが不可視なこと」**である。
既定を選んだ事実と理由が決定ログに載っていれば、それは捏造ではなく**可視化された仮置き**であり、
依頼者は一覧を見て異議のある行だけ直せる。書くのは安く、依頼者の時間は高い。

## 判定手順（この順で、全論点に適用する）

未確定の論点 1 件ごとに、次を上から順に試す。

1. **依頼文・回答に答えがあるか探す。** あれば確定事項（根拠は原文の引用）。
   **依頼文に答えがある論点を質問にしてはならない** — 「確認のため」も禁止。
   依頼文と食い違う情報を別の入力が持つときだけ、食い違いの確認として聞く。
2. **スキルが固定する前提（`references/fixed-premises.md`）にあるか。** あれば前提を使う。
   質問にしない。
3. **妥当な既定を選べるか。** 次のいずれかなら選べる:
   - 候補のうち 1 つが他候補の**上位互換**（他案でできることを全部含む）
   - どの候補を選んでも**成果物の正しさが変わらない**（書式・構成・命名などの執筆規約）
   - 分野の標準的な選択が存在し、依頼文にそれを避ける記述が無い
   → **決定として起票し、質問にしない。** 決定ログに載せて統合ゲートで報告する（下記書式）。
4. **どれも不可なら blocking 質問。** 出せる条件は 2 つとも満たすこと:
   - 既定を選べない（依頼者の運用・意図・リスク許容にしか答えが無い）
   - 間違えたときのやり直しコストが、質問 1 回のコストを上回る
   質問には「**依頼文を探したが答えが無かった**」ことの申告を必須とする（探した箇所を書く）。

## 決定ログ（decisions）の書式

```json
{
  "id": "D-001",
  "topic": "何についての決定か（1 行）",
  "value": "選んだ既定",
  "why": "なぜこの既定か（上位互換 / 正しさ不変 / 標準的選択 のどれに当たるか）",
  "source": "default",
  "reversibility": "変更するとき何を直せばよいか（1 行）"
}
```

- 依頼文から確定した事項は `source: "input"` とし、`why` に原文の引用を入れる。
- **決定ログは承認待ちにしない。** 統合ゲートで一覧として報告し、「異議のある行だけ
  教えてください」の形にする。異議が出た行はその周回の回答として上書きする。
- writer は決定を根拠に使うとき、出所を `（既定: D-001）` と表記する。**依頼者の回答や
  外部規格の名で書かない** — 出所の偽装は fabrication-auditor の指摘対象である。
- fabrication-auditor は `（既定: D-N）` を出所とする記述を、対応する決定が `[DECISIONS]` に
  実在する限り捏造としない。実在しない D-N への参照は捏造として指摘する。

## 既定にしてはならないもの

決定ログは万能の抜け道ではない。次は既定で埋めず、blocking 質問にする。

- **案件の要求そのもの**（何を作るか・何を守るか）。既定で置けるのは**書き方と進め方の選択**まで
- 金額・期限・法的義務など、間違いが外部に波及する値
- 依頼文が「未定」「後で決める」と明示した事項（依頼者が保留の意思を示している）

## TBD に起票してよいもの（decision との棲み分け）

TBD と決定ログは両方「未確定の可視化」だが、役割が違う。**同じ論点を両方に積まない。**

- **TBD に起票してよいのは、判定手順 4 に落ちた論点だけ**（依頼者にしか決められない、かつ
  やり直しコストが質問コストを上回る）。
- **decision で仮置きした論点は TBD に重複起票しない。** 仮置きの可視化と変更手順は
  decision 自身（`value` / `reversibility`）が担う。両方に積むと、読み手には「決めたのか
  決まっていないのか」が二重に見え、残 TBD 数が実態より多く報告される。
- **writer が執筆・改稿中に新しく見つけた論点にも、この判定手順を適用する。** 既定を
  選べる論点（執筆規約・書式・単位の選択など）は TBD にせず、本文で決めて出所を
  `（既定: 執筆判断）` と書く。判定手順 4 に落ちた論点だけを TBD として起票する。
