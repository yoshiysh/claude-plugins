## パターン一覧

### 1. Orchestrator-Subagent（指揮と実行）

**定義**：リードエージェントがタスクを分解・委任し、Sub-agent が個別タスクを実行して結果を返す階層構造。

**適用条件**：
- タスク分解が明確で、サブタスクの境界が明確
- Sub-agent が短期・集中型の作業をこなす場合
- 全体の進行を1つのエージェントが管理すべき場合

**利点**：全体目標を保ちつつ分業が可能。
**欠点**：Orchestrator が情報ボトルネックになる。逐次実行だとコスト増。

**SKILL.md への反映**：
- SKILL.md = Orchestratorの指示書（誰に何を渡すかのみ）
- `agents/` 配下に各 Sub-agent のプロンプトファイルを置く
- Sub-agent はそれぞれ単一の責務のみ持つ

---

### 2. Generator-Verifier（生成と検証）

**定義**：生成エージェントが出力を作成し、検証エージェントが評価・フィードバックを返すループ構造。

**適用条件**：
- 品質が重要な出力（HTML生成・コード・文書）
- 評価基準を明示的なチェックリストで定義できる場合
- 誤出力のコストが高い場合

**利点**：反復的な品質改善が可能。
**欠点**：検証基準が曖昧だと機能しない。上限回数と差し戻しレベルの定義が必須。

**SKILL.md への反映**：
- editor → verifier の順で呼ぶ
- verifier が返す判定は「✅ / ❌（計画レベル） / ❌（実装レベル）」の3種
- ❌ 計画レベル → 上流の planner に差し戻し
- ❌ 実装レベル → editor に差し戻し（上限2回）
- 2回目以降も ❌ → ユーザーに提示して判断を仰ぐ

---

### 3. Parallelization（並列実行）

**定義**：独立した複数のサブタスクを同時に起動し、結果を統合する。

**適用条件**：
- サブタスクが互いに独立している（出力が他の入力にならない）
- 同じ対象を複数の観点で検証・評価したい場合
- 実行時間の短縮が重要な場合

**利点**：レイテンシ削減。各エージェントが専門知識に集中できる。
**欠点**：エージェント間の独立性が崩れると競合が発生する。

**SKILL.md への反映**：
- 独立した複数の Agent 呼び出しを1ターンで発行する
- 各エージェントが同じ入力を受け取り、異なる観点で処理する
- 例：verifier を「構造チェック係」「コード品質係」「コンテンツ品質係」に分割して並列実行

---

### 4. Agent Teams（チーム型並列）

**定義**：コーディネーターが複数のワーカーを独立プロセスとして起動。ワーカーは長期・複数ステップの作業をこなしながらコンテキストを蓄積する。

**適用条件**：
- 各サブタスクが長期・複数ステップの作業を必要とする
- ドメイン専門知識の蓄積が効果的な場合

**利点**：ワーカーがコンテキストを保持し続けるため、反復でパフォーマンスが向上。
**欠点**：完了検知が複雑。共有リソースへの競合リスク。

**SKILL.md への反映**：
- 短期スキルには Orchestrator-Subagent で十分。Agent Teams は長期・反復作業に使う。
- 同一スキルを定期的に呼び続けるループが必要な場合に検討する。

---

### 5. Shared State（共有状態）

**定義**：中央コーディネーター不在で、エージェントが共有データストア（ファイル・DB）を直接読み書きして協調する。

**適用条件**：
- エージェントが互いの発見を基に協調する調査・研究系タスク
- 単一障害点の排除が優先される場合

**利点**：リアルタイムで知見が共有される。
**欠点**：リアクティブループ（A→B→A→...の無限循環）が最大リスク。終了条件の設計が必須。

**SKILL.md への反映**：
- 終了条件（時間制限・収束閾値・専任終了判定エージェント）を必ず定義する。
- 調査・情報収集系スキルに適している。

---

### 6. Message Bus（メッセージバス）

**定義**：エージェントが publish/subscribe で通信し、ルーターがイベントの種別に応じて適切なエージェントへ配信する。

**適用条件**：
- イベント駆動のパイプライン処理
- 今後エージェント数やイベント種別が増える見込みがある場合
- 処理ルートをイベント種別で動的に切り替えたい場合

**利点**：エージェント同士が疎結合。新しいエージェントをルーターに登録するだけで拡張できる。
**欠点**：ルーターの誤分類でサイレント障害が起きやすい。イベントの追跡・デバッグが複雑になる。

**SKILL.md への反映**：
- ルーターエージェントが入力イベントを分類し、担当エージェントへ振り分ける設計にする
- ルーティングルールは `references/` に定義して明示化する
- サイレント障害を防ぐため、未知のイベント種別への fallback 処理を必ず定義する

## パターン選択ガイド

| 状況 | 推奨パターン |
|------|------------|
| 品質重視・評価基準が明確 | Generator-Verifier |
| タスク分解が明確・短期サブタスク | Orchestrator-Subagent |
| 独立した複数観点の検証 | Parallelization |
| 独立した長期並列サブタスク | Agent Teams |
| 協調調査・発見の共有 | Shared State |
| イベント駆動・エコシステム拡張予定 | Message Bus |

**基本方針**：まず Orchestrator-Subagent から始め、具体的な課題が見えてから他パターンを組み合わせる。本番設計はパターンの組み合わせが一般的。

## モデル選定基準

| タスクの性質 | モデル |
|------------|--------|
| 深い創造・推論・高品質な生成 | Opus |
| 構造的判断・分類・計画 | Sonnet |
| 定型処理・パターンマッチング | Haiku |

**注意**：Haiku は処理が完全に定型化できてから適用する。曖昧さや推論が残るタスクには Sonnet 以上を使う。
