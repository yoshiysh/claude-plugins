# Commit Skill

This skill analyzes staged changes, generates appropriate commit messages compliant with **Conventional Commits**, and executes the commit.

## Overview

1.  **Staging Verification**: Check if there are staged changes.
2.  **Pre-Commit Validation**: Run the repository's own quality checks before committing.
3.  **Message Generation**: Infers the intent from changes and generates a message.
4.  **Execution**: Executes the commit and displays the result.

## Detailed Steps

### 0. Authority Check (CRITICAL)

**Before proceeding, verify:**
- Did the USER explicitly say "Commit this"?
- OR, did the USER explicitly approve a plan that included "Commit" as the *immediate next step*?

**IF NO:**
- **STOP IMMEDIATELY.**
- Do NOT proceed to validation or execution.
- Notify the user: "Changes are complete. May I commit now? (Verification passed/failed)"

**IF YES:**
- Proceed to Step 1.

### 1. Staging Verification

First, check if there are staged changes.

```bash
git diff --staged --name-only
```

- **CRITICAL**: If the output is empty, **STOP HERE** and inform the user "No staged changes found".
- **PROHIBITED**: Do NOT run `git add .` on your own accord. Commit only what the user has explicitly staged.
- **NOTE**: Ignore unstaged changes. Proceed without asking.

### 2. Pre-Commit Validation

Before generating the message, ensure code quality and stability.

**Execution**:
Run the repository's own format / test / verify commands, in that order. Which commands
those are is a property of the repository, not of this skill -- resolve them from what the
repository actually declares, in this order of preference:

1. Project instructions (`CLAUDE.md`, `AGENTS.md`, `.claude/rules/`) that name the commands.
2. A `Makefile` with `format` / `lint` / `test` / `verify` targets.
3. The package manifest's scripts (`package.json`, `pyproject.toml`, `Cargo.toml`, ...).

If none of these exist, say so and commit without validation rather than inventing a command.

- **ARTIFACT RULE**: A verify step may generate artifacts (e.g., reports, JSON outputs).
    - **CRITICAL**: Do NOT stage or commit any products generated by verification unless the user explicitly instructs you to do so.
    - If formatting modifies files that were already staged, re-stage them to include formatting fixes.

### 3. Message Generation

Analyze `git diff --staged` and generate a message in the following format.

**Format (Conventional Commits)**:
```
<type>: <description>
```

- **Types**:
  - `feat`: New feature
  - `fix`: Bug fix
  - `docs`: Documentation only
  - `style`: Changes that do not affect the meaning of the code (white-space, formatting, etc.)
  - `refactor`: A code change that neither fixes a bug nor adds a feature
  - `perf`: Performance improvement
  - `test`: Adding missing tests or correcting existing tests
  - `chore`: Changes to the build process or auxiliary tools

- **Breaking Changes**: If there are breaking changes, append `!` after the type (e.g., `feat!: ...`) or include `BREAKING CHANGE:` in the body.

### 4. Execution

Execute the commit with the generated message.

```bash
git commit -m "<generated_message>"
```

### 5. Post-Execution

Display the result of the commit.

```bash
git show --stat --oneline HEAD
```

**Preview Mode**:
If the user asks for a "Preview" or "Dry run", only display the generated message and do NOT execute `git commit`.

**CRITICAL**: The final output to the user regarding the action taken must be in **JAPANESE**.
