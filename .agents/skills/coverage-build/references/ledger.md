## 構成（ブラックボード）

| 部品 | 実体 | 持つもの |
|---|---|---|
| ボード | `stateDir/build.json`（束の `snap/`・設計の写しの `design/`・検査の `audit/`・check の `checks/` は別ファイル） | 目標・基準・制約・単位・レビューの取り込み・出来事・意図・原因・戻した層・人間に返したもの・起動の記録 |
| 知識源 | 2 つの Workflow source の役（`scripts/roles.json`）と coverage-audit | 1 体 1 単位の判断か生成だけ。ボードを書かない |
| 制御 | `scripts/build-cli.mjs`（`next`・`ingest`・`import-audit`・`run-checks`） | 次の 1 手の決定、受け入れ、層への戻し、止める判定 |

## 段と、script と LLM の分け方

| 段 | LLM がすること | script がすること |
|---|---|---|
| init | なし | 目標・基準・制約の各項目に引用があり、引用が依頼文か決定の記録に逐語であるか（`readGoalFiles`）。通らなければ台帳を作らない |
| design | 目標の照合（依頼文と決定の記録が求める成果を引用つきで挙げ、受け止める項目の id を付ける）、方式設計（単位・持つファイル・依存・効く基準）、単位ごとの詳細設計（仕様・受け入れ・ケース） | 束を書く。照合役の成果の引用の実在・項目の id の実在、受け止められていない成果を人間に返す（`checkGoalMap`・`goalGaps`）。単位の id・種類・ファイルの持ち主の重なり・ファイル数の上限（`MAX_UNIT_PATHS`）・相対 path・依存の循環・全ての基準と制約の受け皿・入力ごとの読んだ証拠の引用（本文に逐語か）・仕様の行数の上限（`MAX_SPEC_LINES`）・code の単位のケース。設計の写し（方式設計 1 枚と単位ごとに 1 枚）を台帳から書く |
| audit | coverage-audit が検査する（目標の照合は流さない） | 検査の目標・依頼・決定の記録・基準・制約・対象と init の引数を書く。取り込みで、検査が終わったか、渡した後に対象が変わっていないか、指摘の引用が今の本文にあるか、指摘の path から単位とテストかを決める |
| tests・implement | 単位ごとに 1 体が受け持ちのファイルを書く | 書いてよい path を券のように渡す。呼び出しの前後の hash で、受け持ちの外の変更、書くはずのファイルの欠け、実装の担当によるテストの変更を見つけて、その回を受け付けない。依存の順（`waves`）で、依存先が実装済みの単位だけを渡す |
| checks | なし | 利用者が init で固定した argv だけを shell を通さずに実行し、exit code と出力を記録する |
| retro | 計画役が意図を出し、実行役が 1 意図を確かめ、別のモデルの検証役が受理を決める | 意図の根拠の id の実在、結論の形、証拠の引用（読めるファイルの中に逐語か）、周の上限と乾き |
| route | なし | 出来事ごとの層を決め、単位の設計・テスト・実装のやり直しか、人間への返しにする（次節） |

静的な照合の正本は `scripts/build-step.js` の `// <checks>` 区間だけで、CLI は同じ文を読み込む（runner の source は import できないので、写しを持たずに 1 か所にするため）。Workflow は本文を持たないので、Workflow の中では形だけを照らして 1 回やり直させ、引用の照合は CLI がファイルに対して行う。args の照合の式（`// <sum>`）は 2 つの source に同じ文があり、一致はテストが照らす。目標の照合の静的な部分（`// <goalmap>`）は coverage-audit の Workflow source と同じ文を置き、一致は `tests/coverage-build-goalmap.test.mjs` が照らす（2 つのスキルは互いのファイルを読まないので、片方から読み込まずに同じ文の小さい関数にした）。

目標の照合は、このスキルの 1 か所だけで行う。LLM の照合役の仕事は、利用者が求める成果を挙げて項目へ対応づけることだけで、項目が依頼に無いものを足したか・範囲を狭めたか・手順かを判定させない（判定が回ごとに揺れたので）。足していないことは init の引用の照合が静的に確かめ、落とした要求は対応の無い成果として人間に返す。目標・基準・制約・決定の記録は `answer` で直せ、直したら引用を照らし直して照合からやり直す。

## 層への戻し方

coverage-audit の層は `LAYER_MAP` で 3 つに写す（方針・要求 → 目標、方式設計・詳細設計 → 設計、実装 → 実装）。出来事ごとの層は、その出来事を根拠に辿る受理済みの原因の層と、監査の層のうち、最も上流のもの（目標 → 設計 → 実装）。振り返りは層を上げられるが、監査の層より下げられない。

| 層 | 戻す先 |
|---|---|
| 目標 | 人間（needs_input）。回答は制約に足し、方式設計からやり直す |
| 設計 | 単位が決まれば、その単位と、それに依存する単位の全てを詳細設計から。決まらなければ（方式設計の写しの指摘など）方式設計から |
| 実装 | テストのファイルの指摘ならテストから、それ以外は実装から。単位が決まらなければ人間 |
| 進め方 | 報告だけ（`notes`）。スキルの段・役・検査の欠けで、成果物の層ではない |
| 決まらない | 人間（check の失敗で原因を辿れなかったときなど） |

やり直しの入力は、単位の設計と、確かめた欠陥と原因（手がかり）で、「この引用の箇所を直せ」ではない。単位のやり直しが `max_unit_rounds` を超えたら人間に返す。やり直した後は、ファイルの中身が同じでもレビューと check をやり直す（同じ欠陥が残れば、もう一度戻して上限で止まる）。

## 振り返りの探索グラフ

| 要素 | 実体 |
|---|---|
| 事実 | 悪かった出来事（`events`: 受け付けなかった出力・返らなかった役・書き込みの違反・読まなかった入力・レビューの指摘・検証不能・見ていない枡・check の失敗）と、受理した原因（`facts`） |
| 意図 | 「原因はこれか」（`intents`）。根拠の事実の id・仮説・層・読むファイル |
| 辺 | 意図 → 根拠の事実、原因 → 根拠（出来事か、さらに下流の原因）。原因の原因を問う意図で上流へ辿る |

1 周は 1 回の Workflow（計画役 → 意図ごとに実行役 → 支持なら検証役）。計画役には件数も例も与えない。原因は、実行役の引用が読めるファイルに逐語であり、別のモデルの検証役が受理したものだけ。振り返りは、レビューか check の後に、まだ振り返っていない全ての段の出来事を対象に始め、全ての出来事が原因に辿られたか、`DRY_ROUNDS` 周続けて新しい原因が受理されないか、`RETRO_MAX_ROUNDS` 周で終わる。終わったら層への戻しを決める。

## coverage-audit との口

- 渡すもの: CLI が `stateDir/audit/<段>-<対象の集合と入力の hash>/in/` に書く goal.md（先頭に検査の段を述べる文）・request.md・decisions.md・criteria.md・constraints.md と、対象のファイルの一覧と、それらを並べた init の引数（`init_argv`）。受け入れ基準は制約と取り違えないよう criteria.md で渡し、実装レビューでは単位ごとの受け入れ（`U<n>A<m>`）も基準に入る。init の引数は照合済みの印 `--goal-checked coverage-build` を含み、coverage-audit は目標の照合を流さない。同じ対象の集合なら同じ置き場なので、coverage-audit の台帳が持ち越され、変わった枡だけが読み直される。
- 受け取るもの: coverage-audit の `status` の出力（確かめた指摘・検証不能・開示した枡・止まった種類）。写しを `stateDir/audit/<段>-status.json` に置き、振り返りの読めるファイルに入れる。
- 指摘の結び付け: 指摘の id（枡#hash、枡は 資産|観点|回、資産は path#見出し）から path を取り、設計の写しなら単位、実装なら持ち主の単位とテストかを決める。

## 止める条件

`next` が返す `stop` の種類と、その条件。上から順に判定する。

| stop | 条件 |
|---|---|
| blocked（cause: input） | 入力か対象のファイルが読めなくなった |
| blocked（cause: failure） | 全ての役が欠けた呼び出しが `MAX_FAIL_STREAK` 回続いた／実装の残った単位があるのに依存が揃わない |
| limit | 周が `max_cycles` を超えた、起動数が `max_agents_total` に達した |
| needs_input | 依頼文・決定の記録が求める成果を、どの項目も受け止めていない（`goal_gaps`）／試行の上限（`MAX_ATTEMPTS`）まで欠けた段か単位がある／人間に返した欠陥がある／利用者への質問がある |
| complete | create・update: 全ての単位を設計・実装し、check（指定があれば）と両方のレビューを今の中身で通し、戻す欠陥が無い。review: 対象を検査し、戻す先を決めた |

周は、振り返りの結論で何かをやり直すたびに 1 つ進む。

## 記録と持ち越し

- 起動ごとに役・label・指定した model・effort・成否（`agents`）、呼び出しごとに起動数・欠け・token（`calls`）。token は native の `budget.spent()` が読めるときだけ数で、runner では null と理由を残す。
- 台帳は run をまたいで残る。`next` のたびに設計の写しと対象の hash を取り直し、レビューと check は、取り込んだときの hash と今の hash が違う段だけをやり直す。人が実装のファイルを直した後の `next` は、check と実装レビューだけを流す。
- 試行の回数・単位のやり直しの回数・周の数は台帳にあり、再開しても 0 に戻らない。

## 設計の型から変えた点

このリポジトリの Workflow の設計の型（`docs/design/skill-design-patterns.md`）から、次の点を変えている。

- 運搬役を置かない。状態を書くのは CLI だけという点は守り、CLI は Workflow の外で呼び出し側が流す。1 回の Workflow は 1 段を 1 回だけ流し、ループは台帳と `next` が持つ。運搬役の失敗・写し違いの欠陥を作らないため（coverage-audit と同じ）。
- 状態の寿命を 1 run でなく、run をまたぐものにする（利用者の決定）。
- 探索グラフは、作る作業の形ではなく振り返りに使う。作る作業は試すものの集合（単位）が方式設計で決まるので、設計と実装の段の並びは固定集合の反復型で、戻りは層への戻しだけ。
- 計画役（方式設計）は 1 体。独立な 2 案と統合は置かず、方式設計の検証は script の静的な検査と coverage-audit の設計レビューに任せる。
- 設計から実装へ進む前に人間の承認の門を置かない（依頼に無いので）。人間に返すのは、目標・方針の層の欠陥と、決められない・上限に達したものだけ。

## 照合しないもの

- 単位が持つファイル以外への書き込み（どの単位にも持たれない path）。git の作業ツリーの照合は持たないので、見えない。
- 同じ `next` の券で書く Workflow を 2 回流し、どちらも `ingest` の前に書き終えたときの 1 回目の書き込み。
- 書く Workflow が途中で落ちた後の `next` は、その時点の中身を前の hash として記録するので、落ちる前の部分的な書き込みは受け持ちの外の変更として見えない（受け持ちの中なら、次の回が書き直す）。
- 目標の照合役が挙げた成果が、依頼文と決定の記録の全てを尽くしているか（引用と id は照らすが、挙げ漏れは LLM に依る）。利用者の言葉そのものに手段が書かれていれば、引用は通る。
- coverage-audit の中身（読む役が 1 枡しか読まないので、設計と実装を突き合わせる観点は受け入れの制約を通してしか持てない）。
