# 仕様と実行テストの対応を検証する

Node.js 22 以降で実行する。規約は [テスト指針](../../docs/guidelines/testing.md) を参照する。この文書は設定と実行方法を扱う。

```bash
node scripts/traceability/cli.mjs --config traceability.config.json --output .artifacts/verification
node scripts/traceability/cli.mjs --config traceability.config.json --output .artifacts/verification --complete
node scripts/traceability/cli.mjs --config traceability.config.json --output .artifacts/verification -- tests/bp-author-cli.test.mjs
```

`--` 以降は実行するテストファイルの置き換えで、カレントディレクトリから解決する。置き換えても、仕様に結び付けるテストは設定のテストファイルの集合（`testFiles` と `testDirectories`）の中のものだけで、集合の外で範囲内の ID を名指すテストは結び付けずに `untracedTests` に載せる。仕様とソースの対象も設定のまま保持するため、部分実行で他の完了仕様を実行しなければ終了コード `1` になり得る。`--complete` は対象全仕様の完了と、成功した leaf test、採用済みの全シナリオを要求し、対応テストの skip を拒否する。通常実行では仕様先行の追加や作成中の行を認めるが、「完了」の検証行には成功した対応テストが必要になる（例外は下記の環境による skip だけ）。ID の対応だけでは、その検証行の内容を assert しているかまでは判定できず、結果の `semanticMatch` はレビュー待ちになる。

## 設定

JSON 設定は次のフィールドを使う。パスは、設定ファイルから解決した `root` の内側に置く。グロブは使わない。

| フィールド | 意味 |
|---|---|
| `root` | 設定ファイルを基準にしたリポジトリのパス。省略時は設定ファイルのディレクトリ |
| `scopePrefixes` | 検証する仕様 ID の接頭辞 |
| `specFiles`, `testFiles`, `sourceFiles` | root からの相対パスによる明示対象 |
| `specDirectories`, `testDirectories`, `sourceDirectories` | 再帰探索する対象。文字列のパス、または `{ "path": "...", "prefix": "ファイル名の接頭辞" }` |
| `scenarios` | 仕様 ID ごとのシナリオ計画。下記形式 |
| `unmeasuredSources` | 対象ソースの相対パスと、未計測とする具体的な理由の対応 |
| `environmentSkip` | `{ "module": "...", "export": "..." }`。この環境でテストを skip する理由を返す関数（理由が無ければ `null`）。skip する側はこの関数の値を skip の理由に含める。下記の skip の扱いに使う。省略時は skip を許さない |

探索と明示対象は結合する。仕様は Markdown、テストは `.test.js` / `.test.mjs`、ソースは `.js` / `.mjs` を収集する。ソースからテストファイルを除き、全探索で `node_modules`、`.git`、fixture とテスト用のディレクトリを除く。除外名の正本は `specs.mjs` の `discover` にある。探索中の symlink は拒否する。各対象種別に一つ以上のファイルが必要で、対象仕様がゼロの場合も成功にはならない。実際の探索起点とファイル一覧は出力の `inventory` に残る。

仕様は、見出しの先頭にある `SP-...` を定義として読み込む。検証表（トレーサビリティ表）は `tools/lib/bp-docs.mjs` の `traceTable` で読み、見出しの行・4 列・`\|` のエスケープ・状態の語彙（`TRACE_STATUSES`）・仕様項目 ID の形の検査はこの関数を正本とする。テスト名の仕様 ID は同じファイルの `specIds` で読み、範囲（`SP-X-027〜031`）の展開はテスト名にだけ掛かる。`tests/bp-trace-status.test.mjs` と `tools/` の試走の記録も同じ関数と状態の定数を使う。対象の仕様書はどれも検証表を持たなければならず、表が無い・列が合わない・状態が語彙に無い・仕様項目 ID の形が崩れた行は設定エラーになる（崩れた ID を範囲外として捨てると、未完了の行が見えないまま完了になり得る）。コードフェンスの中の見出しと表は読まない。全ファイルの定義を先に集めるので、他ファイルの仕様への参照も解決できる。重複定義と対象内の未知 ID は設定エラーになる。

シナリオ計画の一例:

```json
{
  "scenarios": {
    "SP-EXAMPLE-001": {
      "normal": [{ "id": "accepted", "expectation": "有効な入力を受理する" }],
      "recovery": { "notApplicable": "状態を保存せず回復操作を持たない" },
      "error": [{ "id": "invalid", "expectation": "無効な入力を拒否する" }],
      "boundary": [{ "id": "empty", "expectation": "空入力を拒否する" }]
    }
  }
}
```

採用した仕様では上記の全分類にケース一覧または理由つきの `notApplicable` を置く。未採用仕様は `unplanned` として残り、通常実行のエラーにはならない。注釈は、テストが結び付く仕様 ID のうち計画のあるものだけと照合する。一つの実行を複数の仕様へ結び付けるとき、計画の無い仕様を名指しても失敗しない。範囲内の既知の仕様 ID を持ち、そのどれにも計画が無いテストに注釈を付けた場合は未知シナリオとして失敗する。範囲内の仕様 ID を持たないテストの注釈は照合しない（別の範囲の注釈であり得るため）。分類は互いに排他的ではなく、一つのテストに複数注釈を付けられる。

```js
test('SP-EXAMPLE-001', async t => {
  await t.test('@error:invalid @boundary:empty', () => {
    assert.throws(() => parse(''), /empty/);
  });
});
```

子テストは親の仕様 ID と注釈を継承する。子に仕様 ID または注釈がある場合、それぞれの継承値を置き換える。成功件数は leaf だけを数える。親を含む全宣言の未知 ID・分類・ケースも検査するので、子で置き換えても親の誤記は隠れない。複数の対象 ID を持つテストでは、その注釈が計画のある全対象 ID に適用される。別の接頭辞の ID は検証外として件数と ID 一覧を開示する。テスト名の ID 範囲の両端の接頭辞が違う、または終わりが始まりより前の場合は対応の不整合になる。skip / todo / cancelled は成功扱いにせず、未知参照の検査対象に含める。

skip した leaf を 1 件でも持つ仕様を `unverified` に載せ、skip は成功に数えない。対応テストが skip だけの仕様・ケースは `skipped` になる。「完了」の行で `skipped` を許すのは、`environmentSkip` の関数が理由を返し、かつ skip の理由にその理由がそのまま含まれる skip だけである（skip を出す側が同じ関数の値を理由に書くので、その判定で skip した印になる。固定の文言とは照合しない）。検証表に「完了」の行を持つ仕様の ID に結び付く skip がそうした skip だけなら、通常実行は報告にとどめて失敗させない。理由の無い skip・別の理由の skip（関数が `null` を返す環境と設定が無い場合は全ての skip）が、そうした仕様の ID に 1 件でも結び付けば、成功した兄弟のテストがあっても、行とケースの別なく通常実行で失敗する。`--complete` は環境を問わず skip を拒否する。対応テストが無い、または todo・cancelled だけの「完了」の行は常に失敗する。

## 出力と失敗時の扱い

同じ実行から `traceability.json`、`coverage.json`、`report.md` を生成する。JSON は共通の `runId` を持ち、Markdown には同じ値と分類別の進捗を載せる。`summary` は対象全体の仕様数と、検証表の全行が「完了」の仕様数（`specificationsMarkedDone`。表の状態の数で、検証済みを意味しない）に並べて、計画済みの仕様数（`planned`）、そのうち全ケースが成功した数、計画済みケースの成功・skip の件数を示す。失敗したテストは、仕様に結び付くかを問わず名前・ファイル・原因を `failures` と report に載せ、標準エラーにも出す。失敗は 1 回ずつ数える。子の失敗だけで落ちた親（`subtestsFailed`）は除く。続けて取り消された列は最上位の 1 件で数え、列の直上の取り消されていない祖先が載る失敗（timeout など）ならその祖先が説明するとして除き、pass・`subtestsFailed` なら取り消しそのもの（親が子を待たずに終わった・イベントループが空になったなど）を載せる。より上の祖先の失敗は、途中の親が子を待たずに終わったことを説明しないので見ない。親自身のコードや hook の失敗、ファイル単位の hook の失敗は載せる。testId を持たない列（Node 22 の文書の形）では親を `test:start` の入れ子で決め、親を決められない取り消しは、取りこぼさないよう単独で載せる（二重に数えることがある）。Node 22 の列についてのこの扱いは、列を合成したテストで確かめた範囲で、Node 22 での実行は確かめていない。テストの diagnostic は全て `notes` と report に載せ、標準エラーにも出す。テスト終了後の非同期の例外の原因はここにだけ現れ、実行全体の件数の行も混ざる（件数の行と見分ける構造上の印を Node の文書に確かめられないため、見分けずに全て出す）。仕様の `complete` は、対象が非空、参照エラーなし、テスト実行成功、skip による未検証なし、全仕様でシナリオ計画が採用され、全仕様とその計画が完了したときだけ真になる。

| 終了コード | 意味 |
|---|---|
| `0` | 検証成功。仕様作成中や未計画、skip による未検証、カバレッジの部分計測は残り得る |
| `1` | テスト失敗・取消・未完了、対応の不整合、完了ゲート未達 |
| `2` | 設定・対象読取・runner・出力処理の異常 |

実行開始時に前回のレポートを消すため、設定や runner が異常終了しても古い成功結果を今回の結果として残さない。同一出力先は `.traceability.lock` で排他し、競合した実行は前回の出力を変更せず終了する。ロックには取得した実行の PID とホスト名を記録する。シグナルで終了してロックが残った場合、同じホストで記録された PID が終了していれば次の実行が古いロックとして取り直す。ロックは、中身を書いた下書き（`.traceability.lock.<PID>.<id>.tmp`）を link で置く。古いロックの削除は、その中身ごとの回収用ファイル（`.traceability.lock.reclaim-<hash>`）を持つ間に、中身が死んだ持ち主のままのときだけ行い、生きた持ち主のロックは動かさない。下書きと回収用ファイルも持ち主の PID を持ち、取得の途中で強制終了して残ったものは、持ち主が死んでいれば次の実行が片付ける（回収用ファイルは同じ手順で回収する）。PID が生きている・別のホスト・記録が読めない場合は取り直さず、エラーメッセージに記録された持ち主とロックのパスを出す。その実行が終了したことを確認してから、そのファイルを削除して再実行する。回収用ファイルを生きた実行が持ち続けて回収が終わらない場合は、そのパスと持ち主の PID をメッセージに出す。

コードカバレッジは仕様・シナリオの充足度とは別の指標である。実行した行・分岐・関数を集計するが assertion の妥当性は証明しない。未ロードの対象も一覧に残す。Node 22 では未ロードソースをゼロとして取り込む include-all が利用できない場合があるため、`unloaded` として部分計測を開示する。対応する Node では include-all を使い、計測できたゼロ実行のソースを `zero-covered` とする。

変換して実行する Workflow ソース二つは現在の設定で理由つきの `unmeasured` として明示し、計測率の分母から除く。対象ファイルと理由の正本は `traceability.config.json` の `unmeasuredSources` にある。未計測や未ロードのソースがあれば全体は `partial` となり、任意のカバレッジ閾値で合否を補わない。
