#207 の目的（案。利用者に確定してもらう）

## 防ぐ失敗
1. 作業が目的を見失って膨らむこと。設計の往復（design-v2〜v2h）では、レビュー役が突いた端の場面を 1 件ずつ塞ぎ、利用者への問いの答えをそのまま規範に足した。その結果、AGENTS.md に入る中身が膨らんだ。要求の改稿でも同じことが起きた（指摘 1 件ごとに要求を 1 本足し、33 項目が約 70 項目になった）。
2. 検証が同じ観点に偏ること。検証役は何体も立てたが、渡した観点は全員同じだった。そのため「目的に要るか」「AGENTS.md に置くべきか」「変更自体が要るか」は全員の死角になった。
3. 入口の文書が重くなること。AGENTS.md は main で 235 行あり、深い規範・経緯の実測・人が行う install の手順・重複が混ざっている。そのため重要な制約が埋もれ、古い写しが残る（OpenAI の記事が挙げる、大きな AGENTS.md の失敗の形）。

## 達成すること
- 作業の流れを規範にする。流れは「目的の固定 → 設計 → 設計レビュー → 実装 → 実装レビュー」。設計と設計レビューは「根本原因の除去」を規範とする。形式検証は要求・仕様・実装の全てに掛ける。
- AGENTS.md を約 100 行の地図にする。正本は docs/ の構造化した文書・スキル・script・agent 定義に置く。何を AGENTS.md に置くかの基準も、それ自体を正本の 1 つとして置く。
- 多角的なレビュー観点を agent として定義する。どの段でどの観点を当てるかを 1 か所に置く。

## 目的に入らないもの（#207 でやらないこと）
- スキルの修正ループを「設計に戻る」に揃える改修（repo-implement・address-review・build_skill.js・pr-review-fix・prd-spec.js・review-document）。Q1 により直後の別 PR で行う。
- formal-methods スキルの未決の解消（実行形態・契約の書式・取り込みの採否）。Q2 により、#207 では参照するだけにする。
- quick_validate.py・address-review の evals.json の語の揃え。Q4 により別 PR で行う。
- Codex の hook の再導入と、検査の時機の設計。Q8 により後で見直す。#207 では削除だけを行う。
- design-v2h/later.tsv の残りの行（develop-skills-redesign.md の AGENTS.md の引用の照合など）。
- 観点の agent を既存のスキル（repo-review・pr-review・skill-creator の reviewer）へ組み込むこと。#207 では agent 定義と段の対応表を置くまでにする。
- 規則を機械の検査（lint・make test）へ昇格させること。#207 では候補を挙げるだけにする（例: plugins/ 配下の symlink の検査は verify_install.py にあり、make test には無い）。
- docs/ の鮮度を定期的に検査する仕組み（記事の文書整備 agent・CI）。
