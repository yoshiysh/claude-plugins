# 質問と既定の判定（question policy）

このファイルが**唯一の正**である。「ユーザーに聞くか、既定で進めるか」の判定手順と、
決定ログ（decisions）の書式を定める。intake（既定選定係）・司令塔（統合ゲート）・
fabrication-auditor（[DECISIONS] の受理）がここを見る。

## なぜ質問を最小化するか

質問のコストは 1 問あたりの往復時間ではない。**質問が多いほど 1 問あたりの回答の質が
下がり、結局どれも決まらない**。「依頼者にしか決められない」と分類された質問でさえ、
再検査すると依頼文に答えがあるか上位互換候補を持つものが大半である。**自分の
分類を信用せず、下の判定手順で機械的に落とす。質問 0 件が目標値である。**

一方、推測で埋めることの害は「間違えること」ではなく**「間違いが不可視なこと」**である。
既定を選んだ事実と理由が決定ログに載っていれば、それは捏造ではなく**可視化された仮置き**であり、
依頼者は一覧を見て異議のある行だけ直せる。書くのは安く、依頼者の時間は高い。

## 判定手順（この順で、全論点に適用する）

未確定の論点 1 件ごとに、次を上から順に試す。

1. **依頼文・回答に答えがあるか探す。** あれば確定事項（根拠は原文の引用）。
   **依頼文に答えがある論点を質問にしてはならない** — 「確認のため」も禁止。
   依頼文と食い違う情報を別の入力が持つときだけ、食い違いの確認として聞く。
2. **スキルが固定する前提（`references/fixed-premises.md`）にあるか。** あれば前提を使う。
   質問にしない。
3. **妥当な既定を選べるか。** 次のいずれかなら選べる:
   - 候補のうち 1 つが他候補の**上位互換**（他案でできることを全部含む）
   - どの候補を選んでも**成果物の正しさが変わらない**（書式・構成・命名などの執筆規約）
   - 分野の標準的な選択が存在し、依頼文にそれを避ける記述が無い
   → **決定として起票し、質問にしない。** 決定ログに載せて統合ゲートで報告する（下記書式）。
4. **どれも不可なら blocking 質問。** 出せる条件は 3 つとも満たすこと:
   - 既定を選べない（依頼者の運用・意図・リスク許容にしか答えが無い）
   - 間違えたときのやり直しコストが、質問 1 回のコストを上回る
   - **論点がプロダクトの価値に関わる**（プロダクトが何をすべきか・何を許すか・何を優先するか）。
     書式・構成・分割・測定方法・文書間整合のような方法論の論点は、既定を選べなくても
     質問にしない — 司令塔が決めて決定として事後提示する（方法論の間違いは改稿経路で
     可逆に直せるが、質問はゲートを承認ボタン化させる不可逆な希釈を起こす）
   質問には「**依頼文を探したが答えが無かった**」ことの申告を必須とする（探した箇所を書く）。

## 決定ログ（decisions）の書式

```json
{
  "id": "D-001",
  "topic": "何についての決定か（1 行）",
  "value": "選んだ既定",
  "why": "なぜこの既定か（上位互換 / 正しさ不変 / 標準的選択 のどれに当たるか）",
  "source": "default",
  "reversibility": "変更するとき何を直せばよいか（1 行）"
}
```

- 依頼文から確定した事項は `source: "input"` とし、`why` に原文の引用を入れる。
- **決定ログは承認待ちにしない。** 統合ゲートで一覧として報告し、「異議のある行だけ
  教えてください」の形にする。異議が出た行はその周回の回答として上書きする。
- writer は決定を根拠に使うとき、`trace` に `{ kind: "decision", ref: "D-001" }` として申告する。
  **本文には出所を書かない**（正は `document-structure.md` §4）。**依頼者の回答や外部規格の名で
  申告しない** — 出所の偽装は fabrication-auditor の指摘対象である。
- fabrication-auditor は `kind: "decision"` の申告を、対応する決定が `[DECISIONS]` に実在する
  限り捏造としない。実在しない D-N への参照は捏造として指摘する。

## 既定にしてはならないもの

決定ログは万能の抜け道ではない。次は既定で埋めず、blocking 質問にする。

- **案件の要求そのもの**（何を作るか・何を守るか）。既定で置けるのは**書き方と進め方の選択**まで
- 金額・期限・法的義務など、間違いが外部に波及する値
- 依頼文が「未定」「後で決める」と明示した事項（依頼者が保留の意思を示している）

## TBD に起票してよいもの（decision との棲み分け）

TBD と決定ログは両方「未確定の可視化」だが、役割が違う。**同じ論点を両方に積まない。**

- **TBD に起票してよいのは、判定手順 4 に落ちた論点だけ**（依頼者にしか決められない、かつ
  やり直しコストが質問コストを上回る）。
- **decision で仮置きした論点は TBD に重複起票しない。** 仮置きの可視化と変更手順は
  decision 自身（`value` / `reversibility`）が担う。両方に積むと、読み手には「決めたのか
  決まっていないのか」が二重に見え、残 TBD 数が実態より多く報告される。
- **writer が執筆・改稿中に新しく見つけた論点にも、この判定手順を適用する。** 既定を
  選べる論点（執筆規約・書式・単位の選択など）は TBD にせず、本文で決めて `trace` に
  `{ kind: "decision", ref: "執筆判断" }` として申告する。判定手順 4 に落ちた論点だけを
  TBD として起票する。

## 規範の授権はどこから来るか（規範の新設が要るとき）

**このスキルの中で、新しい規範を置いてよいという授権を作れるのは統合ゲートの回答だけである。**
依頼文・回答・決定ログ・固定前提・計測結果は、いずれも「既にある根拠」であって、そこに無い
規則を足す権限は誰も持っていない。writer は文を書けるが授権は持たない。だから改稿で規範を
足すと、その記述は根拠を持たないまま本文に入り、次ラウンドの fabrication 監査で blocking に
なる。**改稿予算を 1 回分使ったうえで、論点は同じゲートへ戻る** — 1 周遅れて同じ場所に着く。

この機序から、**改稿で「〜が一意に定まらない」「適用範囲が重なる」型の指摘に応えるときに
使ってよいのは、既にある根拠だけで閉じる次の 3 つ**である。

| | 形 | 授権の出どころ |
|---|---|---|
| (a) | 既存の既定・決定・既述への**追認**として書く（適用範囲の限定を含む） | 既に受理済みの `[DECISIONS]` / `[TBD_ANSWERS]` / 本文 |
| (b) | 問題の記述そのものを**削除**して指摘前の範囲へ戻す | 授権を要さない（規範が減る） |
| (c) | **TBD として起票**し、統合ゲートへ上げる | ゲートの回答としてこれから作られる |

**(c) は逃げではなく、授権を取りに行く経路である。** blocking の TBD として起票された論点は
統合ゲートで依頼者に提示され、その回答が `[TBD_ANSWERS]` として次ラウンドの writer に渡る。
そこで初めて、その規範は根拠を持って書ける。だから (c) を選んだ論点は「書けなかった」ではなく
「まだ授権が無い」であり、ゲートを 1 回通れば書ける。

**規則の発明が必要だと感じた時点で、その解消手段は (a) にも (b) にもならない。** 自分の判断で
規則を置くことと、(a) の追認とは別物である（追認は既にある文言を指せるが、発明は指せない）。
発明が要ると気づいたら (c) を選ぶ。

同じ機序が分類側にも効く。ladder-judge が「解消に規範の新設が要る」と見た指摘を
`question` へ落とすのはこのためであり、その判定基準は `schemas/agent-contracts.md`
§ladder-judge が正である。writer 起票の TBD と、ladder-judge 由来で script が起票する
`TBD-NI-` は、どちらも同じ統合ゲートに合流する。
