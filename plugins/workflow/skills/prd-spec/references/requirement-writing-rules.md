# 要求文の書き方

**目次**: [1. 助動詞規約（JIS Z 8301 準拠）](#1-助動詞規約jis-z-8301-準拠) · [2. 曖昧語（検出したら欠陥として指摘する）](#2-曖昧語検出したら欠陥として指摘する) · [2.5 条件節の構文（EARS）](#25-条件節の構文ears) · [2.6 境界値](#26-境界値) · [4. 根拠の申告](#4-根拠の申告) · [5. 出自](#5-出自)

このファイルは PRD・仕様書の**要求文**に適用する規律を定める。案件の規模・ドメインで緩めない。

曖昧語の検出は文体の良し悪しの話ではない。**曖昧語を含む要求文はテスト設計ができない** ——
検証可能性の欠落という欠陥として扱う。

## 1. 助動詞規約（JIS Z 8301 準拠）

生成する文書の冒頭に必ず次の凡例を置く。

```markdown
## 表記規約

本文書の要求文は次の語尾で区分する（JIS Z 8301 が定める助動詞対応に従う）。

| 区分 | 語尾 | 対応する英語 |
|---|---|---|
| 必須 | 〜しなければならない | shall / MUST |
| 推奨 | 〜することが望ましい | should / SHOULD |
| 許容 | 〜してもよい | may / MAY |
| 禁止 | 〜してはならない | shall not / MUST NOT |
```

要求文はこの 4 語尾以外で終わらせない。

**英語で出力する場合は `shall` を軸にし、`must` を避ける。** `must` は「緊急性」や「物理的
制約」の意味に流れやすく、契約上の義務を指す語としては `shall` の方が一意である
（ISO/IEC Directives Part 2 Clause 7 が shall = requirement と定めている）。RFC 2119 の
MUST / SHOULD / MAY を使う場合は、**全て大文字で書かれているときにのみ定義された意味を持つ**
（RFC 8174）。同じ文書内で shall 系と MUST 系を混在させない。

**平叙終止は要求文として認めない。** 「〜する」「〜を行う」「〜対応する」「〜が可能」は、
要求なのか現状の説明なのか読み手に判別できない。

| 不可 | 可 |
|---|---|
| 申請者に通知する | 申請者に通知しなければならない |
| ログを保存する | ログを 90 日間保存しなければならない |
| 高速な検索が可能 | 検索結果を 1 秒以内に返さなければならない |

説明文・背景・前提は要求文ではないので、この規約の対象外。ただし**要求一覧の中には要求文しか
置かない**（説明を混ぜると、どれが要求か数えられなくなる）。

## 2. 曖昧語（検出したら欠陥として指摘する）

次の語が要求文に含まれていたら、測定可能な形への書き換えを求める。

```
適切に / 必要に応じて / 可能な限り / 柔軟に / 速やかに / 原則として / 等（など）/
十分な / 適宜 / 基本的に / 高速に / 使いやすい / 安定した / 極力 / なるべく /
場合によっては / 想定される / 考慮する / **〜まで / 最大 / 最小 / 程度 / 前後**

末尾の 5 語は境界値に関わる（§2.6）。数量に付くと「境界を含むか」が読み手によって変わる。

英語で出力する場合の対応リスト:

minimize / maximize / optimize / fast / prompt / quick / rapid / user-friendly / easy /
intuitive / sufficient / adequate / appropriate / approximately / about / around /
usually / typically / normally / as needed / as required / if necessary / etc. /
and so on / including but not limited to

加えて英語では次の 2 種を疑う。

- **all / any / both** — 集合全体に作用するのか各要素に作用するのかが判別できない
- **and / or / but** — 1 文に複数の要求が入っている兆候（§3 の単一要求違反）
```

指摘するときは、**書き換えの候補を 2〜3 提示する**。「曖昧です」だけでは書き手は動けない。

| 曖昧な要求文 | 書き換え |
|---|---|
| 承認されたら速やかに通知する | 承認処理の完了時刻から 3 秒以内に通知しなければならない |
| 必要に応じてログを出力する | 認証の失敗時に、失敗理由と発生時刻をログへ記録しなければならない |
| 適切な権限管理を行う | 申請者は他者の申請を参照してはならない |
| 大量のデータでも安定して動作する | 同時接続 200 件において、応答時間の 95 パーセンタイルを 2 秒以内に保たなければならない |
| 障害時は可能な限り復旧する | 障害検知から 30 分以内にサービスを復旧しなければならない |

この書き換えは、決済システムでも社内の勤怠ツールでも同じように必要である。**閾値の厳しさが
変わるだけで、閾値を書くという規律は変わらない。**

閾値が決まっていない場合は、勝手に数値を置かない。TBD として起票する
（`references/traceability.md` §TBD 管理）。

## 2.5 条件節の構文（EARS）

**要求文の条件節は次の 5 パターンのいずれかで書く。** 助動詞規約が「義務の強さ」を固定するのに
対し、EARS は「**いつ有効か**」を固定する。

| パターン | 日本語 | 英語 |
|---|---|---|
| 常時 | システムは〜しなければならない | The `<system>` shall `<response>` |
| **状態** | **〜である間**、システムは〜しなければならない | **While** `<precondition>`, the `<system>` shall `<response>` |
| **イベント** | **〜したとき**、システムは〜しなければならない | **When** `<trigger>`, the `<system>` shall `<response>` |
| **任意機能** | **〜を備える場合**、システムは〜しなければならない | **Where** `<feature>`, the `<system>` shall `<response>` |
| **望ましくない事象** | **〜したならば**、システムは〜しなければならない | **If** `<trigger>`, **then** the `<system>` shall `<response>` |
| 複合 | 〜である間に〜したとき、システムは〜しなければならない | While `<precondition>`, When `<trigger>`, the `<system>` shall `<response>` |

### なぜ固定するか

**「〜である間」と「〜したとき」の違いが、実装を分ける。**

- 「ログイン中である間、システムはセッションを保持しなければならない」→ 状態が続く限り有効
- 「ログインしたとき、システムはセッションを発行しなければならない」→ その瞬間に 1 回発火

この区別が構文で付いていないと、実装者は「継続的な条件」と「1 回のトリガー」のどちらかを
自分で決めることになり、**決め方は人によって変わる**。

**「〜したならば」（If ... then）が異常系専用**である点も重要。エラー・失敗・不正入力を
このパターンで書かせることで、望ましくない事象の書き漏らしが目立つようになる。

### 出自

EARS（Easy Approach to Requirements Syntax）。2009 年に Alistair Mavin と Rolls-Royce の
同僚が発表した記法で、テンプレート構文は公式ガイドで確認できる（`citation-policy.md`）。
**このスキルは EARS の 5 パターンを条件節の書式として借りているだけで、EARS への準拠を
主張しない。**

## 2.6 境界値

数量・時間・サイズ・件数を要求文に書くときは、**次の 4 つを必ず揃える**。

| 決めること | 悪い例 | 良い例 |
|---|---|---|
| 単位 | 「3 以内」 | 「3 **秒**以内」 |
| **境界を含むか** | 「3 秒まで」 | 「3 秒**以内**」（含む）/「3 秒**未満**」（含まない） |
| **上限と下限の両方** | 「1 件以上」 | 「1 件以上 100 件以下」／「1 件以上（上限は設けない）」 |
| **境界を超えたときの挙動** | 「上限は 100 件」 | 「100 件を超える要求を受け取ったならば、システムは要求を拒否しなければならない」 |

3 つ目と 4 つ目が抜けやすい。「1 件以上」だけでは、実装者は 10 万件を受けるコードを書くか、
勝手に上限を決めるかのどちらかになる。「上限は 100 件」だけでは 101 件目の扱いが決まらない
（拒否か、切り詰めか、警告して通すか）。

### 境界を含むかを示す語

| 表現 | 意味 | 使用 |
|---|---|---|
| 以上 / 以下 / 以内 | 境界を**含む**（≧ ≦） | 使う |
| 超 / 未満 | 境界を**含まない**（＞ ＜） | 使う |
| 〜まで / 最大 / 最小 / 程度 / 前後 | 含むかどうかが読み手によって変わる | **使わない**（§2 の曖昧語として扱う） |

英語で境界の包含を示すために使ってよい表現は、次の **4 つに限る**。

| 表現 | 意味 |
|---|---|
| `greater than or equal to` | 境界を含む（≧） |
| `less than or equal to` | 境界を含む（≦） |
| `greater than` | 境界を含まない（＞） |
| `less than` | 境界を含まない（＜） |

**この 4 つ以外は使わない。** `up to` / `at least` / `no more than` / `within` / `by` は、
包含が読み手によって変わるか、片側しか決まらないため使わない。日本語側の 5 語
（以上 / 以下 / 以内 / 超 / 未満）と同じく、**集合が閉じていることに意味がある** —
閉じていないと、英語で生成した文書に対して何を合格とする検査を書けばよいかが決まらない。

「〜し、かつ〜する」「および」「または」で複数の要求を 1 項目に詰めない。

理由: テスト設計時に部分合格が発生し、トレーサビリティが破綻する。「片方は満たすがもう片方は
満たさない」状態を、その項目の合否として表現できなくなる。

| 不可 | 可 |
|---|---|
| 申請者へ通知し、かつ経理へ連携しなければならない | PR-001 申請者へ通知しなければならない<br>PR-002 経理システムへ連携しなければならない |

**条件節（〜の場合）は分割対象ではない。** 「承認された場合、通知しなければならない」は
単一要求である。分割するのは**動作が 2 つ以上ある**とき。

## 4. 根拠の申告

各要求文には、それがどこから来たかの根拠が要る。**根拠は本文に書かず、writer が返す `trace`
に申告する**（本文に置いてよいものの一覧は `document-structure.md` §4 が正）。

```markdown
### PR-APPROVAL-001 承認完了の通知
申請が承認された場合、システムは申請者へ承認完了を 3 秒以内に通知しなければならない。
```

```json
{ "item_id": "PR-APPROVAL-001", "kind": "answers", "ref": "", "quote": "3 秒以内" }
```

根拠にできるのは次のものだけ。

- 依頼文（`[INPUT]`）・ユーザーの回答（`[ANSWERS]` / `[TBD_ANSWERS]`）
- ドメイン分析の判定（`[DOMAIN_FINDINGS]`）で、ユーザーが承認したもの
- 決定ログ（`[DECISIONS]`）・スキルの固定前提（`[SKILL_PREMISES]`）— ただし書き方・進め方の
  選択に限る（正は `question-policy.md`）
- 計測結果（`measurement` agent が証拠付きで確定した事実）

**これら以外を根拠にした要求は書いてはならない。** 業界の常識・類似システムの慣行・
「普通はこうする」は根拠にならない。それらは要求ではなく提案なので、TBD として
「こうすることを提案します。決めてください」の形で起票する。

### 既存実装は根拠にならない

対象に既存の実装があり、それを読める場合でも、**実装は要求の根拠にならない。**
実装を読んでよいことと、実装を根拠にできることは別である。

「実装がこう動いている」は**現状の記述**であって、要求でも仕様でもない。要求が答えるのは
「**なぜそうする必要があるのか**」であり、仕様が答えるのは「**どう実現するか**」である。
現状の記述はそのどちらでもないため、そのまま書くと文書が要求文書でも仕様書でもなくなる。

読み取った実装の行き先は 3 つに分かれる。

| 読み取ったもの | 行き先 |
|---|---|
| 振る舞い・制御フロー・データの形 | **仕様書**（「どう実現するか」の記述として） |
| その振る舞いが何のためにあるかが、依頼文・回答・ドメイン分析から辿れる | **要求文書**（根拠はその入力であって、実装ではない） |
| 目的が入力から辿れない | **TBD として起票**（「この振る舞いが何のためにあるか確認が要る」） |

3 つ目を「実装がそうなっているから」で埋めるのが、既存実装がある案件で最も起きやすい失敗である。
それは要求の捏造と同じ構造を持つ — **入力に無い要求を、もっともらしい出所を添えて書いている。**
出所が「業界の常識」ではなく「動いているコード」なので気づきにくいだけで、ユーザーがそれを
要求したという根拠はどこにも無い。

この歯止めが無いと、既存実装のある案件では要求が実装の記述に置き換わっていく。そうなった文書は
要求文書でも仕様書でもなく、現行実装の説明書である。読み手は「何を作りたいか」を知る手段を失う。

**この規律はモードによらず適用する。** 新規作成でも、既存文書のレビューでも、要求からの
仕様展開でも同じで、既存実装がある案件でも要求は入力から書き起こす。

### 引用は 1 文に収める

`trace[].quote` が果たす役割は「**どこを見れば確かめられるか**を示すこと」であって、そこを
読み直さなくて済むようにすることではない。原本に実在する文字列を、該当箇所を特定できる
最小限の長さで写す。

- 良い: `"quote": "3 秒以内"`
- 悪い: 回答の段落をそのまま貼り、なぜその回答が妥当かの説明まで加える

**引用は 1 文以内を目安とする。** 超えるときは、たいてい根拠ではなく設計判断の説明が混ざって
いる。判断の理由が要るなら、それは自明でない規則に添える本文 1 文か、章の導入文に 1 度だけ
書く（要求ごとに繰り返さない）。

引用は**言い換えない**。照合は文字列で行われるので、要約した引用は「原本に無い」＝根拠なしと
して扱われる。

## 5. 出自

曖昧語リストの発想は、日本語文の曖昧さを検出する既存の取り組み（stop-ai-slop-jp 等）から
借りている。ただし本スキルでは**文体の良し悪しを一切扱わない**。要求文が検証可能かどうかだけを見る。

## 6. 定型句を文書間で反復しない

複数文書の案件で、同じ文言の宣言（「本文書の実質的な読み手は AI agent 群である」
「投資判断そのものは依頼者が行う」など）を各文書に書き写さない。上位文書に 1 回書き、
下位文書は参照するか、書かない（上位が全文書に効くと宣言していれば参照も要らない）。
実測（Alphora 7 文書）で、機械検出できた真の過剰記述はほぼ全てこの型だった —
文書ごとの writer が並列で書くと、同じ足場文が文書の数だけ複製される。

## §7 spec-driven 実務からの追加規範（一次情報確認済み・2026-08）

AI を読み手とする仕様駆動ツールの公開仕様から採る規範。いずれも出典を確認済み。

- **変更しない挙動の明記**: 既存システムの改修を扱う要求では、保持すべき既存挙動を
  「〜の場合、システムは引き続き〜しなければならない」の形で明示する。書かれていない
  既存挙動は AI 実装者に保護されない（出典: Kiro best practices の
  「WHEN … THEN the system SHALL CONTINUE TO …」 https://kiro.dev/docs/specs/best-practices/）。
- **曖昧箇所のマーカー**: 未確定を暗黙の仮定で埋めさせないためのマーカー運用は、
  このスキルでは TBD 起票（`references/traceability.md` §4）がその実装である
  （同型の外部実装: GitHub Spec Kit の `[NEEDS CLARIFICATION]`
  https://github.com/github/spec-kit/blob/main/spec-driven.md）。
- **粒度の上限**: 詳細に書くほど良いのではない。「期待挙動を完全に規定する最小の情報量」を
  超えた具体性は brittle さを生む（出典: Anthropic effective context engineering の
  altitude 論 https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents）。
  分量の決まり方は `references/prd-and-spec.md` §7 を正とし、本節は上限側の根拠を足すだけである。
- **移行要求の置き場**: データ移行・並行運用・切替など transition に属する要求は
  機能要求と混ぜず、独立の節に置く（出典: BABOK v3 の requirements classification schema
  https://www.iiba.org/knowledgehub/business-analysis-body-of-knowledge-babok-guide/2-business-analysis-key-concepts/2-3-requirements-classification-schema/）。

## §8 仕様書固有の規範（一次情報確認済み・2026-08）

仕様書（specifications）にのみ適用する規範。出典を確認済み。

- **詳細度の下限**: `prd-and-spec.md` §5「どこまで書けば十分か（下限）」を正とする
  （ISO/IEC/IEEE 29148 §9.6.10）。
- **入力×状況の完全性**: 定義した全入力クラス × 全状況クラスへの応答を、invalid な入力を
  含めて定義する。valid 側だけの項目は不完全（IEEE 830-1998 §4.3.2、公開複製で逐語確認）。
- **検証方法の 4 分類**: 各仕様項目の検証方法は inspection / analysis / demonstration / test
  のいずれかを明記する（NASA SE Handbook SP-2016-6105
  https://www.nasa.gov/reference/5-3-product-verification/）。要求種別から方法を機械的に
  決める決定表は一次情報に無い（cannot-verify）— 選定は書き手の判断で、選んだ方法を書く。
- **関心事駆動の完全性**: 扱う関心事を列挙し、各関心事を必ずいずれかの節が扱う
  （IEEE 1016-2009 §4.3–4.4 の design concern / viewpoint 対応。公開複製で確認）。
- **観点の独立**: インタフェース・データ・状態・相互作用・アルゴリズムは独立の観点として
  揃える（IEEE 1016-2009 の viewpoint。公開複製 §5.2–5.13 で確認）。
- **コード・詳細アルゴリズムは本文に置かない**: 必要なら別ファイルへ逃がす
  （IEEE 830 §4.2(b) + GitHub Spec Kit spec-driven.md の implementation-details 分離）。
- **TBD の残存は不完全の定義そのもの**: 仕様書に残す TBD は解消条件付きに限る
  （IEEE 830 §4.3.2）。
- **仕様項目の単位の自己宣言**: 何を 1 つの仕様項目として切り出すかを、本文の一箇所で
  機械的に判別できる形（見出し階層の水準など）で宣言する
  （例:「本書は `####` 見出し 1 つを 1 仕様項目とする」）。単位が宣言されていないと、
  読み手ごとに項目の切り出し方が変わり、件数・網羅の判定が文書間で揃わない。
  宣言の実在は構造検査（`ST-NOUNIT`・degraded）が機械判定する
  （スキル独自の設計判断。外部帰属で書かない）。

**帰属の注意**: 本スキルの「状態遷移図＋状態×イベント表の分担規律」と「仕様書の常設章の
集合」は外部規格が命じるものではなく、スキル独自の設計判断である（IEEE 1016 State dynamics
viewpoint と 830 の completeness は方向が一致する根拠に留まる）。外部帰属で書かないこと。
