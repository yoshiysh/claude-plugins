# スキルが固定する前提（案件ごとに問い直さない）

このファイルが**唯一の正**である。ここに列挙された前提は、prd-spec の構造・既定・規律として
スキル側で決まっており、**案件の未確定事項ではない**。各 agent は次のように扱う。

- **intake**: これらを質問リストに入れない。依頼文がこれらと**食い違う**ときだけ、
  食い違いの確認として聞く。
- **writer**: これらを前提として使ってよい。`trace` に `{ kind: "premise", ref: "前提 N" }` と
  申告する（本文には出所を書かない。正は `document-structure.md` §4）。
  依頼文・回答を根拠に偽装しない。外部規格の名を出所として借りない。
- **fabrication-auditor**: `kind: "premise"` の申告は、対応する前提が
  本ファイルに実在する限り捏造ではない。**出所の偽装**（スキル既定の内容を規格名・依頼者の
  回答・業界慣行の名で書くこと）は引き続き指摘する。
- **司令塔**: これらに関わる TBD が起票されたら、人間ゲートに出す前にこのファイルで解消する。

## この前提が「根拠」と違う点

前提は**執筆の枠組み**であり、**案件の確定要求の根拠にはならない**。
「読み手は AI である」（前提 1）を使って記述水準を決めるのは正しいが、
「システムは〜しなければならない」という個別要求の根拠は依然として
`[INPUT]` / `[ANSWERS]` / `[TBD_ANSWERS]` / `[DECISIONS]`（範囲は question-policy.md）にしか無い。前提を根拠欄に書いてよいのは、
その記述が**書き方の選択**（語尾・書式・構成・語彙の選定）であるときだけである。

この区別が無いと、前提を口実に案件の要求が捏造される。逆にこの前提が agent に
渡っていないと、スキル既定の規律で書いた箇所の出所が説明できず、writer は外部規格の
権威を借りて偽装し、auditor はスキルの語彙表由来のリストを捏造と誤判定する。
