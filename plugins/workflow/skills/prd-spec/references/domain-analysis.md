# ドメイン分析

共通規律（助動詞規約・曖昧語・単一要求・ID・トレーサビリティ・常設章）は案件を問わず適用する。
このファイルが扱うのは、**その上に載る案件固有の追加分**である。

金銭が動くなら二重実行の防止と突合が要る。個人情報を扱うなら保持期間と削除請求への対応が要る。
共通規律だけではこれらを拾えない。かといって「金融プロファイル」「医療プロファイル」を選ばせる形は、
選択を誤ると必要な章が丸ごと落ちる。だから**案件を分析して導出する**。

## 1. 判定は三値。推測で断定しない

各観点について次のいずれかを返し、**該当・非該当のどちらにも入力からの根拠を必ず添える**。

| 判定 | 条件 |
|---|---|
| `該当` | 入力・回答に、この観点が関係することを示す記述がある |
| `非該当` | 入力・回答に、この観点が関係しないことを示す根拠がある |
| `不明` | 根拠が無い。**質問候補に回す** |

根拠が書けないものは `不明` にする。「決済と書いてあるから当然カード情報も扱うだろう」という
業界知識からの補完は、**要求の捏造と同じ失敗**として扱う。

同様に、根拠なく `非該当` と切り捨てるのも誤り。「個人情報は扱わないだろう」と推測で消すと、
本当は扱っていた場合に必要な要求が丸ごと落ちる。分からないものは `不明` にする。

## 2. 分析の観点（10 軸）

1. 人の生命・身体・健康に影響しうるか
2. 金銭・資産が動くか（決済・送金・与信・請求・会計処理）
3. 個人情報・機微情報を扱うか（誰の、どの範囲の情報か）
4. 法令・業界規制・契約上の義務が課されているか
5. 第三者監査・当局報告・社内統制の対象か
6. 停止が許されない時間帯・可用性の要求があるか
7. 外部システム・第三者への提供・連携があるか
8. 不可逆な操作を含むか（削除・送信・課金・公開）
9. 利用者の範囲（社内限定 / 一般公開 / 未成年・要配慮者を含むか）
10. データの保持期間・削除や開示の請求に応じる義務があるか

## 3. 導出のしかた

`該当` と判定した観点から、その案件に必要な要求カテゴリを導出する。

**下表は導出の例示であって、貼り付けるテンプレートではない。** 案件の実態に合わせて具体化する
（「二重実行の防止」ではなく「同一の領収書画像による申請の重複登録の防止」のように）。

| 該当した観点 | 追加で必要になりやすい要求カテゴリ |
|---|---|
| 金銭・資産が動く | 二重実行の防止（冪等性）/ 金額の丸めと通貨の扱い / 突合と照合 / 取消・返金の扱い / 処理の証跡保持 |
| 個人情報・機微情報 | 取得時の同意 / 保持期間と削除 / 開示・訂正請求への対応 / アクセス権限の最小化 / 保管場所と越境 |
| 生命・身体・健康 | 異常時の既定動作（フェイルセーフ）/ 機能縮退時の挙動 / リスク低減策と残存リスクの記載 |
| 監査・統制の対象 | 変更の申請と承認の流れ / 証跡の改ざん防止 / 証跡の保持期間 / 権限分離 |
| 可用性要求 | 目標復旧時間・目標復旧時点 / 縮退運転の定義 / 計画停止の告知手段 |
| 不可逆操作 | 実行前の確認 / 取消可能な時間 / 誤操作からの復旧手段 |
| 外部連携 | 相手側障害時の挙動 / データ提供範囲の限定 / 契約上の制約 |
| 利用者の範囲 | 権限の区分 / 未成年・要配慮者への配慮 / 公開範囲の制御 |
| 法令・契約上の義務 | 該当する義務の特定（**推測で規格名を挙げない**）/ 対応方針 |
| データ保持・削除請求 | 保持期間 / 削除の手順と反映時間 / バックアップからの削除の扱い |

### 規格名を出すときの制約

法令・規制が絡む観点でも、**規格名・条番号を推測で挙げてはならない**。挙げてよい条件と
書き方は `references/citation-policy.md` を正とする。多くの案件では、規格名を出さずに
「対応すべき義務があるかを確認する」という TBD を立てるのが正しい。

## 4. 導出結果の扱い

- 導出したカテゴリは `required_categories` として**人間ゲートで提示し、ユーザーが否定・追加できる**。
  提示は「〜と判断しました。根拠は〜です。違っていれば教えてください」という、**否定しやすい形**にする。
- ユーザーが判定を否定したら、そのカテゴリを除外して再構成する。根拠を残したまま押し通さない。
- 確定したカテゴリは script（`draft.js` / `refine.js`）に渡り、writer が反映し、**coverage-auditor が実在を検査する**。
  提案しただけで文書に無い状態を「完了」にしない。
- 情報が未確定で章として書けないカテゴリは、**捏造せず TBD として起票**し、
  `categories_deferred` に入れる（そうすれば coverage-auditor が反映漏れと誤判定しない）。
- `非該当` と判定した観点は、文書の「リスクと影響」章に「該当なし（根拠: 〜）」として残す。

## 5. 全観点が `不明` だったとき

依頼が 1 行しか無い場合、10 観点のほとんどが `不明` になる。これは分析の失敗ではない。

**「判定できなかった」と正直に提示し、観点をそのまま質問に回す。** 業界知識で埋めない。
埋めた瞬間、このスキルは「もっともらしい PRD を書く道具」に変わる。
