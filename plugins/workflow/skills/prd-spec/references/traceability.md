# ID 体系とトレーサビリティ

**目次**: [1. ID 体系](#1-id-体系) · [2. トレーサビリティ表](#2-トレーサビリティ表) · [3. 双方向であること（片側にしか現れない ID は欠陥）](#3-双方向であること片側にしか現れない-id-は欠陥) · [4. TBD 管理](#4-tbd-管理) · [5. 出自](#5-出自)

要求文書と仕様書を繋ぐ背骨。ここが切れると、2 つの文書は別々の読み物になる。

## 1. ID 体系

| 種別 | 形式 | 例 |
|---|---|---|
| 要求 | `PR-<領域>-<連番>` | `PR-AUTH-001` |
| 仕様項目 | `SP-<領域>-<連番>` | `SP-AUTH-001` |
| 未確定事項 | `TBD-<領域>-<連番>` | `TBD-AUTH-001` |
| リスク・影響 | `RK-<連番>` | `RK-001` |

**領域は文書の topic に対応させる。** 文書は複数に分割され、各文書は並列に書かれて互いの
採番を知らない。領域を冠さないと別文書と番号が衝突する。ID が衝突すると、トレーサビリティ表が
どちらを指すか決まらない。**TBD も同様で、衝突すると統合時に片方が消え、消えた側が着手を
止める項目でも人間に提示されないまま完了する。**

重複は構造検査（`ST-DUP` / `ST-DUP-TBD`）が機械的に検出する。

- 領域名は英大文字の短い語（`AUTH` / `APPROVAL` / `NOTIFY` / `AUDIT` 等）。案件に合わせて決める。
- 連番は領域ごとに 001 から。
- **一度振った ID は変えない。** 要求が削除されたら欠番にする（詰め直すと、既に ID を引用した
  会話・チケット・テストが全部ずれる）。
- 要求 ID と仕様項目 ID を 1 対 1 に対応させる必要はない。1 つの要求が複数の仕様項目に
  分かれることも、複数の要求が 1 つの仕様項目で実現されることもある。

## 2. トレーサビリティ表

**各仕様文書が、自分がカバーする要求の分だけ**を持つ。INDEX に写しを置かない
（`document-splitting.md` §7）。

```markdown
## トレーサビリティ表

| 要求 ID | 仕様項目 ID | 検証方法 | ステータス |
|---|---|---|---|
| PR-APPROVAL-001 | SP-APPROVAL-001 | 結合テスト（通知の送出時刻を計測） | 未着手 |
| PR-APPROVAL-002 | SP-APPROVAL-003 | 単体テスト（同一画像の重複登録） | 作成中 |
```

| 列 | 中身 |
|---|---|
| 要求 ID | その仕様項目が実現する要求 |
| 仕様項目 ID | 実現する側 |
| 検証方法 | どうやって満たしたと判定するか（テスト種別と、何を測るか） |
| ステータス | `未着手` / `作成中` / `完了` |

**この 4 列は本スキルの規約であって、規格準拠ではない。** 要求トレーサビリティマトリクスの
列構成には業界標準が存在しないことを調査で確認している。案件の都合で列を足すのは構わない。

## 3. 双方向であること（片側にしか現れない ID は欠陥）

| 状態 | 意味 | 扱い |
|---|---|---|
| 要求 ID が表に無い | その要求を実現する仕様が無い＝未実装 | 欠陥として報告 |
| 仕様項目 ID が表に無い | 根拠となる要求が不明な仕様＝作る理由が説明できない | 欠陥として報告 |
| 表にあるが文書に無い ID | 参照先が存在しない | 欠陥として報告 |

この検査は script（`draft.js` / `refine.js` の `structuralFindings`）が集合差分で行う。auditor の判断とは独立に走るので、
auditor が応答しなくても検出される。

要求が意図的に実装対象外なら、**要求文書側でスコープ外として明記する**（表から消すのではなく、
そもそも要求一覧に「スコープ外」として書く）。黙って表から落とすと、次に読む人には
「実装漏れ」と「意図的な対象外」の区別がつかない。

## 4. TBD 管理

未確定事項は、確定した要求と**同じ場所に混ぜない**。要求文書の「未確定事項（TBD 一覧）」章に集める。

### ブロッキングの区分（件数より重要）

各 TBD には「これが決まらないと実装・QA に着手できないか」を付ける。

| 区分 | 意味 |
|---|---|
| **着手不能**（`blocking: true`） | これが決まらないと下流業務に入れない。仕様が変わる・作るものが決まらない |
| 進行可能（`blocking: false`） | 決まっていなくても着手できる。決めた時点で追記すればよい |

**blocking は希少でなければ機能しない。** ゲート②の提示容量は 1 案件あたり数十件が上限であり
（20 件超で絞り込み・周回は最大 2）、blocking を乱発すると「未提示の blocking 0 件」という
完成保証が構造的に到達不能になる。次の基準で絞る。

- `blocking: true` にしてよいのは、**実装または QA の最初の作業日で手が止まる**ものだけ。
  「いずれ決めないと困る」「決まると品質が上がる」は `blocking: false`。
- **書き手が決められることは TBD にしない。** 書式・章立て・ID の連番規則・INDEX の節構成の
  ような執筆規約は、依頼者に問うても意味がない。書き手（このスキル）が決めて本文に書き、
  決めた事実だけを残す。
- **欠陥は TBD にしない。** 存在しない ID への参照・文書間矛盾のような検査指摘は「決めれば
  消える事項」ではなく直すべき欠陥であり、TBD 一覧に混ぜると残件数の見積もりを狂わせる。
  構造検査・監査の指摘として扱う。

### 提示済みかどうか（`presented`）

**このスキルの完成条件は「blocking が 0 件」ではなく「未提示の blocking が 0 件」である**
（理由は SKILL.md「完成の定義」を正とする）。

人間ゲートで提示した TBD は `presented_tbd_ids` に記録され、script が
`unpresented_blocking`（blocking かつ未提示）を算出する。**これが 0 でない限り完了しない。**

記録は `{ id, digest }` の形で持つ。**digest は script が `blocking_tbd_items[]` の各項目に
計算済みの値を転記する**（手で text から作らない — 照合はハッシュで行われる。渡し方の正は
SKILL.md の args 表）。ID だけだと、改稿で同じ番号が別の論点に振り直された
ときに「聞いていないのに提示済み」になる。**一度振った TBD 番号は、解決後も別の論点に
再利用しない。**

### 解決した TBD は消す

ユーザーが答えて本文に反映されたら、TBD 一覧から外す。残したままにすると
「あと N 個決まれば着手できます」の N が永遠に減らない。script は前ラウンドとの差分を
`resolved_tbd_ids` として返すので、「解決 N 件 / 残 M 件」の形で報告できる。

**区分が無いと、着手を止める数件と、決まらなくても進む数十件が同列に並ぶ。** 読み手には
「未確定だらけで使えない文書」に見え、本当に止まっている項目が埋もれる。

一覧は**着手不能を先頭に集める**。

```markdown
## 未確定事項（TBD 一覧）

### 着手不能（これが決まるまで実装・QA に入れない）

| ID | 内容 | 誰が決めるか | いつまでに |
|---|---|---|---|
| TBD-001 | 申請可能な金額の上限 |  |  |

### 進行可能（決まった時点で追記する）

| ID | 内容 | 誰が決めるか | いつまでに |
|---|---|---|---|
| TBD-002 | 領収書画像に第三者の情報が写り込む運用の有無 | 経理部 | 2026-09-30 |
```

判定に迷ったら「これを知らないまま実装に着手したら、後で作り直しになるか」を問う。
なるなら着手不能。

### その他の規則

- **「誰が決めるか」「いつまでに」が空欄なら、空欄のまま残す。** 埋まっているように見せない。
  空欄は「まだ担当者が決まっていない」という情報であり、それ自体が伝えるべき事実である。
- TBD の本文に推測を書かない。「おそらく 10 万円程度」ではなく「申請可能な金額の上限」と、
  決めるべき論点だけを書く。
- TBD に関連する要求がある場合は、要求文の側から TBD-ID を参照する
  （例:「金額の上限を超える申請を却下しなければならない（上限値は TBD-001）」）。
- **実装済みの値の由来・将来の拡張余地・書式の細目を TBD にしない。** それらは文書の
  読み手が着手するのに要らない（`agents/intake.md` §質問の合否基準）。

## 5. 出自

成果物と工程を辺で結ぶ見方（`成果物 >> 工程 -> 成果物`）と、成果物ごとのステータス
（done / wip / todo）の発想は、プロセスフローを記述する既存の DSL（pfdsl 等）から借りている。
**DSL そのものや、その CLI には依存しない**（配布先で解決できないため）。借りているのは
「成果物と工程を辺で結び、各成果物に状態を持たせる」という概念だけである。
