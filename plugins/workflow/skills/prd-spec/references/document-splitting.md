## 0. 何を作るか（依頼文の語と作成対象の対応）

分割を考える前に、**要求文書と仕様書のどちらを作るか**が決まっていなければならない。
これは依頼文に現れる語で判定し、**下表を唯一の根拠とする**。

| 依頼文に現れる語 | 作成対象 |
|---|---|
| PRD / 要件定義 / 要件 / 要求 / 要求文書 | requirements |
| 仕様書 / spec / specification / 設計書 | specifications |
| 上記のいずれも無い、または両方が現れる | **両方** |

**実装が独自に語を追加してはならない。** 表を根拠にする意味は、同じ依頼文から作られる文書の
種類が実装ごとに変わらないことにある。語を足したければ、この表を直す。

「要件だけまとめて」「仕様書だけ書いて」のように片方を名指しされたときは、その片方だけを
作る。判定結果は人間ゲート①の分割案提示に必ず現れるので、誤判定はそこでユーザーが訂正できる。

## 1. 何のために分けるか

**読み手が「この機能を実装する」ときに、1 ファイル読めば足りる状態**を作るため。

全部を 1 ファイルに詰めると、認証だけを実装する人が決済の仕様まで読むことになる。
逆に細かく割りすぎると、1 つの機能を追うのに複数ファイルを行き来することになり、
文書間の重複と矛盾が増える。**分割は目的ではなく手段である。**

## 2. パスと命名

```
docs/requirements/INDEX.md      （導出物）
docs/requirements/<topic>.md    （1 つ以上）
docs/specifications/INDEX.md    （導出物）
docs/specifications/<topic>.md  （1 つ以上）
```

`<topic>` は短い kebab-case の語。**英字始まり、英小文字・数字・ハイフンのみ。**

| 良い | 悪い | 理由 |
|---|---|---|
| `auth` | `2fa` | 数字始まりは ID の領域コードにできない |
| `audit-trail` | `監査証跡` | ASCII 以外は ID に使えない |
| `notification` | `notif_v2` と `notif-v2` の併存 | どちらも同じ領域コードになり衝突する |

script は `topic` から ID の領域コードを作る（`auth` → `PR-AUTH-001`）。
**異なる topic が同じコードになると実行を打ち切る**（承認された分割案の問題なので、
script が勝手に別名を作らない）。

## 3. 分割の軸は「スコープ」であって「件数」ではない

**項目数で分けない。** ISO/IEC/IEEE 29148 は文書種別（BRS / StRS / SyRS / SRS）の区分軸を
一貫して**対象スコープ**（business/mission → stakeholder → system → software）に置いており、
**要求数への言及は規格全体に無い**。何件を超えたら分けるという閾値は、規格に根拠が無い。

件数で切ると、同じ関心事が 2 ファイルに割れたり、無関係なものが 1 ファイルに同居したりする。
**読み手が探す単位は件数ではなく関心事**なので、件数で切った分割は目的（1 ファイル読めば
足りる状態）を達成しない。

### 何を軸に切るか

IEEE 830-1998 §5.3.7 は、**システムの性質によって最適な構成が違う**と明言し、7 通りの軸と
その選択基準を示している（§5.3.8 の複合形を含めて 8 通り）。

> There is **no one optimal organization for all systems**. Different classes of systems
> lend themselves to different organizations...

主な軸: 動作モード別 / 利用者クラス別 / オブジェクト別 / 機能別 / 刺激（イベント）別 /
機能階層別 / それらの複合。

**対象がどれに当てはまるかで軸を選ぶ。** 状態を持つものはモード別、利用者の役割で振る舞いが
変わるものは利用者クラス別、外部イベントで駆動されるものは刺激別が向く。軸を決めずに切ると、
どのファイルを開けばよいかが読み手に伝わらない。

### そのうえでの実務的な目安

- **1 でよい。** 小さい案件で無理に割らない
- **依頼から関心事が読み取れないなら、割らずに 1 つにする。** 推測で境界を引くと、
  後から「この要求はどっちのファイル？」が毎回発生する
- requirements と specifications の topic は**揃える必要が無い**。要求 1 つに対して
  仕様が複数になることも、その逆もある
- 1 文書が大きくなりすぎたと感じたら、**件数を減らすのではなく軸を見直す**。同じ文書に
  複数の関心事が入っていないかを疑う

分割案は `splitter` が作り、**人間ゲート①でユーザーが承認する**。執筆側が自律的に分けると、
同じ案件を再実行するたびにファイル構成が変わる。

## 4. 既存文書があるとき

**既存の topic を維持するのが既定。** 変えると既存文書との対応が取れなくなり、
「既存文書の改稿」が「別名ファイルの新規執筆」に化けて、レビュー対象の本文が消える。

script は分割案と既存文書の対応が取れないと実行を打ち切る。改名したい場合は理由を添えて
提案し、ユーザーの承認を取る。

## 5. ID は文書を跨いで一意

**ID の形式は `traceability.md` §1 を正とする。** ここで定めるのは、その `<領域>` を文書の
topic にどう対応させるかだけである（形式を両方に書くと、片方だけ変わって食い違う）。

領域を文書の topic に対応させることで衝突を避ける。**TBD にも領域を付ける** — 各文書は
並列に書かれて互いの採番を知らないため、領域が無いと番号が衝突し、統合時に片方が消える。
消えた側が着手を止める項目でも、人間に提示されないまま完了する。

重複は構造検査（`ST-DUP` / `ST-DUP-TBD`）が機械的に検出する。

## 6. INDEX は目次であって、トレーサビリティのビューではない

**INDEX の役割は「どのファイルに何が書いてあるか」を一望させること。**
トレーサビリティ表の写しを置く場所ではない。

**手書きしない。** script が各文書の返り値（ID 一覧・要約）から機械的に組み立てる。
手書きの目次は必ず本体と drift する。

### `docs/requirements/INDEX.md`

| 節 | 中身 |
|---|---|
| 文書一覧 | 各文書のパス・扱う関心事・**そこにどういう要求が書かれているか**の要約 |
| 要求一覧 | 全要求 ID・見出し・所在文書 |
| 関連する仕様文書 | 各要求文書に対応する仕様文書 |
| 未解決 | blocking TBD（提示済みか未提示かを区別する） |
| 検査結果 | ID の重複・実現されていない要求の件数 |

### `docs/specifications/INDEX.md`

| 節 | 中身 |
|---|---|
| 文書一覧 | 各文書のパス・扱う関心事・**そこにどういう仕様が書かれているか**の要約 |
| 仕様項目一覧 | 全仕様項目 ID・見出し・所在文書 |
| 検査結果 | ID の重複の件数 |

### 逆参照（仕様 → 要求）を INDEX に持たない理由

**情報の所在が非対称だから、ビューも非対称でよい。**

| 向き | どこにあるか | INDEX に要るか |
|---|---|---|
| 仕様 → 要求 | **各仕様文書のトレーサビリティ表に既にある**（そのファイルを開けば分かる） | 要らない（重複になる） |
| 要求 → 仕様 | どの仕様文書にあるか分からないと辿れない | 要る |

対称性に引きずられて両方向のマップを置くのは冗長である。

## 7. トレーサビリティ表の置き場

**各仕様文書が、自分がカバーする要求の分だけを持つ**（局所・コンテキスト最小）。
これが仕様 → 要求の正であり、INDEX に写しを置かない。

全要求を各文書に書き写すと、他の仕様文書と重複してどちらが正か決まらなくなる。
