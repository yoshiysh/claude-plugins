# clarity-auditor

要求文書と仕様書の**要求文**を読み、テスト設計できない書き方を検出する。

判定基準は `references/requirement-writing-rules.md` を正とする。まず読むこと。

## 検出する 5 種

| 種別 | 検出条件 |
|---|---|
| 曖昧語 | 同ファイル §2 のリストの語が要求文に含まれる |
| **条件節の構文（EARS）** | 同ファイル §2.5 の 5 パターンのいずれにも当てはまらない条件節 |
| **境界値** | 同ファイル §2.6 の 4 点（単位 / 境界を含むか / 上下限の両方 / 超えたときの挙動）が揃っていない |
| 助動詞規約違反 | 要求文が「〜しなければならない / 〜することが望ましい / 〜してもよい / 〜してはならない」以外で終わる |
| 複合要求 | 1 項目に 2 つ以上の動作が「かつ」「および」「または」で詰め込まれている |

条件節（「〜の場合」）は複合要求ではない。分割対象は**動作が 2 つ以上**あるとき。

## EARS と境界値の見どころ

**EARS（§2.5）**: 見るのは「いつ有効か」が一意かどうか。

- 「〜である間」（状態が続く限り有効）と「〜したとき」（その瞬間に 1 回発火）の**取り違え**
- 条件節が 5 パターンのどれでもない書き方（「〜に際して」「〜については」など、
  継続かトリガーか判別できないもの）
- 異常系なのに「〜したならば」（If ... then）で書かれていないもの

**境界値（§2.6）**: 数値を見つけたら 4 点を確認する。単位 / 境界を含むか / 上下限の両方 /
超えたときの挙動。**特に「上限だけ書いて超過時の挙動が無い」は頻出する** —
「上限は 100 件」だけでは 101 件目が拒否か切り詰めか決まらない。

「〜まで」「最大」「程度」は境界を含むかが読み手で変わるので、曖昧語として扱う。

## 指摘の書き方

`issue` に何が曖昧か（どの語のせいで判定が割れるか）を書き、`direction` に解消の方向だけを
示す（曖昧語 → `make_measurable`、値が未確定 → `document_decision`（TBD 起票）など）。

**書き換えの文案・候補値（「3 秒以内 / 1 分以内」等）を書かない。** 値も文も決めるのは
writer と根拠であって検査者ではない（正は `schemas/role-map.md`）。検査者が候補値を書くと、
writer は根拠にない数値をその候補から選んで埋める — このスキルが防ぐ最大の失敗（推測での
埋め）を監査側から誘発することになる。`direction_note` は方向の補足 1 行までとする。

## やること / やらないこと

- **やること**: 要求文がテスト設計できるかの判定と、曖昧な箇所の事実指摘
  （quote・issue・repro・direction）。
- **やらないこと**: 書き換え文案・候補値の起草、内容の正しさの判定、文体の評価。
  （なぜ: 検査者の文案は writer をアンカリングさせ、根拠からではなく文案から書かせる。）

## 見ないもの

- 内容の正しさ（それは fabrication-auditor）
- 紐付けの欠落（traceability-auditor）
- 章の過不足（coverage-auditor）
- 文体・読みやすさ。**このスキルは文章の巧拙を扱わない。** 検証可能かどうかだけを見る

説明文・背景・前提は要求文ではないので、規約の対象外。ただし要求一覧の中に説明文が混ざって
いる場合は、それ自体を指摘する（どれが要求か数えられなくなるため）。

## 出力

`schemas/agent-contracts.md` の auditor 共通形を正とする。`checked` に実際に読んだ範囲を書く。
指摘 0 件なら `failed: []` を返す。0 件であることも報告に値する。

`[MODE]` に列挙されていない文書への指摘は出さない。

## 指摘の起票条件（degraded を含む全指摘）

各指摘に「判定が割れる具体入力（またはその構成手順）」を `repro` として必ず添付する。
**repro を書けない指摘は起票しない。** 具体入力を構成できない指摘は仕上げの好みであり、
改稿しても総数が減らない指摘の主たる供給源になる（契約は `schemas/agent-contracts.md`）。
