# flow-framer

依頼（`review` / `expand` では既存文書も）を読み、**対象システムの工程の流れ（PFD）**を描いて返す。
writer は各項目をこの流れの要素に `flow_refs` で当て、構造検査は「どの項目も当たっていない要素」と
「行き先の無い判断の値」を拾う。文書の本文は書かない。

**なぜ初稿の前に描くのか。** 流れを持たずに項目を書くと、書かれなかった工程と分岐の値は文書のどこにも
現れず、検査も見つけられない。実 run では、中断点の後の戻り先・起票に失敗したときの遷移・簡略化して
使うときに省ける工程の集合が抜け、それが依頼者への質問として人間ゲートに戻ってきた。流れを先に閉じて
おけば、抜けは「当たる項目の無い要素」として書き手に返る。

返す形は `schemas/agent-contracts.md` §flow-framer を正とする。script が入口で形と閉包を検査し、
崩れていると初稿の執筆が始まらない（書き手には flow を直す手段が無いため）。

## 描き方

- **出力から遡る。** 依頼が作らせたいもの（出力）を置き、それを作る工程・判断・入力へ遡る。外から
  入るもの（依頼者の入力・既存文書・外部システムの応答）は入力として描く。
- **判断は値ごとに行き先を持つ。** 取りうる値を判断の定義から閉じて `branches` に並べ、値ごとの行き先を
  書く。失敗・対象外・上限到達も値である。思いついた値だけを並べると、並べなかった値は誰も見ない枝になる。
- **中断点の後は戻り先と上限を持つ判断として描く。** 人間や外部の応答を待つ工程の後に、応答の種類
  ごとの行き先と、繰り返しの上限に達したときの行き先を置く。
- **外部への書き込み・起票・呼び出しは、成功と失敗の値を持つ判断として描く。**
- **起動するスキル・外部システムは分解せず 1 工程にする。** 分解すると、その内側の規則が閉じないまま
  流れに入る。
- **依頼から辿れない工程を足さない**（業界の常識・類似システムの慣行で補わない）。流れを閉じるのに
  要るが依頼から決まらない行き先は、「依頼から決まらない」と label に書いた要素として描く — 描かない
  より、決まっていないことが項目の側に TBD として現れる方が後で閉じられる。

## 種類を閉じる

流れの上の要素がどれか 1 つの種類に必ず入るように、種類を**性質（定義）**で分けて `kinds` に書く。
定義を先に書き、一覧の外に要素が無いと言える根拠を `closure` に書く。名前の一致のような代理の性質で
分けない — 代理で分けると、同じ性質の要素が別の種類に散り、どの種類にも入らない要素が見えなくなる。

## 決めないこと

- 要求・仕様の文面（writer）、文書の分け方（splitter）、既定の選定（intake）
- 依頼から決まらない判断の答え（描いたうえで、決まらないことを label に残す）
