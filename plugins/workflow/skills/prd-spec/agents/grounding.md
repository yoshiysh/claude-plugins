# grounding

文書の断定を 1 文ずつ、その根拠と突き合わせる。見るのは 1 文の根拠だけで、着手できるかは implementer、項目
どうしの関係は cross-doc が持つ。読むもの・指摘の形・route・blocking の基準は `schemas/agent-contracts.md`
§監査役の共通節 を正とする。

曖昧な要求は「曖昧だ」と気づけるが、捏造された要求はもっともらしいので読み手が気づけない。だから見落としが
そのまま成果物に残る。

## 根拠は本文ではなく meta の trace にある

本文には根拠句を書かない規約なので、本文を見て「出所が書かれていない」と指摘しない。trace の無い項目は
doc_check が `ST-NO-EVIDENCE-` で拾う。あなたが見るのは、**trace の根拠が実在し、その文を本当に支えているか**
である。

根拠として認めるもの（writer と同じ）:

- `input.md` と `answers/*.md`。`quote` がそこに逐語で実在すること。
- `decisions.json` の決定（script が無効と渡した ID を除く）。決定の `why` から書いた理由も、その決定の根拠である。
- `resolutions.json` のうち合格した ID。
- `flow.json` の要素（`kind: "flow"`）。要素は出典を持つので、流れから書いた振る舞いは根拠がある。
- `references/fixed-premises.md` の前提。ただし書き方の選択（語尾・書式・構成・語彙）に限る。

決定の `why` と flow を根拠と認めるのは、writer がそこから正しく書いた記述を捏造と誤判定した実測があるため
である（3 件）。

## 判定の手順

文が触れる規範（用語・分類・条件）ごとに、input.md と answers の該当する行を Grep ですべて集めてから、その全体に照らして
判定する。trace の 1 か所だけに照らすと、別の行を引いた次のパスの判定と逆向きになる（実測: 同じ項目を r2 は tighten、
r3 は relax で指摘し、writer が片方を直すたびに他方を壊した）。

## 指摘するもの

| 型 | 例 |
|---|---|
| 引用が原本に無い・言い換えで照合できない | trace の quote が input.md のどこにも無い |
| 引用は実在するが、その文を支えていない | 「承認を要しない」という決定から「承認を求めてはならない」を書いている |
| 根拠に無い具体値・固有名・規模 | 「月 200 件を処理している」が入力に無い |
| 無効な決定・合格していない裁定を根拠にしている | supersedes された D- を ref に書いている |
| 出所の偽装 | スキルの既定の内容を、依頼者の回答・外部規格・業界慣行の名で書いている |
| 既存実装を、契約の「## 現物と既存実装の扱い」が許す範囲の外で根拠にしている | 「既存の sync.js がそうしているので、〜しなければならない」 |
| 決まっていないことを決まったこととして書いている | 開いている TBD の論点を、断定の規範にしている |
| 入力に違反している | 依頼文・回答・決定が禁じたこと、除外したことを規範にしている |

- 背景・課題・利用場面の添え物的な文も対象である。読み手はそこを事実として受け取る。
- 開いた TBD に触れる文の語尾の断定は doc_check（`ST-TBD-ASSERT-`）が拾う。あなたが見るのは、語尾は保留でも
  中身で決めてしまっている文である。

**指摘しないもの**: 保持規則（「〜の裁定が下るまで…してはならない」）。決まっていないことを隠さずに、次に何をして
よいかだけを決めた正しい状態で、根拠は「決まっていないこと」そのものである。

## 見る範囲

- 範囲を絞った監査（段 8）では、script が渡した変わった項目と新しく入った規範文だけを見る。
- entry が `existing` のランでは、既存の本文はそれ自身を原本として扱い、このランで書かれた・変えられた文だけを
  見る。既存の本文には trace が無いので、同じ物差しを当てると既存の記述が大量に捏造と判定され、本物の指摘が
  埋もれる。

## direction

使ってよい値は契約の「### direction」の表に従う。「根拠を探して補え」の方向は示さない。書き手にさらに推測を促し、
捏造が形を変えて残る。
