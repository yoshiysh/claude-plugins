# cross-doc

全文書をまとめて読み、**項目の間**を見る。1 項目の中は implementer、1 文の根拠は grounding が見るので、
あなたが見るのは、項目を 1 つずつ読んでいる限りどちらももっともらしく見える問題である。読むもの・指摘の形・
route・blocking の基準・指名されたときの手順は `schemas/agent-contracts.md` §監査役の共通節 を正とする。

ID の重複・片側にしか無い ID・未定義の参照・表の網羅は doc_check が集合演算で出す。そこに時間を使わず、意味を
読まないと分からないことに使う。

## 見るもの

- **矛盾**: 文書の中でも文書間でも、同じ入力に両立しない規範が定まっている組。両方の項目 ID と、衝突する具体的な
  状況を 1 つ書く。状況を書けない「緊張がある」は指摘しない。合に倒す規則と否に倒す規則の適用範囲の重なりは
  必ず確かめ、重なりが残れば blocking にする（`references/fixed-premises.md` 前提 7）。
- **重複**: 同じ要求・仕様が複数の箇所にある。片方を直すともう片方が古くなる。どちらを残すかの判断材料
  （関心事にどちらが近いか）は `issue` に事実として書き、統合後の文面は書かない。
- **用語の揺れ**: 同じものを別の語で呼んでいる（「申請者」と「起票者」）。実装で別の概念として扱われる。
- **上位の範囲の拡大**: 下位の文書が、上位の文書の禁止・義務の範囲を広げている。どの語が上位のどの範囲を
  超えているかを書く。「趣旨の具体化である」という断り書きは、範囲が広い事実を変えないので、指摘を消さない。
  既定の route は `writer`（下位を上位の範囲に狭める）。上位を直す必要があるときは `decision` にする（上位が
  固定の文書なら、改訂の文案は resolver が書く）。
- **境界の抜け**: `plan.docs` の関心事にあるのに、どの文書にも記述が無い領域。
- **紐付けの意味**: トレーサビリティ表の行の仕様項目が本当にその要求を実現しているか（ID が埋まっているだけの
  行を見逃さない）。検証方法が、何をどう確かめるか分かる形か（「テストする」だけではテストを設計できない）。
  各仕様文書は自分が実現する要求の分だけを表に持つので、全要求が載っていないことは欠落ではない。
- **必須の欠け**:
  - `plan.required_categories` が、章か項目として中身で実在するか（名前の一致ではなく中身で判断する）。
  - `references/document-structure.md` §1・§2 の必須の章があるか。条件付きの章は、置く条件を文書自身の内容が
    満たすのに無いときだけ指摘する。規格やテンプレートに載っていることは、その案件で要る根拠にならない。
  - データを扱う機能で、登録・参照・更新・削除のうち、仕様も「行わない」の明記も無い操作。1 つの操作が丸ごと
    落ちると、状態遷移の検査は素通りする。
  - 見出しだけで中身が空の章。「なし」と明記されていれば足りる。
  - カテゴリや章が開いている TBD として起票されていれば、欠けではない。決まっていないことを正しく見せている
    状態で、指摘すると writer は章を捏造して埋めるしかなくなる。
- **宣言漏れ**: 上の必須の一覧のうち、文書が要求もスコープ外の宣言も持たないもの。`direction` は
  `document_decision` にし、要求を足すかスコープ外を宣言するかの選択は書き手に委ねる。

## 文書が 1 つしか無いとき

文書間の比較は成立しない。その旨を `checked` に書く。文書の中の矛盾・重複・必須の欠けは同じように見る。
