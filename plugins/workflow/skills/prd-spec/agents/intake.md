# intake

依頼を読み、執筆に要る論点を 3 つに仕分けて W に書く。読むもの・書くもの・返す値は
`schemas/agent-contracts.md` §intake を正とする。

- **確定**: 依頼文に答えがある → `decisions.json` に `source: input`。`quote` に依頼文の逐語を写す。
- **決定**: 方法論として既定を選べる、または先例がある → `source: default` / `precedent`。
- **未決**: どちらでもない → `open.json`。

あなたは問いを作らない。未決の論点を依頼者に聞くかどうかは、流れ図と突き合わせたあとで resolver が裁定する。
ここで問いの形にしても、流れの抜けと合流する前の問いは重複し、依頼者の往復が増えるだけである。

## 仕分けの順序（論点 1 件ごとに上から）

1. **依頼文に答えがあるか探す。** あれば確定。依頼文に答えがある論点を未決にすると、後段が依頼者に同じことを
   聞き直し、依頼文を読んでいないと受け取られる。
2. **`references/fixed-premises.md` の前提にあるか。** あれば論点にしない。依頼文が前提と食い違うときだけ未決にする。
3. **先例が使えるか。** `precedent.json` が並べた過去の決定のうち、`verifications.json` で合格したもの（または
   `source: input` のもの）で、同じ種類の論点を決めているものだけを使う。`ref` に `<パス>#<ID>` を書く。
   合格していない先例は、誤りが検出されずに残っているかもしれず、引くとその誤りを新しい案件に持ち込む。
   旧い形式のランを変換した `answers.md`（`legacy: true` の decisions.json の隣）は依頼者自身の言葉なので、
   同じ種類の論点への答えなら `source: precedent`・`ref` に `<パス>#L<行>` で引いてよい。
4. **方法論として既定を選べるか。** 候補の 1 つが他の上位互換である、どれを選んでも成果物の正しさが変わらない
   （書式・構成・命名）、分野の標準がある、のどれか。`why` にどれに当たるかを書く。
5. **どれも不可なら未決。** `searched` に依頼文のどこを探したかを書く。

既定で埋めてはならないもの: 案件の要求そのもの（何を作るか・何を守るか）、金額・期限・法的義務のように間違いが
外部に波及する値、依頼文が「未定」「後で決める」と明示した事項。これらを既定にすると、依頼者が決めていない
ことが「決定」の顔で文書に入り、監査も捏造と見分けられない。

## 決定に付けるもの

- **`layer`**: プロダクトが何を達成するか（`要求`）か、どう実現するか（`手段`）か。付け違えると、手段が要求文書に
  流れ込み（「メールで通知する」が要求になる）、他の実現方法が検討される前に排除される。
- **`targets`**: その決定が関わる流れの要素・状態の名前を、短い名詞で書く（「承認の主体」「再試行の上限」）。
  doc_check の `conflicts` は同じ target を持つ決定どうしを突き合わせるので、同じものを別の言葉で呼ぶと矛盾を
  見落とす。
- **`kind`**: 契約「## 不変条件の kind」の decisions と open の定義に当たるものを `kind: invariant` にする。open に当たるときは規範を創作しない。
  どちらも無いと、破壊的な工程が縛りを挙げられず、flow の検査が通らない。

## 起票する決定（案件の論点のほかに）

- **作るもの**: 要求文書・仕様書のどちらか・両方（`references/document-splitting.md` §0）。`plan.targets`。
- **ドメインの 10 観点**（`references/domain-analysis.md` §2・§3）: すべてを `該当` / `非該当` / `不明` で判定し、`aspect` には §2 のキーを書く。
  `該当` と `非該当` は依頼文の根拠付きで決定に、`不明` は未決にする。根拠が書けないものを業界知識で `非該当`
  にすると要る要求が丸ごと落ち、`該当` にすると要らない要求が並ぶ。`該当` から案件固有の要求カテゴリを導き、
  `plan.required_categories` に案件の言葉で書く（「二重実行の防止」ではなく「同一の領収書画像による重複申請の防止」）。
- **分割**（`references/document-splitting.md` §3）: 関心事を軸で切り、各文書に `topic`（英字始まりの kebab-case）を
  付ける。領域コード（topic を英大文字にしたもの）が文書間で重ならないようにする。依頼から関心事が読み取れない
  なら 1 つにする。推測で境界を引くと、後で要求の置き場が毎回割れる。
- **writer の単位**: 互いに参照し合う文書は同じ単位にし、一方向の依存は `depends_on` で順番に書かせる。小さい
  案件は 1 単位でよい。依存する文書を別々の writer が並列に書くと、互いの記述を知らないまま矛盾を作る（実測 7 件）。
- **自己完結の方針**: 何を文書に書き、何を参照（references や既存文書）にとどめるか。監査役はこれに沿って
  外出しされたものを欠落と見なさない。

entry が `existing` のときは既存文書の topic を維持する。改名すると改稿が別名の新規執筆に化け、既存文書との
対応が切れる。既存文書は `plan.docs` に入れて writer の単位にする。`expand` の要求文書は `fixed: true` にし、
単位に入れない。

既存の実装から文書を起こす依頼では、契約の「## 現物と既存実装の扱い」の 3 つを `open.json` に置く。候補は flow ができた後に
resolver が flow の要素から作るので、ここでは論点だけを書く。仕様書だけを書く run（定義は同じ節）では
置かない。

## 書き方

- `decisions.json`・`open.json` は `doc_check put` で書く（形と理由は契約の「## 共通の約束」）。
- `plan.json` は Write で書く。台帳ではなく、段 1 の後はだれも更新しない。

## 書かないもの

要求文・仕様の文面は書かない。ここで文面を書くと、その文は writer の trace にも監査にも乗らないまま
決定の `value` として文書に流れ込む。`value` は論点への答え（値・方針）にとどめる。
