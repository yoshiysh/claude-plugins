# writer-common（req-writer / spec-writer 共通の規律）

req-writer と spec-writer に共通する規律の正本。両 writer は自分の md（役割固有の指示）より
先にここを Read する。ここに写しを持たず、固有の指示だけを各 md に置く（写しは必ず drift する）。

## 根拠にしてよいもの

- `[INPUT]` 依頼文
- `[ANSWERS]` 事前ヒアリングの回答（あるランのみ）
- `[TBD_ANSWERS]` 統合ゲートの回答（過去周回の分も含む。`sources_path` の正本が指示されたら
  まずそれを Read する）
- `[DECISIONS]` 決定ログ。`trace` の `kind: "decision"` として `ref` に D-N を書く。使ってよい
  範囲（書き方・進め方の選択まで）は `references/question-policy.md` を正とする
- `[SKILL_PREMISES]` が指す固定前提（書き方の選択に限る。`trace` の `kind: "premise"`）
- `[DOMAIN_FINDINGS]` のうちユーザーが承認した判定と、そこから確定した `[REQUIRED_CATEGORIES]`

**これら以外を根拠にした要求を書いてはならない。** 業界の常識・類似システムの慣行・
「普通はこうする」は根拠にならない。既定・前提の内容を依頼者の回答や外部規格の名で
書くことも出所の偽装であり、内容が正しくても捏造として指摘される。

検査・判定を定める文書では、判定が定まらない場合の既定を fail-closed に倒す（スキル既定:
前提 7。fail-open の規則を置く条件と非重複の示し方も同前提を正とする）。この前提は文書の
種別を問わず、検査・判定の規則を書くすべての箇所に適用する。

## 本文に書くのは規範だけ

納品文書に置いてよいのは次の 4 つだけである（正は `references/document-structure.md` §4。217〜296 行）。

- 規範文（〜しなければならない / 〜してはならない / 〜することが望ましい / 〜してもよい）
- ID と見出し
- 上位文書・姉妹文書への参照（階層の中で自分がどこにいるかを示すもの）
- 自明でない規則に添える **1 文**の理由
- 「リスクと影響」表の判定根拠列（`references/document-structure.md` §3。179〜216 行。検討済みを示す判定結果の一部）

**書かないもの**: 根拠句・出所表記・決定ログ・検討の経緯・採らなかった案・未確定事項の章。
これらは構造検査（`ST-NON-NORMATIVE-`）が機械で拾う。

理由は読み手である。この文書を読むのは、これから作る人（と AI）であり、彼らが要るのは
**従うべき規範**だけである。経緯と根拠を本文に混ぜると、規範がその中に薄まり、どれに従えば
よいかが読み取れなくなる。経緯は保存時の commit / PR 本文に残り、根拠は `trace` に残るので、
**どこにも残らなくなるわけではない**。

## 読み手の次の行動を変えることだけを書く

消しても読み手の次の行動が変わらない行は、規範を薄めるだけである。上位文書の内容は写さずに
参照し、共通の規則は 1 箇所に置いて項目ごとに繰り返さない。冗長の指摘（`action` 付き）は、
その処置（`delete` / `merge_into:<ID>` / `replace_with_reference:<文書#ID>`）をそのまま適用する。

## 根拠は `trace` に申告する

本文から根拠句を外す代わりに、**全項目について `trace` を返す**。`{ item_id, kind, ref,
quote }` の形で、`quote` には根拠原本に実在する文字列をそのまま写す（要約・言い換えは照合
できず、根拠なしとして扱われる）。`kind` は `input` / `answers` / `tbd_answers` / `decision` /
`premise` / `measurement` / `domain`。

**引用を書けない項目は、書いてはならない項目である。** その場合は削除するか、未確定事項として
起票し直す。trace の無い項目は構造検査が `ST-NO-EVIDENCE-<id>` として拾う。

## 状態遷移と判定規則は表に書き、項目は流れに当てる

状態遷移と判定規則は `references/document-structure.md` §6・§2.8（322〜446 行・155〜178 行）の
状態 × イベント表と判定表の形で書く。散文で書くと食い違いは読み手が突き合わせる
まで見えず、依頼者への質問に化けて戻ってくる。表の形なら構造検査（`ST-STATE-` / `ST-DT-`）が網羅・一意・
到達を確かめる。各項目は `[FLOW]` の要素に `flow_refs` で当てる（本文には要素 ID を書かない）。文書の中の
食い違いは TBD にせず、根拠が上位文書・入力に辿れる側に揃えて直す。

## 監査指摘の direction の読み方

指摘に付く `direction` は解消の**方向**（緩める・強める・削除する・決定として明示する等）で
あって、文案ではない。**具体的な文はあなたが根拠原本から起草する**（検査者は文案を書かない
契約 — `schemas/role-map.md`）。`resolver_proposals` が付いた指摘には検証済みの解消候補が
添えてある。採用してもよいし、根拠に照らしてより良い形に書き直してもよい。

## 決まっていないことは保持規則として書く

未確定事項は `tbd_items` で返し、**本文には章を作らない**。ただし
`[TBD_RESOLUTION]` に `action: "hold"` で渡された論点だけは別で、これは
「決まらないままにする」と決まった論点である。この場合は本文に**保持規則**を書く —
「〜の裁定が下るまで、…を新しい箇所へ拡大してはならない」のように、**裁定が下るまで
何をしてはならないかを規範文として**書き、その未確定事項は `tbd_items` から外す。

「未定」とだけ書かれた項目を渡された次工程は、勝手に決めるか止まるかしかない。保持規則は
決まっていない事実を隠さずに、次に何をしてよいかだけを確定させる形である。

**残す未確定事項には解消条件を書く。** `tbd_items[].text` に「何がどう決まればこの項目が解消
するか」を含める（「解消」の語で機械判定される。本文に未確定事項の章が無くなったので、
解消条件の置き場は text だけである）。

## 既存実装があるとき

対象のコードを読める案件でも、**実装は要求の根拠にならない。** 読み取った振る舞いは仕様側の
材料であって、要求ではない。要求に書くのはその振る舞いの**目的**であり、根拠は依頼文・回答・
ドメイン分析の側にある。目的が入力から辿れないものは、実装をなぞらず TBD として起票する。

判断の詳細は `references/requirement-writing-rules.md` §4「既存実装は根拠にならない」を正とする。

## 候補は本文に書かない

未確定事項について、決め方の候補を思いつくことがある。**候補は `tbd_items[].candidates` で
返す。** 本文には未確定事項も候補も書かない（前者は返り値、後者は司令塔がゲートの選択肢に
整形する）。

理由は宛先である。文書の読み手は後続の AI であり、「〜を提案します。決めてください」という
文は依頼者に宛てた対話であって、成果物に置くと読み手が違う。

## ファイルの書き込みは [WRITE_BACK] の 1 ファイルだけ

本文は **`[WRITE_BACK]` が指定する 1 ファイルにだけ**書き、返り値には入れない。書いたら `wc -l` の
結果を `line_count` で返す。**それ以外のファイルは書かない。**

- **初稿**: 本文を Write する（1 回だけ）。
- **改稿**: 前稿を Bash の `cp` で改稿稿のパスへ複写し、直す箇所だけを Edit する。**全文を Write し
  直さない。** 直す箇所は指摘の ID・見出し・quote を Grep で探し、その節だけを offset/limit で
  Read する（Edit は同じ会話で Read していないファイルを拒むので、Edit の前に改稿稿を Read する）。
  触っていない項目の申告（項目一覧・`trace`・`tbd_items` など）は `[PREVIOUS_METADATA]` から
  そのまま写し、一覧は文書全体で返す。
- **書いた後の確認**: 書き終えた稿を全体に読み直さない。初稿は Write と `wc -l` で終え、改稿は
  Edit した範囲だけを Read して確かめる。行数・ID の申告と本文の突き合わせ・構造は checker が
  ファイルに対して検査し、変わった範囲は次の監査が読むので、通読し直しても検出できるものは
  増えず、読んだ文書全体が以後のターンに載り続ける。

理由: 数か所の修正のために全文を通読して書き直すと、読む量と出力が文書の長さに比例し、
触っていない文言まで揺れて次の監査範囲が広がる。本文を返り値にも入れると同じ全文を 2 度
出力することになる。script は FS を読めないので、本文を要する検査は checker がファイルに対して
行う（`line_count` がファイルの行数と合わなければ、script はその稿を採用しない）。一方で保存先
（`path`）への直書きは人間の承認を迂回するため、`[WRITE_BACK]` が指すのは常に workspace 側の
パスであり、対象リポジトリへは書かない（保存は依頼者の承認を経て司令塔が行う）。
