# role-map（1 role = 1 責務の正本）

**この表がロール設計の正である。** 各 `agents/*.md` は担当の振る舞いを持つが、責務の宣言がこの表と食い違ったら
この表に合わせて直す。ファイルの形と所有は `schemas/agent-contracts.md` を正とする。

## 設計規範

> **検証者（監査役・resolver-verifier）は判定と事実指摘のみ。解決策・要求文の文案・候補の起草は生成側の責務。
> 1 role = 1 責務。司令塔は中継と状態管理だけを持ち、生成しない。**

この境界を破ると何が壊れるか。検証者が文案を書くと、writer が文案にアンカリングして根拠からではなく文案から
書き（実測）、しかもその文案は誰にも検証されない。司令塔が決定や回答の文面を書くと、依頼者の言葉と司令塔の
言葉が同じ欄に混ざり、writer はどちらを依頼者の判断として扱うべきか区別できない（実測: 司令塔が起草した決定が
回答の欄にも複写され、同じ決定が 2 つの出所から届いた）。だから検証者が出せるのは判定・事実・方向（`direction`）
までで、文は常に生成側（writer・resolver）が書き、生成物は必ず別の検証者を通る。

## ロール表

処理順（S0 → 段 9）に並べる。model / effort の既定は `scripts/prd.js` の `ROLE_OPTS` が正で、司令塔が `role_opts` で上書きできる。

| 段 | role | 種別 | 責務（1 つ） | やらないこと | なぜ（破ると何が壊れるか） |
|---|---|---|---|---|---|
| 1 | intake | 生成（仕分けと決定の起票） | 依頼を確定・決定・未決に仕分け、観点・分割・writer の単位・自己完結の方針を決定として起票する | 問い・要求文の起草 | 問いを先に作ると流れの抜けと重複し、要求文を書くと検証されない文が決定の顔で文書に入る |
| 2・3b | flow-framer | 生成（流れの起草） | 出典付きの流れ図を描き、決まらない分岐を未決に足し、doc_check で閉じる | 組の判定・要求の文面 | 流れを持たずに書くと、書かれなかった工程と分岐が初稿の後に問いとして戻る |
| 3・3a・3b・6・輪を出た後 | resolver | 生成（裁定と問い） | 未決・組・決定が要る指摘・新しい TBD を 6 つの裁定で閉じ、問い・保持規則を書く | 本文の改稿・裁定の自己承認・指摘の真偽の裁定 | 本文を直すと監査を迂回し、自己承認すると価値の判断が方法論として黙って決まる |
| 3・3a・3b・3a'・6・輪を出た後（verifier の後に resolver を起動したとき） | flow-check | 検証（決定的な検査の実行） | 台帳を書いた resolver の後に doc_check flow を実行し、stdout をそのまま返す | ファイルの書き込み・指摘の修正・stdout の加工 | 台帳を書いた resolver の stdout だけで進むと、少なく申告した指摘が誰にも見えないまま次の段へ届く |
| 3v・6 | resolver-verifier | 検証 | 裁定・intake の既定・flow の出典・回答の対応づけの合否 | 書き直し・改良案 | 検証者が書き直すと、その文を誰も検証しない |
| 4・7 | writer | 生成 | 担当の単位の文書と meta の起草と改稿（同じファイルを Edit） | 監査の判定・他の単位のファイルの書き込み | 判定を兼ねると自己承認になり、他のファイルを書くと検証の前提が崩れる |
| 5・8 | implementer | 検証 | 1 項目の中: 着手可能性・項目自身の目的に対する過不足・曖昧さ | 文案・根拠の判定・項目間 | 観点が重なると同じ箇所に 2 つの指摘が付き、writer が逆向きに直す |
| 5・8 | grounding | 検証 | 1 文の根拠: 捏造・偽装・未決の断定・入力への違反 | 文案・着手可能性・項目間 | 同上 |
| 5・8 | cross-doc | 検証 | 項目の間: 矛盾・重複・用語・上位の要求と照らした範囲・紐付け・必須の欠け。段 5 で監査の基準（audited-1）を保存する | 文案・1 項目で完結する問題 | 同上 |
| 全段 | doc_check（script） | 検証（決定的） | 語尾・曖昧語・ID・trace・表と流れの網羅・開いた TBD の断定・snapshot と diff | 意味の判定 | 算術を LLM に載せると揺れ、落ちた agent が「0 件」に化ける |
| 全段 | prd.js（Workflow script） | 制御 | 段の順序・起動の条件・上限・返り値の検査と引き継ぎ | ファイルの読み書き（できない） | 実行経路を agent に任せると、段が飛ばされても誰も気づかない |
| S0・G0・G0-2・G1・9 | 司令塔（SKILL.md） | 中継 | 依頼と回答を逐語で書く、`doc_check questions`・`doc_check report` で問いと事後報告を導出し、questions.md と report.md をそのまま見せる、next_args を渡す（references/workflow-io.md §3）、保存の前の digest の文字列比較 | 決定・問い・回答・文書の文面を書くこと | 司令塔が書くと、生成と検証の分離が最後の工程で破れる |

## 責務の重複・空白の確認

- **文を書くのは生成側だけ**: writer（本文と meta）、resolver（裁定・問い・保持規則）、intake（決定の値）、
  flow-framer（流れ）。検証側（3 監査役・resolver-verifier・doc_check）は文を持たない。
- **監査の観点は排他**: 1 項目の中・1 文の根拠・項目の間、に分け、機械で判定できるものは doc_check に置く
  （`schemas/agent-contracts.md` §監査役の共通節）。
- **指摘の一生**: 監査役が起票（route を付ける）→ `writer` は script が束ねて改稿へ、`decision` は resolver が裁定 →
  resolver-verifier → 改稿 → 範囲を絞った監査。残れば次のパスを回し、収束しなければ blocked。
- **論点の一生**: intake・flow-framer が未決に起票（writer は TBD の候補を meta に起票）→ resolver が裁定 →
  resolver-verifier → 合格すれば決定台帳に入って writer が使う。`question` は依頼者の回答で決まり、`hold` は保持規則と
  Issue の文案になる。どの経路にも「誰の責務でもない工程」は無い。
