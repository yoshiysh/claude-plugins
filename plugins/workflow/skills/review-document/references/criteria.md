追加基準リスト（番号は既存の続きから）：

24. **rubric 更新の陳腐化耐性**：rubric.md 自体がレビュー対象文書の実例やスコア数値をハードコードしていないか（同梱スキル本体の改稿でサンプル文が変わった際、rubric 側だけが古いまま残る「参照ズレ」を起こさない構造か。「Old patterns」節等の陳腐化対策が要件に無い）
25. **改稿と検証可能性の両立を測る具体的シグナル**：revise の制約条件に「根拠追跡・検証可能性」の維持が挙げられているが、updater 側でこれを壊したかどうかを機械的/半機械的に検知する手掛かり（例: 参照リンク数・要求ID出現数の before/after 差分を staging 突き合わせで見る）が定義されているか。単に「壊さない」という宣言だけで、壊れたことを検出する手段が無いと事故を防げない
26. **axis-scorer 間の評価基準ブレ**：「短さ」「平易さ」「独自用語」の3軸が独立並列 fan-out で採点されるが、同じ最悪文引用や同じ用語指摘が複数軸から重複して suggestions に上がった場合の統合規則（synthesizer 側の重複排除方針）が定義されているか
27. **改善提案の「効果順」の根拠**：suggestions[] が「効果順」とあるが、順位付けの基準（影響範囲・修正コスト・複数軸への効果等）が rubric.md か SKILL.md に明記されているか、それとも synthesizer の主観任せか
28. **staging 出力の後始末（クリーンアップ）**：承認されなかった revise の staging ディレクトリが放置されないためのライフサイクル規定（次回実行時の扱い、手動削除の要否）があるか。無いと本体との混同や誤参照のリスクが残る

統合後の完全な基準リスト（既存 + 追加）：

1. **description の When/What 両立**：「review-document」の description に、いつ使うか（対象文書種別・呼び出し文脈）と何をするか（3軸採点+改稿）の両方が明記されているか
2. **除外条件の明記**：「対象外: 文書の新規執筆、コードレビュー、翻訳」が description またはSKILL.md本体に明記され、判定不能な境界（例:文書に近いコード内コメント）を誤って拾わない記述になっているか
3. **文字数閾値の不使用（正本準拠）**：SKILL.md・rubric.md 内に文字数/行数の合否ライン（「N文字以内なら合格」等）が一切登場しないか。grep で数値+文字/行のパターンが無いことを確認できるか
4. **圧縮可能性の判定基準が具体的**：「短さ」の採点根拠が「規範文に対する足場・自己言及・重複の比率」という測定可能な形で rubric.md に定義され、抽象語（「簡潔」「無駄がない」）だけで終わっていないか
5. **削除ではなく移動を優先する指示の明文化**：改善提案が「削除」でなく「置き場の移動」（根拠句→末尾表、却下案→別ファイル）を優先する旨が具体例つきで書かれているか
6. **証拠つき採点の強制**：review モードの出力契約に「最悪文の実引用」「平易な書き換え例」「独自用語表」「分量内訳概算」の4点が必須項目として明示され、1つでも欠けたら出力が不完全と判定できる形になっているか
7. **独自用語の「失うもの」判定基準**：jargon 指摘が「言い換えで失うものが無い用語のみ」に限定される判定手順（loses フィールドの記入義務、無しの場合のみ指摘採用）が定義されているか。⚠️ 判定者（axis-scorer）が「失うもの」の有無をどう判断するかの手掛かりがrubricにあるか
8. **review/revise の書き込み境界**：review モードで「ファイルは1バイトも書かない」、revise モードで「本体ファイルは承認まで一切書き換えない」という不可逆操作の禁止が、実行構造（updater の書き込み先=staging限定）として担保されているか（散文の宣言だけでなく script/workflow 側の制約になっているか）
9. **非ブロッキングの徹底**：review モードが「FAIL判定をしない」原則を持ちながら、出力の scores や suggestions が誤って合否表現（PASS/FAIL, ✅/❌）を含んでいないか実例で確認できるか
10. **入力例・出力例のセット同梱**（document系デフォルト）：SKILL.md か rubric.md に、実際の文書断片→採点結果→改善提案という一連の入出力例が最低1パターン、省略なしで含まれているか
11. **対象読者に応じた語彙**（document系デフォルト）：rubric.md・SKILL.md 自体が「独自用語の不使用」を課すスキルでありながら、自らMAGI固有語やスキル内部の専門語（axis-scorer, refuter, synthesizer 等）を無定義で多用し、規範との自己矛盾を起こしていないか
12. **正常系エッジケース**：⚠️ 3軸すべてが満点/最低点に近い極端な文書（すでに極めて平易・短い文書、逆に用語だらけの文書）を入力したときの採点・出力仕様が定義されているか
13. **正常系エッジケース**：制約条件（落とせない性質）が「無し」の revise 依頼時、updater が何を守るべきかのデフォルト方針（例: 事実関係と参照先は無条件で保持）が定義されているか
14. **準正常系**：対象パスが複数かつ文書間で規範内容が重複する場合（例: 同じルールが2ファイルに書かれている）に、「短さ」採点や独自用語表がファイル横断でどう扱われるか（file単位かグループ単位か）が定義されているか
15. **準正常系**：「短く書き直して」のような mode 未指定・焦点未指定の曖昧依頼を revise として扱う規則があるが、対象パスも同時に欠けている場合の問い返し文言・粒度が定義されているか
16. **準正常系**：焦点や制約条件が矛盾する入力（例:「用語は残しつつ独自用語ゼロにして」）が来た場合の扱い（そのまま矛盾を通知して停止するか、優先順位を機械的に決めるか）が定義されているか
17. **異常系**：rubric.md が読み込めない/欠落している場合に「欠測として報告（黙ってskipしない）」という明文の禁止・振る舞いが、実際の出力フィールド（例: axis score = null, reason = "rubric unreadable"）にまで落ちているか
18. **異常系**：対象パスが実在しない・権限で読めない場合の停止文言と、部分的に読めたファイルだけで採点を続行するかどうかの方針が定義されているか
19. **異常系**：対象がスキルの想定外（コード、非日本語文書、バイナリ）の場合に「対象外」として明確に断るのか、可能な範囲で採点するのかの境界が定義されているか
20. **欠測とゼロ点の区別**：scorer/refuter が応答しなかった軸・棄却された指摘を「欠測（null/unverified）」として明示し、「問題なし」（=満点や指摘ゼロ）と機械的に混同しない出力契約になっているか（Workflow実行型基準の「欠測を成績に混ぜない」に対応）
21. **反証（refuter）の多数決基準の記述**：「過半数反証で棄却」の分母（axis-scorer 3体か、指摘ごとに立てるrefuterの数か）が曖昧でなく定義されているか。⚠️ 反証者の人数・独立性の担保方法が具体化されているか
22. **staging のミラー構造と before/after の対応**：staging 出力が「対象文書のミラー、本体の兄弟」という配置規則を持ち、複数ファイル revise 時に changed_files と before/after scores の対応が1:1で取れる契約になっているか
23. **後続スキルからの呼び出し契約**：prd-spec 等からの delegation 時に rubric パスを受け渡す入出力形式（パス文字列か、rubric本文埋め込みか）が具体的に定義され、「read rubric できない場合は欠測」という規定と整合しているか
24. **rubric 更新の陳腐化耐性**：rubric.md 自体がレビュー対象文書の実例やスコア数値をハードコードしていないか。参照ズレ防止の構造（時間依存記述を避ける等）があるか
25. **改稿と検証可能性の両立を測る具体的シグナル**：根拠追跡・検証可能性の維持を updater が壊していないか検知する半機械的な手掛かり（参照リンク数・要求ID出現数の before/after 差分等）が定義されているか
26. **axis-scorer 間の評価基準ブレ**：3軸から重複して同じ最悪文/用語指摘が上がった場合の synthesizer 側の重複排除方針が定義されているか
27. **改善提案の「効果順」の根拠**：suggestions[] の順位付け基準（影響範囲・修正コスト等）が明記されているか、主観任せになっていないか
28. **staging 出力の後始末（クリーンアップ）**：承認されなかった revise の staging ディレクトリのライフサイクル規定（放置防止）があるか
