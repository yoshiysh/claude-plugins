# agent 間の文脈共有をどう持つか（設計根拠）

このループの agent は fresh context で立つ。前の agent が何を見て何を裁定したかは、
明示的に渡さない限り失われる。共有の持ち方には既知のパターンがあり、ここでは
**どれを採り、どうなったら次へ移るか**を成文化する。移行条件を先に書いておかないと、
「重い機構を入れたが効果は測っていない」か「限界が来ているのに気付かない」のどちらかになる。

## 採った形: ledger（file ベース shared state の軽量形）

追記型の 1 ファイル（[references/ledger.md](ledger.md)）を run の共有記憶にし、
workflow script が全 agent の prompt に読ませる。書き込みは script が構成し、
`scripts/ledger.py` が検査して追記する。

この用途でこれが足りるのは、共有したいものが次の性質を持つためである。

- **量が小さい**: 1 run の裁定・findings・結果は数十 entry で、prompt に載る
- **時系列で足りる**: 後段が要るのは「今までに何が決まったか」であり、
  agent 同士の往復交渉ではない
- **書き手が 1 つでよい**: 実際に書くのは script だけなので、並行書き込みの
  競合・ロック・バージョニングが要らない
- **経路が既に決定的**: 順序・反復・上限は script が持っており、誰が次に動くかを
  共有状態から判断する必要がない

複数 agent の協調パターンのうち、**orchestrator-subagent から始めて、詰まった所だけ
別パターンへ寄せる**のが定石で、このスキルの骨格（script が経路を持ち、agent が判断する）は
その orchestrator 側そのものである。ledger は「協調の機構」ではなく、その orchestrator が
落としていた**記憶**を足したものにあたる。

## 採らなかった形と、その理由

| 形 | 何が要るとき有効か | ここで採らない理由 |
|---|---|---|
| **agent teams**（常駐する worker が文脈を蓄積する） | 長期・多段の subtask を各 worker が持ち続けることに価値があるとき | このループの agent は 1 回の判断で終わる短命な仕事（1 run の実行、1 本の採点）。常駐させても蓄積する文脈が無く、一方で「作る側と測る側の独立」が worker の持ち越しで崩れる |
| **message bus**（publish / subscribe で経路が事後に決まる） | ワークフローが事象から立ち上がり、経路が事前に決まらないとき | 経路は Plan → Do → Check → Act で確定しており、決定的な script が持つのが本スキルの前提。bus にすると経路が追跡不能になり、「Phase の省略不能」を構造で保証できなくなる |
| **本格的な shared state**（DB・並行書き込み・収束条件） | agent が互いの中間発見に反応し合いながら収束するとき | 反応し合う設計をこのスキルは避けている（生成者と検証者の独立が要）。並行書き込みの制御コストだけが乗る |

## いつ teams / bus へ移るか（evolve 条件）

次のどれかが**実測として**出たときに再検討する。印象では動かさない。

1. **ledger が prompt に載らない**: 1 run の entry が肥大し、後段 agent に全文を
   渡せず要約が要るようになった（要約を挟んだ時点で「読んでから書く」は担保されない）
2. **同一 agent への往復が必要になった**: 前段の agent に追加の質問を返し、その答えで
   後段が変わる経路が繰り返し要るようになった（1 往復で終わらない協調は teams の領分）
3. **経路が事前に決まらなくなった**: 条件・レンズ・戻り先が入力によって大きく分岐し、
   script の分岐が入力の種類ごとに増え続けるようになった（bus の検討条件）

いずれも telemetry（`scripts/skill_telemetry.py`）に現れる量として観測し、
移行そのものをこのスキルの PDCA の対象にする。
