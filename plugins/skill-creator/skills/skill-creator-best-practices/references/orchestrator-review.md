# 司令塔：review / update の提示と適用

`scripts/review_skill.js` の戻り値を人間に見せ、update なら承認を得て本体へ反映するまでの手順。
SKILL.md の「結果の提示と適用（review/update）」から Read される。

## 提示の原則

1. **3 つのバケットを必ず区別する。** `confirmed`（確定）・`rejected`（反証で棄却）・
   `unverified`（検証が揃わず判断保留）。棄却と未検証を黙って落とすと、
   「見ていない」が「見て問題が無かった」に化ける。件数だけでも必ず出す。
   これは update の再検証結果（`staging.unverified`）でも同じ。
2. **観点の欠落を隠さない。** `by_category.before` が `null` の観点は「その観点では見ていない」。
   合格の材料に数えない。`by_category.after` 全体が `null` なのは別の意味で、
   「再検証のパス自体が走らなかった」（review、または改稿前に止まった場合）。
3. **どちらの時点の指摘かを言う。** `findings_source` が `"before"` なら改稿前、
   `"after"` なら再検証後。取り違えると「まだ直っていない」と「もう直した」が逆に読める。
4. **数値の判定を再計算しない。** verdict は script が決めている。ここで条件を
   組み直すと、同じ判定が 2 箇所に存在することになる。
5. 技術用語を避ける。「指摘」「反論で消えたもの」「確かめきれなかったもの」で通じる。
6. **update では「手修正の有無」と「その再検証の結果」を必ず 1 行で出す。** staging は
   Workflow が書いたあとに司令塔も書ける場所で、手が入ったかどうかは読み手には見えない。
   この行が無いと、検証を経ていない手修正入りの staging をそのまま「適用済み」として
   報告できてしまう。判定材料（ダイジェスト）は「承認後の適用手順」の手順 0 で取り、
   値ごと提示に載せる。

## review の提示フォーマット

```
このスキルを見た結果です。

【直した方がよいもの】（3件）
1. [blocker] SKILL.md — モード判定の表に「範囲が読み取れない場合」の行が無い
   根拠: 「| 何を対象にするか読み取れない | ...」の行が存在しない
   直し方: 判定不能の行を追加し、聞き返す内容を書く
2. [major] ...
3. [minor] ...

【反論で消えたもの】2件（実物と照合したところ、指摘が成り立ちませんでした）
【確かめきれなかったもの】1件（検証が揃わなかったため、判断を保留しています）

観点ごとの確定件数: 理由の無い命令 1 / 散文に残った確定的処理 0 / 二重定義 1 /
経路の無い依頼 1 / description との乖離 0 / ベストプラクティス準拠 0
```

- `confirmed` は `severity` 順（`blocker` → `major` → `minor`）に並べる。
- `unverified` が 1 件でもあれば、`confirmed` が 0 件でも「問題なし」とは言わない。
- 最後に「このまま直すこともできます（update）」と一言添える。review だけを頼まれた
  ときに勝手に直さないための線引きが、ここで初めて相手に見える。

`verdict: review_incomplete` のときは、冒頭に次を置く。

```
※ 一部の観点（〜）が実行できなかったため、この結果は全体を見たものではありません。
```

## update の提示フォーマット

```
staging に改稿を書きました（本体はまだ変えていません）。

書き出し先: <staging.dir>
　※ ここには対象スキルの全ファイルが複製されています。実際に書き換えたのは下の一覧だけです。

【変更したファイル】
- SKILL.md — モード判定セクションを追加（指摘 2 件を解消）
- agents/finder.md — 新規（意図: Issue #31 の観点分離）

【解消できた指摘】3件
【まだ残っている指摘】1件
  - [major] ...
【新しく出てきた指摘】0件
【確かめきれなかった指摘】1件（再検証で判断が揃いませんでした）
  - [minor] ...
【言い換えの可能性がある指摘】0件（同じ箇所・同じ観点だが文言が変わったもの）
【再検証で見られなかった箇所の指摘】0件（消えたのか見ていないだけかが分かりません）
【改稿前は未検証・棄却だったが今回確定した指摘】0件（改稿が持ち込んだものではありません）
【差分範囲の外で見つかった指摘】0件（scope: diff のときのみ。元からあった可能性が高いものです）
【改稿前から同じ文言で存在していた指摘】0件（改稿前の検査が見落としたもの。改稿が持ち込んだものではありません）

【staging への手直し】なし（この時点の中身の指紋: a1b2c3d4e5f6）
　※ 反映の直前にもう一度この指紋を取り、変わっていたら別の担当が読み直してから反映します。

本体に反映してよいですか？
```

- `staging.dir` は必ず見せる。承認しない場合でも、そこを直接見たいと言われる。
- 【staging への手直し】の行は必ず出す。値は「承認後の適用手順」の手順 0 で取った
  ダイジェストの先頭 12 桁で、**提示のこの時点で取ったもの**であることが読み手に見える形にする。
  司令塔が staging を直したあと（例外経路 — ユーザーの明示指示か minor の文言修正のみ。
  「司令塔がやらないこと」参照）に反映する場合は、手順 2 の再検証を済ませてから、
  この行を次の形に差し替える。
  ```
  【staging への手直し】あり（2 ファイル）
  　再検証の結果: 新しく出た指摘 1 件 / 承認時に出ていた指摘と同じもの 3 件
  　- [major] agents/finder.md — <新しく出た指摘の内容>
  ```
  「新しく出た指摘」が手直しについての判断材料で、既出と一致したものは承認時に見た指摘の
  再掲。0 件でも行を消さない（手直しを検証したことと、検証していないことが同じ表示になる）。
- `remaining` / `new` / `unverified` は件数だけでなく中身を出す。件数だけだと承認の判断ができない。
- `possibly_rephrased` と `unobserved` は 0 件でも行を消さない。0 と「その概念を出さない」は
  読み手にとって別の意味で、行が無いと「そういう区別はされていない」と読まれる。
- `unobserved` があるときは、`resolved` の件数に含まれていないことを明示する。
- `reclassified` / `out_of_scope` / `preexisting` も 0 件で行を残す。`new` が「改稿で悪くなったか」を判断する
  唯一の数字なので、そこに入れなかった理由が読み手に見える必要がある。
- verdict ごとの言い回しは SKILL.md の verdict 表に従う。ここで条件を再解釈しない。

## 承認後の適用手順

この節はnative Workflowで完了したupdateだけに適用する。Codex runner v1のreview/updateはexecution前に
`rejected_source`となるため、stagingや承認済み結果があると推定してこの手順へ進まない。

承認を得てから、司令塔が次を行う。Workflow は実行中にユーザー入力を受け取れないため、
この工程だけは script の外にある。

反映する中身は、Workflow が返した時点の staging と同じとは限らない。例外経路の手直しや
ユーザーの追加指示で、司令塔自身が staging を書き換えることがある。改稿した本人には
改稿の欠陥が見えない —— update 経路はこの非対称性を前提に Update と Reverify を別の担当に
分けているので、司令塔の手直しだけをその外に置く理由が無い。手順 0〜2 がその埋め合わせで、
手順 3 のコピーはここを通ったあとにしか始めない。

### 手順 0: 基準の指紋を取る（Workflow の戻り値を受け取った直後）

```bash
cd <staging.dir> && find . -type f -print0 | LC_ALL=C sort -z | xargs -0 shasum -a 256 \
  > <作業ディレクトリ>/staging-hashes-0.txt
shasum -a 256 <作業ディレクトリ>/staging-hashes-0.txt
```

ファイル 1 つずつの hash を一覧として残し、その一覧の hash を指紋にする。一覧を捨てて
指紋だけを持つと、手順 1 で「変わった」ことは分かってもどのファイルが変わったかが分からず、
コピー対象が司令塔の記憶に戻る（それは指紋で閉じたはずの自己申告と同じ穴）。一覧は staging の
外（作業ディレクトリ）に置く。中に置くと、指紋を取る対象自体が増えて値が変わる。

- **戻り値を受け取った直後**に 1 回実行し、得た値を提示メッセージの【staging への手直し】行に
  載せる。編集したあとに基準を取れば不一致は起きないので、後から取る運用では自分で取った
  2 つの値を自分で比べるだけになり、自己申告に戻る。ユーザーの目に触れた値になって初めて
  あとからの照合が意味を持つ。
- 対象は staging ツリー全体。`changed_files` だけを hash すると、updater が触っていない
  ファイルを司令塔が直した場合（例外経路の手直しで最も起きやすい形）を取りこぼす。
  ファイル 1 つずつの hash をさらに hash しているので、追加・削除でも値が動く。
- `LC_ALL=C` と `sort` で列挙順を固定するのは、同じ中身なら常に同じ値を返させるため。
  順序が環境で変わると、手直しが無くても不一致になってゲートが信用されなくなる。
- 検出できないのは「戻り値を受け取る前に staging を触った場合」だけ（基準自体が既に
  手直し後になる）。手直しをしたら言う、という前提はこれで消えない。指紋は申告の代わりでは
  なく、申告が無かったときの検出。

### 手順 1: コピーの直前に取り直して比べる

コピーを始める前に取り直し、手順 0 の値と文字列として比較する。

```bash
cd <staging.dir> && find . -type f -print0 | LC_ALL=C sort -z | xargs -0 shasum -a 256 \
  > <作業ディレクトリ>/staging-hashes-1.txt
shasum -a 256 <作業ディレクトリ>/staging-hashes-1.txt
# 不一致のとき、変わったファイルを一覧の差分から機械的に出す
diff <作業ディレクトリ>/staging-hashes-0.txt <作業ディレクトリ>/staging-hashes-1.txt
```

- **一致** → 手直しなし。手順 3 へ。
- **不一致** → 手直しあり。`diff` に現れたパスが手直ししたファイルで、これが手順 2 の
  `focus` と手順 3 のコピー対象になる。思い出しで数えない（数え落としたファイルは、
  再検証を通った staging と反映後の本体を食い違わせる）。手順 2 を終えるまでコピーしない。

### 司令塔がやらないこと（明示）

司令塔は staging の**内容を書かない**。改稿は updater の仕事で、major 以上の残存・新規は
script がループ内で updater へ戻す（`REVISE_SEVERITIES`）。この禁止が暗黙だったとき、
ループの出口から漏れた指摘を司令塔が手で塞ぐ運用が実際に発生した — 役割の don't は
推論可能なだけでは守られない。手直しがどうしても要る場合（ユーザーの明示指示・minor の
文言修正）だけが下の手順 0〜2 の対象で、それは例外経路である。

### 手順 2: 手直しの再検証（不一致のときだけ）

staging を対象に review をもう 1 回回す。書いた本人ではない担当が読み直す形になる。

```
Workflow({
  scriptPath: "[SKILL_DIR]/scripts/review_skill.js",
  args: {
    skillDir: "[SKILL_DIR]",
    mode: "review",
    target: {
      skillPath: "<staging.dir>",
      scope: "full",
      focus: "<手直ししたファイルと、その手直しで狙ったこと>"
    }
  }
})
```

- `mode: "review"` なのでファイルは 1 バイトも書かれない。staging はそのまま残り、
  非承認で終わっても失われない。`stagingDir` は渡さない（review では使われない）。
- `scope` は `full` 固定。staging は git の追跡外なので `diff` にすると差分が空になり、
  finder は「見るべき箇所が無い」と判断して何も読まない。
- 返った `findings.confirmed` を、最初の提示で既に出した指摘（`remaining` / `unverified` /
  `unobserved` / `reclassified` / `preexisting` / `out_of_scope` に載せたもの）と突き合わせる。
  突き合わせは `scripts/diff_findings.py` に両方の配列を渡して行う（同一性キーと正規化の
  正本はこの script。手作業でなぞらない — 正規化の目視再現は件数が増えるほど揺れ、
  この判定はコピー可否のゲート条件そのものになる）:

  ```bash
  python3 [SKILL_DIR]/scripts/diff_findings.py <<'JSON'
  {"reverify_confirmed": <再検証の findings.confirmed>, "already_presented": <既出の指摘の配列>}
  JSON
  ```

  - `matched` → 承認の時点で人間が見た指摘。手直しについて新しく分かったことではない。
  - `new` → 手直しが持ち込んだ可能性がある指摘。**判断材料はこれだけ**で、
    ここに blocker がある間はコピーしない。
  この切り分けを置かないと、再検証は毎回「承認済みの既知の指摘」を並べ直すので、
  ゲートは邪魔なだけの装置になって迂回される。
- 返った `findings.unverified` も同じ script で突き合わせる（`reverify_confirmed` キーに
  `findings.unverified` の配列を渡す — script は confirmed/unverified を区別しない汎用の
  突き合わせで、キー名は入力の出所を縛らない）。手直しに関係する行（`new` 側に出たもの）
  は件数と中身を提示に含める。**unverified の blocker 級が 1 件でもあればコピーを止める**
  （検証が足りないことは手直しの繰り返しでは直らない — update 本編の
  `needs_human_decision` と同じ扱いで人間の判断を仰ぐ）。
- 新しく出た指摘をどう扱うか（直す / 受け入れて反映する / 指摘を落とす）は人間が決める。
  直した場合は手順 0 の基準を取り直してから手順 1 に戻る（2 度目の手直しも同じ形で検出する）。
- 再検証が `verdict: review_incomplete` を返したら「手直しを検証できていない」。直ったとも
  壊れたとも言わずコピーを止め、どの観点が欠けたかを添えて提示する。

### 手順 3: コピーと基本バリデーション

1. `staging.changed_files` に挙がったファイルと、手順 1 の `diff` に現れたパスを合わせた集合を、
   staging 内の相対パスのまま対象スキルディレクトリへコピーする。**それ以外は触らない** ——
   staging は全ファイルのミラーなので、ディレクトリごとコピーすると、変更していない
   ファイルまで（改行や属性の差を含めて）上書きされ、承認された変更に紛れる。
2. コピー後、基本バリデーションの実行をユーザーに案内する。

```bash
python3 [SKILL_DIR]/scripts/quick_validate.py <対象スキルの実パス> --verbose
```

3. 検証で落ちた項目があれば、その内容をそのまま伝える。落ちたことを黙って直そうとすると、
   承認された変更に承認外の変更が混ざる。

## 非承認・中断のときの扱い

- staging は**消さない**。消すと「やっぱり見せて」に応えるために全部を回し直すことになる。
- 「どこにあるか」だけを伝えて終了する。
- `verdict: update_failed` のときは、改稿の担当が応答しなかったため
  **staging に何がどこまで書かれたかは分からない**。`staging.changed_files` は空で返るが、
  これは「何も書かれていない」ことの証明ではない（一覧を返す前に落ちた可能性がある）。
  `staging.dir` を提示し、中身を見て判断してもらう。「何も書かれていません」とは言わない。

## 設計上の制約

SKILL.md の「設計上の制約」から参照される。制約の本文はここが唯一で、SKILL.md 側には
要約を置いていない（2 箇所に分けると片方だけが更新される）。

### パスは呼び出し側が実体で渡す

Workflow script はファイルシステムに触れず、symlink の解決も自分ではできない。
`skillDir` と `target.skillPath` は司令塔が `realpath` で実体に解決してから渡し、script 側は
「空でない絶対パスか」だけを検査して落とす。`.claude/skills/...` のような参照パスを
script に埋め込むと、install 先（別ディレクトリに展開される）で解決できなくなる。

### staging はスキル本体の外に置く

`stagingDir` の既定値は `scripts/review_skill.js` が持つ（対象スキルディレクトリの**兄弟**で
あって内部ではない）。スキルディレクトリを列挙する検証スクリプトや参照実在チェックは
配下を再帰的に見るため、内部に置くと未承認のドラフトが本体スキルの一部として
検査・配布の対象に入る。明示的に `stagingDir` を渡す場合も対象スキルの配下は指定できず、
script が起動時に落とす。

### staging の指紋は司令塔が計算する（script は返せない）

Workflow script はファイルシステムに触れないため、staging の中身から値を作れない。
手直しの検出に使うダイジェストは、script の戻り値ではなく司令塔が
「承認後の適用手順」手順 0 のコマンドで取る。計算と比較はコマンドと文字列一致で閉じており、
判断（再検証で出た指摘を受け入れるか）だけが人間側に残る。script 側に digest を足そうとすると、
ファイルを読めないまま常に空を返すフィールドができる。

### 新設ファイルはこのスキルの直下に実体で置く

`agents/finder.md` `agents/refuter.md` `agents/updater.md` `references/orchestrator-review.md`
`scripts/review_skill.js` はすべてこのスキルディレクトリ直下の実ファイル。配布サブツリーに
symlink を置くと、取得側によっては symlink が落ちて中身が空になる。

### agent の frontmatter は既存と同じフィールドに揃える

新設 agent の frontmatter は `model` / `subagent_type` / `description` のみ。
配布先ごとに解釈の異なるフィールドを増やすと、片方の plugin 定義にしか無い項目が
できて整合が崩れる。
