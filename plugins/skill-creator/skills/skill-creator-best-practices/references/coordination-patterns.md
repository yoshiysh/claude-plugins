## パターン一覧

### 1. Orchestrator-Subagent（指揮と実行）

**定義**：リードエージェントがタスクを分解・委任し、Sub-agent が個別タスクを実行して結果を返す階層構造。

**適用条件**：
- タスク分解が明確で、サブタスクの境界が明確
- Sub-agent が短期・集中型の作業をこなす場合
- 全体の進行を1つのエージェントが管理すべき場合

**利点**：全体目標を保ちつつ分業が可能。
**欠点**：Orchestrator が情報ボトルネックになる。逐次実行だとコスト増。

**SKILL.md への反映**：
- SKILL.md = Orchestratorの指示書（誰に何を渡すかのみ）
- `agents/` 配下に各 Sub-agent のプロンプトファイルを置く
- Sub-agent はそれぞれ単一の責務のみ持つ

---

### 2. Generator-Verifier（生成と検証）

**定義**：生成エージェントが出力を作成し、検証エージェントが評価・フィードバックを返すループ構造。

**適用条件**：
- 品質が重要な出力（HTML生成・コード・文書）
- 評価基準を明示的なチェックリストで定義できる場合
- 誤出力のコストが高い場合

**利点**：反復的な品質改善が可能。
**欠点**：検証基準が曖昧だと機能しない。上限回数と差し戻しレベルの定義が必須。

**SKILL.md への反映**：
- editor → verifier の順で呼ぶ
- verifier が返す判定は「✅ / ❌（計画レベル） / ❌（実装レベル）」の3種
- ❌ 計画レベル → 上流の planner に差し戻し
- ❌ 実装レベル → editor に差し戻し（上限2回）
- 2回目以降も ❌ → ユーザーに提示して判断を仰ぐ

---

### 3. Parallelization（並列実行）

**定義**：独立した複数のサブタスクを同時に起動し、結果を統合する。

**適用条件**：
- サブタスクが互いに独立している（出力が他の入力にならない）
- 同じ対象を複数の観点で検証・評価したい場合
- 実行時間の短縮が重要な場合

**利点**：レイテンシ削減。各エージェントが専門知識に集中できる。
**欠点**：エージェント間の独立性が崩れると競合が発生する。

**SKILL.md への反映**：
- 独立した複数の Agent 呼び出しを1ターンで発行する
- 各エージェントが同じ入力を受け取り、異なる観点で処理する
- 例：verifier を「構造チェック係」「コード品質係」「コンテンツ品質係」に分割して並列実行

---

### 4. Agent Teams（チーム型並列）

**定義**：コーディネーターが複数のワーカーを独立プロセスとして起動。ワーカーは長期・複数ステップの作業をこなしながらコンテキストを蓄積する。

**適用条件**：
- 各サブタスクが長期・複数ステップの作業を必要とする
- ドメイン専門知識の蓄積が効果的な場合

**利点**：ワーカーがコンテキストを保持し続けるため、反復でパフォーマンスが向上。
**欠点**：完了検知が複雑。共有リソースへの競合リスク。

**SKILL.md への反映**：
- 短期スキルには Orchestrator-Subagent で十分。Agent Teams は長期・反復作業に使う。
- 同一スキルを定期的に呼び続けるループが必要な場合に検討する。

---

### 5. Shared State（共有状態）

**定義**：中央コーディネーター不在で、エージェントが共有データストア（ファイル・DB）を直接読み書きして協調する。

**適用条件**：
- エージェントが互いの発見を基に協調する調査・研究系タスク
- 単一障害点の排除が優先される場合

**利点**：リアルタイムで知見が共有される。
**欠点**：リアクティブループ（A→B→A→...の無限循環）が最大リスク。終了条件の設計が必須。

**SKILL.md への反映**：
- 終了条件（時間制限・収束閾値・専任終了判定エージェント）を必ず定義する。
- 調査・情報収集系スキルに適している。

---

### 6. Message Bus（メッセージバス）

**定義**：エージェントが publish/subscribe で通信し、ルーターがイベントの種別に応じて適切なエージェントへ配信する。

**適用条件**：
- イベント駆動のパイプライン処理
- 今後エージェント数やイベント種別が増える見込みがある場合
- 処理ルートをイベント種別で動的に切り替えたい場合

**利点**：エージェント同士が疎結合。新しいエージェントをルーターに登録するだけで拡張できる。
**欠点**：ルーターの誤分類でサイレント障害が起きやすい。イベントの追跡・デバッグが複雑になる。

**SKILL.md への反映**：
- ルーターエージェントが入力イベントを分類し、担当エージェントへ振り分ける設計にする
- ルーティングルールは `references/` に定義して明示化する
- サイレント障害を防ぐため、未知のイベント種別への fallback 処理を必ず定義する

---

### 7. Workflow 実行型（orchestration の決定化）

**定義**：実行順序・ループ・並列・集約・閾値判定を **script が握り**、agent は各ノードでの判断だけを行う。パターン 1–6 が「Claude がターンごとに次を決める」形なのに対し、これだけは plan が script 側にある。詳細と公式の 4 分類表は `best-practices.md` §13。

**適用条件**：
- 人間ゲートを挟まない区間に fan-out・集約・閾値判定・条件付き再実行が連なる
- 1 会話で調整できる数を超える agent が要る（監査・大規模移行・相互検証つき調査）
- orchestration 自体を読める・再実行できる資産にしたい
- ループの正しさを監視するコード（skip 検出・bypass 検出・記録漏れ検知）を書き始めた

**利点**：スキップ・bypass・閾値の目分量判定が**構造的に起こりえなくなる**（監視機構ごと削除できる）。集計を LLM にさせないので数字が正確。中断しても同一 session 内で resume 可能。
**欠点**：**実行中にユーザー入力を受け取れない**。Claude Code 専用（Codex には該当機能が無い）。1 run のトークン消費が大きい。

**SKILL.md への反映**：
- SKILL.md は「script を呼ぶ前」と「結果を受け取った後」だけを書く。区間の内側の手順を散文で再掲しない（script が唯一の正）
- script は `<skill>/scripts/<name>.js` に置き、`Workflow({ scriptPath, args })` で呼ぶ
- 人間ゲートは script の**境界**に置く。段階ごとに別 workflow として回し、gate FAIL は `status: "BLOCKED"` と理由・証拠を返して止める
- agent プロンプトは `agents/` に残す（skill は専門知識、workflow は実行順序という分担）
- Claude Code 専用である旨を SKILL.md に明記する

**入れ子**：パターン 1–6 は script の制御フローとしてそのまま内側に入る（`parallel()` = Parallelization、designer→reviewer の until-pass = Generator-Verifier）。置換ではなく階層。

**参照実装**：`dispatch`（`scripts/orchestrate.js`）、`skill-creator-best-practices`（`scripts/build_skill.js`）、`search`（`scripts/investigate.js`）。

## パターン選択ガイド

### ステップ 0：orchestration を script に移すか（軸が違うので先に判定する）

| 状況 | 判定 |
|------|------|
| 人間ゲートを挟まない区間に fan-out・集約・閾値判定・条件付き再実行が連なる | **Workflow 実行型** |
| 1 会話で調整できる数を超える agent が要る（監査・大規模移行・相互検証つき調査） | **Workflow 実行型** |
| adversarial verify・多角ドラフト比較を**構造として強制**したい | **Workflow 実行型** |
| ループが正しく回るかの監視コード（skip 検出・bypass 検出・記録漏れ検知）を書き始めた | **Workflow 実行型**（→ 監視ごと消せる） |
| 各ステップに人間の判断・承認が挟まる | 1–6 のまま（workflow は実行中にユーザー入力を受け取れない） |
| agent が数個で、逐次の判断がそのまま流れになる | 1–6 のまま |

判定の根拠と詳細は `best-practices.md` §13。**「警察装置」シグナル**（監視機構を書き始めたら script に移すサイン）はここで必ず確認する。

Workflow 実行型を採る場合でも、人間ゲートは workflow の**境界**に置ける（段階ごとに別 workflow として回し、gate FAIL は `status: "BLOCKED"` で返して止める）。全区間を script に入れる必要はない。

### ステップ 1：内側の形を選ぶ

| 状況 | 推奨パターン |
|------|------------|
| 品質重視・評価基準が明確 | Generator-Verifier |
| タスク分解が明確・短期サブタスク | Orchestrator-Subagent |
| 独立した複数観点の検証 | Parallelization |
| 独立した長期並列サブタスク | Agent Teams |
| 協調調査・発見の共有 | Shared State |
| イベント駆動・エコシステム拡張予定 | Message Bus |

**基本方針**：ステップ 0 で Workflow 実行型を採らないと決めた場合は、まず Orchestrator-Subagent から始め、具体的な課題が見えてから他パターンを組み合わせる。採る場合は、同じ表で選んだ形を script の制御フローとして表現する（`parallel()` = Parallelization、designer→reviewer の until-pass ループ = Generator-Verifier）。本番設計はパターンの組み合わせが一般的。

## モデル選定基準

| タスクの性質 | モデル |
|------------|--------|
| 深い創造・推論・高品質な生成 | Opus |
| 構造的判断・分類・計画 | Sonnet |
| 定型処理・パターンマッチング | Haiku |

**注意**：Haiku は処理が完全に定型化できてから適用する。曖昧さや推論が残るタスクには Sonnet 以上を使う。
