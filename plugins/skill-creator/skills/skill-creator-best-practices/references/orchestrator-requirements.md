## 1. ドメイン知識の要否を判定する

**先に判定する。** 要件を構造化してからでは、鍵となる語を自分の理解のまま固定してしまう。

### 判定の問い

> **このスキルの出力は、鍵となる語のどの定義を採るかで形が変わるか。**

変わるなら知識の確認が要る。変わらないなら飛ばす。

| 判定 | 例 |
|---|---|
| **要る** | 「PRD と仕様書を書くスキル」— 出力する文書の種類そのものが、定義の定まらない語である |
| **要る** | 「会計処理を仕訳に落とすスキル」— 仕訳の正しさが会計基準の定義に依存する |
| **要らない** | 「月報を生成するスキル」— 月報の理論を確定しなくても、その組織の月報は作れる |
| **要らない** | 「PDF を要約するスキル」— 要約の定義が争点にならない |

**「その領域に規格があるか」で判定しない。** 規格があっても出力の形が変わらないなら要らないし、
規格が無くても（PRD のように）語の定義が争点なら要る。見るのは**成果物の同一性が語に依存するか**である。

### 要ると判定したときにやること

**手段は問わない。** 一次情報検証つきの調査スキル（`research:search` 等）を呼んでもよいし、
公式ドキュメントを数件読んでもよいし、ユーザーが持っている資料を貼ってもらってもよい。
深く調べるほど良いが、**全ビルドに重い調査を課すとスキル生成そのものが使えなくなる**ため、
案件に見合う深さを選ぶ。

集めた結果は `domainKnowledge` として Workflow に渡す。

```
domainKnowledge: {
  summary: "この領域について分かったことの要約",
  claims: [
    { claim: "...", strength: "一次情報確認済み", source: "規格名 §条番号 / URL" },
    { claim: "...", strength: "実務慣行", source: "提唱者・企業名" },
    { claim: "...", strength: "未確認", source: "" }
  ],
  do_not_write: ["確認できていないので書いてはならないこと"]
}
```

### `strength` を必ず付ける

**内容よりも、どの主張がどれだけ確かなのかが下流で効く。** 強度の無い知識ファイルは、
根拠のある記述と無い記述を見分けられなくするだけで、防ごうとしている失敗をそのまま再生産する。

| strength | 意味 |
|---|---|
| `一次情報確認済み` | 規格本文・原典を実際に読んで確認した。条番号を引用してよい |
| `実務慣行` | 広く使われているが、規格・公式の定めではない。**そう明示して使う** |
| `未確認` | 確からしいが裏を取れていない。**生成物に書かない** |

`do_not_write` には「確認できなかったので書いてはならないこと」を入れる。これが無いと、
writer は自分が知っていることで空白を埋める。

## 2. 要件を構造化する

ユーザーの入力から以下を整理する：

1. **スキルの目的**：何をできるようにするか
2. **トリガー条件**：どんな言葉・文脈で発動すべきか
3. **入出力の形式**：何を受け取って何を返すか
4. **対象ユーザー**：技術者？非エンジニア？どんな業務の人？
5. **タスク種別**：`document` / `procedure` / `data` から選ぶ。これは**ドメイン分類**であり、orchestration の形（Workflow 実行型か否か）とは別軸。両者を結び付けない
   - `document`：文書・レポート・HTML 生成系
   - `procedure`：業務フロー自動化・複数ステップ処理系
   - `data`：データ変換・分析・抽出系
6. **後続スキルからの呼び出し**：このスキルが別のスキルから呼ばれることを想定するか確認する
   - **呼ばれる場合**：出力フォーマットに後続スキルが必要とするフィールドを含める。直接呼び出し（ユーザー起動）とパイプライン呼び出し（別スキル経由）で動作が変わる場合は分岐を設計する
   - **呼ぶ場合**：既存スキルをパイプライン呼び出しで再利用できないか確認する（重複実装を避ける）。その呼び出しも専用の agent に委譲する（SKILL.md から直接呼ばない）
   - 後続スキルが未作成でも「どんなスキルと組み合わせることを想定するか」を聞いておくと出力フォーマット設計に活かせる

**ユーザーが挙げた一例を、対象範囲の定義に格上げしない。** 「個人で使うなら 1 行で足りる」は
分量の下端を示した例であって、「個人利用のみを対象にする」ではない。例を範囲として固定すると
反対側の案件で使えないスキルになり、しかも**そう決めた形跡がどこにも残らない**ので、後から
誰も気づけない。範囲は例からではなく、**幅の両端を確かめて**決める。

不明点があれば、技術用語を使わず平易な言葉でユーザーに確認する。
確認は一度にまとめて行い、何度も往復しない。

## 3. アーキテクチャパターンを選ぶ

`references/coordination-patterns.md` を Read し、生成するスキルに適したパターンを選択する。

**最初に判定するのは「誰が plan を握るか」**（`coordination-patterns.md` のパターン選択ガイドが持つ判定。同ファイル内の番号であって、この文書の番号ではない）。パターン 1–6 はいずれも Claude がターンごとに指揮する形で、Workflow 実行型だけが軸が違う。ここを飛ばして 1–6 から選び始めると、orchestration を script に移す選択肢が最後まで検討されない。判定の根拠は `references/best-practices.md` §13 を Read すること。

### 責務分離の原則（判断不要・常に適用）

**SKILL.md はフローの進行のみを担う。処理の実行責任は Sub-agent が持つ。**

- SKILL.md が書くこと：「誰に何を渡すか」の順序・分岐・完了条件のみ
- Sub-agent が担うこと：実際の処理（API 呼び出し・スクリプト実行・ファイル生成を含む）
- スクリプト（scripts/）を呼ぶかどうかの判断も Sub-agent の責務

「この処理はシンプルだから Sub-agent に切り出さなくていい」という判断は行わない。
単純な情報収集スキルでも必ず Sub-agent に切り出す。

**Workflow 実行型を採る場合、この原則の適用先が変わる。** 実行順序を握るのは SKILL.md ではなく
script になるので、SKILL.md は「script を呼ぶ前」と「返り値を解釈して人間に見せる」だけを担う。
区間の内側の手順を SKILL.md に散文で再掲しない（script が唯一の正になるため、二重管理は必ずズレる）。
agent への切り出し原則そのものは変わらない — script のノードが agent を呼ぶ形になるだけ。

### 選択手順

0. **orchestration を script に移すかを判定する**（判定表は `coordination-patterns.md` にある）：
   - 人間ゲートを挟まない区間に fan-out・集約・閾値判定・条件付き再実行が連なるか
   - 1 会話で調整できる数を超える agent が要るか
   - adversarial verify・多角比較を構造として強制したいか
   - **「警察装置」シグナル**：ループが正しく回るかの監視（skip 検出・bypass 検出・記録漏れ検知）を SKILL.md に書きたくなっていないか。書きたくなっていれば、それはループ自体を script に移すサイン（`best-practices.md` §13）
   - いずれかに当てはまれば **Workflow 実行型**。この場合も人間ゲートは script の境界に置けるので、全区間を script にする必要はない
   - 当てはまらなければ 1–6 のまま進む

この判定結果は、Workflow へ `architecture` として渡す（`workflow` か `coordinator`）。`taskType` とは別のフィールドなので、両方を明示的に設定する。ここを渡し忘れると既定の `coordinator` になり、Workflow 実行型を選んだ判断が下流に届かない。

1. **Sub-agent の分割単位を決める**：各ステップを「1入力 → 1出力」の単一責務に分割する
   - 例：「入力検証」「API取得」「フォーマット変換」「ファイル保存」はそれぞれ別 agent

2. **追加パターンを検討する**（`references/coordination-patterns.md` を参照）：
   - 品質保証が重要か → Generator-Verifier を追加
   - 独立した複数観点の検証があるか → Parallelization を追加
   - サブタスクが長期・複数ステップか → Agent Teams を追加
   - Workflow 実行型を採った場合、これらは script の制御フローとして内側に入る（置換ではなく入れ子）

3. **各 Sub-agent のモデルを決定する**：
   - 深い創造・推論・高品質な生成 → Opus
   - 構造的判断・分類・計画 → Sonnet
   - 定型処理・パターンマッチング → Haiku（定型化できてから）

4. 以下をユーザーに提示して確認を取る：
```
## アーキテクチャ設計

採用パターン：[パターン名（複数可）]

Sub-agent 一覧：
- [agent名]（[モデル]）：[単一の責務を1行で説明]
- ...

assets に分離するもの：
- [ファイル名]：[内容]

このまま進めますか？変えたい設計があれば教えてください。
```

## 4. eval を設計しスキーマを定義する

### eval-first 設計

スキルの実装前に評価テストケースを設計する。
「想定される問題」ではなく「実際の問題」を解くために必ず先に作る。

ユーザーに以下を提示して確認を取る：

```
## eval 設計（テストケース）

以下の形式で3件のテストケースを設計します。
内容を確認・修正してから実装を進めます。

evals.json フォーマット：
{
  "skill_name": "[スキル名]",
  "evals": [
    {
      "id": 1,
      "prompt": "[正常系エッジケース：境界値的だが動作すべき入力]",
      "assertions": ["〜が含まれているか", "〜が明記されているか"]
    },
    {
      "id": 2,
      "prompt": "[準正常系：不完全・曖昧な入力でスキルが適切に問い返すケース]",
      "assertions": ["問い返しのメッセージが含まれているか"]
    },
    {
      "id": 3,
      "prompt": "[誤発動リスク：発動すべきでない境界ケース]",
      "assertions": ["スキルが発動していないか"]
    }
  ]
}

このまま進めますか？テストケースを修正したい場合は教えてください。
```

### schemas 先行設計（マルチエージェント系スキルの場合）

Sub-agent を複数使う設計の場合、エージェント間の入出力フォーマットを先に定義する。
`references/schemas.md` を Read して定義方法を確認すること。

生成するスキルのディレクトリに `schemas/agent-contracts.md` を含める設計にする。

## 5. フローと依存関係を確認する

`references/flow-design.md` を Read し、手順に従って生成するスキルのフロー設計を行う。

- 各ステップの入出力を列挙する
- 依存関係から並列・直列を判定する（直感で決めない）
- 選択したパターンに従って並列・直列を決める（Parallelization なら並列で発行）
- フロー図を作成し、完了時に SKILL.md の「全体フロー」として記載する

## 6. ペルソナを推論して提示する

要件が確定したら、タスク種別・対象ユーザー・スキルの複雑さをもとにペルソナを推論し、以下のフォーマットでユーザーに提示する：

```
## 今回のスキル制作で使うペルソナ（役割分担）

スキル種別：[document / procedure / data]
アーキテクチャ：[coordinator / workflow]（Workflow 実行型なら workflow）
対象ユーザー：[推論結果]

- 基準生成係：[推論したペルソナ]（「このスキルが失敗するとしたらどこか」を考えられる人物）
- 基準補完係：[推論したペルソナ]（基準生成係とは別職種・別視点の人物）
- 構成設計係：[推論したペルソナ]（document タイプのみ。情報設計・コンテンツ構成を得意とする人物）※ document タイプ以外は「不要」と記載
- 構成検証係：[推論したペルソナ]（document タイプのみ。構成案を第三者目線で評価できる人物）※ document タイプ以外は「不要」と記載
- 執筆係：[推論したペルソナ]（対象ユーザーと同じ言語感覚を持ち、曖昧さに敏感な人物）
- テスト作成係：[推論したペルソナ]（このスキルの典型的な利用者。完璧な入力は書かない）
- 検証係：[推論したペルソナ]（書き手の意図を知らない第三者。テキストのみを根拠に判断）
- script 検証係：[推論したペルソナ]（アーキテクチャが workflow のときのみ。並行処理と集計の誤りを実行前に見抜ける人物）※ coordinator の場合は「不要」と記載

このまま進めますか？変えたい役割があれば教えてください。
```

ユーザーが承認または修正指示をしたらペルソナを確定して次のフェーズへ進む。
