### 基準チェック
各基準について以下の形式で判定してください：
- ✅ 満たしている（テキストに明示されている）
- ⚠️ 部分的・曖昧
- ❌ 満たしていない

⚠️ と ❌ は具体的にどこが問題かをテキストの引用で示すこと。

### 規範的主張の出所チェック（全スキル共通）

**このスキルが「〜すべき」「〜しなければならない」と述べている箇所を 1 つずつ、出所に当てる。**

| 見るもの | 失格の条件 |
|---|---|
| 規格・標準の名前を挙げた記述 | その規格が実際にそう定めているか。**確認されていない条番号・引用は失格** |
| 権威に帰属させた記述（「〜が推奨している」） | 帰属先が実在し、実際にそう述べているか。実務慣行を規格由来のように書いていないか |
| 数値の閾値（件数・分量・時間） | 出所があるか。**根拠なく置かれた数値は失格** |
| 領域固有の用語の定義 | その定義がこのスキルの独自解釈でないか。独自なら、そう明示しているか |

`[DOMAIN_KNOWLEDGE]` が渡されている場合は、**その強度の区別が生成物で保たれているか**も見る。
「実務慣行」とされた主張が規格の定めとして書かれていたら失格である。

**この検査が無いと、書き手が知っていることがそのまま規範として通る。** 曖昧な記述は「曖昧だ」と
気づけるが、**もっともらしい出所を添えた誤りは気づけない**。

### ワークフロー設計チェック（Sub-agent を使う設計の場合のみ）

SKILL.md が Orchestrator-Subagent パターンを採用している場合、以下を追加でチェックすること。

**1. 単一責務（SRP）**
- 各 agent は「1入力 → 1出力」になっているか
- 判断・変換・生成が1つの agent に混在していないか
- 参照（assets読み込み）と出力生成が同一 agent に混在していないか

**2. Orchestratorの純粋性**
- SKILL.md（Orchestrator）にドメイン知識が混在していないか。以下が SKILL.md に書かれていたら ❌：
  - 変換ルール・マッピング表（例：「HTML タグ X は Markdown の Y に変換する」）
  - 定型エラーメッセージ・案内文の本文（フロー制御の条件だけでよい）
  - 設定値・URL・閾値のハードコード
  - 業務判断ロジック（「もし〇〇なら△△する」という条件分岐の中身）
- SKILL.md は「誰に何を渡すか」の制御フローだけを定義しているか
- 上記のドメイン知識が `references/`・`assets/`・`scripts/` に適切に分離されているか

**3. パターン適用の妥当性**
- Generator-Verifier：品質が重要な出力に適用されているか。ループの終了条件（上限回数・差し戻しレベル・エスカレーション先）が定義されているか
- Parallelization：並列化した agent が本当に独立しているか（出力が互いの入力にならないか）
- その他パターンが採用されている場合：選択理由が要件と一致しているか

**4. モデル適合性**
- 深い創造・推論・高品質な生成 → Opus が割り当てられているか
- 構造的判断・分類・計画 → Sonnet が割り当てられているか
- 定型処理・パターンマッチング → Haiku が割り当てられているか（定型化済みのタスクのみ）

**5. インターフェースの整合性**
- 各 agent の `[PLACEHOLDER]` 入力と、前の agent の出力が対応しているか
- Orchestrator が渡す形式と agent が受け取る形式が一致しているか
- **閉じた主張が 2 つ以上のファイルに無いか。** 「この N 個が揃えば足りる」「〜だけである」
  「〜に限る」のように**範囲を閉じる文**が、同じ対象について複数ファイルにあると、両方を
  読む agent は矛盾を自分で裁くことになる。正の所在を 1 つに決め、他方は参照させる。
  重複した「説明」は冗長なだけだが、重複した「閉包」は矛盾になる

**6. エラー伝播の定義**
- 各 agent が ❌ を返したとき、Orchestrator がどう分岐するかが書かれているか
- ❌ の種類（計画レベル / 実装レベル）が区別されているか

**7. assets 分離と外部化**
- 変化しない参照データ（仕様・コンポーネント集・設定値）は `assets/` に分離されているか
- `agents/` にある .md ファイルは「処理の指示」だけを含んでいるか（参照データは `assets/` を Read させる）
- 確定的な処理（フォーマット変換・集計・ファイル操作）は `scripts/` に分離されているか
- 定型エラーメッセージや案内文の本文が SKILL.md や agent に直書きされていないか（`assets/` または `references/` に置くべき）

**8.5 反復（改稿・審査・実験の繰り返しを持つ設計の場合）**
- 基準は `[SKILL_DIR]/references/criteria-by-task.md`「反復（グラフ）」節を読んで適用する（正本。ここに複製しない）
- 必ず ❌ にするもの: 較正根拠の無い回数上限を停止条件の本体にしている設計（backstop としての明記が無い）
- 判断の根拠は `[SKILL_DIR]/references/best-practices.md` §13「反復の停止と戻り先」

**8. ハーネス（状態を持ち越す・長時間走る設計の場合）**
- 基準は `[SKILL_DIR]/references/criteria-by-task.md`「ハーネス」節を読んで適用する（正本。ここに複製しない）
- 必ず ❌ にするもの: 永続状態（DB・索引・resolved・メモリ）への書き込みが生成側の「完了」の自己申告で終端化している設計。別 context の verifier の再取得証拠で gate されていなければ ❌
- 判断の根拠は `[SKILL_DIR]/references/best-practices.md` §14

### ベストプラクティス準拠チェック（全スキル共通）

基準チェックとは別に、以下を追加でチェックすること。

**description の品質**
- description が3人称で書かれているか（"I can" や "〜できます" の形式は ❌）
- [What]（何をするか）と [When]（いつ使うか）の両方が含まれているか
- 除外条件（対象外）が明記されているか

**SKILL.md の構造**
- name が kebab-case か。gerund 形式（processing-pdfs など）が望ましい
- SKILL.md 本体が500行以内か
- 参照ファイルが1レベルの深さに収まっているか（SKILL.md → ref.md → deeper.md は ❌）
- 100行を超える参照ファイルに冒頭目次があるか（目次がない場合は ⚠️）
- 時間依存の情報（「〇年以降は〜」「〇月まで旧 API を使う」など）が含まれていないか

**生成スキルの設計**
- マルチエージェント設計の場合：agents/ 各ファイルにフロントマター（`model:`）があるか
- マルチエージェント設計の場合：schemas/ または schemas.md でエージェント間の入出力が定義されているか
- マルチエージェント設計の場合：各 agent の description に以下の3要素が含まれているか
  - いつ呼ばれるか（前ステップの agent 名またはスキル起動タイミング）
  - 何をするか（単一の責務）
  - 除外条件（何をしないか・エラー時の挙動）
- マルチエージェント設計の場合：agent 本文に Why-driven の説明があるか（命令だけでなく理由が書かれているか）
