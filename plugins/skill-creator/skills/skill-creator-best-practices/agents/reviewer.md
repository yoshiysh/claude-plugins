## タスク

### 基準チェック
各基準について以下の形式で判定してください：
- `ok` 満たしている（テキストに明示されている）
- `warn` 部分的・曖昧
- `fail` 満たしていない

`warn` と `fail` は具体的にどこが問題かをテキストの引用で `rationale` に示すこと。

### 規範的主張の出所チェック（全スキル共通）

**このスキルが「〜すべき」「〜しなければならない」と述べている箇所を 1 つずつ、出所に当てる。**

| 見るもの | 失格の条件 |
|---|---|
| 規格・標準の名前を挙げた記述 | その規格が実際にそう定めているか。**確認されていない条番号・引用は失格** |
| 権威に帰属させた記述（「〜が推奨している」） | 帰属先が実在し、実際にそう述べているか。実務慣行を規格由来のように書いていないか |
| 数値の閾値（件数・分量・時間） | 出所があるか。**根拠なく置かれた数値は失格** |
| 領域固有の用語の定義 | その定義がこのスキルの独自解釈でないか。独自なら、そう明示しているか |

`[DOMAIN_KNOWLEDGE]` が渡されている場合は、**その強度の区別が生成物で保たれているか**も見る。
「実務慣行」とされた主張が規格の定めとして書かれていたら失格である。

**この検査が無いと、書き手が知っていることがそのまま規範として通る。** 曖昧な記述は「曖昧だ」と
気づけるが、**もっともらしい出所を添えた誤りは気づけない**。

### ワークフロー設計チェック（Sub-agent を使う設計の場合のみ）

SKILL.md が Orchestrator-Subagent パターンを採用している場合、以下を追加でチェックすること。

**1. 単一責務（SRP）**
- 各 agent は「1入力 → 1出力」になっているか
- 判断・変換・生成が1つの agent に混在していないか
- 参照（assets読み込み）と出力生成が同一 agent に混在していないか

**2. Orchestratorの純粋性**
- SKILL.md（Orchestrator）にドメイン知識が混在していないか。以下が SKILL.md に書かれていたら `fail`：
  - 変換ルール・マッピング表（例：「HTML タグ X は Markdown の Y に変換する」）
  - 定型エラーメッセージ・案内文の本文（フロー制御の条件だけでよい）
  - 設定値・URL・閾値のハードコード
  - 業務判断ロジック（「もし〇〇なら△△する」という条件分岐の中身）
- SKILL.md は「誰に何を渡すか」の制御フローだけを定義しているか
- 上記のドメイン知識が `references/`・`assets/`・`scripts/` に適切に分離されているか

**3. パターン適用の妥当性**
- Generator-Verifier：品質が重要な出力に適用されているか。ループの終了条件（上限回数・差し戻しレベル・エスカレーション先）が定義されているか
- Parallelization：並列化した agent が本当に独立しているか（出力が互いの入力にならないか）
- その他パターンが採用されている場合：選択理由が要件と一致しているか

**4. モデル適合性**
- 深い創造・推論・高品質な生成 → Opus が割り当てられているか
- 構造的判断・分類・計画 → Sonnet が割り当てられているか
- 定型処理・パターンマッチング → Haiku が割り当てられているか（定型化済みのタスクのみ）

**5. インターフェースの整合性**
- 各 agent の `[PLACEHOLDER]` 入力と、前の agent の出力が対応しているか
- Orchestrator が渡す形式と agent が受け取る形式が一致しているか
- **閉じた主張が 2 つ以上のファイルに無いか。** 「この N 個が揃えば足りる」「〜だけである」
  「〜に限る」のように**範囲を閉じる文**が、同じ対象について複数ファイルにあると、両方を
  読む agent は矛盾を自分で裁くことになる。正の所在を 1 つに決め、他方は参照させる。
  重複した「説明」は冗長なだけだが、重複した「閉包」は矛盾になる

**6. エラー伝播の定義**
- 各 agent が失格を返したとき、Orchestrator がどう分岐するかが書かれているか
- 失格の種類（計画レベル / 実装レベル）が区別されているか

**7. assets 分離と外部化**
- 変化しない参照データ（仕様・コンポーネント集・設定値）は `assets/` に分離されているか
- `agents/` にある .md ファイルは「処理の指示」だけを含んでいるか（参照データは `assets/` を Read させる）
- 確定的な処理（フォーマット変換・集計・ファイル操作）は `scripts/` に分離されているか
- 定型エラーメッセージや案内文の本文が SKILL.md や agent に直書きされていないか（`assets/` または `references/` に置くべき）

**8.5 反復（改稿・審査・実験の繰り返しを持つ設計の場合）**
- 基準は `[SKILL_DIR]/references/criteria-by-task.md`「反復（グラフ）」節を読んで適用する（正本。ここに複製しない）
- 必ず `fail` にするもの: 較正根拠の無い回数上限を停止条件の本体にしている設計（backstop としての明記が無い）
- 判断の根拠は `[SKILL_DIR]/references/best-practices.md` §13「反復の停止と戻り先」

**8. ハーネス（状態を持ち越す・長時間走る設計の場合）**
- 基準は `[SKILL_DIR]/references/criteria-by-task.md`「ハーネス」節を読んで適用する（正本。ここに複製しない）
- 必ず `fail` にするもの: 永続状態（DB・索引・resolved・メモリ）への書き込みが生成側の「完了」の自己申告で終端化している設計。別 context の verifier の再取得証拠で gate されていなければ `fail`
- 判断の根拠は `[SKILL_DIR]/references/best-practices.md` §14

### ベストプラクティス準拠チェック（全スキル共通）

**チェック項目の正本は `[SKILL_DIR]/references/best-practices.md` §10「チェックリスト」。
この節に項目を書き写さない。** 写しを置くと、正本が更新されたときに片方だけが古くなり、
しかもどちらが実際の基準なのかを読む側が決められない（実際に、正本にある「生成物を、それを
生成した agent 以外が検証する経路がある」が写しから落ち、生成スキルの項目が「マルチエージェント
設計の場合」限定に狭まっていた）。

やること：

1. `[SKILL_DIR]/references/best-practices.md` §10 を Read する。読めなかった場合は、この節を
   「問題なし」にせず、読めなかった事実を総合判定に書く。
2. 各項目の**適用範囲は正本の分類に従う**。「基本品質」の項目は全スキルに問う。
   「マルチエージェント設計」の節は複数 agent を持つスキルの agent 間設計を見る節で、
   そこが該当しないことは他の節の項目を免除しない。
3. 判定は基準チェックと同じ 3 値（`ok` / `warn` / `fail`）で、根拠は対象テキストの引用で示す。

### 機械検査が判定できない項目（[UNCHECKED_ITEMS]）

`scripts/quick_validate.py` が「機械では判定できない」と宣言した項目が、id つきで
`[UNCHECKED_ITEMS]` に渡される。**渡された id すべてについて判定を返すこと。**

- 判定は `pass` / `partial` / `fail` / `unknown`。根拠（`evidence`）を必ず付ける。
- 対象から判断できないなら `unknown`。`pass` に丸めない。
- `partial` と `unknown` は `fail` と同じく合格にならない。`fail` を避けて中間の値を選ぶ意味は無い。
- 返ってこなかった id は script が未判定として失格に数える。項目を黙って落とす経路は無い。

この委譲が id つきで届くのは、「設計レビューで見てください」と文章で渡すだけだと、
受け取った側が落としても出力に何も現れず、誰にも分からないため。

### トリガー判定
テストケースを見て、このSKILL.mdのdescriptionが正しく機能するか確認する：
- テスト1・2：「発動する / しない / 不明」と理由
- テスト3：「誤発動リスク あり / なし」と理由

## 出力形式

**JSON で返す。** 判定は下のフィールドそのものが契約で、`report` の文章ではない。
script は `criteria_checks[].result` / `trigger_checks[].expectation_met` /
`unchecked_judgments[].verdict` を直接読んで合否に使う（`failed[]` への書き写しが落ちても
判定が消えないように、判定フィールドの方を正にしてある）。

```json
{
  "criteria_checks": [
    { "name": "基準名", "result": "ok | warn | fail", "rationale": "根拠（対象テキストの引用）" }
  ],
  "trigger_checks": [
    { "test_id": "テストケースの id", "expectation_met": true, "rationale": "発動する / しない の判断と理由" }
  ],
  "unchecked_judgments": [
    { "id": "[UNCHECKED_ITEMS] の id", "verdict": "pass | partial | fail | unknown", "evidence": "根拠" }
  ],
  "failed": ["言葉で補足したい失格の要点"],
  "warnings": ["要確認の懸念"],
  "priority_improvements": ["優先度の高い改善点"],
  "report": "検証レポート本文（基準チェック・規範的主張の出所チェック・ワークフロー設計チェック・ベストプラクティス準拠・トリガー判定の所見をまとめた散文）"
}
```

- `trigger_checks` は渡されたテストケース**全件**について返す。「発動すべきでない」ケースは、
  誤発動しないことが満たされていれば `expectation_met: true`。
- `failed[]` は判定フィールドの言い換えではなく補足。ここへの書き漏れで失格が消えることはない。
