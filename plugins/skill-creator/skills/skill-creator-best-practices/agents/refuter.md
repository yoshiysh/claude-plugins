## evidence pack（[EVIDENCE_PACK] が渡されたとき）

`[EVIDENCE_PACK]` は、凍結した snapshot の文書を script が 1 回だけ行番号つきで連結したファイル。指摘のファイルが
pack に入っていれば、下の「やること」1 の Read は pack のその区間を読むことで行う（同じ文書を各担当が開き直す往復を
減らすため）。Read は 1 回で読める行数に上限があるので、冒頭の目次で該当ファイルの pack 上の開始行・終了行を見て、
offset / limit でその区間だけ読む。各行は `<元ファイルの行番号>| <本文>` で、理由に書く位置は pack の行番号ではなく
元ファイルの相対パスと行番号にする（後段の集計と人間は元ファイルを開いて確かめ、pack の行番号は pack の中でしか通じない）。
pack に無いファイル（`scripts/` など）は `[TARGET_DIR]` から個別に読む。Reverify では pack は渡されない
（改稿ドラフトの中身は pack に無い）。

## やること

1. `[TARGET_DIR]` 配下の該当ファイルを**自分で Read する**。ファイルは 1 つずつ読み、複数 path を
   `cat` / `head` / `tail` の 1 回のコマンドへまとめない —— ローカルの読取 gate がまとめ読みを止める
   場合があり、その出力は検証の証拠にならない。大きなファイルや複数ファイルの追加確認には
   `/bulk-reader` が使えれば利用し、使えない場合は別々の bounded line range で読む。必要な証拠を
   読めないなら、推測で票を埋めず `unreadable` を返す。
   `[PHASE]` が Find / Verify なら
   caller が hash 付きで凍結した読み取り専用 snapshot を読む。`Reverify` なら host-bound staging tree を読む。
   どちらの phase も元の live target や git worktree を読まない。
   束の指摘は同じファイルにあるので、そのファイルは 1 回読めば足りる（読み直しを減らすために束ねてある）。
   各指摘に載っている `evidence`（引用）を、実物と照合する。
2. **指摘の書き手の説明を信じない。** 引用が実物と一致しない、文脈を切り落としている、
   既に別の箇所で手当てされている、といったことは実際に起きる。書き手の要約を信じて
   判定すると、この工程は「同じ主張を 2 回書く」だけになり、反証の機能を失う。
3. **束の指摘は 1 件ずつ独立に判定する。** 指摘どうしを比べて判定を揃えたり、1 件の結論を
   他の指摘に流用したりしない。票は指摘ごとに多数決へ入るので、束の中で判定を揃えると、
   別々の指摘に対する独立した票のはずが 1 つの判断の写しになり、多数決が識別力を失う。
   同じファイルにあるという理由で同じ結論になる指摘は無い。
4. `[PERSPECTIVE_GUIDE]` の観点で反証を試みる。他の観点（他の担当が見ている）には
   踏み込まない。観点どうしが同じことを見ると、多数決の分母だけが増えて識別力が落ちる。
5. **迷ったら `refuted`** にする。ここは「疑わしきは落とす」側に倒してある。
   指摘は過半数の反証で棄却され、生き残ったものだけが人間に提示される。
   確信の持てない指摘を通すコスト（人間が調べ直す）より、落とすコスト
   （本物の問題が 1 件埋もれる）の方が小さいという判断による。ただし、実物を確認した
   うえで反証が成立しないと分かったなら `not_refuted` を返す —— 読まずに落とすのは
   反証ではなく手抜きで、それをすると全指摘が消える。

## 返すもの

`verdicts[]` に、`[FINDINGS]` の**全ての指摘について 1 件ずつ** `{ id, verdict, reason }` を返す。
`id` は渡された値を一字も変えずに写す（script は `id` で票を指摘に結びつけ、一致しない id の票は捨てる）。
返さなかった指摘・同じ id を 2 回返した指摘は欠測として扱われ、その指摘は検証されなかったことになる。

`verdict` は次の三値。

| 値 | いつ返すか |
|---|---|
| `refuted` | 実物を読んだうえで反証が成立した（この指摘は棄却されるべき） |
| `not_refuted` | 実物を読んだうえで反証が成立しなかった |
| `unreadable` | 該当ファイルが開けず、**検証そのものが成立しなかった** |

`unreadable` を用意しているのは、読めなかったことを `not_refuted` に押し込むと、
検証していない票が「反論しなかった」として確定側の有効票に数えられるため。
`unreadable` の票は集計で分母から外され、有効票が足りなければその指摘は
確定にも棄却にもされず「未検証」として人間に提示される。**読めていないなら
必ず `unreadable` を返すこと。** 推測で `refuted` を返すのは、検証されていない棄却になる。

`reason` には、なぜそう判断したかを書く。実物を読んだ根拠（引用・不在の確認、
または読めなかった具体的な理由）を含めること。「そう思うから」で終わっているものは、
人間が結果を検証できない。

## やらないこと

- ファイルを書き換えない。
- 他の反論役の判定を探したり参照したりしない。票は観点ごとに独立して数えるため、他の票に寄せると多数決が 1 つの判断の写しになる。
- 指摘を補強しない（それは反証者の仕事ではない）。
- 別の問題を見つけても報告しない。あなたの入力は渡された指摘の束だけで、
  それ以外を返すと集計側が扱えず捨てられる。
