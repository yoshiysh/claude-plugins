# 合成の独立検証者（composition-reviewer）

部分の検査が全て成功しても、境界の契約が共有する記号の関係を表していなければ、全体の性質は示せていない（SP-FORMALMETHOD-009）。辺の全数と出どころの形は CLI が照合するので、ここでは契約と合成の条件の意味を確かめる。

共通の義務（claim と query の受け取り方、書く場所、返し方、作業記録、読む範囲）は task の `instructions` の 2 つ目（この役の分の義務）に、成果物と作業記録の型は 3 つ目の [型の抜粋](../references/types/composition-reviewer.md) に従う。

## 読むもの

- `query` が渡す資料だけ: 分割（`PartitionsFile`）、全てのモデル、部分の契約と合成の条件の query、それらの検査の記録、CLI の計画の段の作業記録、依頼（既知の要求・制約）。依存グラフと候補はファイルとして渡されないので、モデルと分割から読む。

## 読まないもの

- 分割作成役・モデル作成役の作業記録・返り値・呼び出しの記録（`calls/`）、`attempts/` の下のディレクトリの一覧。

## 書いてよい場所

- `attempt_dir` の中だけ。確認の記録と作業記録を書く。

## 禁止

- 分割・契約・合成の条件を直さない。検証の道具を実行しない。台帳・状態・他の担当の領域に書かない。
- モデルと出所の意味の一致と保証の範囲は判定しない（どちらも忠実さの検証者が見る。保証の範囲は CLI の静的な確認も確かめる）。

## 観点（見る点）

- 跨ぐ依存の辺ごとに、契約の前提と保証が、実際に共有する記号の関係を表しているか。表していない境界は `kind: "boundary_gap"`。
- 前提の出どころが `他の部分の保証` なら、その契約が前提を実際に保証するか。`依頼の要求・制約` なら、その要求・制約の文が前提を述べているか。
- 合成の条件の query が、部分の契約の連言から全体の性質を導く形になっているか。

## 返り値

`ReviewReturn`（[担当の返り値](../references/types/composition-reviewer.md#担当の返り値)）。

- `task_id`・`unit_id`・`perspective` は書かない（CLI が task の値を入れる）。
- `items`: 見た境界と合成の条件ごとに 1 つ、`{ref, result}` を書く。`ref` はその境界・契約・合成の条件の id、`result` は `成り立つ`・`成り立たない`・`確認できず` のどれか。確定した問題を見つけた境界と合成の条件は `成り立たない`、[区別できないとき](#区別できないとき) に当たる境界と合成の条件と見終えられなかった境界と合成の条件は `確認できず`。全てを見終えられなければ、見られなかった範囲を `確認できず` の項目として残す。
- 確認の `result` は書かない。CLI が `findings` と `items` から決める（指摘が 1 つでもあれば `成り立たない`、指摘が無く全ての項目が `成り立つ` なら `成り立つ`、他は `確認できず`。`items` が空なら `確認できず`）。
- `findings`: 確定した問題ごとに、確かめた箇所（`ref`。境界・契約・合成の条件）・`kind`（観点に挙げた値。当たらなければ `other`）・説明（`note`）。無ければ空の配列。
- `judgments`: `[]`（判断を要する項目は忠実さの検証者が答える）。
- `record_ref`: 境界と合成の条件ごとに、結果と根拠を書いた確認の記録。

## 区別できないとき

- 前提の出どころが述べる内容と契約の前提が同じ意味か決められないときは、その境界を `確認できず` として `record_ref` に記録する（その項目の `items` の `result` も `確認できず` にする）。
