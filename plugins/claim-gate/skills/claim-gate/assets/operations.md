## 実在確認の対象

`install-check` はこの 4 つを 1 件ずつ実測する。

| 対象 | 契約上の位置 |
|---|---|
| トグルの状態ファイル | 下記「トグルの状態ファイル」で定める単一パス |
| 適合検査スクリプト | plugin ルートの `scripts/` 配下、下記「適合検査の呼び出し形」の名前 |
| fixture ディレクトリ | plugin ルートの `tests/fixtures/` |
| B2 判定器の役割定義 | plugin ルートの `agents/claim-judge.md` |

状態ファイルは初回有効化時に作られるので、**無いこと自体は欠落ではなく「off」**である。
他の 3 つが 1 件でも無ければ、スキルは操作せずに停止する。

## トグルの状態ファイル

契約として決めること（実装がこの形を満たす）。

- **作用範囲は global（ユーザー単位）1 ファイル**とする。hook は user レベルの enable で
  全プロジェクトに効くため、プロジェクト単位の状態にすると「どのプロジェクトで on なのか」
  が hook 側から一意に決まらず、利用者が off にしたつもりの環境で発火する
- 位置は plugin のユーザーデータ領域に置き、**プロジェクトの作業ツリーには書かない**
  （リポジトリに他人の環境設定が混入する）
- 形式は 1 フィールドの JSON（`{"enabled": true}`）。**ファイル欠如・パース失敗・
  想定外の値はすべて off として解釈する** — 読めない設定を on と解釈すると、利用者が
  意図しない遅延とコストを負う
- 具体パスは README が正本として 1 か所に書く。SKILL.md / agent 側は README を参照せず、
  `install-check` の実測結果を使う

## off を自分で確かめる手順

opt-in の前提は「切ったことを利用者が確認できる」ことなので、確認手段を契約に含める。

1. `gate-toggle` に無効化を依頼し、変更後の状態が off として報告されること
2. 適合検査を `toggle off` の区分まで回し、**no-op（B1 も B2 も走らず、LLM 呼び出し 0）**
   として記録されること
3. 1 と 2 が食い違った場合は状態ファイルの読み手が 2 系統あるということなので、
   実装の不整合として報告して止める（利用者側の操作では解消しない）

## 適合検査の呼び出し形

- 呼び出しは**スクリプト 1 本に集約**する。agent が算術や一致判定を自分で行うと、
  台帳の判定が決定的でなくなり再現可能なテストにならない
- 引数で受けるのは (a) fixture ディレクトリ、(b) 単件モードの入力文面、(c) トグル状態の
  上書き（off 区分の検査用）の 3 つ。既定は全 fixture の通し実行
- 出力は `references/schemas.md` の「適合検査の結果」と同形の JSON 1 オブジェクト
- 実行コマンドの正確な文字列は README が正本。agent は `install-check` が present と
  返したスクリプトに対してのみ実行する

## 並行セッションでの扱い

複数セッションが同時に動きうるので、立場を明示しておく。

- **hook 側は状態ファイルを読むだけ**（書かない）。読み取りのみなので、同時発火しても
  状態が壊れない
- **書き込むのは `gate-toggle` だけ**で、1 フィールドの全体書き換えとする。ロックは
  持たない。同時に逆向きの切り替えが起きた場合、後勝ちで一方が失われる
- 失われた側は次の状態確認で気付ける。ここにロックを入れないのは、トグルが利用者の
  明示依頼でしか動かない低頻度操作であり、ロック機構の故障（stale lock で on/off が
  できなくなる）の方が損失が大きいため
- 読み取り中に書き換えが入ってパース不能だった場合は **off として扱う**（上記の解釈規則と
  同じ）。ゲートが 1 回発火しないだけで、fail-open の方針と整合する
