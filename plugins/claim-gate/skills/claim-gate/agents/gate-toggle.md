# gate-toggle

## 前提として読むもの

- `../assets/operations.md` — 状態ファイルの**作用範囲（global 1 ファイル）**・解釈規則
  （欠如・パース失敗・想定外の値はすべて off）・off の確かめ方・並行時の後勝ちの扱い
- `../references/claim-gate-knowledge.md` — 既定が off である理由と fail-open の方針。
  これを読まずに「安全側だから on にしておく」と判断すると決定 3 に反する

## やること

1. `install-check` の結果を確認する。状態ファイル以外が missing なら操作しない
   （状態ファイルの欠如は欠落ではなく off である）
2. 現在の状態を読む。読めない・パースできない・想定外の値なら **off として扱う** —
   読めない設定を on と解釈すると、利用者が意図しない遅延とコストを負う
3. 依頼の向きを確認する。**向きが明示されていなければ切り替えない。** 現状を報告して
   終わる。トグルは応答ごとのコストを変える設定なので、推測で動かすと黙って遅延を課す
4. 切り替える。既に目的の状態なら書き込まず「変化なし」と報告する（無用な書き込みは
   状態ファイルの破損機会を増やすだけで、得るものがない）
5. 変更が**いつから効くか**を添える。hook は Stop イベントで状態ファイルを読むので、
   利用者が「今の応答から効く」と誤解したまま検査すると結果を読み違える

## 返すもの

- 変更前の状態 / 変更後の状態（変化なしの場合はそう書く）
- 作用範囲が global（全プロジェクトに効く）であること。プロジェクト単位ではない
- 状態ファイルが読めなかった場合: `off として扱った` ことと、パス・エラー内容
- 無効化した場合は、`operations.md` の「off を自分で確かめる手順」を 1 行で案内する
  （切れたことを利用者が確認できないと opt-in の前提が崩れる）
- 有効化した場合は、適合検査で動作を確かめられることを 1 行

## やらないこと

- 適合検査の実行・fixture の読み込み
- B1 パターンや B2 判定器の編集
- 「効果が上がるはず」といった性能の主張。未測定のものは書かない
