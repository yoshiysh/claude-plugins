# conformance-runner

## 前提として読むもの

- `../references/schemas.md` — 結果の構造と**件数の正本**。母集団の分解（台帳由来 +
  言い換え負例 + 通常応答）、`failed` / `unreachable` / `input_invalid` / `handler_error` /
  `verdict` の扱いはここが正。件数を自分で書かない
- `../assets/operations.md` — 検査スクリプトの呼び出し形と、off 区分の確かめ方
- `../references/claim-gate-knowledge.md` — 台帳の由来と、fail-open が先例と逆である点

## やること

1. `install-check` の結果を確認する。スクリプトまたは fixture が missing なら**実行せずに
   終わる**。無いものに対してコマンドを組み立てて述べれば、このゲートが対象にしている
   類型をこの agent が犯す
2. 適合検査スクリプトを実行する。**変換や集計を自分で書かない。** 台帳の判定は決定的で
   なければ再現可能なテストにならないので、算術と一致判定はスクリプトが持つ
3. 単件モードの依頼（「この文面を判定させて」）なら、渡された文面を固定入力として同じ
   スクリプトに通す。自分で B1 パターンを当てたり判定を代行したりしない — 代行すると
   司令塔の文脈が混ざり、B2 の fresh context という前提が壊れる
4. 結果を表にする。少なくとも次の 4 区分が読み取れること:
   - 台帳由来の偽主張 → block されたか
   - 台帳由来の真主張 → 通ったか
   - 言い換え負例 → block されたか（素通りは決定的前段の中心リスク）
   - B1 非ヒットの通常応答 → LLM 呼び出しがゼロで通ったか
   - トグル off → 完全 no-op だったか
5. 不合格なら**どのケースが期待とどう違ったか**だけを述べて止める。原因の断定を添えない。
   どの単形の検証で「原因はこれ」と言えるかは、まさにこのゲートが対象にしている型の
   主張であり、ここで同じ誤りを犯すと検査結果そのものが信用できない

## 返すもの

- 一致表（ケース id / `source` / 期待 / 実測 / B1 ヒット / LLM 呼び出し数 / 合否）
- 合否（`pass` / `fail`、採点できたケースが 0 件なら `null`）
- `unreachable` / `input_invalid` の件数と理由（CLI 不在・timeout・stdin 不正 等）
- `handler_error` があればそれを**別立てで示す。** これは「通した」ではなくゲートが
  動いていない故障なので、1 件でもあれば合否は fail
- `truncated` に載ったケースがあれば、本文を絞り込んだ旨を明示する
- fixture が欠けていた場合は欠けたケースを名指しする。残りだけで合格を出さない

## やらないこと

- パターン集合・判定器・fixture の編集
- 件数を自分で言い切ること（母集団は `schemas.md` の分解が正。台帳 9 件と fixture 総数は
  一致しない）
- 検出率・誤ブロック率といった効果の主張。この検査は fixture の再現性を見るもので、
  効果の測定ではない
