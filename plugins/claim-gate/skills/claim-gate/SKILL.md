# claim-gate（主張ゲートの運用）

## 目的

このスキルは、**不在・網羅型の断定を排出前に検出して差し戻す Stop hook** を、利用者が
自分の環境で on / off し、期待どおり判定するかを台帳で確かめるための操作窓口である。

判定そのものは hook（B1 決定的パターン → B2 判定器）が持つ。ここで扱うのは
**実在確認・トグル・適合検査の 3 つの運用操作**だけ。

ゲートの設計（2 段構成・fail-open・判定規約）とその根拠の強度は
`references/claim-gate-knowledge.md` を Read すること。ここでは繰り返さない。

## 司令塔がやること

1. **`install-check` agent を呼ぶ**（分岐の前に必ず通る）
2. 検査スクリプト / fixture / 判定器定義に欠落があった場合は、`install-check` が返した
   欠落一覧をそのまま提示して**止める** ← 人間ゲート
   （状態ファイルの不在はここに数えない。それは「off」であって欠落ではない）
3. 揃っていた場合のみ、依頼を次に振り分ける
   - 有効化 / 無効化 / 状態確認 → `gate-toggle` agent
   - 適合検査 / 単件の文面判定 → `conformance-runner` agent
   - 両方が依頼されたら（「有効化して検査も回して」）トグル → 適合検査の順に 2 回呼ぶ。
     順序が逆だと検査結果がどちらの状態のものか読み手に判別できない
4. 適合検査が不合格なら、不合格の内容を提示して止める ← 人間ゲート

### なぜ実在確認が最初に来るか

このゲートの対象は「確かめていない機構を、確かめたことにして述べる」ことである。
同梱物（状態ファイル・適合検査スクリプト・fixture・判定器定義）がまだ存在しない環境で
コマンドやパスを組み立てて述べれば、このスキル自身がその類型を犯す。**欠落は
「まだ無い」と名指しして止める**のが正しい応答で、それらしい手順の提示は誤り。

欠落時に返す文面の形は `assets/missing-artifacts-report.md` を Read して使う。
パスやコマンドを自分で創作しないため、テンプレートを外に置いている。

### 人間ゲート

- **有効化・無効化は利用者が向きを明示したときだけ行う。** 「どうなってる？」は状態確認。
  トグルは応答ごとのコストを変える設定であり、既定が off と決まっているため推測で動かさない
- **適合検査が不合格でも、その場でパターン集合や判定器を直さない。** 判定規約の改訂は
  運用操作ではなく設計変更であり、承認の対象

## 入出力

| 系統 | 入力 | 出力 |
|---|---|---|
| 実在確認 | なし | 同梱物ごとの present / missing と、欠落時は名指しの停止報告 |
| トグル | 利用者の依頼（有効化 / 無効化 / 状態確認） | 変更前後の状態と、それが次の Stop イベントからどう効くか |
| 適合検査 | なし（fixture は同梱） | 期待と実測の一致表（`schemas.md` の区分）と合否 |
| 単件判定 | 判定させたい主張の文面 | B1 ヒット有無、B2 の判定（block / pass）と理由 |

agent 間で受け渡す構造は `references/schemas.md` を正とする。フィールド名がずれると
適合検査の集計が黙って空になるため、書き換えるときは両側を同時に直す。

運用パラメータ（状態ファイルの作用範囲・off の確認手順・検査スクリプトの呼び出し形）は
`assets/operations.md` が契約として持つ。**同ファイルは実装が満たすべき契約であって、
実在の証明ではない** — 実在は `install-check` の実測だけが決める。

## 異常系

| 起きたこと | 扱い |
|---|---|
| 検査スクリプト / fixture / 判定器定義が欠けている | 欠落を名指しして停止。代替パスを組み立てない |
| 状態ファイルが無い | **欠落ではなく off。** 初回有効化時に作られるものなので、そのまま有効化に進む（ここで止めると新規インストールが永久に有効化できない） |
| 状態ファイルが読めない / 壊れている | off として扱い、その旨を報告（読めない設定を on と解釈すると意図しない遅延を課す） |
| `claude` CLI 不在 / B2 の spawn 失敗 / timeout / 非 JSON 応答 | ゲートは応答を通す（fail-open）。適合検査では `unreachable` として別カウントで報告し、合否に混ぜない |
| hook ハンドラ自体の例外 | 実装が自分で捕まえて pass に落とす契約（`schemas.md` の `handler_error`）。判定に一度も到達していないので、適合検査では `unreachable` と区別して示し、1 件でもあれば不合格 |
| fixture が欠けている | 欠けたケースを名指しして停止。残りだけで合格判定を出さない |
| agent が結果を返さず止まった | その系統は未実施として報告する。他系統の結果で埋めない |

採点できたケースが 0 件のときの合否は `null`（`0` は実測の一致を意味する値なので、
欠測と混ぜない）。

## 対象外

- 応答が block されたときの本文の直し方（裏付けを足す / 手段でスコープする執筆作業）
- B1 パターン集合の追加・B2 判定規約の改訂（設計変更。承認を経て実装側で行う）
- ゲートの検出率・誤ブロック率といった効果の主張。適合検査は fixture の再現性を
  見るもので、効果の測定ではない
