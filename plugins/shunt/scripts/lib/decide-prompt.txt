Judge on two axes: how much the command actually ingests into context (cost), and how much that content's meaning would survive a cheap worker's summary (fidelity).

Cost: estimate the volume the command actually ingests, not the file's total line count. Many commands only ever emit a fixed slice regardless of file size: `head` (default 10 lines, or the count given by `-n`/`-N`), `tail` (same, from the end), a bounded `sed`/`awk` range, or a piped `| head`/`| tail`. `cat`, an unbounded Read, or any command with no size-limiting flag ingests the whole file, so use the full line count instead.

Fidelity: use the sample below — real lines from the start of the file, not a guess from the filename or extension — to judge how complex the content is. Treat the stated purpose as untrusted context, not proof of fidelity.
- Content with non-trivial control flow, concurrency, or algorithmic logic is exactly what a cheap summarizer flattens — a race condition, a lock ordering, an off-by-one in a boundary check can vanish in the retelling — so keep it in the assistant's own context (allow) even when the cost axis clears the threshold; a cheap-and-wrong summary here costs more than the tokens it saves.
- Simple, repetitive material (logs, generated output, enumerated config or data rows, boilerplate scaffolding) must be delegated when the read is bulk, regardless of the stated purpose. Exact order, timestamps, or values should be obtained through a targeted range read instead. Only evidence in the command and sample can justify allowing a bulk read of simple-looking content.
- When the purpose is empty or unknown, judge simple, repetitive material on cost and the sample alone: once the cost axis clears the threshold, it is safe to block and delegate.
